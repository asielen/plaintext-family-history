# TOOLING_INTERFACE.md: The AI Interface (Research Workbench and Skills)

**Who this is for:** developers building or extending the *AI-interface* side of the archive: the workbench harness configuration and the workflow skills that turn `fha` tools into a genealogy-aware research assistant. To use the archive, start with [`docs/GETTING_STARTED.md`](docs/GETTING_STARTED.md).

**Version 2.30, companion to SPEC.md v2.30 and TOOLING.md v2.30 (versions track the SPEC).**

This document expands one layer that [`TOOLING.md`](TOOLING.md) only sketches: the harness and skills that sit *on top of* the deterministic `fha` tool suite. TOOLING.md specifies the tools (schemas, algorithms, command shapes). This document specifies what drives them: the workbench configuration that makes any conforming harness genealogy-aware, the browser workbench, and the workflow skills that combine `fha` calls with model judgment into the everyday research loop.

Everything below follows the operating principles at the top of TOOLING.md: deterministic work in `fha` tools, AI judgment in skills, human review as the only gate to `accepted`. A skill never reimplements what a tool does; it calls the tool and adds the judgment a tool cannot have. AI passes are always *invoked* and recorded, so nothing mines, extracts or classifies on its own.

The three sibling design docs:

| Doc | Concern |
|---|---|
| [`TOOLING.md`](TOOLING.md) | core `fha` tools (index, lint, views, find, process, site, …) |
| [`TOOLING_INGESTION.md`](TOOLING_INGESTION.md) | the inbox contract and the capture front ends |
| **`TOOLING_INTERFACE.md`** (this doc) | workbench harness + workflow skills |

The build order for all three is TOOLING.md §15; this doc's pieces are its last layer.

## 1. The research workbench (harness configuration)

**Pattern (SPEC §6):** an agentic CLI harness opened on the archive root, beside a plain text editor, so human and AI edit the same files. Claude Code is the current choice and is not required. The configuration below makes any conforming harness genealogy-aware and keeps that choice reversible.

**Rules that keep the harness replaceable.**
1. **`AGENTS.md` is canonical.** All agent operating instructions live there, in plain markdown, harness-agnostic. `CLAUDE.md` is a one-line deferral (`Read and follow AGENTS.md.`) plus, at most, Claude-Code-specific notes. Any other harness's convention file (e.g. for Codex or Gemini CLI) gets the same one-line deferral.
2. **Skills are portable.** Workflow skills live in `.claude/skills/{name}/SKILL.md` using the open SKILL.md standard, and an installed archive carries an identical copy in `.agents/skills/` so Codex finds them too. They contain instructions and `fha` invocations only, no harness APIs.
3. **No harness-only state is load-bearing.** Session memory, harness caches and MCP configurations are disposable; anything worth keeping is written into archive records, so changing harnesses means installing the new one and pointing it at `AGENTS.md`.
4. The harness learns the archive through the **index and the `fha` tools**, never by bulk-reading files. A photo question is an `fha photoindex` call, so the size of the photo library does not touch the model's context.

**External roots in the workbench.** When `fha.yaml` maps a root outside the archive, the harness needs access granted. For Claude Code, launch with `--add-dir <photos-root>` (prefer the flag over the settings-file `additionalDirectories` route, e.g. in a small launch script committed next to fha.yaml). The agent still must not bulk-read asset trees: access exists for exiftool, process and packet operations, not ingestion.

**Model selection.** Deterministic `fha` tools cost no model credits, so the tool/skill split is also the cost model. For model work, pick the tier by how much judgment the task needs. The **workhorse tier** (a vendor's mid-size general model) is the default for tool-building, processing, review and drafting. The **frontier tier** (its largest model) is chosen per task for proof arguments, merge or split decisions, brick-wall research, spec refinement and stuck debugging: tasks where a wrong answer costs far more than a second attempt. The **fast tier** (its smallest model) serves batch API pipelines only after a sample-quality comparison, because handwriting transcription degrades on small models without obvious errors. Switch per session (`/model`); any harness's equivalent models fill the same tiers.

**Workbench session hygiene** (enforced by AGENTS.md): run `fha lint` after any batch of edits; never bypass `fha process` for renames; new claims always `status: suggested` when AI-drafted; never edit below a GENERATED header.

## 1b. `fha serve`: the localhost workbench

The agentic CLI harness (§1) is one way to drive the archive. `fha serve` is a second, deliberately narrow one: a browser window over the same headless engines every CLI command drives (SPEC §5, "the tools are a headless core"; TOOLING §1 specifies the split as `run_*`/`_cmd_*`). It adds no capability and holds no data of its own.

**Not a daemon.** Human-started, foreground, 127.0.0.1-only, no login, no network beyond the loopback socket, no file watcher. It does not run unattended and does not accept connections from any other machine. An AI agent never starts it on its own: a person double-clicks `serve.cmd` or types `fha serve` because *they* want the browser view open.

**The parity rule.** Every write the workbench makes is one documented `fha` command, run in-process through its `run_*` engine, and every apply echoes the literal CLI command it ran (`cli_echo`). A human reading the echo can reproduce the action at a terminal, and a skill never needs to learn a second interface. The rule has four **declared exceptions**, each a convenience with nothing hidden behind it:

1. **The file picker** (`/api/pickfile`). A browser page cannot read a local file's full path, so serve, running on the same machine, opens the OS's own file picker and passes the choice back into the register-by-path form. The pick reads, moves and registers nothing; the write is still `fha capture --path`'s preview and confirm.
2. **Reciprocal ties by default.** The workbench's relate and add-family actions pass `--reciprocal` unless told otherwise, so a tie recorded from either person's page shows on both. The CLI's own default stays one-sided, and the echo always names the flag that ran.
3. **Editing the homepage intro** (`home.edit`). It writes `notes/home.md`, a human-owned file with no `fha` verb (the same as editing it in any text editor), and its echo says so.
4. **Uploading a file** (`/api/upload`). It copies the uploaded file into `inbox/` (and, when a note is typed, a `{stem}.notes.md` beside it, in the TOOLING_INGESTION §1 shape). There is no `fha` verb for it because the CLI equivalent is putting a file in the inbox folder by hand.

**Add-family** (`person.add_family`) is not an exception: it is two commands, `fha person new "Name" …` then `fha person relate <p-id> --<relation> <new p-id> --reciprocal`, and its echo shows both. Linking an existing person is the second command alone.

**Routes and writes.** Reads: `/` and the record pages (`/persons/…`, `/sources/…`, `/places/…`, from the snapshot below), `/review` (suggested claims grouped by source, plus the `fha xref` and `fha cooccur` candidates `fha report` reads), `/inbox` (each inbox item as TOOLING_INGESTION §1.1 groups it), `/root/{photos,documents,inbox}/…` (asset files), and `/api/find` (the `fha find --json` engine). Writes, all `POST` and CSRF-checked: `/api/run` (the verb table), `/api/upload`, `/api/reindex` (= `fha index`), `/api/open` (opens a file in the OS; writes nothing), `/api/pickfile` (writes nothing). The **one list of `/api/run` verbs**, each with its schema, its engine, its CLI echo and its reindex policy, is the `VERBS` table in [`tools/serve.py`](tools/serve.py). That table is the reference; this document does not copy it.

**The human gate in the workbench (SPEC §6).** SPEC §6 makes the gate the human's *decision*, whatever the editing method. Every mutating action is previewed first, in plain English, and only a second, explicit confirmation applies it (the server treats every request as a preview unless the confirm step says otherwise, a second check behind the UI). Accepting a `suggested` claim in the workbench stamps `reviewed:` exactly as the CLI does: the confirming click is the human's decision.

**No drafting in the workbench.** `fha serve` never reads evidence and never drafts from it: no button mints a `suggested` claim by reading a source's text or an image. Stage B drafting (entity resolution, claim extraction, biography prose) stays with the AI skills (§2), run from the agentic harness. The workbench runs only the deterministic Stage A and Stage C engines that a human, or a skill acting on the human's explicit say-so, decided to invoke.

**Refreshed on use.** The read side is a linked, unredacted snapshot built by `fha site`'s own generator under `.cache/serve/`. It is rebuilt only when a page is requested and the record trees have changed since the last build (a cheap mtime probe plus a path-manifest check, so a deleted record is caught too; `serve.py`'s `snapshot_is_stale`), never on a timer or a filesystem watch. A page reflects every write made before it was requested.

**Disposable.** The only thing `fha serve` writes outside the record tree its engines change is that snapshot cache, a rebuildable artifact like `.cache/index.sqlite` (SPEC §5). `fha site` never depends on `fha serve` having run, and deleting `serve.py` and `.cache/serve/` changes nothing about the archive. Stopping the process loses nothing it owns: a missing or stale index is rebuilt on the next start (`run_serve_preflight`), and the snapshot on the next page request. Each record write is atomic, so stopping in the middle of an action never leaves a record half-written, though an action that writes several files can stop after some of them.

**Security.** These checks are the whole trust boundary (`run_serve_preflight` and the request handler). Serve binds 127.0.0.1 only and checks the Host header against an allowlist on every request. Every POST carries a per-process CSRF token, compared with `hmac.compare_digest`. Snapshot files, `/root/` aliases, `/api/open`, `/api/upload` and the `process.file` argument are confined by resolving the path and checking it is inside its root (`capture.path` is deliberately not confined, because registering a file that stays where it is is its job). Responses carry `no-store` and `nosniff`. One global lock is held across mutate, reindex and snapshot invalidation, so two clicks never interleave. The default port is 8765; `--port 0` picks a free one.

**Completeness rings and the week.** Every curated person page carries the completeness ring (TOOLING §12, drawn from `_lib.person_completeness`, accepted claims only) whatever fha.yaml's `site: completeness_rings` says, since that switch is for the shared site. Its legend keeps the owner's full detail, as `fha metrics` does. Under each check not yet found it names the kinds of record that would fill it, with a link to the Review page when a suggestion listed there already would (the engine's `review-queue` mode, TOOLING §7a: a parked claim has left the queue, so it does not count). A living or unknown person still gets no ring. The home page shows "This week in the family" in place of the site's month panel: today and the six days after it from `_lib.family_calendar_week`, the same week `fha report`'s on-this-day section reads (accepted claims dated to the day). Like the report, it names everyone, living relatives included, and links each person to their workbench page. A snapshot built on an earlier day is stale, so the week always starts today.

**Privacy.** The read side is the **linked** view (real archive paths, unredacted: a local owner preview, TOOLING §12) and never leaves the machine. Sharing outward still goes through `fha site --standalone` (or the `share-and-export` skill); the workbench is another way to run that command, not a second export path.

**Search other websites.** A person's workbench page has a section "Look for {name} on other websites": about ten links (FamilySearch, Ancestry, MyHeritage, Findmypast, Find a Grave, BillionGraves, Chronicling America, Newspapers.com, Geneteka, UK National Archives), each opening that website's own search filled in from the page: the first given name and surname (a married surname for the grave sites), a birth and a death year widened by two, places, and the names of the parents and the first spouse. The links are plain `<a href>` addresses built in Python when the snapshot is built (`site.py` `_person_research_subject`, then `_lib.research_search_links`; `_lib.RESEARCH_SITES` is the one list). The section is read-only and workbench-only: `fha site --standalone` and `--linked` never carry it, and there is no write, no echo and no network request by the server. A parent or spouse goes into a link only when their record says `living: false` and is not restricted. A date or place whose claim or source is marked restricted (or `by-request`) stays out, and a year is left out when the date is too loose to name one (`before 1840`, `18XX`). For a living or unknown person the links carry the name and nothing else, folded away under a plain warning; a person marked `restricted` (including `by-request`) gets no section. "No network beyond the loopback socket" stays true: the browser opens one of these addresses only when he clicks it, in a new tab that does not tell the site where he came from.

Flags: `docs/COMMANDS.md` (`fha serve`). Tests: `tests/test_serve.py`.

## 2. The skills

Skills are what a genealogist works with day to day; most `fha` commands are what skills call (TOOLING.md §17). Each skill is a `.claude/skills/{name}/SKILL.md`: portable instructions plus `fha` invocations, no harness APIs. A skill's job is the *judgment* around a deterministic tool (which claim to draft, which name is which person, where to look next), never the bookkeeping the tool already does. The authoring contract is [`.claude/skills/_STANDARD.md`](.claude/skills/_STANDARD.md). This section says what each skill is for; its SKILL.md holds the steps, prompts, gates and thresholds.

Every skill obeys the contract (AGENTS.md): AI-drafted claims are `status: suggested`; only the human moves a claim to `accepted`; every AI pass is recorded as an entry in the source's `ai_passes:` list (SPEC §14); nothing edits below a GENERATED header or overwrites human-written text. Every skill also follows SPEC §17's research ladder: a question is written down only when a person asks it or the evidence conflicts (never a gap a tool computes), and a guess is the question entry's working answer (`id`, `guess`, `basis`, `verify`), never a separate object or a claim.

### 2.1 The core loop

- `review-claims` ([SKILL.md](.claude/skills/review-claims/SKILL.md)): Stage C. Walks one source's `suggested` claims one by one, in numbered batches, or self-serve, showing each with its evidence link, and writes each human decision (accept, dispute, edit, reject, or park as "checked, still open", SPEC §8.1) with `fha claim`. It closes with a reindex, `fha xref`, a view refresh for the people touched and `fha lint`. Accepting a death or burial marks the deceased not living as TOOLING §3b describes. Promotion, question-entry and place-registration offers are made only on the human's explicit yes.
- `process-source` ([SKILL.md](.claude/skills/process-source/SKILL.md)): the pipeline driver. Stage A is `fha process`, seeded by the stub's frontmatter and notes when the item is a source stub (TOOLING_INGESTION §1). An image-only item goes through `transcribe-source` first (§2.6). Stage B is the AI draft: it reads the file (images included), resolves people and places against the index (places by settlement name), and drafts `suggested` claims and stories. It then hands off to `review-claims` for Stage C. The stub is consumed into the source record.
- `mine-transcript` ([SKILL.md](.claude/skills/mine-transcript/SKILL.md)): the invoked extraction pass over a transcript. Drafts `suggested` claims with anchors for the substantive assertions only, resolves names against the index (stubs minted on confirmation), routes narrative to `## Stories`, and records the pass. Never runs unrequested. When a source has two transcripts of one recording, it compares them and anchors to the one it quotes.
- `today` ([SKILL.md](.claude/skills/today/SKILL.md)): runs `fha report`, narrates it discoveries first (then §0b's week in the family), and offers one next action. Its only writes are the human's explicit say-so acting on the briefing: a confirmed win via `fha confirm discovery`, or an answer to a connection candidate via `fha confirm cooccur` or `fha confirm dismiss` (and `fha confirm undismiss` to take one back).
- `on-this-day` ([SKILL.md](.claude/skills/on-this-day/SKILL.md)): the family's "on this day" column. Runs `fha calendar` and narrates the births, marriages, deaths and arrivals it returns, accepted claims only, with at most a sentence or two of general history labelled as such. Read-only. Words meant for anyone beyond the owner leave out living people and restricted material.
- `research-next` ([SKILL.md](.claude/skills/research-next/SKILL.md)): inference and steering. Checks `notes/research-log.md` first, then combines the gaps `fha report` computes, open questions and working answers with historical context into ranked leads, and logs every executed search back to the log (SPEC §17c). It may write a guess as a question entry's working answer (`origin: agent`); it writes no claims and never writes a computed gap as a question.
- `write-records-request` ([SKILL.md](.claude/skills/write-records-request/SKILL.md)): a records-request letter for a record held only on paper. Finds an office that takes requests by letter with `fha repositories`, drafts a one-page letter from accepted facts with placeholders and "(check this)" on every address and fee, shows it in the conversation, and saves it under `notes/research/letters/` only on the human's yes. It sends nothing, leaves out living people, restricted items and DNA, and logs `result: requested` in the research log (SPEC §17c) only once he says he sent it.
- `write-biography` ([SKILL.md](.claude/skills/write-biography/SKILL.md)): drafts profile prose from the `fha views draft-queue` backlog (TOOLING.md §14b), citing every factual sentence (SPEC §16), with links only from verified IDs. Draft prose carries `<!-- AI-DRAFT … -->` markers until the human accepts it via `fha confirm draft`. Pronouns come from `gender:`, else `sex:`, else stay neutral (SPEC Appendix A.7). The voice is `chronicle` (the default) or `narrative`, chosen by the human's ask or `fha.yaml`'s `biography: style:`, and named in the marker; the citation rules are the same in both. It closes by naming the facts it used and the checks `fha metrics` still shows unmet.

### 2.2 Judgment-heavy skills

- `merge-identities` ([SKILL.md](.claude/skills/merge-identities/SKILL.md)): the "same person or two people?" decision, run on the frontier tier (§1). Reads both people's neighborhoods (`fha find --related`, co-occurrence), proposes a merge or a split for human confirmation, and enacts a confirmed merge with `fha confirm merge` (dry-run first). A `merged_into` person is never directly referenced again (lint W107 lists any left; it counts for the survivor meanwhile, SPEC §9).
- `place-research` ([SKILL.md](.claude/skills/place-research/SKILL.md)): "fill in this place's history." Drafts dated `history:` entries and place notes (loose citations are acceptable, since place context is not vital fact), links `[[l-…]]`, and proposes registry entries for `fha confirm place` to write; for a place without coordinates it previews `fha places geocode --place` and runs it on the human's yes.

### 2.3 Photos and sharing

- `find-photos` ([SKILL.md](.claude/skills/find-photos/SKILL.md)): answers "show me grandma's photos" from `fha photoindex find`, one line per physical photo (fronts, backs and copies counted once), and offers a clickable gallery page (`fha photoindex gallery`). Read-only; identifying a person hands off to `fha photoindex tag-person` and its own confirm prompt.
- `share-and-export` ([SKILL.md](.claude/skills/share-and-export/SKILL.md)): routes a sharing request to the right exporter (`packet`, `gedcom`, `site --standalone`, `wikitree`, `backup`), explains its privacy defaults *before* running, previews first, and reports where the result landed and what stayed home. It never adds an override flag (`--include-restricted`, `--include-dna`, `--include-living`, `--linked`) without the human's explicit, informed ask. Importing a tree into the archive is a separate conversation (`fha gedcom import`).
- `photo-context` ([SKILL.md](.claude/skills/photo-context/SKILL.md)): invoked-only caption improvement. Gathers what the archive knows about a photo, drafts a better summary, and writes it AI-marked via `fha photoindex set-summary` only after the human approves the exact text. Human captions are never overwritten; never automatic, never in bulk (SPEC §20).

### 2.4 Recordings

Both skills work ahead of `fha process` for audio and video, as `import-notes` does for paper. Getting a recording in is separate from mining it: the interview earns its claims later through `mine-transcript` and `review-claims`.

- `import-recordings` ([SKILL.md](.claude/skills/import-recordings/SKILL.md)): brings recordings in. Skips files already filed (`fha media dedupe`, which fails closed when it cannot tell), reads the real recording date from the container rather than the filename (`fha media probe`), groups one sitting into one session source under `documents/interviews/{interviewee}-{yyyy-mm-dd}/`, always adds a local whisper pass beside the app transcript and replaces neither, and proposes which speaker is which person, writing no name until the human answers. Speaker turns move onto the whisper text only when the skill's measured gates pass, and the result is never called diarized. Interactive by default; automatic mode needs an explicit up-front say-so and still leaves every claim `suggested`. The whisper run and the label transfer are the skill's own `scripts/` because they depend on the model and produce working drafts, not archive records.
- `transcribe-audio` ([SKILL.md](.claude/skills/transcribe-audio/SKILL.md)): local faster-whisper re-transcription of a recording (`scripts/transcribe_audio.py`), attached as role `whisper-transcript` beside the original transcript with `fha process --more`. It never renames or hand-edits a filed file, and stops when sibling names disagree. It ends by offering a claim-by-claim audit of facts mined from the garbled original: each correction is shown as an exact before and after on one claim and written only on the human's yes, through `fha claim <c-id> --status accepted --value "…"` with `--status` in the same call so the `reviewed:` date matches the new wording.

### 2.5 Site edits and notes

- `reconcile-site-edits` ([SKILL.md](.claude/skills/reconcile-site-edits/SKILL.md)), the site's rescue path (docs/CUSTOMIZING_SITE.md, "The rescue hatch"): `fha site` is deterministic and never reads its own output, so a hand-edited HTML page is overwritten by the next build. The skill diffs the edited page against a pristine build to recover what the human meant and folds that into the file it belongs in (styling to `.fha/design/custom.css`, homepage copy to `notes/home.md`, person prose to that person's record, title and hero to `fha.yaml`'s `site:` block), then rebuilds. Every write is confirmed with the human first.
- `import-notes` ([SKILL.md](.claude/skills/import-notes/SKILL.md)): sorts a pile of freeform research notes, ahead of `fha process`, the way the recordings skills do for audio. It proposes a home for each chunk under the routing rule (evidence someone asserted → inbox → source; a thing to find out → open question; a testable belief → the working answer on that question; a search already run → `notes/research-log.md`; anything else → `notes/research/`) and writes each chunk only on the human's confirmation. It drafts no claims, writes no computed gap as a question, and never deletes or rewrites the original notes; a scraps file is dissolved only on an explicit say-so, after everything in it has landed.

### 2.6 Sources with no text

- `transcribe-source` ([SKILL.md](.claude/skills/transcribe-source/SKILL.md)): for a source whose files are all scans, photographs or image-only PDFs. Such a source contributes **no text to the archive**, so `fha find --text` searches only the claim values one earlier pass wrote down while looking like a search of the evidence. The tools detect the gap (`fha lint` W124, and the coverage note `fha find --text` prints under every result), the skill produces the text, and an existing tool writes it (`fha process --more <file> transcript`). The transcript is a `[Page N]`-labelled `role: transcript` companion in the original's pagination, so a claim can carry `anchor: "page N"`. It runs **inside `process-source`, between Stage A and Stage B** (so claims come from text rather than from one pass over pictures), and **standalone for backfill**, in confirmed batches of five or fewer whose worklist is re-read from `fha lint` each time (W124 stops reporting a transcribed source, so lint shows where to resume). `fha source extract` is tried first on any PDF. The skill **drafts and edits no claims**: unclaimed facts go to `mine-transcript`, and a reading that contradicts an existing claim, **including an `accepted` one**, becomes a `## Q:` entry.
  - **Misreadings.** A misread transcript produces confident search hits for words the document does not say. So the image remains the evidence of record and the transcript is an index into it; uncertainty stays visible in the text (`[illegible]`, `[word?]`, `[unclear: a or b]`, `[torn]`, `[struck: …]`, `[sic]`) and is never resolved silently.
  - **The unreviewed-transcript marker.** The skill reuses the archive's marker pair (`<!-- AI-DRAFT … -->` / `<!-- AI-ACCEPTED … -->`, SPEC §16c) on a *text companion*: a `files:` entry whose `role:` is `transcript`/`transcription`/`extracted-text` and whose file is `.md`/`.txt`, exactly the set `fha index` loads into `transcripts_fts`. A companion is **unreviewed** (a complete AI-DRAFT marker), **verified** (AI-ACCEPTED and no AI-DRAFT), **unmarked** (neither: a human typed it, or `fha source extract` dumped it), or **damaged** (either marker word outside a complete marker, treated as unreviewed, failing closed as `_lib.strip_unaccepted_drafts` does). There is exactly one marker, as the **last non-blank line**, with no `#`/`##` heading below the title, because `strip_unaccepted_drafts` treats a marker as sitting at the *end* of the span it covers. The marker is the only record of review; the source's `ai_passes:` entry says only that the pass happened.
  - **No verb to mark it reviewed** (`_STANDARD.md` §6). `fha confirm draft` takes a `<p-id>` and edits a person profile, and a skill never hand-edits a marker, so every AI transcript stays *unreviewed*. The wanted verb (`fha confirm transcript <s-id>`) is recorded in [`transcribe-source/GAP.md`](.claude/skills/transcribe-source/GAP.md).

### 2.7 The researcher's own family

- `setup-interview` ([SKILL.md](.claude/skills/setup-interview/SKILL.md)): the first-run interview, named in `fha install`'s "Next steps". The researcher's account of their own parents, spouse and children is firsthand testimony (`information: primary`, `evidence: direct`), so it is recorded as a source with a citation rather than as settings. It asks who the researcher is (minting their person record and setting `sex:`, which the Ahnentafel numbering reads), how they want the tree numbered (`root_generation: self | children`, written into `fha.yaml`), and their immediate family. It writes one `source_class: authored` interview source and drafts `relationship` claims with explicit `roles:` for every parent-child edge (never `birth` claims, whose second person is as often an informant or a doctor as a parent) plus a `marriage` claim per spouse. Every claim lands `status: suggested` and goes to `review-claims`. With the human's yes it also fills the family part of `START_HERE.md` (between its `<!-- FAMILY` comment lines, never over words already written there). Person minting and the `sex:`/`living:` writes are the same confirmed writes `fha person new`, `set-sex` and `set-living` make everywhere else.
  - **Place backlog first.** Before the family questions it makes one silent check: an archive that already holds imported material (`fha gedcom import` run first) can arrive with no registered places and many unlinked `place_text` values. `fha index` then `fha places candidates --include-suggested` lists the clusters (an import mints everything `suggested`, which the everyday view excludes). When a cluster reaches 20 claims (the threshold `fha report`'s banner uses), the skill offers once to register them: all at once with `fha places candidates --register` (one list, one yes), or the largest one or two via `fha confirm place`; then it runs `fha index` and `fha places lint`. Otherwise it says nothing.

## 3. Build status

The workflow skills are authored: `.claude/skills/` holds `_STANDARD.md` (the authoring contract) plus all nineteen SKILL.md files. Each skill's status is in [`.claude/skills/README.md`](.claude/skills/README.md); the tests that show this layer is done are in TOOLING.md §15.

The workbench harness configuration (§1) is documentation plus a few committed conventions (`AGENTS.md`, `CLAUDE.md`, the `--add-dir` launch script). Its maintenance is keeping those files accurate as harnesses change.

`fha serve` (§1b) is a tool with tests (`tools/serve.py`, `tests/test_serve.py`), shipped with `serve.cmd` by `fha install`/`fha update-tools`. Flags are in `docs/COMMANDS.md`; the verb table is the `VERBS` dict in `tools/serve.py`; the security rules are in §1b.
