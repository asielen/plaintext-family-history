# TOOLING_INTERFACE.md - The AI Interface: Research Workbench & Skills

**Who this is for:** developers building or extending the *AI-interface* side of the archive - the workbench harness configuration and the workflow skills that turn `fha` tools into a genealogy-aware research assistant. If you just want to use the archive, start with [`GETTING_STARTED.md`](GETTING_STARTED.md).

**Version 1.2 - companion to SPEC.md v1.2 and TOOLING.md v1.2 (versions track the SPEC).**

This document is a focused expansion of one layer that the main [`TOOLING.md`](TOOLING.md) only sketches: the **harness + skills** layer that sits *on top of* the deterministic `fha` tool suite. TOOLING.md specifies the tools (schemas, algorithms, command shapes); this document specifies the AI interface that drives them - the workbench configuration that makes any conforming harness genealogy-aware, and the workflow skills that orchestrate `fha` calls plus model judgment into the everyday research loop.

The governing split, stated once and obeyed everywhere below: **deterministic work belongs in `fha` tools; AI judgment belongs in workbench skills; human review is the only gate to `accepted`.** A skill never reimplements what a tool does - it calls the tool and adds the judgment a tool cannot have. AI passes are always *invoked* and recorded - nothing mines, extracts, or classifies silently.

## 1. The research workbench (harness configuration)

**Pattern (SPEC §6):** an agentic CLI harness opened on the archive root, beside a plain text editor - human and AI edit the same files.
Claude Code is the operating choice, not a required one.
The configuration below is what makes any conforming harness genealogy-aware, and what keeps the choice reversible.

**Vendor-lock prevention rules.**
1. **`AGENTS.md` is canonical.** All agent operating instructions live there, in plain markdown, harness-agnostic. `CLAUDE.md` is a one-line deferral (`Read and follow AGENTS.md.`) plus, at most, Claude-Code-specific notes. Any other harness's convention file (e.g. for Codex or Gemini CLI) gets the same one-line deferral.
2. **Skills are portable.** Workflow skills live in `.claude/skills/{name}/SKILL.md` using the open SKILL.md standard (adopted beyond Claude Code); they contain instructions and `fha` invocations only - no harness APIs.
3. **No harness-only state is load-bearing.** Session memory, harness caches, and MCP configurations are disposable; anything worth keeping is written into archive records. Switching harnesses must cost one afternoon, not a migration.
4. The harness's "knowledge" of the archive is the **index and the `fha` tools**, never bulk file ingestion - ten thousand photos cost zero context because photo questions are `fha photoindex` calls.

**External roots in the workbench.** When `fha.yaml` maps a root outside the archive, the harness needs access granted: for Claude Code, launch with `--add-dir <photos-root>` (the settings-file `additionalDirectories` route has had reliability reports; prefer the flag, e.g. in a small launch script committed next to fha.yaml).
The agent still must not bulk-read asset trees - access exists for exiftool/process/packet operations, not ingestion.

**Model selection (workbench economics).** Deterministic `fha` tools cost no model credits - the deterministic/judgment split is also the cost model.
For model work, tier by judgment density, not habit: the **workhorse tier** (currently Claude Sonnet) is the default for tool-building, processing, review, and drafting; the **frontier tier** (currently Claude Opus / Fable) is escalated per task for proof arguments, merge/separate judgment, brick-wall research, spec-refinement, and stuck debugging - the tell is *cheap to attempt, expensive to get wrong*; the **fast tier** (currently Claude Haiku) serves batch API pipelines only after a sample-quality bake-off (handwriting transcription degrades quietly on small models).
Switch per session (`/model`); the tiers are roles, not vendors - any harness's equivalents slot in.

**Workbench session hygiene** (enforced by AGENTS.md): run `fha lint` after any batch of edits; never bypass `fha process` for renames; new claims always `status: suggested` when AI-drafted; never edit below a GENERATED header.

## 1b. `fha serve` - the localhost workbench front door (plan 17)

The agentic CLI harness (§1) is one front door onto the archive. `fha serve` is a second, deliberately narrow one: a **non-load-bearing front door onto the same headless engines** every CLI command drives (SPEC §5's "the tools are a headless core" principle - the engine/interface split TOOLING §1 specifies as `run_*`/`_cmd_*`). It adds no new capability and owns no truth of its own; it is a browser window over the exact same `fha` commands a human or an agent would otherwise type.

**Not a daemon.** Human-started, foreground, 127.0.0.1-only, no login, no network beyond the loopback socket, no file watcher. It does not run unattended, does not accept connections from any other machine, and an AI agent never starts it on its own - a person double-clicks `serve.cmd` or types `fha serve` because *they* want the browser view open.

**The parity rule.** Every button in the workbench is exactly one documented `fha` command - the same command this document and TOOLING.md §17 already specify, run in-process through its `run_*` engine. Every apply echoes the literal CLI command it just ran, so nothing the workbench does is a hidden or undocumented capability; a human reading the echo can reproduce the action verbatim at a terminal, and a skill or another harness never needs to learn a second interface.

**Two workbench conveniences inside the parity rule (2026-07-17).** (1) *The native file picker* (`/api/pickfile`): a browser page cannot read a local file's full path, but the register-by-path flow needs exactly that path - so serve, which runs on the same machine as the browser, opens the OS's own file-picker dialog and passes the choice back into the form field. The pick itself reads, moves, and registers nothing; the write still goes through `fha capture --path`'s ordinary preview → confirm, so no command exists behind this button that the CLI lacks. (2) *Reciprocal ties by default*: the workbench's relate/add-family buttons pass `--reciprocal` unless told otherwise (an unsourced tie recorded from either person's page lands on BOTH records, so it shows from both - one-sided display reads as silent failure from the other tab). The CLI's own default is unchanged (`--reciprocal` stays opt-in there), and the echo always names the flag that actually ran, so parity holds: the button equals the echoed command, exactly.

**The human gate is a click, not a method (SPEC §6).** SPEC §6 is explicit that the review gate is the human's *decision*, not any one editing method - "a typed instruction today, a click later." The workbench honors that literally: every mutating action is dry-run-previewed first, in plain English, and only a second, explicit confirmation applies it (the server itself defaults every request to preview unless the confirm step says otherwise, defense in depth behind the UI). A `suggested` → `accepted` claim review through the workbench still stamps `reviewed:` exactly as the CLI does - the click *is* the human decision, carrying the same weight as directing the CLI.

**The mechanical/generative boundary.** `fha serve` never reads evidence and never drafts anything from it - there is no button that mints a `suggested` claim by reading a source's text or an image. Stage B drafting (entity resolution, claim extraction, biography prose) stays exactly where TOOLING_INTERFACE.md §2 puts it: with the AI skills, run from the agentic harness. The workbench only ever runs deterministic engines a human (or a skill acting on the human's explicit say-so) already decided to invoke - it is Stage A/C infrastructure with a browser skin, never Stage B.

**Refresh-on-use, not a watcher.** The workbench's read-side view is a linked, unredacted snapshot of `fha site`'s own generator, rebuilt only when a page is requested AND the record trees have changed since the last build (a cheap mtime probe) - never on a background timer or filesystem watch. This keeps the implementation simple and the guarantee simple: what you see is never older than your last click, and there is no daemon polling the disk between sessions.

**Disposability - killing it loses nothing.** The only thing `fha serve` writes outside the record tree its engines mutate is its own snapshot cache under `.cache/serve/` - a rebuildable artifact, same as `.cache/index.sqlite` (the archive test's disposability criterion, SPEC §5). `fha site` never depends on `fha serve` having run; deleting `serve.py` and `.cache/serve/` changes nothing about the archive. Stopping the process (Ctrl-C, or closing the window) is always safe - there is no shutdown sequence to get wrong, because there is no state to lose.

**Privacy is unchanged.** The workbench's read side is the **linked** view (real archive paths, unredacted - a local developer/owner preview, per TOOLING §12) and never leaves the machine it runs on (127.0.0.1 only, no network). Sharing anything outward still goes through the one sanctioned path, `fha site --standalone` (or the `share-and-export` skill), exactly as it did before `fha serve` existed; the workbench adds a convenient front end onto that command, not a second export surface.

Full command surface, security model, and flag reference: TOOLING §17 and `tools/README.md`'s "fha serve - implementation status".

## 2. The skills (the working surface)

Skills are the layer a genealogist actually touches - most `fha` commands are what skills shell into (TOOLING.md §17). Each skill is a `.claude/skills/{name}/SKILL.md`: portable instructions plus `fha` invocations, no harness APIs. A skill's job is the *judgment* around a deterministic tool - which claim to draft, which name resolves to which person, where to look next - never the bookkeeping the tool already owns.

Every skill obeys the contract (AGENTS.md): AI-drafted claims are `status: suggested`; only the human moves a claim to `accepted`; every AI pass is recorded; nothing edits below a GENERATED header or overwrites human-written text.

### 2.1 Initial skills (build alongside linter v1)

- `review-claims` - Stage C: walk a source's `suggested` backlog in one of three styles - guided one-by-one (the default), **batched** (numbered groups of ~5 grouped by person, each claim a one-line sentence + anchor + confidence flag + its source link; the human answers with one grouped decision, so each claim still receives an individually stated human decision; offered proactively past ~6 suggested claims), or self-serve skimming of the source file - human's choice. Every claim presented, in any style, carries its evidence link: the anchored source file path (the asset file when the anchor identifies it, else the record `.md`) followed by the `[[S-id]]` token. Capture accept/dispute/edit and manual claim additions; set `reviewed`; a grouped same-status decision is written as one batch `fha claim C-a C-b … --status X` (one preview, one apply), while field edits stay per-claim calls. Finish with a reindex (full when the pass minted new people/places, else `--source`), `fha xref`, a timeline/sources-index/draft-queue refresh for the touched curated persons (a `views brackets` check too when a relationship claim was accepted), and lint. The human gate from the engine side: the skill assesses and presents; the human's decision is written with `fha claim`. After the human accepts a `death` claim for a person whose `living:` is `true` or `unknown`, the close-out *offers* the flag flip - "mark them as no longer living? → `fha person set-living <P-id> false`" - and runs it only on his explicit yes; nothing ever flips `living:` automatically (TOOLING §3c). Two more explicit-yes-only offers: parking a claim at `needs-review` offers to record what would settle it (a SPEC §17 `## Q:` block into the person's `_research` file when person-specific else `notes/questions.md`, appended to an existing same-question block rather than twinned - or a `verify:` hypothesis in the person's research file), and the close-out nudges promotion once when a decided-on person is still `tier: stub` with accepted claims at/over `fha.yaml` `promotion:`→`claims_threshold` (default 5) or flagged as a direct-line stub - running `fha person promote <P-id>` and handing off to `write-biography` only on the yes.
- `process-source` - the pipeline driver. If the inbox item is a **source stub** (a `*.notes.md` sidecar or a bundle folder, SPEC §12.1), its frontmatter + notes seed Stage A (pre-filling §14 frontmatter) and its parsed-person/vital hints seed Stage B's draft; otherwise Stage A starts from the bare file. Stage A `fha process`; Stage B AI draft (file reading incl. vision, entity resolution with candidate proposals against the index, `suggested` claims + stories); hand-off to `review-claims` for Stage C, whose close-out (reindex, xref, view refresh, lint) finishes the pipeline. The stub is consumed - promoted into the source record, not left behind.
- `mine-transcript` - the invoked extraction pass: selective claim drafting (`suggested` + `anchor:`), name→P-id resolution against the index with candidate proposals for unresolved names (mint stubs on confirmation), stories to `## Stories`, the pass recorded in the source's `## AI Passes` block (model, date). Never runs unrequested.
- `today` - run `fha report`, narrate it discoveries-first, offer to start the top item (e.g. a `review-claims` session). Surfaced as the `/today` slash wrapper. Its only writes are the human's explicit say-so acting on the briefing: a confirmed win via `fha confirm discovery`, or a narrated connection candidate he answers ("yes, they were neighbors" / "no, stop suggesting that pair") via `fha confirm cooccur` / `fha confirm dismiss` - dry-run echoed first, minted `suggested` unless his flat, unhedged answer is the review.
- `research-next` - inference and steering (checks the research log FIRST - never proposes a search already logged unless the nil has aged past the re-run horizon; emits plan-shaped output whose executed searches are logged back): combine open questions, vitals gaps, and open hypotheses with historical context (which record sets exist for the time/place, where they are held, what era events imply) into concrete research leads; may draft hypotheses (origin: agent) into research files - leads and hypotheses, never claims.
- `write-biography` - drafting rules for profiles: citation density (SPEC §16), uncited-prose-is-context, summary-block format, `[[P-…]]`/`[[S-…]]` links only from verified IDs. Consumes the `fha views draft-queue` backlog (TOOLING.md §14b); draft prose carries `<!-- AI-DRAFT … -->` markers until the human accepts it via `fha confirm draft`. **Voice is a named style** (owner decision 2026-07-22): `chronicle` (era-by-era, fact-forward - the default) or `narrative` (story-driven; texture only from cited claims or clearly-flagged period context, never invention). Resolution: the human's in-session ask wins, else an `fha.yaml` `biography: style:` block (the skill reads it directly - the `site:` block precedent; no new verb), else chronicle. The style used is named in the AI-DRAFT marker and the AI-pass task so later sessions match the register; the citation contract is identical in both styles - SPEC §16 needs no change.

### 2.2 Further skills (frontier-tier candidates)

- `merge-identities` - "same person" / "two people" judgment. Frontier-tier: cheap to attempt, expensive to get wrong. Reads the candidate neighborhood (`fha find --related`, co-occurrence), proposes a merge or a split for human confirmation; the mechanical write is the deterministic tool's job, never the skill's silent action. A `merged_into` person is never directly referenced again (lint E016/W107).
- `place-research` - "fill in this place's history." Loose citations are acceptable here (place context is narrative scaffolding, not vital fact); drafts dated `history:` entries and place notes, links `[[L-…]]`, and proposes registry entries for `fha confirm place` to write.

### 2.3 Usability-review skills (2026-07)

The 2026-07 usability review added three skills and the `today` connection-reaction extension (§2.1). The former skill backlog's one entry, `photo-context`, shipped in this wave - the backlog is now empty; see [`BUILD_INTERFACE.md`](BUILD_INTERFACE.md) Layers I4-I5 for the authoritative status.

- `find-photos` - the photo subsystem's front door: resolves "show me grandma's photos" to a P-id (`fha find`), translates spoken dates to EDTF, answers from `fha photoindex find` at variation-group granularity in plain language (one line per physical photo; fronts/backs/copies counted once), and offers a clickable single-file gallery page (`fha photoindex gallery`). Read-only: identifying a person hands off to `fha photoindex tag-person` and its own confirm prompt.
- `share-and-export` - the conversational front door for the privacy-sensitive act: routes the request to the right exporter (`packet` / `gedcom` / `site --standalone` / `wikitree` / `backup`), speaks each tool's privacy defaults in plain words *before* running, previews first (`--dry-run`, or the stdout render for gedcom/wikitree), then reports exactly where the artifact landed and what stayed home. Never adds an override flag (`--include-restricted`/`--include-dna`/`--include-living`/`--linked`) without the human's explicit, informed ask; importing a tree INTO the archive is a gedcom-import/migration conversation, not this skill.
- `photo-context` - invoked-only caption improvement: gathers what the archive knows about a photo (identified people's relationships via `fha relate`, the event/claim context, place history), drafts a better summary, and - only after the human approves the exact text - writes it AI-marked via `fha photoindex set-summary` (group-addressed so fronts/backs/copies stay consistent). Human captions are never overwritten; never automatic, never bulk. Writes marked as AI per SPEC §20.

### 2.4 Recordings skills (2026-08)

Authored in a live archive against real phone-app exports, then ported here (design: BUILD_INTERFACE.md Layer I6). The pair stands in front of `fha process` for audio and video the way `import-notes` does for paper - intake is not extraction; the interview earns its claims later through `mine-transcript` and `review-claims`.

- `import-recordings` - the recordings on-ramp. Content-hashes every incoming file against what is already filed and skips duplicates (a real 16-file phone export held 6 byte-identical repeats hidden by app renaming); reads the real recording date from the container rather than the filename, settling the recording's own UTC offset BEFORE converting (device-written local-with-offset tag, else the filename clock solved for the offset, else one plain question) and writing an EDTF interval rather than an exact day when it cannot be settled, with the trap written into the record (`creation_time` is UTC at the moment recording *stopped*, an app filename clock is local at the moment it *started*); groups one sitting into one session source under `documents/interviews/{interviewee}-{yyyy-mm-dd}/` named so each topic's audio / app transcript / whisper pass cluster in a listing; always adds a local whisper pass beside the app transcript and never replaces either (they disagree in exactly the spots a reviewer needs); transfers the app's speaker turns onto the whisper text only under measured gates the script enforces as its defaults (hard abort below a 50% token match measured against **both** streams - the matched words over the LONGER of the two, so 50% of the app transcript AND 50% of the whisper transcript, resting on at least 20 matched words; dividing by the shorter stream answered the weaker question "is the small file contained in the big one", and a five-word app export sharing one phrase with one whisper segment scored a perfect 1.00, cleared the gate and had that segment published at confidence 1.00 with the wrong speaker on it, so the gate now reports both coverages in its refusal and a genuinely partial export - 83% of the app against 41% of whisper - fails it too and needs the `--force` it names; label only at a confidence of 0.65 or better, where confidence is coverage × (2 × agreement - 1) and every word of a segment has ONE vote it gives once however many methods claim it, so a fully covered segment needs ≥ 82.5% agreement and a unanimous one ≥ 65% coverage. The gate read 0.90 until the two methods' evidence was pooled per word rather than per speaker total: the alignment and the app's clock could each claim the same word, so a ten-word segment matched on five words (5.0) and overlapping one speaker's interval for 45% of its duration (4.5) scored 9.5/10 = 0.95 for 50% real coverage, and 0.90 of that doubled number was really asking for about 0.45 of honest coverage - which is not what this entry, the SKILL.md or the script's own docstring said it was asking for. 0.65 is the gate MEASURED to reproduce the operating point that was already working once each word votes once (32 synthetic interview pairs, ~2,800 segments with known speakers: 72.7% of segments labelled before against 72.1% after, at the same or a slightly better share correct); an app export with no usable timestamps was never double-counted, so the lower gate does genuinely loosen that path, from ~57% labelled to ~68%, which is the price of one number covering both paths. The often-quoted field figure - precision plateaus near 96% at ~75% coverage - was measured under the OLD arithmetic and has NOT been re-measured here; the calibration above is fixtures, and the script's HONEST LIMITS says so; the timestamp path only switches on when ≥ 80% of app turns really carry a stamp AND the last span that names a speaker reaches ≥ 90% of the audio, because a count of timed turns says nothing about WHERE the coverage sits - an app transcript ending halfway through a recording passed the count while the last speaker's interval stretched to the end of the audio and voted on a tail it never covered; the final interval is capped at that turn's own span, an untimed turn between two timed ones blanks that span rather than extending the earlier speaker over it; never interpolate across a speaker change) and never calls the result diarized; refuses to write over an existing `--out` or `--report` rather than warning about it, because the Stage B command names its output deterministically (`<stem>.md`) and the second run of a session aims straight at the file a human may have spent an afternoon correcting - the script cannot tell its own earlier output from a corrected copy of it (its AI marker survives a human's edits, so the marker proves nothing and no sound cheap test exists), so both cases are refused identically at exit 1 naming the file, and `--replace` is the one flag that authorises the overwrite: `--force` means the mispair gate and only the mispair gate, since forcing past a mispair suspicion is not consent to destroy a corrected transcript, and a run that could attribute nothing at all still refuses even with `--replace` (a file may go, but not for an unlabelled pass-through copy); asks both destinations whether they could ever be written BEFORE the alignment rather than after it, so the ordinary typo (a folder standing on the output name, a parent that is a file) costs a stat call instead of a minute of work followed by half a result - and, for the mid-run surprise that no pre-flight can see, the transcript is **kept** rather than rolled back when the JSON report cannot be saved, because `--out` is the artifact the run exists to produce and `--report` is an optional diagnostic: the message says the transcript was kept, names it, and prints the complete rerun command including the `--replace` that the just-written `--out` now requires (the earlier message said only "re-run with a writable --report path", which the overwrite refusal then blocked - a recovery instruction the tool refuses is worse than none, so every message here that asks for another run prints the whole command and a test executes it); proposes speaker → person as a table with evidence and word shares and writes no name until the human answers per file. Interactive by default; automatic mode needs an explicit up-front say-so and still leaves every claim `suggested`. Two capabilities it reaches for are not `fha` verbs and are enacted under the `_STANDARD.md` §6 owner exception, recorded in its `GAP.md`: content-hash dedupe (wanted `fha media dedupe`, #43 - enacted by the skill's own `scripts/find_duplicate_media.py`, size from the directory entry first and SHA-256 only on a size collision, read-only on both sides, and the `--json` report path is canonicalised and refused before any hashing if it resolves onto an incoming or archived recording, `fha.yaml`, or anywhere inside a media root. The gate **fails closed**: a same-size candidate that cannot be hashed - disconnected storage, a permission-restricted file - yields the third verdict `indeterminate` and **exit 3**, never `new`, because a gate that reports 'not a duplicate' when it simply could not look authorizes the import it exists to prevent. Exit 3 outranks exit 2 deliberately: 2 means 'skip these and carry on', which is the wrong reading when part of the run was never checked; `fha search` finds a transcript that reads alike, which is a lead and not proof of an identical recording) and the container probe (wanted `fha media probe`, #44 - enacted by `ffprobe`). The whisper run and the label transfer are the skill's own `scripts/` by design - model-dependent, non-portable, producing working drafts rather than archive records.
- `transcribe-audio` - local faster-whisper re-transcription of an archived or new recording (`scripts/transcribe_audio.py`), attached as role `whisper-transcript` beside the original transcript with `fha process --more`; the `--name` rule keeps every file of one source under one prefix so a listing shows audio, app transcript and whisper pass together. `--name` takes the source's **shared stem with no role suffix**, because `attach_more` appends the role itself (`{stem}-{role}_{S-id}.{ext}`) - a `--name …-whisper` would file as `…-whisper-whisper-transcript_S-….md` - and the finished `.md` is copied under the documents root before attaching, since `--more` only attaches files already filed there. Where sibling names disagree the skill **says so and stops**: a documents-root file is renamed exactly once, by `fha process`, no verb renames it again (`fha reconcile` re-ties files that *moved*, matching the unchanged basename), and neither the file nor its `files:` entry is ever hand-edited. The script itself holds two invariants the skill's batch advice depends on: **all-or-nothing publication** (segments stream into `.part` siblings and the three outputs are renamed into place only after the iterator is fully consumed, so an interruption, a decode failure or a zero-speech run leaves nothing a "skip what already exists" queue would mistake for a finished pass; the three renames are one commit - destinations preflighted before a segment is decoded and again before the first rename, each previous final set aside so any refused replacement rolls the whole set back - and an incomplete promotion is recognised on the next run by a marker file plus an all-three-present check, since a kill between renames leaves three well-formed but mixed files no consistency check can see, while a kill before the marker leaves one or two files no marker records; only a complete set is a clean no-op, and then only unless `--force`) and a **portable transcript header** (the `.md` names the recording by filename only - never the absolute path typed on the command line, which would publish the operator's directory layout into an archived file and break the day the archive moves). Ends by offering the claim-by-claim audit of facts mined from the garbled original, and that audit is **proposal-only**: agreeing to run it is not agreeing to its findings, so every correction is put to the human as an exact before/after on one named claim and written only on his yes for that claim. When he takes one, the fix goes through `fha claim <C-id> --status accepted --value "…"` - `--status` in the *same* call, because `fha claim` refuses `--reviewed` without it and a bare `--value` would leave the old `reviewed:` date standing over wording no human has read, which is an unreviewed machine reading wearing a human's signature. Declining writes nothing; `--status needs-review` is offered, never assumed, for a claim he wants to park. A reading that changes *which* fact is asserted (a different person, place or event) is new material, not a repair: it becomes a `suggested` claim for `review-claims` and the old claim's fate is his call. `notes:` and `anchor:` have no `fha claim` flag at all, so the audit blocks rather than hand-rolling one - the corrected reading is recorded with `fha source note`, the in-place repair happens only on his explicit ask (paired with a `--status accepted` re-stamp), and the wanted verb is filed in the skill's `GAP.md` per `_STANDARD.md` §6. Every correction carries its whisper timestamp and what the app transcript had instead.
- `mine-transcript` extension - when a source carries more than one transcript of the same recording, mine from the side-by-side comparison: whisper wins on proper names, places and numbers; the app transcript on turn structure; a divergence in coverage usually means the app truncated or mis-attached a file. Anchor to the transcript actually quoted, naming it when the source has several.

### 2.5 Escape hatch and legacy on-ramp

Two skills that landed with the work they serve rather than with a numbered wave, and so are easy to
lose from an inventory. Build status: [`BUILD_INTERFACE.md`](BUILD_INTERFACE.md) Layer I7.

- `reconcile-site-edits` - the static site's escape hatch (docs/SITE_PLAN.md layer (e)). `fha site` is deterministic and never reads its own output, so a hand-edited HTML page is silently overwritten by the next build. The skill reads the edited page, diffs it against a pristine baseline build to recover what the human meant, and folds that intent into the SOURCE it belongs to - styling to `.fha/design/custom.css`, homepage copy to `notes/home.md`, person prose to that person's record, title/hero to `fha.yaml`'s `site:` block - then rebuilds so the edit survives. Every source write is confirmed with the human first; the generator itself learns nothing and stays deterministic.
- `import-notes` - the legacy-notes on-ramp, standing in front of `fha process` for paper the way the recordings pair does for audio. Chunks a pile of freeform notes and proposes a home for each chunk under the routing rule (evidence someone asserted → inbox → source; a thing to find out → open question; a testable belief → hypothesis; a search already run → research log; anything else → `notes/research/`), writing each chunk only on the human's confirmed ruling. It drafts no claims - intake is not extraction, and evidence earns its claims later through `process-source` and `review-claims` - and it never deletes or rewrites the original notes; a scraps file is dissolved only on an explicit say-so, after everything in it has landed.

### 2.6 The image-only gap (2026-08, issue #46)

One skill, added after an archive with **43 image-only sources carrying 135 accepted claims** was found to have no way to say so. A source whose files are all scans, photographs or image-only PDFs contributes **no text to the archive at all**: its claim values are the only searchable words about it, so `fha find --text` searches what one earlier pass chose to write down while looking exactly like a search of the evidence. That null result was read as a negative finding - a surname judged invented and struck, while it sat in plain handwriting on a chart inside a 22-page image-only scan.

The split is the one `fha xref` already uses, and it is why this is a skill and not a verb. **The tools detect the gap:** `fha lint`'s **W124** (accepted claims resting on evidence the archive holds no words for) and the coverage note `fha find --text` prints under *every* result, hit or miss. **The skill produces the text** - irreducibly model work, since the agent reads the images. **An existing deterministic tool writes it** - `fha process --more <file> transcript`, `role: transcript` being SPEC §13 vocabulary already. No new verb was needed and none was invented.

- `transcribe-source` - reads an image-only source and writes out what it says as a `[Page N]`-labeled `role: transcript` companion, in the original's pagination so a claim can carry `anchor: "page N"`. Two entry points, one procedure: **inside `process-source`, between Stage A and Stage B** (the ordering rule is the win - the transcript exists before claims are drafted, so claims come from text rather than from a single pass over pictures, and `process-source` is the only place that ordering can be enforced), and **standalone for backfill** of already-ingested sources, in confirmed batches of five or fewer whose worklist is re-read from `fha lint` each time rather than carried in session memory (a transcribed source stops being reported by W124, so lint *is* the resume). `fha source extract` is tried first on any PDF, so the model is never asked to re-read text the file already contains. The skill **drafts and edits no claims**: unclaimed facts hand off to `mine-transcript`, and a reading that contradicts an existing claim - **including an `accepted` one** - becomes a `## Q:` block in `notes/questions.md` under the AGENTS.md rule, never a silent correction. Hand-transcribing three such sources found two accepted claims materially wrong (a death age off by seventeen years; a photograph identified as the wrong couple by an inference the document contradicts), a time of death wrong in two claims and in a note that purported to quote the page verbatim, a scribal error being carried as a reading ambiguity, and three substantive facts never claimed at all - and the errors were *not* in the hard-to-read sources.
- **A wrong transcript is worse than no transcript**, which is the design constraint the whole skill is shaped around: #46's failure was a null result read as a negative finding, and a misread transcript produces confident *hits* - the same error with the evidence apparently on your side. So the image remains the evidence of record and the transcript is an index into it, never a substitute; uncertainty survives into the text (`[illegible]`, `[word?]`, `[unclear: a or b]`, `[torn]`, `[struck: …]`, `[sic]`) and is never silently resolved; and a scribal error is transcribed `[sic]` with the observation logged as a question, because a transcript that quietly resolves ambiguity is how a slip of a pen becomes a family fact.
- **The unreviewed-transcript marker contract.** So a consumer can tell a machine reading nobody has checked from one a human has verified, the skill reuses the archive's existing marker pair rather than inventing a third convention: `<!-- AI-DRAFT … -->` / `<!-- AI-ACCEPTED … -->`, same grammar as `write-biography`'s and `fha confirm draft`'s. It applies to a *text companion* - a `files:` entry whose `role:` is `transcript`/`transcription`/`extracted-text` and whose file is `.md`/`.txt`, exactly the set `fha index` loads into `transcripts_fts`, so the state is decidable from indexed content with no extra file reads. Four states on the companion's full text: **unreviewed** (contains a complete AI-DRAFT marker), **verified** (contains AI-ACCEPTED and no AI-DRAFT), **unmarked** (neither - a human typed it, or `fha source extract` dumped it mechanically), **damaged** (either marker word outside a complete marker). *unreviewed* outranks *verified*; *damaged* is treated as unreviewed, failing closed exactly as `_lib.strip_unaccepted_drafts` does. Placement is load-bearing, not decoration: exactly one marker, as the **last non-blank line**, with no `#`/`##` heading below the title, because `strip_unaccepted_drafts` treats a marker as sitting at the *end* of the span it covers and a `#`/`##` heading as a block boundary - a marker at the end of a heading-free file withholds the whole unchecked transcript from any publication path that ever runs that function, while a top-of-file marker publishes all of it. The source's `## AI Passes` entry mirrors the state (`human_reviewed:`), but **the file's marker wins**: the file travels, and must state its own status without its record.
- **One gap, blocked not enacted** (`_STANDARD.md` §6): nothing flips that marker. `fha confirm draft` takes a `<P-id>` and edits a person profile; there is no verb reaching a source's companion file, and a skill never hand-edits a marker. So every AI transcript stays *unreviewed*, which is at least true, and the wanted verb (`fha confirm transcript <S-id>`, preserving date/model and flipping `human_reviewed:` in the same write) is recorded in [`transcribe-source/GAP.md`](.claude/skills/transcribe-source/GAP.md).
