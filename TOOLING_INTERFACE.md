# TOOLING_INTERFACE.md - The AI Interface: Research Workbench & Skills

**Who this is for:** developers building or extending the *AI-interface* side of the archive - the workbench harness configuration and the workflow skills that turn `fha` tools into a genealogy-aware research assistant. If you just want to use the archive, start with [`docs/GETTING_STARTED.md`](docs/GETTING_STARTED.md).

**Version 2.3 - companion to SPEC.md v2.3 and TOOLING.md v2.3 (versions track the SPEC).**

This document is a focused expansion of one layer that the main [`TOOLING.md`](TOOLING.md) only sketches: the **harness + skills** layer that sits *on top of* the deterministic `fha` tool suite. TOOLING.md specifies the tools (schemas, algorithms, command shapes); this document specifies the AI interface that drives them - the workbench configuration that makes any conforming harness genealogy-aware, the browser workbench, and the workflow skills that orchestrate `fha` calls plus model judgment into the everyday research loop.

The governing split, stated once and obeyed everywhere below: **deterministic work belongs in `fha` tools; AI judgment belongs in workbench skills; human review is the only gate to `accepted`.** A skill never reimplements what a tool does - it calls the tool and adds the judgment a tool cannot have. AI passes are always *invoked* and recorded - nothing mines, extracts, or classifies silently.

The three sibling design docs:

| Doc | Concern |
|---|---|
| [`TOOLING.md`](TOOLING.md) | core `fha` tools (index, lint, views, find, process, site, …) |
| [`TOOLING_INGESTION.md`](TOOLING_INGESTION.md) | the inbox contract and the capture front ends |
| **`TOOLING_INTERFACE.md`** (this doc) | workbench harness + workflow skills |

The build order for all three is TOOLING.md §15; this doc's pieces are its last layer.

## 1. The research workbench (harness configuration)

**Pattern (SPEC §6):** an agentic CLI harness opened on the archive root, beside a plain text editor - human and AI edit the same files.
Claude Code is the operating choice, not a required one.
The configuration below is what makes any conforming harness genealogy-aware, and what keeps the choice reversible.

**Vendor-lock prevention rules.**
1. **`AGENTS.md` is canonical.** All agent operating instructions live there, in plain markdown, harness-agnostic. `CLAUDE.md` is a one-line deferral (`Read and follow AGENTS.md.`) plus, at most, Claude-Code-specific notes. Any other harness's convention file (e.g. for Codex or Gemini CLI) gets the same one-line deferral.
2. **Skills are portable.** Workflow skills live in `.claude/skills/{name}/SKILL.md` using the open SKILL.md standard, and an installed archive carries an identical copy in `.agents/skills/` so Codex finds them too; they contain instructions and `fha` invocations only - no harness APIs.
3. **No harness-only state is load-bearing.** Session memory, harness caches, and MCP configurations are disposable; anything worth keeping is written into archive records. Switching harnesses must cost one afternoon, not a migration.
4. The harness's "knowledge" of the archive is the **index and the `fha` tools**, never bulk file ingestion - ten thousand photos cost zero context because photo questions are `fha photoindex` calls.

**External roots in the workbench.** When `fha.yaml` maps a root outside the archive, the harness needs access granted: for Claude Code, launch with `--add-dir <photos-root>` (prefer the flag over the settings-file `additionalDirectories` route, e.g. in a small launch script committed next to fha.yaml).
The agent still must not bulk-read asset trees - access exists for exiftool/process/packet operations, not ingestion.

**Model selection (workbench economics).** Deterministic `fha` tools cost no model credits - the deterministic/judgment split is also the cost model.
For model work, tier by judgment density, not habit: the **workhorse tier** (currently Claude Sonnet) is the default for tool-building, processing, review, and drafting; the **frontier tier** (currently Claude Opus / Fable) is escalated per task for proof arguments, merge/separate judgment, brick-wall research, spec-refinement, and stuck debugging - the tell is *cheap to attempt, expensive to get wrong*; the **fast tier** (currently Claude Haiku) serves batch API pipelines only after a sample-quality bake-off (handwriting transcription degrades quietly on small models).
Switch per session (`/model`); the tiers are roles, not vendors - any harness's equivalents slot in.

**Workbench session hygiene** (enforced by AGENTS.md): run `fha lint` after any batch of edits; never bypass `fha process` for renames; new claims always `status: suggested` when AI-drafted; never edit below a GENERATED header.

## 1b. `fha serve` - the localhost workbench front door

The agentic CLI harness (§1) is one front door onto the archive. `fha serve` is a second, deliberately narrow one: a **non-load-bearing front door onto the same headless engines** every CLI command drives (SPEC §5's "the tools are a headless core" principle - the engine/interface split TOOLING §1 specifies as `run_*`/`_cmd_*`). It adds no new capability and owns no truth of its own; it is a browser window over the same `fha` commands a human or an agent would otherwise type.

**Not a daemon.** Human-started, foreground, 127.0.0.1-only, no login, no network beyond the loopback socket, no file watcher. It does not run unattended, does not accept connections from any other machine, and an AI agent never starts it on its own - a person double-clicks `serve.cmd` or types `fha serve` because *they* want the browser view open.

**The parity rule.** Every write the workbench makes is one documented `fha` command, run in-process through its `run_*` engine, and every apply echoes the literal CLI command it just ran (`cli_echo`), so a human reading the echo can reproduce the action at a terminal and a skill never needs to learn a second interface. The rule has four **declared exceptions**, each a convenience with nothing hidden behind it:

1. **The file picker** (`/api/pickfile`). A browser page cannot read a local file's full path, so serve, running on the same machine, opens the OS's own file-picker and passes the choice back into the register-by-path form. The pick reads, moves and registers nothing; the write is still `fha capture --path`'s preview → confirm.
2. **Reciprocal ties by default.** The workbench's relate and add-family actions pass `--reciprocal` unless told otherwise, so a tie recorded from either person's page shows on both. The CLI's own default stays one-sided, and the echo always names the flag that ran.
3. **Editing the homepage intro** (`home.edit`). It writes `notes/home.md` - a human-owned file with no `fha` verb, the same as editing it in any text editor - and its echo says exactly that.
4. **Uploading a file** (`/api/upload`). It copies the uploaded file into `inbox/` (and, when a note is typed, a `{stem}.notes.md` beside it, in the TOOLING_INGESTION §1 shape). There is no `fha` verb for it because the CLI equivalent is putting a file in the inbox folder by hand.

**Add-family** (`person.add_family`) is not an exception: it is two commands, `fha person new "Name" …` then `fha person relate <P-id> --<relation> <new P-id> --reciprocal`, and its echo shows both. Linking an existing person is the second command alone.

**Routes and writes.** Reads: `/` and the record pages (`/persons/…`, `/sources/…`, `/places/…`, from the snapshot below), `/review` (suggested claims grouped by source, `fha xref` and `fha cooccur` candidates - the engines `fha report` reads), `/inbox` (each inbox item as TOOLING_INGESTION §1.1 groups it), `/root/{photos,documents,inbox}/…` (asset files), and `/api/find` (the `fha find --json` engine). Writes, all `POST` and CSRF-checked: `/api/run` (the verb table), `/api/upload`, `/api/reindex` (= `fha index`), `/api/open` (opens a file in the OS; writes nothing), `/api/pickfile` (writes nothing). The **one list of `/api/run` verbs** - each with its schema, its engine, its CLI echo and its reindex policy - is the `VERBS` table in [`tools/serve.py`](tools/serve.py), described row by row in `tools/README.md`'s "fha serve - implementation status"; that table is the reference, and this document does not copy it.

**The human gate is a click, not a method (SPEC §6).** SPEC §6 is explicit that the review gate is the human's *decision*, not any one editing method. Every mutating action is dry-run-previewed first, in plain English, and only a second, explicit confirmation applies it (the server defaults every request to preview unless the confirm step says otherwise, defense in depth behind the UI). A `suggested` → `accepted` claim review through the workbench stamps `reviewed:` exactly as the CLI does - the click *is* the human decision.

**The mechanical/generative boundary.** `fha serve` never reads evidence and never drafts anything from it - no button mints a `suggested` claim by reading a source's text or an image. Stage B drafting (entity resolution, claim extraction, biography prose) stays with the AI skills (§2), run from the agentic harness. The workbench runs only deterministic engines a human (or a skill acting on the human's explicit say-so) decided to invoke - Stage A/C infrastructure with a browser skin, never Stage B.

**Refresh-on-use, not a watcher.** The read side is a linked, unredacted snapshot of `fha site`'s own generator under `.cache/serve/`, rebuilt only when a page is requested AND the record trees have changed since the last build (a cheap mtime probe plus a path-manifest check, so a deleted record is caught too; `serve.py`'s `snapshot_is_stale`) - never on a timer or a filesystem watch. What you see is never older than your last click.

**Disposability - killing it loses nothing.** The only thing `fha serve` writes outside the record tree its engines mutate is that snapshot cache - a rebuildable artifact, like `.cache/index.sqlite` (SPEC §5). `fha site` never depends on `fha serve` having run; deleting `serve.py` and `.cache/serve/` changes nothing about the archive. Stopping the process is always safe.

**Security is the whole trust boundary** (`run_serve_preflight` and the request handler). Serve binds 127.0.0.1 only and checks the Host header against an allowlist on every request. Every POST carries a per-process CSRF token, compared with `hmac.compare_digest`. Snapshot files, `/root/` aliases, `/api/open`, `/api/upload` and the `process.file` argument are confined by resolving the path and checking it is inside its root (`capture.path` is deliberately not confined: registering a file that stays where it is is its job). Responses carry `no-store` and `nosniff`. One global lock is held across mutate, reindex and snapshot invalidation, so two clicks never interleave. The default port is 8765; `--port 0` picks a free one.

**Privacy is unchanged.** The read side is the **linked** view (real archive paths, unredacted - a local owner preview, TOOLING §12) and never leaves the machine. Sharing outward still goes through `fha site --standalone` (or the `share-and-export` skill); the workbench adds a front end onto that command, not a second export surface.

Flags: `docs/COMMANDS.md` (`fha serve`). Tests: `tests/test_serve.py`.

## 2. The skills (the working surface)

Skills are the layer a genealogist actually touches - most `fha` commands are what skills shell into (TOOLING.md §17). Each skill is a `.claude/skills/{name}/SKILL.md`: portable instructions plus `fha` invocations, no harness APIs. A skill's job is the *judgment* around a deterministic tool - which claim to draft, which name resolves to which person, where to look next - never the bookkeeping the tool already owns. The authoring contract is [`.claude/skills/_STANDARD.md`](.claude/skills/_STANDARD.md).

Every skill obeys the contract (AGENTS.md): AI-drafted claims are `status: suggested`; only the human moves a claim to `accepted`; every AI pass is recorded as an entry in the source's `ai_passes:` list (SPEC §14); nothing edits below a GENERATED header or overwrites human-written text. Every skill also follows SPEC §17's research ladder: a question is written down only when a person asks it or the evidence conflicts - never a gap a tool computes - and a guess is the question entry's working answer (`id`, `guess`, `basis`, `verify`), never a separate object or a claim.

### 2.1 The core loop

- `review-claims` - Stage C: walk a source's `suggested` backlog in one of three styles - guided one-by-one (the default), **batched** (numbered groups of about five grouped by person, each claim a one-line sentence + anchor + confidence flag + its source link; the human answers with one grouped decision, so each claim still receives an individually stated human decision; offered proactively past about six suggested claims), or self-serve skimming of the source file. Every claim presented carries its evidence link: the anchored source file path (the asset file when the anchor identifies it, else the record `.md`) followed by the `[[S-id]]` token. Decisions are accept, dispute, edit, reject, or **park**: a parked claim stays `suggested` with today's `reviewed:` date ("checked, still open", SPEC §8.1). A grouped same-status decision is one batch `fha claim C-a C-b … --status X` (one preview, one apply); field edits stay per-claim calls. Close-out: a reindex (full when the pass minted new people/places, else `--source`), `fha xref`, a timeline/sources-index/draft-queue refresh for the touched people (a `views brackets` check when a relationship claim was accepted), and lint. Accepting a `death` or `burial` claim marks the person it names `deceased:` (or its one person) as no longer living when their flag read `unknown` (TOOLING §3b), and the close-out reports that line; where `fha claim` warned instead, the close-out asks and runs `fha person set-living <P-id> false` only on an explicit yes (TOOLING §3c). Three more explicit-yes-only offers: on a park, recording what would settle it as a §17b question entry (with a working answer if the human voices a guess) in the person's research file or `notes/questions.md`; a promotion nudge, once, for a decided-on stub at or over `fha.yaml` `promotion:` → `claims_threshold` (default 5) or flagged direct-line - `fha person promote <P-id>` or `--into connections/` (SPEC §12.3), then `write-biography`; and a place-registration nudge, once, for the largest `fha places candidates` cluster holding a claim decided on this session when it is at or over 10 claims, looked up with `fha find --json … --kind place` before the offer is spoken and written with `fha confirm place` (`--into` an existing place, else a fresh mint). That write lands after the done-gate, so it reopens the close-out with `fha index` + `fha places lint` + `fha lint`.
- `process-source` - the pipeline driver. If the inbox item is a source stub (TOOLING_INGESTION §1), its frontmatter and notes seed Stage A (pre-filling §14 frontmatter) and its person/vital hints seed Stage B; otherwise Stage A starts from the bare file. Stage A `fha process`; for an image-only item, `transcribe-source` before any drafting (§2.6); Stage B AI draft (file reading incl. vision, entity resolution with candidate proposals against the index, `suggested` claims + stories) - places resolve against the registry by their **settlement name** (`fha find --json "<town>" --kind place` matches `name:`/`alt_names:` and never `hierarchy:`), an unlinked place stays a legitimate permanent state, and a text already carrying 10+ claims in `fha places candidates` earns one explicit-yes-only registration offer whose write carries its own `fha index` + `fha places lint`; hand-off to `review-claims` for Stage C. The stub is consumed - promoted into the source record, not left behind.
- `mine-transcript` - the invoked extraction pass: selective claim drafting (`suggested` + `anchor:`), name→P-id resolution against the index with candidate proposals for unresolved names (stubs minted on confirmation), stories to `## Stories`, the pass recorded in the source's `ai_passes:` list. Never runs unrequested. When a source carries more than one transcript of the same recording, it mines from the side-by-side comparison: whisper wins on proper names, places and numbers; the app transcript on turn structure; a divergence in coverage usually means the app truncated or mis-attached a file. It anchors to the transcript actually quoted, naming it when the source has several.
- `today` - run `fha report`, narrate it discoveries-first, offer to start the top item (e.g. a `review-claims` session) - with §6b eligible to win that one slot when its largest place-text cluster carries more claims than §1's oldest backlog has suggested ones, handing off to `place-research`. Its only writes are the human's explicit say-so acting on the briefing: a confirmed win via `fha confirm discovery`, or a narrated connection candidate he answers ("yes, they were neighbors" / "no, stop suggesting that pair") via `fha confirm cooccur` / `fha confirm dismiss` - dry-run echoed first, minted `suggested` unless his flat, unhedged answer is the review.
- `research-next` - inference and steering. Checks `notes/research-log.md` FIRST and never proposes a search already logged unless the nil has aged past the re-run horizon; combines the gaps `fha report` computes, open questions, and open working answers with historical context (which record sets exist for the time and place, where they are held, what era events imply) into concrete, ranked leads; logs every executed search back to `notes/research-log.md` (SPEC §17c). It may write a guess as the working answer on its question entry (`origin: agent`), in the person's research file or `notes/questions.md` - leads and working answers, never claims, and never a computed gap written as a question.
- `write-biography` - drafting rules for profiles: citation density (SPEC §16), uncited-prose-is-context, summary-block format, `[[P-…]]`/`[[S-…]]` links only from verified IDs. Consumes the `fha views draft-queue` backlog (TOOLING.md §14b); draft prose carries `<!-- AI-DRAFT … -->` markers until the human accepts it via `fha confirm draft`. Pronouns come from the person's `gender:`, else `sex:`, else the prose stays neutral (SPEC Appendix A.7). **Voice is a named style**: `chronicle` (era-by-era, fact-forward - the default) or `narrative` (story-driven; texture only from cited claims or clearly-flagged period context, never invention). Resolution: the human's in-session ask wins, else an `fha.yaml` `biography: style:` block (read directly, like `site:`), else chronicle. The style is named in the AI-DRAFT marker and the pass's `note:` so later sessions match the register; the citation contract is identical in both styles.

### 2.2 Judgment-heavy skills

- `merge-identities` - "same person" / "two people" judgment. Frontier-tier: cheap to attempt, expensive to get wrong. Reads the candidate neighborhood (`fha find --related`, co-occurrence), proposes a merge or a split for human confirmation, and enacts a confirmed merge with `fha confirm merge` (dry-run first). A `merged_into` person is never directly referenced again (lint W107 lists any left; it counts for the survivor meanwhile, SPEC §9).
- `place-research` - "fill in this place's history." Loose citations are acceptable here (place context is narrative scaffolding, not vital fact); drafts dated `history:` entries and place notes, links `[[L-…]]`, and proposes registry entries for `fha confirm place` to write.

### 2.3 Photos and sharing

- `find-photos` - the photo subsystem's front door: resolves "show me grandma's photos" to a P-id (`fha find`), translates spoken dates to EDTF, answers from `fha photoindex find` at variation-group granularity in plain language (one line per physical photo; fronts/backs/copies counted once), and offers a clickable single-file gallery page (`fha photoindex gallery`). Read-only: identifying a person hands off to `fha photoindex tag-person` and its own confirm prompt.
- `share-and-export` - the conversational front door for the privacy-sensitive act: routes the request to the right exporter (`packet` / `gedcom` / `site --standalone` / `wikitree` / `backup`), speaks each tool's privacy defaults in plain words *before* running, previews first (`--dry-run`, or the stdout render for gedcom/wikitree), then reports exactly where the artifact landed and what stayed home. Never adds an override flag (`--include-restricted`/`--include-dna`/`--include-living`/`--linked`) without the human's explicit, informed ask; importing a tree INTO the archive is a gedcom-import/migration conversation, not this skill.
- `photo-context` - invoked-only caption improvement: gathers what the archive knows about a photo (identified people's relationships via `fha relate`, the event/claim context, place history), drafts a better summary, and - only after the human approves the exact text - writes it AI-marked via `fha photoindex set-summary` (group-addressed so fronts/backs/copies stay consistent). Human captions are never overwritten; never automatic, never bulk. Writes marked as AI per SPEC §20.

### 2.4 Recordings

The pair stands in front of `fha process` for audio and video the way `import-notes` does for paper - intake is not extraction; the interview earns its claims later through `mine-transcript` and `review-claims`.

- `import-recordings` - the recordings on-ramp. Content-hashes every incoming file against what is already filed and skips duplicates (`fha media dedupe`: size first, SHA-256 only on a size collision, read-only on both sides; a same-size candidate that cannot be hashed is `indeterminate`, exit 3, never `new` - the gate fails closed); reads the real recording date from the container (`fha media probe`) rather than the filename, settling the recording's own UTC offset BEFORE converting (device-written local-with-offset tag, else the filename clock solved for the offset, else one plain question) and writing an EDTF interval rather than an exact day when it cannot be settled, with the trap written into the record (`creation_time` is UTC at the moment recording *stopped*, an app filename clock is local at the moment it *started*); groups one sitting into one session source under `documents/interviews/{interviewee}-{yyyy-mm-dd}/` named so each topic's audio / app transcript / whisper pass cluster in a listing; always adds a local whisper pass beside the app transcript and never replaces either (they disagree in exactly the spots a reviewer needs); transfers the app's speaker turns onto the whisper text only under measured gates the script enforces as its defaults - a hard abort below a 50% token match measured against **both** streams (the matched words over the LONGER of the two, resting on at least 20 matched words), and a label only at a confidence of 0.65 or better, where confidence is coverage × (2 × agreement - 1) and every word of a segment has ONE vote it gives once however many methods claim it, so a fully covered segment needs ≥ 82.5% agreement and a unanimous one ≥ 65% coverage; the timestamp path only switches on when ≥ 80% of app turns carry a stamp AND the last span that names a speaker reaches ≥ 90% of the audio, the final interval is capped at that turn's own span, and an untimed turn between two timed ones blanks that span rather than extending the earlier speaker over it - and never calls the result diarized; refuses to write over an existing `--out` or `--report` (it cannot tell its own earlier output from a corrected copy), with `--replace` the one flag that authorises the overwrite and `--force` meaning the mispair gate only; checks both destinations before the alignment, and when only the optional report cannot be saved the transcript is kept and the complete rerun command printed; proposes speaker → person as a table with evidence and word shares and writes no name until the human answers per file. Interactive by default; automatic mode needs an explicit up-front say-so and still leaves every claim `suggested`. The whisper run and the label transfer are the skill's own `scripts/` by design - model-dependent, non-portable, producing working drafts rather than archive records.
- `transcribe-audio` - local faster-whisper re-transcription of an archived or new recording (`scripts/transcribe_audio.py`), attached as role `whisper-transcript` beside the original transcript with `fha process --more`. `--name` takes the source's **shared stem with no role suffix**, because `attach_more` appends the role itself (`{stem}-{role}_{S-id}.{ext}`), and the finished `.md` is copied under the documents root before attaching, since `--more` only attaches files already filed there. Where sibling names disagree the skill **says so and stops**: a documents-root file is renamed exactly once, by `fha process`, and neither the file nor its `files:` entry is ever hand-edited. The script publishes all-or-nothing (segments stream into `.part` siblings, the three outputs are renamed into place together only after the run completes, and an interrupted promotion is marked on disk and repaired on the next run) and writes a portable header (the recording by filename, never an absolute path). It ends by offering the claim-by-claim audit of facts mined from the garbled original, and that audit is **proposal-only**: every correction is put to the human as an exact before/after on one named claim and written only on his yes for that claim, through `fha claim <C-id> --status accepted --value "…"` (or `--notes`, `--anchor`) - `--status` in the *same* call, because a bare field edit would leave the old `reviewed:` date standing over wording no human has read. A claim he wants to park goes back to `suggested` with today's `reviewed:` date, offered, never assumed. A reading that changes *which* fact is asserted is new material: a `suggested` claim (`fha claim new … --anchor "…-whisper, 00:41:22"`) for `review-claims`, and the old claim's fate is his call. Every correction carries its whisper timestamp and what the app transcript had instead.

### 2.5 The escape hatch and the notes on-ramp

- `reconcile-site-edits` - the static site's escape hatch (docs/SITE_PLAN.md layer (e)). `fha site` is deterministic and never reads its own output, so a hand-edited HTML page is overwritten by the next build. The skill reads the edited page, diffs it against a pristine baseline build to recover what the human meant, and folds that intent into the SOURCE it belongs to - styling to `.fha/design/custom.css`, homepage copy to `notes/home.md`, person prose to that person's record, title/hero to `fha.yaml`'s `site:` block - then rebuilds so the edit survives. Every source write is confirmed with the human first; the generator itself stays deterministic.
- `import-notes` - the legacy-notes on-ramp, standing in front of `fha process` for paper the way the recordings pair does for audio. Chunks a pile of freeform notes and proposes a home for each chunk under the routing rule (evidence someone asserted → inbox → source; a thing to find out → open question; a testable belief → the working answer on that question; a search already run → `notes/research-log.md`; anything else → `notes/research/`), writing each chunk only on the human's confirmed ruling. It drafts no claims and files no computed gap as a question, and it never deletes or rewrites the original notes; a scraps file is dissolved only on an explicit say-so, after everything in it has landed.

### 2.6 The image-only gap

- `transcribe-source` - for a source whose files are all scans, photographs or image-only PDFs, and so contributes **no text to the archive**: its claim values are the only searchable words about it, so `fha find --text` searches what one earlier pass chose to write down while looking exactly like a search of the evidence. **The tools detect the gap** (`fha lint` W124, and the coverage note `fha find --text` prints under every result); **the skill produces the text**; **an existing tool writes it** (`fha process --more <file> transcript`). It writes a `[Page N]`-labeled `role: transcript` companion in the original's pagination, so a claim can carry `anchor: "page N"`. Two entry points, one procedure: **inside `process-source`, between Stage A and Stage B** (the transcript exists before claims are drafted, so claims come from text rather than from one pass over pictures), and **standalone for backfill**, in confirmed batches of five or fewer whose worklist is re-read from `fha lint` each time (a transcribed source stops being reported by W124, so lint *is* the resume). `fha source extract` is tried first on any PDF. The skill **drafts and edits no claims**: unclaimed facts hand off to `mine-transcript`, and a reading that contradicts an existing claim - **including an `accepted` one** - becomes a `## Q:` entry, never a silent correction.
  - **A wrong transcript is worse than no transcript.** A null result read as a negative finding is the failure the skill prevents; a misread transcript produces confident *hits* - the same error with the evidence apparently on your side. So the image remains the evidence of record and the transcript is an index into it; uncertainty survives into the text (`[illegible]`, `[word?]`, `[unclear: a or b]`, `[torn]`, `[struck: …]`, `[sic]`) and is never silently resolved.
  - **The unreviewed-transcript marker.** The skill reuses the archive's marker pair (`<!-- AI-DRAFT … -->` / `<!-- AI-ACCEPTED … -->`, SPEC §16c) on a *text companion* - a `files:` entry whose `role:` is `transcript`/`transcription`/`extracted-text` and whose file is `.md`/`.txt`, exactly the set `fha index` loads into `transcripts_fts`. Four states on the companion's full text: **unreviewed** (a complete AI-DRAFT marker), **verified** (AI-ACCEPTED and no AI-DRAFT), **unmarked** (neither - a human typed it, or `fha source extract` dumped it), **damaged** (either marker word outside a complete marker, treated as unreviewed, failing closed as `_lib.strip_unaccepted_drafts` does). Exactly one marker, as the **last non-blank line**, with no `#`/`##` heading below the title, because `strip_unaccepted_drafts` treats a marker as sitting at the *end* of the span it covers. The marker is the only record of review; the source's `ai_passes:` entry says only that the pass happened.
  - **One gap, blocked not enacted** (`_STANDARD.md` §6): no verb flips that marker. `fha confirm draft` takes a `<P-id>` and edits a person profile, and a skill never hand-edits a marker, so every AI transcript stays *unreviewed*. The wanted verb (`fha confirm transcript <S-id>`) is recorded in [`transcribe-source/GAP.md`](.claude/skills/transcribe-source/GAP.md).

### 2.7 The researcher's own family

- `setup-interview` - the first-run on-ramp, named in `fha install`'s "Next steps". The researcher describing his own parents, spouse and children is firsthand testimony (`information: primary`, `evidence: direct`), so it earns a real source with a real citation, not a config value. It asks, once: **who are you** (mints his own person record and sets `sex:`, which the Ahnentafel numbering reads); **how do you want to be numbered** (`root_generation: self | children`, asked in plain words and written straight into `fha.yaml`, which is plain and hand-editable); and **immediate family** - parents, spouse(s), children, names/sexes/rough dates. It writes one `source_class: authored` interview source and drafts `relationship` claims with explicit `roles:` maps for every parent-child edge (never `birth` claims: a birth claim's second person is as often an informant or a doctor as a parent) plus a `marriage` claim per spouse. Every claim lands `status: suggested` and hands off to `review-claims`. On his yes it also fills the family part of `START_HERE.md` (between its `<!-- FAMILY` comment lines; never over words he wrote there himself). Person minting and the `sex:`/`living:` writes are the same direct, confirmed-in-conversation writes `fha person new`/`set-sex`/`set-living` make everywhere else.
  - **Step 0, the place-backlog offer.** Before the family questions, one silent, one-time check: an archive that already carries imported material (`fha gedcom import` run first) can reach this interview with zero registered places and a real backlog of unlinked `place_text`. `fha index` then `fha places candidates --include-suggested` surfaces the clusters (an import mints everything `suggested`, which the everyday view excludes). Past a 20-claim oversight bar (the scale `fha report`'s lead-in escalation uses), the skill offers once to register the biggest cluster(s) via `fha confirm place`, then `fha index` + `fha places lint`. Declining, or no cluster past the bar, means it says nothing.
