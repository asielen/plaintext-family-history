# TOOLING.md - Plaintext Family History: Tooling Design

**Who this is for:** developers building or extending the `fha` tool suite. If you just want to use the archive, start with [`GETTING_STARTED.md`](GETTING_STARTED.md).

**Version 1.2 - 2026-06-12 · companion to SPEC.md v1.2 (versions track the SPEC)**

This is the implementation design for every tool that supports the archive.
SPEC.md Part IV states *what* each tool must do; this document specifies *how* - schemas, algorithms, command shapes, libraries, and edge cases - in enough detail to rebuild any tool from scratch in any language.
Tools are conveniences: the archive works by hand without them, and every artifact they produce is a disposable cache.

Tooling design changes that affect the spec must be reflected in SPEC.md; all changes are recorded in git history.

**This doc covers the core `fha` tools.** Two sibling design docs carve out the layers that only sketch here, each with its own build doc:

| Doc | Concern | Build doc |
|---|---|---|
| **`TOOLING.md`** (this doc) | core `fha` tools (index, lint, views, find, process, site, …) | [`BUILD.md`](https://github.com/asielen/plaintext-family-history/blob/master/BUILD.md) |
| [`TOOLING_INGESTION.md`](https://github.com/asielen/plaintext-family-history/blob/master/TOOLING_INGESTION.md) | capture / inbox / web on-ramp | [`BUILD_INGESTION.md`](https://github.com/asielen/plaintext-family-history/blob/master/BUILD_INGESTION.md) |
| [`TOOLING_INTERFACE.md`](https://github.com/asielen/plaintext-family-history/blob/master/TOOLING_INTERFACE.md) | workbench harness + workflow skills (the AI interface) | [`BUILD_INTERFACE.md`](https://github.com/asielen/plaintext-family-history/blob/master/BUILD_INTERFACE.md) |

*Those five, and `AGENTS_TOOLING.md`, are linked to GitHub rather than by relative path on purpose: they are tool-BUILDING docs and are **not** vendored into an installed archive (§13c), so a relative link would be a dead end for anyone reading `TOOLING.md` inside their own archive. Keep new links to them absolute.*

**Operating principles for all tools:** no daemons, watchers, or schedulers - freshness is refresh-on-use (cheap incremental refreshes run at the start of any tool that needs them, notably `fha report`).
Deterministic work belongs in `fha` tools; AI judgment belongs in workbench skills; human review is the only gate to `accepted`.
AI passes are always *invoked* and recorded - nothing mines, extracts, or classifies silently.

**Single writer, no lock** (owner decision, 2026-08-20, #48: document the assumption rather than build a lock). Nothing in this suite takes a file lock or coordinates between processes; every tool opens, edits, and closes plain files directly, the same way a text editor does. That is a deliberate, load-bearing consequence of "no daemons, watchers, or schedulers" above - there is no background process available to arbitrate two writers, so none is assumed. The tools are built and tested for **one writer at a time**: a human at a keyboard, or one agent acting for them, never both at once against the same archive, and never two agents (or two copies of the same agent) against it concurrently. Two processes racing a write to the same file can silently overwrite one side's change - last writer wins, with nothing to detect or report it - which is unlikely with one person at one keyboard and much more likely the moment the archive sits in a continuously-syncing folder (Dropbox, iCloud Drive, OneDrive) or an agent is set loose on it while its owner keeps editing by hand. See `docs/FAQ.md` and `docs/TROUBLESHOOTING.md` for the plain-language version of this same rule.

## 1. Shared foundations

All tools are subcommands of one CLI, **`fha`** (family-history archive), implemented as one Python file per tool under `tools/`, each also runnable standalone (`python tools/lint.py`).
A tool must never import another tool; shared code lives in `tools/_lib.py`.

**Environment.** Python ≥ 3.10.
Permitted dependencies: `PyYAML`, `Jinja2` (site generator only).
External binary: `exiftool` (embedded-metadata read/write).
Everything else stdlib.
No network access except the geocoder's optional gazetteer download.

**Archive root discovery.** An archive root is identified by the presence of `fha.yaml`; discovery walks upward from CWD to find it, and `--root PATH` overrides. (`sources/` and the other record directories are expected but not required for root detection - a brand-new archive may have `fha.yaml` before its record directories exist.)
The spec docs (`SPEC.md`/`TOOLING.md`) normally live at the archive root but may instead be installed with the tools; `--spec-root PATH` points at them when separated. `fha install` always writes them **at the archive root** - only the machinery (`.fha/tools/`, `.fha/design/`, `.fha/browser-companion/`) is vendored under the hidden `.fha/` folder, so `--spec-root` is not needed for an installed archive. Root detection is unaffected either way: it walks up to the `fha.yaml` that every layout keeps at the archive root.
In the public spec repo, the fixture is run explicitly: `fha lint --root example-archive --spec-root .` - the repo root is not itself an archive.
All stored paths are alias-form with forward slashes (normalize on Windows).

**`--root` per subcommand.** Because Python's `argparse` does not propagate parent-parser flags into subparsers, **every subcommand defines its own `--root` flag**. Both `fha --root X lint` and `fha lint --root X` work; the subcommand's own flag wins. Implementations in other languages must respect the same dual-position convention.
`--spec-root` is narrower: only `fha lint` reads it, so only `lint` defines a subcommand-level copy (`fha lint --spec-root X`); every other subcommand relies on the global `fha --spec-root X <command>` position, which the dispatcher threads through (and strips before forwarding to any subcommand, like `doctor`, that builds its own standalone parser unaware of the flag).

**Path resolution (`resolve_path`).** Record paths begin with a root alias (`photos/…`, `documents/…`). `_lib.py` loads `fha.yaml` once per run; `resolve_path(p)` maps the first segment through `roots:` (absolute values used as-is; relative values join the archive root; a missing `fha.yaml` or alias defaults to the internal directory of the same name).
Every tool that touches asset files - lint E011/E012, photoindex, packet, process, site - resolves through this function and never assumes assets are under the archive root.

**Caches.** All generated non-`.md` artifacts live in `archive/.cache/` (index, photo catalog, logs) - gitignored, deletable at any time.
Generated `.md` views are written *into the tree* where humans browse, and always begin:

```
<!-- GENERATED by fha <tool> on <date> - do not edit; regenerate instead -->
```

The linter treats hand-edits below that header as a warning. (Single-file `.html` views under `generated/views/` carry the same marker as their **first line, before the doctype** - §7 D11; ownership is one rule across both formats.)

**Three deliberately different generated-content conventions (2026-08, #75/#76)** now coexist, and no one of them replaces another:

1. **The whole-file GENERATED header**, above - marks an entire file as machine-owned and disposable. `fha views clean` reads it, file by file, as its sole deletion signal.
2. **A GENERATED-BEGIN/END region** (SPEC §21b) - marks ONE named section of an otherwise human-owned file as machine-owned, rewritten in place, everything else left untouched. `_lib.generated_region_markers`/`render_generated_region`/`write_generated_region` are the shared mechanic; a person profile's own `## Sources` section (§7, §16) is the first and so far only user. Paired markers bound the span: `<!-- GENERATED-BEGIN {region} by {cmd} on {date} -->` … `<!-- GENERATED-END {region} -->`. Never stripped by `views clean` (there is no whole file to delete) - rewritten by the same view command that owns it instead.
3. **The purpose block** (SPEC §16a) - a short, human-readable **markdown blockquote**, not an HTML comment, opening the body of every document a tool writes or scaffolds. It answers a different question than either GENERATED convention: not "is this whole file, or this part of it, machine-owned," but "what is this file, who writes it, and where do I work instead if that isn't me" - visibly, in Obsidian preview and on GitHub, where an HTML comment is invisible. `_lib.PERSON_PURPOSE_BLOCK` / `SOURCE_PURPOSE_BLOCK` / `RESEARCH_PURPOSE_BLOCK` / `VIEW_PURPOSE_BLOCKS` hold the wording. Stripped before publication (`fha packet`'s `_strip_scaffolding_blocks`; `fha site` never reaches it structurally - see SPEC §21b), since it is an instruction for whoever edits the ARCHIVE, not content for a reader of the output.

**Parsing layer (`_lib.py`).** The four parsing primitives every tool uses:

```python
ID_RE      = re.compile(r'\b([PSCLH])-([0-9a-hjkmnp-tv-z]{10})\b', re.I)   # Crockford Base32, case-insensitive match
# Prose citation/cross-link tokens: [[ID]] / [[ID|display]] / [[ID#frag]] - one capture group, the
# load-bearing ID. Deliberately a superset: the optional second bracket each side also matches the
# tolerated single-bracket [ID] form, so every consumer resolves both through one chokepoint.
TOKEN_RE   = re.compile(r'\[\[?([PSCLH]-[0-9a-hjkmnp-tv-z]{10})(?:#[^|\]]*)?(?:\|[^\]]*)?\]\]?', re.I)
LEGACY_TOKEN_RE = re.compile(r'(?<!\[)\[([PSCLH]-[0-9a-hjkmnp-tv-z]{10})\](?!\])', re.I)  # single-bracket only
WIKILINK_RE = re.compile(r'\[\[([^\[\]|#]+?)(?:#[^|\]]*)?(?:\|[^\]]*)?\]\]', re.I)         # [[name/stem]] (id OR name)
FRONT_RE   = re.compile(r'\A---\r?\n(.*?)\r?\n---\r?\n', re.S)  # YAML frontmatter
CLAIMS_RE  = re.compile(r'^## Claims.*?```yaml\r?\n(.*?)```', re.S | re.M)
```

Tokens resolve through the alias map (`build_alias_map` / `resolve_ref`): a `[[S-…]]` clicks through because the source record carries the ID in `aliases:`, and a non-ID `[[stem]]` / `[[Ken Smith]]` resolves only if some record claims it as an alias - otherwise it is an inert note-link, not a citation. `TOKEN_RE` is the ID-only chokepoint (its `findall`/`group(1)` is the bare ID); `WIKILINK_RE` is the looser name/stem matcher the citation indexer and `fha normalize-links` use to resolve name-links; `LEGACY_TOKEN_RE` finds single-bracket tokens worth upgrading. `ID_RE`, `FRONT_RE`, `CLAIMS_RE` are unchanged.

`read_record(path)` → `{meta: dict, claims: list, stories: str|None, body: str}`.
The parser **normalizes YAML scalars**: booleans (`living: false`) and dates (`created: 2026-06-12`, read as date objects) are coerced to the canonical strings the index expects (`living TEXT` holds `'true'|'false'|'unknown'`; dates serialize back to ISO).
Person **companion files** (`_research`/`_timeline`, same `P-id` - plus a pre-#76 archive's leftover `_sources-index` companion, still recognized for backward compatibility even though current tooling no longer writes that kind, §7) are linked via `person_files`, not treated as duplicate person rows - the profile populates `persons.path`. The kind is read with the shared filename grammar (`_lib.parse_filename`), which per SPEC §13 takes the kind word only where it sits immediately before the `_{P-id}`: anywhere else in the name it is part of the given names, and a profile is a profile.
Claims blocks parse with `yaml.safe_load`; a parse failure is a lint error, never a crash - tools collect errors and continue.
All file IO is UTF-8.

**Writing a record (`_lib.py`).** Every archive record is written by `write_text_exact_atomic`: the full text to a sibling temp file, `fsync`, then `os.replace` over the target. A write that dies partway (disk full, the process killed) therefore leaves the record holding its old bytes rather than a truncated fragment - which is what makes a verb's "nothing was changed" refusal true. Line endings are byte-faithful in both directions (`read_text_exact` / `newline=''`), so a round-trip churns only the lines the edit touched. Because `os.replace` swaps a *directory entry*, the kernel judges it by the parent folder and the new file arrives wearing the temp file's identity - so the writer restores by hand what an in-place write got for free: an existing record keeps its mode (setgid included), its group and its owner, a new record takes the plain-open umask default, and a record the caller may **not** write is refused with the same `PermissionError` the in-place writer raised, before any temp file is created. Making a record read-only is how a human pins a file he does not want touched; an atomic write must not quietly unpin it. What the swap cannot preserve, and does not pretend to: a symlinked or hard-linked target is replaced rather than written through (the archive has no symlinks by rule - AGENTS.md Don'ts), extended attributes and ACLs do not travel with the mode, and a read-only *parent folder* refuses here where a plain write would have succeeded, since the temp file must be a sibling for the rename to be atomic.

**EDTF handling.** Tools never need full EDTF; they need *validation* and *sortable bounds*. `edtf_bounds(s) -> (min_iso, max_iso)`:

| EDTF | min | max |
|---|---|---|
| `1850` | 1850-01-01 | 1850-12-31 |
| `1850~` / `1850?` | 1849-01-01 | 1851-12-31 (widened ±1y) |
| `185X` | 1850-01-01 | 1859-12-31 |
| `1850-05` | 1850-05-01 | 1850-05-31 |
| `1850-~05` or `1850-05~` | 1850-04-01 | 1850-06-30 (widened ±1m) |
| `[..1920]` | 0001-01-01 | 1920-12-31 |
| `A/B` (interval) | min(A) | max(B) |

**Month-approximate tilde position:** EDTF Level 1 permits the uncertainty qualifier either *before* the month component (`1850-~05`, tilde precedes the month) or *after* the full date component (`1850-05~`, tilde trails the month). Both are valid and treated identically by this system. Real-world data uses both; the validation regex and bounds computation must accept either position.

Validation regex (accepting the subset above) is the linter's date check; anything else is `E014`.

**Exit codes (all tools).** `0` clean · `1` warnings only · `2` errors found · `3` tool failure. `--json` emits machine-readable findings; default output is human lines: `SEVERITY CODE path: message`.

**Structured-result contract (the headless core).** Every command is split into an *engine* and an *interface*, and the seam between them is a single value type, `_lib.Result`:

- **`run_*` computes and returns a `Result`** - a small, JSON-serializable record of what happened. It does not print human-facing report text and does not call `sys.exit`. (File side effects and interactive prompts are out of scope for this rule: a tool that must write `report_2026.md` or ask the human a yes/no question still does so inside `run_*`. The rule governs return values and human-text *printing*, not side effects.)
- **`_cmd_*` is the only layer that renders a `Result`** to stdout/stderr and returns the process exit code.

A `Result` carries: `ok` (did it succeed - no error-level messages); `exit_code` (the `EXIT_*` constant the CLI returns); `data` (the structured payload a consumer wants - matched records, per-check rows, counts, a rendered string); `messages` (human-facing lines, each a `Message{level, text, next_step, code, path}` - a lint `Finding` folds into one: severity → level, E/W code → code, file → path); and `changed` (paths this operation created, wrote, renamed, or embedded into - empty under `--dry-run`). `lint` is the reference implementation: `run_lint` returns a `Result`; `_cmd_lint` renders both the human text and the `--json` payload from it (§3).

This split is what makes the suite a **headless core**: the `fha` tools are an engine any front door drives. A terminal user, an agent shelling out, the in-process report orchestrator (§15a), and a future click-through UI all call the same `run_*` and read the same structured `Result`; the human-text rendering in `_cmd_*` is just one consumer of it. It is also what keeps **the human the only gate to `accepted`** honest across front doors: the deterministic write-backs (§14a/§14a2/§15a, claim review §3b) return a `Result` describing the one edit they made, but they only run because a human directed them - whatever issues the confirmation (a chat instruction today, a click later) is the gate, not the tool.

**The `restricted` contract (all export paths).** `restricted` may appear on a source, claim, person, or name. Public output excludes all of it. Private export (`fha packet`) excludes it by default; `--include-restricted` opens plain restrictions, `--include-dna` is still required for `restricted: dna`, and `restricted: by-request` is honored by every path with no override. A restricted name resolves internally and redacts on export.

## 2. `fha index` - the index builder

**Purpose.** Rebuild `\.cache/index.sqlite` from scratch by walking the tree.
The query surface for every other tool and for ad-hoc research (`sqlite3` or any viewer).
Never appended; never authoritative.

**Incremental mode.** `fha index --source S-xxxx` upserts one source: delete its rows, re-parse the one file, re-insert - sub-second, run automatically at the end of review sessions.
Deletion order matters (child tables before parent rows): collect claim IDs first, then delete `claim_persons` and `claim_links` by those IDs, then delete `claims`; capture `sources.path` before deletion, then delete `citations` by that path, then delete `notes_fts` rows by that path (the FTS virtual table is not covered by FK cascade and accumulates duplicate bodies on upsert), then delete `sources`/`source_files`/`source_people`. Reversing parent/child order leaves orphan rows because the parent subquery finds nothing.
Full rebuild remains the periodic truth-check; any discrepancy between incremental and full states is a bug in incremental, by definition.

**Build algorithm.** (1) glob `sources/**/*.md`, `people/**/*.md`, `places/places.yaml`, `notes/**/*.md`; (2) parse each with the parsing layer; (3) insert in one transaction, building an **alias map** from every record's `aliases:` plus persons'/places' `name` & variants (the `aliases` table); (4) scan all prose bodies for `TOKEN_RE` → citations table, recording each citation's **resolved canonical ID** so a `[[stem]]`- or `[[Name]]`-cited reference is stored ID-uniform; (4a) strip the `[[ ]]` wrapper from frontmatter link-fields (`people:` / `places:` / note `persons:`/`sources:`) and resolve each to an ID the same way (`source_people` / `source_places`); on-demand C-id aliases are derived here - a source aliases a `C-…` only when a `[[C-…]]` citation to it exists; (5) glob asset trees for filenames carrying S-ids → files table reconciliation; (6) build FTS tables.
Target: full rebuild of a mature archive (~5k sources, ~30k claims) in under a minute; correctness over speed.

**Records it could not read.** The parsing layer never raises on a malformed record: `read_record` returns whatever parsed and lists the rest in `parse_errors`. That is right for a walker - one bad file must not take a whole build down - but it means a `## Claims` block whose YAML does not parse indexes as an EMPTY claims list, so the block was simply dropped and the build reported success (#62). The measured cost of one such block in the field was 16% of an archive's spouse edges (166 → 140), with `fha index` printing nothing and exiting 0 throughout, while `fha find`, `fha report` and a generated site all answered confidently from the shortened graph. The claims stay dropped - YAML that will not parse cannot be indexed, and guessing at it would be worse than losing it - but the build now says so. Both record walks (`people/**`, `sources/**`) share one parse-error recorder beside the unreadable-folder one, and each failure becomes one warning naming: the record (archive-relative, never a local absolute path - this text can ride a Result into a committed `fha report`), what the loss actually costs (its claims, when the frontmatter parsed and the source is otherwise indexed; the whole record, when it did not), the parser's own line and column with a valid example, and the way back. `data['unreadable_records']` lists the files. The finding carries `fha lint`'s code (**E010**) rather than a new one of its own: it is the same broken file, and the two must never name it two different ways. `fha index --source` reports identically - an upsert DELETEs the source's claim rows before re-reading the file, so the incremental path can lose a block exactly as silently as the full rebuild did.

**Files it could not decode.** A third failure at the same seam, and the sharpest: three reads here - each `notes/**.md`, `notes/research-log.md`, and `.cache/capture_log.jsonl` - guarded only `except OSError`. `UnicodeDecodeError` is a **ValueError**, not an OSError, so a file saved in the machine's own codepage rather than UTF-8 went straight past the guard and out of `build_index` as an unhandled traceback: not one record lost in silence but **nothing indexed at all**. cp1252 is what a Windows editor writes by default, and the names a genealogy archive is full of (Kraków, Müller, née) are exactly the bytes that differ, so it is reached by writing one note. The `dump_text` read in this module already caught it by name - the three siblings simply never got the same treatment. Each now reports through its own list rather than the parse-error recorder, because that recorder's message promises "`fha lint` reports the same problem" and for these it does not: lint reads the same files behind the same `except OSError` and dies on them too (see the repo-wide sweep in the issue). One warning names the files (archive-relative), says their words are absent from `fha find --text` and that a research or capture log loses the searches recorded in it, and states plainly that the file is fine and untouched - the fix is to re-save it as UTF-8. The file is never rewritten: it is the human's, and it is not damaged, only encoded differently.

**Exit codes.** `0` clean · `1` warnings only (§1): a folder that would not open, a record whose YAML would not parse, a hand-edited `places.yaml` coords line, a `roots:` change that orphaned filed assets · `3` root unresolvable (`--root` without `fha.yaml`), malformed `fha.yaml`, or a `--source` that is not a valid S-id / not found / has no full index to update. There is deliberately **no exit-2 arm**: the index is a rebuildable cache, an incomplete build is still a usable one, and every repair is in the human's own records - so the run reports what is missing and carries on, rather than halting a workflow one step before `fha lint`, which is the command that names the spot.

**Schema (DDL).**

```sql
CREATE TABLE persons(
  id TEXT PRIMARY KEY, name TEXT NOT NULL, surname TEXT, sex TEXT,
  living TEXT NOT NULL,            -- 'true' | 'false' | 'unknown' (unknown = living for exports)
  tier TEXT NOT NULL, status TEXT DEFAULT 'active', merged_into TEXT,
  no_known_marriages INTEGER DEFAULT 0, no_known_children INTEGER DEFAULT 0,
  birth TEXT, death TEXT,         -- optional provisional, unsourced vital estimates (§9; non-load-bearing)
  path TEXT NOT NULL);
CREATE TABLE person_variants(person_id TEXT, variant TEXT);
CREATE TABLE person_face_tags(person_id TEXT, tag TEXT);
CREATE TABLE person_files(person_id TEXT, kind TEXT, path TEXT, generated INTEGER DEFAULT 0,
  PRIMARY KEY(person_id, kind));   -- profile | research | timeline | sources-index | draft-queue; profile populates persons.path
CREATE TABLE person_external(person_id TEXT, system TEXT, ext_id TEXT);

CREATE TABLE sources(
  id TEXT PRIMARY KEY, title TEXT NOT NULL, source_type TEXT,
  date_edtf TEXT, date_min TEXT, date_max TEXT,
  repository TEXT, restricted INTEGER DEFAULT 0,
  source_class TEXT, publication_ok INTEGER,   -- flattened from rights.publication_ok
  status TEXT DEFAULT 'active',
  superseded_by TEXT, path TEXT NOT NULL);
CREATE TABLE source_files(
  source_id TEXT, path TEXT, role TEXT, copy TEXT,
  derived INTEGER DEFAULT 0, original_filename TEXT,
  date_edtf TEXT,                                  -- optional per-file date (SPEC §14, #123)
  exists_on_disk INTEGER, in_inventory INTEGER);   -- reconciliation flags

CREATE TABLE claims(
  id TEXT PRIMARY KEY, source_id TEXT NOT NULL, type TEXT NOT NULL,
  subtype TEXT, date_edtf TEXT, date_min TEXT, date_max TEXT,
  place_id TEXT, place_text TEXT, value TEXT NOT NULL, status TEXT NOT NULL,
  reviewed TEXT, confidence TEXT, information TEXT, evidence TEXT,
  asset TEXT, anchor TEXT, hypothesis TEXT,
  significance_override TEXT, significance_reason TEXT,
  negated INTEGER DEFAULT 0, notes TEXT);
CREATE TABLE claim_persons(claim_id TEXT, person_id TEXT, position INTEGER, role TEXT);
CREATE TABLE claim_links(claim_id TEXT, rel TEXT, target_id TEXT); -- corroborates|contradicts
CREATE TABLE source_people(source_id TEXT, person_id TEXT);  -- people: any source (speakers, photo subjects, household)
CREATE TABLE source_places(source_id TEXT, place_id TEXT);   -- places: any source (resolved from frontmatter [[L-…]] links)

-- Derived, rebuildable edge list for graph traversal (NOT new truth - flattened from
-- accepted relationship/birth/marriage/divorce/death claims; every edge keeps its claim_id).
CREATE TABLE relationships(
  person_id TEXT, rel TEXT,            -- parent | child | spouse | friend | associate | neighbor
  other_id TEXT, claim_id TEXT,        -- provenance: the claim this edge came from
  date_start TEXT, date_end TEXT);     -- spouse edges: marriage date / divorce|death date

CREATE TABLE places(id TEXT PRIMARY KEY, name TEXT, hierarchy TEXT,
  within TEXT, lat REAL, lon REAL,    -- within: recursed for containment queries
  notes TEXT);                        -- notes: SPEC §15 reference prose, rendered on place pages
CREATE TABLE place_names(place_id TEXT, alt_name TEXT);
CREATE TABLE place_history(place_id TEXT, period_edtf TEXT, date_min TEXT, date_max TEXT, hierarchy TEXT);

CREATE TABLE search_log(date TEXT, person_id TEXT, question TEXT,
  repository TEXT, collection TEXT, terms TEXT, result TEXT, source_id TEXT, path TEXT);

CREATE TABLE hypotheses(id TEXT PRIMARY KEY, person_id TEXT, hypothesis TEXT,
  basis TEXT, verify TEXT, origin TEXT, status TEXT, verified_claim TEXT, path TEXT);

CREATE TABLE citations(token TEXT, kind TEXT, path TEXT, line INTEGER);  -- token = resolved canonical ID

-- aliases: the resolution surface every front door (find, lint, normalize) shares. One row per
-- string that resolves to a record: its canonical ID, any human stem, an on-demand C-id (added only
-- when a [[C-…]] citation exists), and a person's/place's display name + variants. Lowercased.
CREATE TABLE aliases(alias TEXT, canonical_id TEXT, kind TEXT);  -- kind: id | stem | name | variant | claim

CREATE VIRTUAL TABLE notes_fts USING fts5(path, content);
-- transcripts_fts holds the archive's copy of what a source SAYS. `fha index`
-- fills it from every files: entry whose role is `transcript`, `transcription`
-- or `extracted-text` and whose file is a .md/.txt on disk: `fha source
-- extract`'s PDF text dumps, the transcribe-audio skill's whisper passes, and
-- any transcript a human typed out from a scan, all on equal terms (#46). A
-- role tag on a non-text file is ignored rather than read as UTF-8.
CREATE VIRTUAL TABLE transcripts_fts USING fts5(source_id, path, content);
```

**Relationship derivation** (during index build, after claims load): for each `accepted` claim - `relationship subtype: child-of` → a `child` edge (subject→parents) and reciprocal `parent` edges; `type: birth` with a `roles:` map naming a child and a parent → the same reciprocal parent/child edge pair; `subtype: spouse-of` and `type: marriage` → reciprocal `spouse` edges dated from the claim, `date_end` backfilled from any `divorce` claim between the pair or a `death` claim on either; social subtypes → `friend`/`associate`/`neighbor` edges. **Marriage and divorce edges are scoped by `roles:`, never by the whole `persons:` list.** A marriage certificate ordinarily names the couple *and* both sets of parents, and listing all six is the correct way to write the claim (§8.3) - so the couple is whoever `roles: spouse:` names when it names **two or more**; otherwise, when exactly two persons are named *and no named person carries an explicit role other than spouse*, those two (the ordinary hand-written claim); otherwise **no edge at all**. People are counted once each: `persons: [P-a, "[[Alice Smith]]"]` is one man written two ways and `claim_persons` stores a row per entry, so counting entries read the duplicate as a couple and married him to himself. A `roles:` map that resolves to fewer than two spouses - one typo'd id, one spouse left out of `persons:`, an alias that stopped resolving - has not answered the question, so it falls through to the same two-person rule as no map at all rather than silently costing an ordinary marriage its edge. What the role test excludes is the opposite state - the claim that answered the question and said no: `roles: {spouse: [P-a], parent: [P-b]}` calls P-b a parent, so pairing the two off contradicts the claim in its own words and marries a man to his father-in-law. A silence is inferred only from a silence. A map naming three or more is the serial case (successive marriages on one claim) and keeps every pairing. The tool does not guess which pair married: a false spouse edge is read back as fact by `fha relate`, the tree views, and the report's confirmed-connections list, while a missing one is merely missing. One rule, one home - `_lib.spouse_parties` - read by `fha index` (spouse edges and the `date_end` a divorce writes) and by `fha gedcom` (which FAM a marriage event belongs to), so the archive and its export can never answer this question differently; `fha lint` reads it too (W115, W125). `fha lint` W125 surfaces every claim this rule leaves without a couple - whenever a couple claim resolves two or more distinct persons and the rule returns nothing, whatever shape produced it - so no refusal here is ever the end of the story. The same scoping governs `divorce`, where an unscoped pair loop does not invent marriages but *ends* real ones - a decree naming both sets of parents pairs each set with itself, and those two are genuinely married.

**Parentage on a `birth` claim is scoped by `roles:` too, and by `roles:` alone.** A birth record is where an archive states parentage most plainly - "born to X and Y" - and `type: birth` is read here for the same reason `type: death` is: a vital record is evidence about the family graph, not only about one person. A `birth` claim whose `roles:` map names a `child` and a `parent` mints the identical reciprocal edge pair an equivalent `relationship` claim mints, through the same writer, so one fact written two ways cannot reach the tree as two different shapes. What it does **not** have is the marriage rule's two-person fallback, and the difference is not fussiness: marriage is symmetric, so exactly two people admit exactly one answer, while parentage is **directed** - `persons: [P-a, P-b]` never says which of them was born, and getting it backwards makes a newborn her own mother's parent. `persons: [child, father, mother]` is a habit, not a contract (§8.3: positional convention alone is too fragile), and the extra person on a birth register is as often an informant, a midwife or the attending physician as a parent. So an unroled birth claim derives **nothing**, at any person count, and `fha lint` **W126** reports every one that names two or more distinct people and yields no parent edge - the same bargain W125 strikes for couple claims, and the reason the indexer is allowed to stay quiet. One rule, one home - `_lib.parentage_parties` - read by `fha index` (both the `birth` and the `relationship` branch) and by `fha lint` (W126). `baptism` and `burial` name parents the same way and are the obvious next candidates, but they are deliberately **not** in the filter yet: each type added needs its own W126 coverage, and a derivation list that grows by guess is how the silence this fixed got its shape (#71).
Edges are pure cache: dropping and rebuilding `relationships` from claims is a no-op on truth.
Bilinear by nature - traversal follows edges wherever they lead, including in-law branches.

**Derived significance** is computed at query time from the SPEC §8.2 table (shipped in `_lib.py` as `SIGNIFICANCE: dict`), honoring overrides.

**Canonical queries** (shipped as views): person timeline; vitals completeness per person; suggested backlog per source; contradiction pairs lacking questions.

**Summary-block parsing detail (E013).** The block is the run of `**Label:** …` entries after the H1, before the first `## Section` header. Labels are: `Born`, `Died`, `Married`, `Parents`, `Children`.
The parser must handle **both** layout styles:
- *Multi-line:* one `**Label:**` per line - the common case in hand-authored profiles.
- *Inline (single-line):* multiple `**Label:**` markers on one line (e.g. `**Born:** … **Married:** … **Parents:** …` all run together) - occurs in practice when the block was written without explicit line breaks.

Implementation: scan the summary text (up to the first `## Section`) with `finditer` on the `**Label:**` pattern; split into segments between consecutive label positions; extract `[[S-id]]` and `[[P-id]]` link ids from each segment (the `|display` and `#fragment` are ignored - the ID is the load-bearing capture). Do **not** split by line - line splitting fails on the inline form.

Comparison rule: each `[[S-id]]` in a segment must correspond to an `accepted` claim of the matching type (`birth`/`death`/`marriage`) for this person from that source; `[[P-id]]`s in Parents/Children must match accepted `relationship` claims. Display text is not parsed for equality - the citation (ID) is the contract.

## 3b. `fha claim` - claim-review write-back and minting

The deterministic write-back pair a human reaches for during review: moving an existing claim's `status:` and stamping `reviewed:`, or minting a brand-new claim onto a source.

```
fha claim <C-id> [<C-id> …]
                 [--status accepted|disputed|rejected|needs-review|superseded]
                 [--value "…"] [--date EDTF] [--type TYPE] [--place L-id] [--place-text TEXT]
                 [--persons P-id[,P-id…]] [--confidence high|medium|low]
                 [--information primary|secondary|undetermined]
                 [--evidence direct|indirect|negative] [--anchor TEXT] [--notes TEXT]
                 [--reviewed DATE] [--root PATH] [--dry-run]

fha claim new --source S-id --type TYPE --value "…" [--date DATE]
              [--place L-id] [--place-text TEXT] [--persons P-id[,P-id…]] [--subtype WORD]
              [--status suggested|accepted] [--negated] [--confidence high|medium|low]
              [--information primary|secondary|undetermined]
              [--evidence direct|indirect|negative] [--anchor TEXT] [--notes TEXT]
              [--root PATH] [--dry-run]
```

**Contract (SPEC §8.2, §8.4, §8.5).** Only the *human* moves a claim to `accepted`, and an accepted claim must carry a `reviewed:` date (lint E006). The human satisfies that contract by *directing* this tool - the editing method does not matter, only that the decision is theirs - so `--status accepted` always writes a `reviewed:` stamp (the explicit `--reviewed DATE` when given, otherwise today, since a human is at the keyboard). The tool never accepts on its own. `disputed`/`rejected`/`superseded` change status rather than delete, preserving the research trail - `disputed` marks a claim actively contested (e.g. a `contradicts:` standoff) rather than settled, distinct from a `rejected` claim the reviewer has ruled out. `--status` on the review verb is **optional** (plan 17): at least one of `--status`/`--value`/`--date`/`--type`/`--place`/`--place-text`/`--persons`/`--confidence`/`--information`/`--evidence`/`--anchor`/`--notes` is required, so a field-only correction needs no status move. `--value`/`--date`/`--type`/`--place`/`--place-text`/`--persons`/`--confidence`/`--information`/`--evidence`/`--anchor`/`--notes` let a reviewer correct the claim in the same surgical edit; `--type`/`--persons`/`--place`/`--confidence`/`--information`/`--evidence` reuse the same validation `claim new` uses (below). `--place` and `--place-text` are independent keys, not two spellings of one (SPEC §15: `place:` is the normalized registry link, `place_text:` the place as the source wrote it; the elevation flow backfills the former while "place_text itself is never altered") - explicitly passing both together writes both keys, and an explicit `--place` is never overridden. But `--place-text` given ALONE (no `--place`, and - on the review verb - the claim not already carrying one) is not purely a `place_text:` write: SPEC §15's write-time resolution (#79 point 3, PR #150) looks the text up against `places/places.yaml` before writing, and an exact match after normalization auto-attaches `place:` too, in the SAME write - reported in the messages as "attached place: automatically" on a live run, or "would attach place: automatically" under `--dry-run` (the two phrasings never contradict the dry-run trailer's "nothing written"). A near match (word order, an abbreviation) is noted but never auto-attached - a wrong `place_id` is worse than an unlinked `place_text`, which `fha places candidates` will still surface on its own. A registry that is missing is a quiet no-op (nothing to check against yet); a registry that EXISTS but fails to parse warns with a `fha lint` pointer rather than silently proceeding as an ordinary miss. Changing a claim's type TO `relationship` is refused on both verbs - see the scope note below.

**Mills fields, `--anchor`, and `--notes` (issue #50, 2026-08).** SPEC §8.5's `information`/`evidence` and §8.4's `anchor`/`notes` were settable only by hand-editing the claim's YAML, even though AI-assisted drafting is directed to populate the Mills fields by default and the linter's own W106/W109 ping an accepted claim still missing them. `--information {primary,secondary,undetermined}` and `--evidence {direct,indirect,negative}` are validated against SPEC §8.5's closed vocabularies (the same `_validate_field_args` helper both verbs already share for `--confidence`); `--anchor TEXT` and `--notes TEXT` are free text, quoted the same way `--value`/`--place-text` are. All four follow the REPLACE contract every other field flag on this verb already has - no append mode. `--notes` deliberately does **not** share `--value`'s block-scalar refusal: SPEC §8.4's own illustrative claim uses `notes: >`, and correcting an already-reviewed claim's notes is exactly this issue's use case - the existing `set_scalar`/`_value_span_end` span-replace machinery (built for `persons:`'s block-list form) already replaces a key's FULL span safely, block-scalar continuation included, so no new corruption guard was needed. On `claim new`, `--evidence` that contradicts `--negated` (anything but `negative`) is refused before any write - SPEC §8.6's pairing is mandatory, not a default a conflicting override silently wins over. **Deliberately out of scope:** amending `roles:` on an existing claim - the issue only sketched `--role parent=P-a,P-b --role child=P-c` as a tentative idea, and it needs real design (arity varies by role family; the interaction with `--persons` is unsettled) rather than a flag, so it stays a hand-edit of the claim block. One direction of that interaction IS settled (#126/#173 follow-up): `--persons` REPLACES the whole list (above), and a replacement that would drop someone an EXISTING `roles:` map still names is refused rather than written - the same hand-edit mistake W133 catches (`persons: [P-widow]`, `roles: {deceased: [P-dead]}` with `P-dead` dropped from the new list), reached here through the sanctioned edit verb instead of a typo. Checked against bare P-id role values only, matching a `roles:` value written as a name-link (`"[[Grandpa Smith]]"`) to the same "different, pre-existing problem" boundary W133 itself draws - `fha lint` is the backstop for that narrower shape.

**Echo on success (issue #54, 2026-08).** A successful field write used to say only "value updated"/"place_text updated" - identical whether the value written was the one intended or a corrupted one. The reported repro: on Windows PowerShell 5.1, a single-quoted argument silently loses its embedded double quotes before this tool ever sees it (`Robert Justin "Bob" Knipscheer` arrives as `Robert Justin Bob Knipscheer`); `--dry-run` showed the damage in its diff, a live run did not show it at all. Every free-text field this verb (and `claim new`) can write - `--value`, `--place-text`, `--anchor`, `--notes` - now echoes the value it actually wrote as an extra line on a live write; `--date`/`--type`/`--place`/`--persons`/`--confidence`/`--information`/`--evidence` already echoed their new value inline in the summary line and needed no change. Cheap insurance against any wrapper (a different shell, a CI runner, an MCP bridge) that mangles an argument before this tool sees it.

**Batch status moves (2026-07).** The review verb takes several C-ids at once - `fha claim C-a C-b C-c --status accepted` - because the review gesture ("accept 1, 2 and 4") is one human decision per claim delivered in one breath, and any of the five review statuses batches the same way (batch-reject and batch-needs-review are as legitimate as batch-accept). A batch is **status-only**: more than one distinct C-id combined with any field-edit flag (`--value`/`--date`/`--type`/`--place`/`--place-text`/`--persons`/`--confidence`/`--information`/`--evidence`/`--anchor`/`--notes`) is a plain refusal - a field correction states a new fact about one particular claim, so it is inherently per-claim and keeps the surgical single-id form. Validation is **all-or-nothing**: every id is checked (shape and existence) before any write, so one unknown or malformed C-id refuses the whole batch with nothing written, naming the bad id and the fix. Duplicate ids in one invocation are deduped preserving order (applied once, said in the output). One `--dry-run` previews every edit in the batch; the live run applies each claim through the same surgical single-claim write in a loop (`run_claim_batch` delegating to `run_claim` - one write path, never a second), folds the per-claim `fha index` reminders into one closing line, and on a mid-batch failure stops immediately, naming what was applied, what was not, and the exact command that finishes the rest.

The review edit is **surgical**: only the one named claim's entry inside its source `.md` `## Claims` block is touched - sibling claims, key order, and hand comments survive - mirroring `places geocode`'s `places.yaml` edit and `process --more`'s frontmatter edit. The claim is located by scanning the `sources/` records directly (the `.md` files are the truth), so the command works even when `\.cache/index.sqlite` is stale or absent; re-run `fha index` after a write to fold the new status into the query surface. A claim whose `value:` is a YAML block scalar is *refused*, not silently corrupted - and after every surgical rewrite the tool **re-parses the claims block before writing**, refusing (file untouched, cause and file named) if the block no longer parses or the requested change did not actually land, so an item whose indentation the editor mis-judges becomes a refusal, never a corruption. The same pre-write guard sits under `fha confirm`'s claim edits. `run_claim` returns a `Result` whose `changed[]` names the one source file written (empty under `--dry-run`); `_cmd_claim` renders it.

This is the human gate from the engine side: the `review-claims` skill (§16) and `fha report`'s answerable-questions/connections prompts all drive `fha claim`, but the accept decision is always the human's. The detection-candidate write-backs (§14a/§14a2/§15a) live in their own sibling tool, `fha confirm`.

**`fha claim new` (plan 17).** Mints a brand-new claim directly onto an existing source's `## Claims` block - the parity command behind a source-page "add a claim" workbench button, and the by-hand alternative to `process-source`'s AI draft pass when a human already knows the fact. Not reachable through the review verb's positional-C-id subparser (`new` would misparse as a claim id); `fha.py` intercepts `fha claim new …` before the flat parser sees it, the same early-interception pattern `fha gedcom import` uses. Defaults to `--status accepted` - typing this command IS the review, so `reviewed:` is stamped automatically; an AI caller is bound by the AGENTS.md contract to pass `--status suggested` explicitly. `--confidence`, required on every claim (SPEC §8.5) but optional on the command line, defaults from the source's `source_type` (`vital-record` → high, `interview` → low, else medium) with a message naming the choice. `--information`/`--evidence`/`--anchor`/`--notes` (issue #50) mint the Mills fields and context note in the same step - before this build the verb wrote `id/type/persons/date/place_text/status/confidence/reviewed` and nothing else, so every claim minted this way landed missing `notes:` and immediately tripped W109. `--persons` is optional - a claim may legitimately be minted before its persons are linked - with a warning naming the follow-up. `--place-text` given alone (no `--place`) gets the same write-time registry resolution the review verb's contract paragraph above describes (SPEC §15, #79 point 3, PR #150) - an exact match auto-attaches `place:` in the same mint, reported as attached (live) or would-attach (`--dry-run`); a near match is noted only; a malformed `places.yaml` warns with a `fha lint` pointer rather than silently minting as if nothing matched. `--negated` mints a SPEC §8.6 **confirmed absence** - "we researched and it did not happen" - as a normal claim of its type carrying `negated: true` plus its §8.6 pairing `evidence: negative` (e.g. `--type marriage --negated --value "no marriage found"` = confirmed never married; the usual home is a proof-argument source assembling the negative searches). This closes the negative-fact authoring gap the backlog carried: everything downstream already understood `negated:` (lint's vitals completeness, xref's polarity contradictions, cooccur/find exclusions) - only the minting path was missing. Every write funnels through the same claim-append helper `fha confirm cooccur` relies on, so a rewrite that would corrupt the block is refused, never saved.

**The relationship-type scope note (both verbs).** Neither verb creates or changes a claim to type `relationship` - that type needs a `roles:` map (SPEC §8.3) these flat-scalar writers do not build. For a hypothesis tie between two people, use `fha person relate` (§3c); for a sourced tie discovered from shared sources, use `fha confirm cooccur` (§14a3); otherwise add the `roles:` map by hand under `## Claims`.

## 3c. `fha person` - person-field write-backs

The deterministic write-backs for a person record's own frontmatter and prose. The group exists so that a field or a bounded prose edit every export decision or workbench button hangs on is a safe one-line command instead of a hand edit. Eleven verbs ship: `set-living`, `set-profile-photo`, `set-sex`, `new`, `rename`, `relate`, `estimate`, `edit`, `note`, `edit-note`, `promote`.

```
fha person set-living <P-id> true|false|unknown [--dry-run] [--root PATH]
fha person set-profile-photo <P-id> PHOTO [--dry-run] [--root PATH]
fha person set-sex <P-id> M|F|intersex|unknown [--dry-run] [--root PATH]
fha person new "Name" [--sex M|F|intersex|unknown] [--gender TEXT] [--birth DATE] [--death DATE] [--birth-place TEXT] [--death-place TEXT] [--surname TEXT] [--dry-run]
fha person rename <P-id> "New Name" [--keep-variant] [--surname TEXT] [--dry-run] [--root PATH]
fha person relate <P-id> (--parent|--child|--sibling|--spouse) <P-id2> [--subtype WORD] [--reciprocal] [--dry-run]
fha person estimate <P-id> [--birth DATE|-] [--death DATE|-] [--birth-place PLACE|-] [--death-place PLACE|-] [--dry-run]
fha person edit <P-id> --section biography|stories|research (--text TEXT|--file PATH) [--append] [--dry-run]
fha person note <P-id> --section stories|research --text TEXT [--dry-run]
fha person edit-note <P-id> --section stories|research --old-text TEXT --text TEXT [--dry-run]
fha person promote <P-id> [--into FOLDER] [--dry-run] [--root PATH]
```

**`promote` (stub graduation).** The SPEC §4 stub → curated graduation as one explicit command, and the one sanctioned tool move of a record out of `people/stubs/` (the §5 carve-out). Up to four writes, transactional with rollback, shared verbatim with `fha views brackets --fix-promote` through `_lib.promote_person_record`: (1) flip `tier:` to curated (the same surgical single-line edit + pre-write guard as `set-living`); (2) backfill the profile's BODY with any SPEC §16 section it is still missing (`ensure_person_body_sections` - purely additive, never touches frontmatter or anything already written), folded into the SAME write as step 1 since both are edits to the same file; a stub minted since #76 already carries every section, so this step is a no-op for it, and only a pre-#76 or hand-made stub actually gains anything here; (3) move the record into its destination folder (created if absent); (4) settle the OPTIONAL `_research` companion (SPEC §16b): if one already sits beside the record's pre-move location, MOVE it to the destination so its notes travel with the record; otherwise **do nothing** - promotion never creates one (#76 - the separate research file is an escape valve for research that has outgrown the profile's own `## Research Notes` section, not a default every promotion scaffolds; a human who wants one still copies `_TEMPLATE.research.md` by hand). TWO DESTINATIONS (#80): a DIRECT-LINE person's destination derives from `root_person` over accepted genetic relationship claims (the shared `_lib.build_ahnentafel_map`, seeded at the position `fha.yaml`'s `root_generation` names - #1 for `self`, the default, #2 for `children`, SPEC §12.2/§12.4, issue #72) into their Ahnentafel couple folder, named `{NNN} {name}` - the P-id-carrying filename makes the move safe per SPEC §12.2 - which makes this the one person verb that hard-requires a fresh index (strict; the index decides WHERE, never WHETHER - the locate still scans disk). An invalid `root_generation` refuses outright, nothing written - the one derivation-config problem this verb cannot degrade past, since guessing would risk filing someone in the wrong couple folder. A person with NO derived position is not stuck: `--into connections/` files them flat in `people/connections/` instead (SPEC §12.3) - same tier flip and body backfill, no numbering, no couple folder; called with no `--into` at all, a non-direct person is refused plainly with that exact command named (their stub is a legitimate resting state either way, so nothing is forced). The position is still derived even on the connections path - not to pick a folder there (always the same flat one), but to REFUSE a genuinely direct-line person routed into connections/ by mistake (SPEC §12.2 and §12.3 are mutually exclusive). `--into FOLDER` naming an ordinary couple folder still overrides the destination for a direct-line person only (one folder under `people/`, never `stubs/`). A record already filed anywhere but `people/stubs/` - a couple folder OR `people/connections/` - is never second-guessed by this verb: promoted in place, the same way a couple-folder mismatch is left to lint (W110) rather than silently re-routed here. An already-curated, already-filed person is a clean `already` no-op (exit 0) - that fast-path check is tier and folder only, so it does not itself go looking for a missing §16 body section on a record that is otherwise already finished; a curated record still parked in `stubs/` is FINISHED, not refused, and gets the same body backfill (step 2) as any other promotion on its way through. A STUB that already carries every §16 section (freshly minted since #76) still promotes normally - the tier flips, the file moves - but step 2 is a true no-op for it: `ensure_person_body_sections` finds nothing left to add, so `fha person promote` on an already-full-shape stub is idempotent by construction. After a live move the index is updated **in place** (`index.relocate_person`: every path-keyed row swapped to the new path, the tier flip applied, the research companion's row moved too when one travels with it) rather than dropped - a move is mtime-invisible, but rewriting the rows is exact and cheap, and it means a batch of promotes needs no rebuild between them (the old cache-drop made the second promote fail on a message that read like corruption). If the in-place update itself fails the record has still moved; the result is a non-zero warning naming `fha index`. The output names the follow-ups: timeline/draft-queue, and (a promotion is often the first time a person's own `## Sources` region gets built at all) `fha views sources-index <P-id>` - or `fha views refresh` for all three at once. Promotion is never a side effect of accepting a claim - a verb the human runs, a previewed fix he confirms, or a report §7b/skill nudge he answers. Exit codes: 0 ok/already/dry-run · 1 not found (with `fha find`) · 3 every refusal, nothing half-written.

**`set-sex` contract (2026-08-15).** Sets or corrects the record's `sex:` (SPEC §9's vocabulary M | F | intersex | unknown, case-folded on input) - the one frontmatter fact the Ahnentafel derivation reads (§7: `F` takes the mother/odd slot, anything else the father/even one; a lone parent with no usable value is placed by default, W120). Same surgical single-line edit, pre-write guard, merged-tombstone refusal, `already` idempotence and `--dry-run` diff as `set-living`; a missing key is inserted in template order (after `name`/`name_variants`/`face_tags`, before `living`). What the verb adds over a hand edit is the ending: a live change prints the reminder that folder numbering may have shifted - run `fha index`, then `fha views brackets` to check, `--realign` to apply - which is exactly the nudge a hand edit could never give (the 2026-07-26 feedback's item 3). The reindex comes first because placement is derived from the indexed `sex:` (§7's Ahnentafel map reads `persons.sex`), and this write has just staled the index: run the other way round, `brackets` reports the pre-correction numbering and `--realign` refuses outright rather than renaming folders from stale data. Workbench parity verb `person.set-sex`.

**`set-profile-photo` contract (2026-07-17).** Sets the record's `profile_photo:` field (SPEC §9 - the portrait shown on the person's page and as their tree thumbnail); the workbench's set-profile-photo picker echoes exactly this command. `PHOTO` is a filename, path, or S-id, written as given and resolved leniently at site-generation time (an unresolvable reference just means no portrait shows - never a write-time refusal, matching how the site treats a missing hero/embed reference). The same surgical single-line edit, pre-write guard, merged-tombstone refusal, `already` idempotence, and `--dry-run` diff as `set-living`; the value is quoted through the shared `yaml_inline` rule, so a `#` or `: ` in a filename can never corrupt the header.

**`set-living` contract.** `living:` drives redaction in every external export (SPEC §9, §19; `unknown` is treated as living - the safe default). The record is located by scanning `people/` for the `_{P-id}.md` filename suffix (stubs and curated profiles alike; a stale or absent index never blocks or misleads a write - the §3b rule, via the shared `_lib.find_person_record_path`). The edit is **surgical text surgery**: only the one top-level `living:` line changes (trailing hand comment preserved; CRLF endings byte-faithful); when the key is absent (a legal hand-made record), a `living:` line is inserted after `name:` in the stub scaffold's field order. Before any write the rewritten frontmatter is **re-parsed and vetted** (the frontmatter twin of `_lib.claims_edit_problem`): it must parse, `living` must equal the target, `id` must be unchanged, and no other field may appear, disappear, or change value - any failure is a refusal with nothing written, so an odd hand-authored file becomes a clean refusal, never a corruption. A **merged tombstone** (`status: merged`) is never edited - readers resolve through `merged_into` (SPEC §9), so the refusal names the surviving record to edit instead. Idempotent: a value already equal to the target is a clean `already` no-op. Every arm previews under `--dry-run` (unified diff, nothing written).

**Exit codes (`set-living`):** 0 flag written (the "run `fha index` when convenient" reminder is advice text, never a warning exit) / `already` / dry-run · 1 person not found (with the `fha find` next step) · 2 argparse (bad value literal, missing args, bare `fha person`) · 3 root unresolvable, invalid P-id shape, merged tombstone, guard refusal, unreadable/unwritable file. `run_set_living` returns a `Result` (`data.status` ∈ ok/already/dry-run/not-found/merged/refused); `changed[]` names the record on a live write.

**The no-auto-flip rule.** Accepting a `death` claim does NOT change `living:` - the flag is a privacy judgment, and judgments are directed by the human. The `review-claims` skill offers the command after the human accepts a death claim for a `living: true|unknown` person, and runs it only on his explicit yes; no tool path flips the flag automatically. The persona-facing output states the privacy consequence of the new value in plain words (a `false` opens exports to the person; `true`/`unknown` redacts them).

**`new` (plan 17).** Mints one P-id and writes its stub under `people/stubs/` - the parity command behind every "+ add person" button and the deliberate counterpart to `fha stubs` (that tool mints stubs FOR references already unresolved in claims; this one is a human deliberately starting from nothing). Shares `_lib.render_stub_content`/`stub_filename` with `fha stubs`, so a stub reads identically no matter which tool wrote it. `--sex`/`--gender` and the two vitals follow the same validation as the record format (§9): `--birth`/`--death` are PROVISIONAL, unsourced estimates, accepted as strict EDTF or loose wording (normalized with a plain gloss). Every input is validated before an ID is minted, so a bad flag never burns a fresh P-id; `--dry-run` still draws a real id (so the preview matches a live run exactly) but never writes it anywhere.

**§13 filename split (issue #53).** `_lib.stub_slug_name`, `lint._person_filename_parts`, and `index.py`'s name-based surname fallback share one rule (`_lib.strip_generational_suffix`) so a trailing generational suffix - Jr, Sr, II, III, IV, V, matched case-insensitively and period-tolerant - is never taken for the surname: "Roy Eugene Dodson Jr" files as `dodson__roy_eugene_jr_P-….md`, sorting the son directly under his father (`dodson__roy_eugene_P-….md`), never under a `jr__` prefix of his own. A leftover single word after the suffix is pulled off ("Roy Jr") gets the same surname-less treatment SPEC §13's mononym case does - the suffix does not promote it into a surname. `--surname TEXT` on `fha person new` overrides the automatic split outright, for names no heuristic should be expected to get right: Spanish double surnames, particles ("van der"), surname-first conventions; `name:` is written exactly as typed either way, only the filename's surname slug changes. `fha stubs --from-names` mints a batch of names in one call and has no way to attach a per-name override, so it does not take `--surname` - a name needing one is minted individually via `fha person new --surname` instead.

**`rename` (issue #51, 2026-08).** Corrects a person's name everywhere it is mechanically derivable, in one command instead of the seven hand steps the issue's reproduction counted (one frontmatter edit, five `git mv`s for the profile/research/timeline/sources-index/draft-queue filenames, one couple-folder rename): (1) `name:` is replaced, and `name_variants:` gains the OLD name under `--keep-variant` (a genuine append - an existing variant is never dropped); (2) the profile FILE is renamed to the filename the new name derives via `_lib.stub_filename` (§13, the same deriver `new`/`fha stubs` use); (3) the research companion (hand-authored, never GENERATED) is renamed alongside it when one exists, its notes untouched; (4) any GENERATED companion (timeline/sources-index/draft-queue) still sitting at the OLD filename is **deleted, never renamed** - identified by the shared `is_generated_file` header check (never by name-guessing, so a non-generated look-alike is left alone and named, not silently skipped) - and regenerated under the new name via `fha views timeline|sources-index|draft-queue <P-id>` (or `fha views refresh`); this is "trigger the existing regeneration machinery through its CLI surface," not a re-implementation of `views.py`'s own `_out_path_for` naming rule, which `tools/` files never import from each other to duplicate; (5) when (and only when) the record lives in a couple folder AND the OLD name is exactly one unambiguous partner-name segment of that folder's own free-form text, the folder itself is renamed to match - 0 or 2+ matches are left alone rather than guessed at, the same conservatism `_lib.spouse_extended_base` already applies to its own narrower "+ second spouse" case (SPEC §12.2: folder names carry no machine meaning, so this REPLACE is new logic for this verb, not a reuse of that add-only rule). Step 5 is the ONE part allowed to fail on its own (`data.status = 'ok-folder-unrenamed'`, `EXIT_WARNINGS`) without failing the whole call - a correctly-renamed record sitting in a stale-named folder is cosmetic, not corruption. The issue's own Windows reproduction - the shell's own working directory sitting inside the folder being renamed, surfacing as a raw `PermissionError`/"used by another process" - is checked and named plainly BEFORE the rename is attempted (`_folder_rename_blocker`), rather than left to leak a raw OS error; neither `promote_person_record` nor `views.py`'s own folder-rename code (`_apply_planned_renames`) carried an equivalent guard to reuse, so this is new, narrowly-scoped defensive code. Steps 1-3 are reversible on a live-write failure (frontmatter restored, any completed rename undone), the same promise `promote_person_record` makes for its own multi-step write; step 4's deletions are never rolled back, since GENERATED output regenerates identically regardless of what else the call did. `--surname` overrides the renamed filename's surname split, the same escape hatch `new --surname` already offers. A live write closes with the same `fha index` reminder `set-living`/`set-sex`/`set-profile-photo` give for their own single-field writes - `name:` and (usually) the record's path both just changed, and `fha site`/`fha packet`/`fha gedcom` all open the index strictly and refuse while it is stale. **Deliberately out of scope:** the issue's own follow-up observation that nothing verifies a filename's sort-name slot still matches `name:` after a rename (a new lint check) is real but is its own focused pass, not bundled here; the other follow-up - a `sex:` setter - was already shipped as `fha person set-sex` (2026-08-15), so no work was needed there.

**`relate` (plan 17).** Appends one entry to a person's `relationships:` list naming a second person and the role (parent/child/sibling/spouse), always `status: hypothesis` - there is no `--status` flag, because a sourced tie is a `relationship` claim (`fha claim`/`fha confirm cooccur`), never this command's job. `--subtype` names the bond's nature (§8.2 kin vocabulary); `--reciprocal` also writes the mirrored entry on the second person, with idempotency and the mirror write checked independently per side so a later `--reciprocal` run fills in just the missing half.

**`estimate` (plan 17).** Writes the provisional `birth:`/`death:` estimate described in the Dates format reference - a normal starting state, not an error - superseded once an accepted vital claim exists. At least one of `--birth`/`--death` is required; `-` clears a field; both dates validate before either is written.

**`edit` / `note` (plan 17).** Two bounded prose-section write-backs for a curated profile's `## Biography`, `## Stories`, or `## Research Notes` (`note` is Stories/Research Notes only). `edit` replaces (default) or appends (`--append`) with `--text`/`--file`; `note` is always append-only, the casual human-typed-a-thought path with no flag to turn that off. Both are bounded surgical edits - frontmatter and every other section are left byte-for-byte alone. `edit` warns (raising the exit code) when replacing a section drops a balanced `<!-- private -->` fence the old text had; `note` refuses outright, before writing anything, when the section's existing fence is unbalanced (it cannot tell which side of the redaction boundary new text belongs on).

**`edit-note` (2026-07-17).** The surgical middle ground between `note` (only ever adds) and `edit` (replaces a whole section): rewrite ONE existing append-log entry - a blank-line-separated paragraph run, exactly what one `note` append wrote - leaving every other entry untouched. This is the workbench's per-entry edit button. The entry is named by its exact current text (`--old-text`), never by position: display filters strip drafts and private markers, so a rendered entry's index cannot be trusted across the render/disk boundary, but its text can. No match (the file changed since the page loaded) or more than one match (an ambiguous duplicate) is a plain refusal with nothing written; an empty `--text` is refused too - removals stay a deliberate hand edit to the record file. The shared matcher is `_lib.replace_paragraph_in_section`, the surgical sibling of `append_paragraph_to_section`.

## 3d. `fha source` - source-field write-backs (plan 17)

The `fha person` sibling for a source record: deterministic write-backs to a source's own text rather than its Claims. Four verbs ship: `note` (appended free text was previously a hand-edit only), `edit-note` (2026-07-17, the per-entry rewrite), `extract` (M11.5, the PDF text-layer dump), and `clear-keyword` (2026-08, #112 - the embedded-keyword correction path).

```
fha source note <S-id> --text TEXT [--dry-run] [--root PATH]
fha source extract <S-id> [--pages RANGES] [--dry-run] [--root PATH]
fha source edit-note <S-id> --old-text TEXT --text TEXT [--dry-run] [--root PATH]
fha source clear-keyword <S-id> --keyword TEXT [--replace-with TEXT] [--file NAME] [--dry-run] [--root PATH]
```

**Contract (`note`).** Appends TEXT as a new paragraph at the end of a source's `## Notes` section (SPEC §14: "the story behind it, context, or where the original is kept"), creating the heading at the end of the file if a hand-made record does not have one yet. Always append-only - an existing note is never edited, reordered, or removed, and no AI marker is written (a human types these words). The record is located by scanning `sources/` directly, so a stale or absent index never blocks the write - the §3b/§3c rule. The edit is bounded to the Notes section by construction; a regression guard re-checks the `## Claims` block before and after and refuses if the edit somehow broke a previously-sound block (a Claims-less source, per §14's "just taking notes? DELETE this whole ## Claims block", is never penalized for staying Claims-less). `status: superseded` is not a reason to refuse - a superseded source still gets its audit trail.

**Contract (`edit-note`).** The `fha person edit-note` twin: rewrite ONE existing `## Notes` paragraph, named by its exact current text, leaving every other note as written - the workbench's per-entry edit button on a source page. Same matcher (`_lib.replace_paragraph_in_section`), same refusals (not found / ambiguous duplicate / empty replacement - removals stay a hand edit), and the same Claims-regression guard and multi-heading refusal as `note`.

**Contract (`extract`, M11.5).** Dumps the source PDF's embedded text layer into a derived companion filed beside the original: `{slug}-extracted-text_{S-id}.md`, `[Page N]`-labeled in the PDF's OWN pagination (so `anchor: "page N"` claims, SPEC §8.4, line up in any copy), with `role: extracted-text, derived: true` appended to the record's `files:` inventory through the shared `_lib.append_file_entry_to_record` (the same single pathway `fha process --more` writes through). The original is never touched (SPEC §12.1); the output is a rebuildable derived artifact (SPEC §5.1). Reads the primary PDF, else the single non-derived PDF; several PDFs without a primary refuse rather than guess. A page with no text layer gets an honest placeholder line; an all-image PDF is a warning refusal toward vision/OCR with NOTHING written (an empty dump would read as "nothing on these pages" - exactly wrong); an encrypted PDF refuses naming the unlock path. Re-running is a clean `already` no-op - extraction never overwrites. `--pages 1-60,102` narrows (1-based, validated against the real page count). pypdf is the borrowed engine (SPEC §5) and an OPTIONAL dependency like Pillow: absent, this one verb refuses with `python -m pip install pypdf`, nothing else degrades; `fha doctor` reports it info-level. On a record-write failure the extract file is removed AND the record restored from the pre-edit text, with an honest message when even the restore fails.

**Contract (`clear-keyword`, 2026-08, #112).** The tool-mediated fix for a stray embedded keyword lint's W131 (§3) finds: a documents-root asset carrying a Keywords/Subject value (IPTC or XMP `dc:subject`) that names a real archive person absent from that source's own `people:` list - most often a leftover tag from before the file entered the archive (a Lightroom pass, typically). AGENTS.md rule 3 permits only spec'd renames and "embedded metadata writes performed through fha tools" as original-file changes; before this verb there was a WRITE path for a documents-root keyword (`fha process` embeds `SOURCE:` on first processing) but no CORRECTION path, so a wrong keyword, once found, had no sanctioned way back out short of a hand edit. Locates the source's documents-root file (`--file NAME` disambiguates when the source lists more than one; with exactly one, it is picked automatically - a source with none, or none matching `--file`, refuses), then reads that file's OWN Keywords/Subject values and matches `--keyword` case-insensitively against them - the removal itself targets the EXACT on-file spelling (exiftool's list `-=` operator is an exact-value match), so a keyword typed slightly differently on the command line refuses naming what is actually on the file rather than silently doing nothing. `--replace-with TEXT` adds the correction in the SAME Keywords/Subject field the stray value came from (never a new field the file did not already carry), skipped rather than duplicated if that field already holds it; omitted, the keyword is simply cleared. Uses the identical `_lib.OriginalBackup` safety-copy discipline (TOOLING §13f) every other embedded write in this codebase follows - `fha process`'s SOURCE: embed, `fha photoindex tag-person`/`set-summary` - so this fifth call site into an original asset does not quietly skip the one protection the other four share; remove and any add happen in one exiftool call, so a mid-way failure never leaves the file carrying neither the old value nor the new one. Documents-root only, matching W131's own scope (see that check's docstring in lint.py for why a photos-root equivalent is a separate, undesigned decision, flagged rather than folded in here).

**Exit codes (all four verbs):** 0 written/ok/already/dry-run · 1 S-id not found, or the on-disk asset not found (with the `fha reconcile`/`fha find` next step) · 3 invalid id shape, blank `--text`/`--old-text`/`--keyword`, unreadable/unwritable file, ambiguous multi-heading record or ambiguous/absent documents-root file, the keyword not currently present on the file, the entry-match refusals, or the Claims-regression refusal. `run_source_note`/`run_source_edit_note`/`run_source_clear_keyword` return a `Result`; `changed[]` names the record (or, for `clear-keyword`, the asset file) on a live write.

**SPEC amendment accepted (#112, 2026-08).** SPEC §20 "Embedded metadata" (`LOCKED`) originally enumerated the write shapes this project embeds (SOURCE: keyword, bare P-id tag, DATE: pattern, AI-marked caption) but said nothing about CORRECTING one once written - `clear-keyword` shipped resting only on AGENTS.md rule 3's general permission ("embedded metadata writes performed through fha tools"), ahead of its own §20 license. That gap is closed: **SPEC §20 rule 7** now licenses the removal/correction path directly - "A wrongly-embedded keyword is cleared or corrected only through `fha source clear-keyword`, never by hand" - the same durable-layer discipline as every other write in this section, scoped to documents-root only (photos-root person-keyword correction remains a separate, undesigned decision).

## 4. `fha id` - minting

`fha id mint P [-n 5]` → prints fresh IDs.
Algorithm: draw 10 chars from the Crockford Base32 alphabet `0123456789abcdefghjkmnpqrstvwxyz` via `secrets.choice` (lowercase, omitting `i l o u`); check non-existence by a ripgrep-style scan of the tree for the candidate; retry on the ~impossible collision. `fha id check <ID>` → where it appears.
Dice-roll fallback documented in output of `fha id --help` (hand-minting: any 10 Base32 chars from the alphabet above + a search to confirm absence). On input, IDs are normalized to lowercase before matching, so a hand-typed uppercase ID still resolves.

## 4a. `fha find` - the universal locator

`fha find <ID>` answers "where does this thing live?" for **any** ID - necessary because photos aren't renamed, so disk search alone can't locate a photo by S-id.
Output by type: **S-id** → record path, every asset file (paths resolved through `fha.yaml`, located via filename for documents / inventory+keyword for photos), citation sites, claim count by status. **P-id** → person file, couple folder, claims naming them, photo count (via §9 resolution), citation sites. **C-id** → its source record + line, status, links in/out. **L-id/H-id** → record + every reference. `fha find <text>` falls through to text search (records, notes, and configured documents root; photo captions when photoindex is fresh; transcripts and extracted PDF text via `transcripts_fts`).
(`fha id check` is an alias.)

**`fha find --related <ID>`** - "show me everything adjacent to this," for **any** ID type, ranked, pure query over the index (no schema change).
What counts as *adjacent* depends on what you point at - each type has a natural neighborhood the index already holds:

- **`--related <P-id>`** (a person's world): **relationship edges** (`relationships` table, rel type + distinct backing source count); **co-occurring people** with no existing edge (sharing a source, ranked by shared-source count - the same grouping `fha cooccur` uses, scoped to this one person); **places** they recur in (claim `place_id`/`place_text` frequency); **shared entities** - occupation/military/membership-style affiliations from their claim values, with the other people who share each; their distinct **source** count; and **photos** via `photo_people` (a clear note when the photoindex is absent). Backs the FAN view and the profile's Friends & Family suggestions.
- **`--related <L-id>`** (a place's world): every **claim** naming the place; the **people** in those claims (ranked by frequency - "who is most associated with Fairview"); the distinct **source** count; **photos** geotagged within ~0.002° of the place's coords; and contained **micro-places** (`within: L-id` children). The building block for "everyone connected to this place."
- **`--related <S-id>`** (a source's world): its **claims** by status; every **person** named; **places** referenced; **other sources** that corroborate/contradict its claims (via `claim_links`, both directions); and **sibling sources** sharing a named person or the same `repository`.
- **`--related <C-id>`** (a claim's neighborhood): its source, persons, place; claims it `corroborates`/`contradicts` (outgoing and incoming); and **sibling claims** - same person + same type (the other residence claims, the competing birth dates), the cluster you'd weigh together. Not time-sliceable by `--date` - a claim's own `date_edtf` already pins it to one point.
- **`--related <H-id>`** (a hypothesis's neighborhood): the person it concerns, the claims that reference its H-id (`claims.hypothesis`), and the verifying claim if resolved. The `hypotheses` table itself is never populated by the index builder, so the normal case derives this entirely from `claims.hypothesis` + `claim_persons` - a missing table row is expected, not a failure.

**`fha find --related --date <EDTF>`** - the *time* neighborhood, orthogonal to ID type: all accepted/needs-review claims (and the people, sources, and places behind them) whose dates overlap the given EDTF range, via the index's `date_min`/`date_max` bounds (§1). Photos are not joined into this standalone form - the photo and claim date fields have no shared key to join on without a second, unrelated overlap pass - see TOOLING's note in `find.py`'s `_related_date` docstring.
"Who and what was active 1869-1874."
Combinable with a **P-id, L-id, or S-id**: `--related <L-id> --date 187X` = the place, narrowed to a decade; `--related <S-id> --date 187X` narrows a source's claims by status to the same window. C/H neighborhoods ignore `--date` (a single claim's own `date_edtf` already pins it to one point, and a hypothesis isn't meaningfully time-sliced).

**`fha find --text "…"`** - full-text search across record bodies and notes, plus the **photo/document index** caption/comment/keyword fields (§9) when the photoindex is fresh, plus **transcripts and extracted PDF text** (the `transcripts_fts` table, populated by `fha index` from `role: transcript` / `transcription` / `extracted-text` companions; see D7).
Returns hits with their record or asset and context.
A hit whose matching words came from a transcript **no human has checked against the image** is labelled `[unchecked AI transcript]` on its own result line, with one sentence after the list saying what that means and that the image is the evidence (D15).

**Every text search declares its own blindness (D14).** The result - hit or miss - carries a count of the sources this archive holds no text for: sources with at least one file, none of which is a `.md`/`.txt` or a `transcript`/`transcription`/`extracted-text` companion the search can read inside. A scan, a photograph, an image-only PDF and an untranscribed recording are all mute to a text search, and without that line a null result over them is indistinguishable from a null result over evidence that was read. See D14 for why it prints on a hit too.
A photo whose file has left the disk keeps its caption searchable (the `MISSING:` row, §9), so its caption hits still come back - printed under the path the photo had, marked `(not on disk)`, never as the internal key. The same rule governs every photo `find` names: a group is located by a member still on disk when it has one, and only a group with none prints its last known path, marked, with `fha photoindex reconcile` as the next step.
Cheap because the corpus is plain text plus the two SQLite FTS tables; one query spans prose and media metadata.

Together these make `find` the **connection-discovery primitive**: any ID or date or phrase → its neighborhood, ranked, every edge carrying provenance - the raw material the report, the FAN view, and `cooccur` all build on.
For bare `fha find <ID>` and `--text`, the index is used when present; if stale, `fha find` prints a warning but still returns the structured index-backed report; if absent or unreadable, it degrades to a tree scan with the same warning. If the index is stale *and* has no row for the requested ID, it falls back to a tree scan rather than reporting "not found" - the record may simply have been added since the last `fha index` run.
`--related` is different: its joins across `relationships`/`claim_links`/`claim_persons` have no meaningful tree-scan equivalent, so an absent or unreadable index is a hard error (exit 3) rather than a degrade. A stale index still warns but is queried, since `--related` is read-only.
(`fha id check` is an alias for the bare locator.)

**Design decision D4 (implemented BUILD.md M4.3):** `--related` and `--related --date` are fully implemented, after `fha xref` and `fha cooccur` populated the corroborates/contradicts and social-edge data the neighborhood view depends on. They are a pure read query over the index - no schema change, no writes.

**Design decision D7 (implemented; transcript search shipped M11.5, widened to every transcript role 2026-08-16):** `fha find --text` searches record bodies and notes (via FTS tables plus a re.search pass) and **photo/document captions** when `.cache/photos.sqlite` is verifiably fresh (present, schema OK, newer than the photos root).  When the photoindex is absent, stale, or unreadable, captions are skipped and the tool prints an explicit note.  The `transcripts_fts` table is **populated** by `fha index` from every text companion - `role: extracted-text` (`fha source extract`'s PDF text dumps), `role: transcript` and its older spelling `role: transcription` (a transcript written by hand, by the transcribe-audio skill, or by anyone who read a picture and typed it out) - and both the CLI text search and the JSON/workbench backend (`find._ranked_search` → `search_json`, used by `fha find --json` and `fha serve`) query it, so a transcript is searchable everywhere after `fha index` no matter what wrote it. Loading only the extract verb's own dumps meant an archive could hold a careful transcript of a scan and still answer a search as though the scan were mute (#46). The role vocabulary lives in `_lib.TEXT_COMPANION_ROLES` so `fha lint` counts the same files the index loads; the `.md`/`.txt` guard is `_lib.SEARCHABLE_TEXT_SUFFIXES`, and a role tag on a media file is skipped rather than read as UTF-8.

**Design decision D14 (implemented 2026-08-16, #46):** **a text search says how much of the corpus it could read.** A source whose files are all scans, photographs, image-only PDFs or untranscribed recordings puts nothing into the archive as text; a search over it returns nothing and looks exactly like a search that read it and found nothing. That ambiguity is not academic - it cost a person her surname: the name was searched for, found only in one claim's value, judged invented and struck, while it stood in plain handwriting on a 22-page image-only scan the search had never been able to open. So every `fha find --text` (and `fha search`, and a bare text `fha find`) ends with a count of the sources in the archive holding no searchable text, and:

- **It prints on a hit as readily as on a miss.** Three results out of a corpus half of which nobody could read are as misleading as none, and worse in practice, because hits feel like confirmation and nobody re-examines a question they believe is answered. The wording differs - "not the whole picture" on a hit, "could not look everywhere" on a miss - the number does not.
- **It names only verbs that exist.** `fha source extract <S-id>` for a PDF that carries its own text layer, and reading the file otherwise. There is no `fha source transcribe`, and printing one would be a promise the tools cannot keep.
- **It is answered from the index, never from the asset roots.** One pass over `source_files` (a few rows per source) and one over `transcripts_fts`'s key column - no walk of the photos or documents tree, because this runs on every single search. A file the index recorded as absent from disk buys no coverage; a source with no files listed at all is counted in neither half, having nothing to read.
- **It never claims coverage it did not check.** With no usable index the note says the coverage question went unanswered and names `fha index`, rather than falling silent - silence is the failure mode this decision exists to end.
- **Every search surface says it, on the channel that surface has for prose (extended 2026-08-16).** `fha find --json` puts the note on **stderr**, leaving stdout the bare hit array its consumers parse; `fha serve`'s `/api/find` returns it as a `coverage` field and the workbench renders it under the search dropdown's results, which on a search that found nothing puts it directly beneath "no matches" - the moment the #46 mistake is made. One composer (`find._searchable_text_note`, reached by every surface through `find.search_json_with_coverage` or `run_find_json`), never a second copy of the wording that could drift into disagreeing about the same archive. **`/api/find` fills that field for an unfiltered search only** (2026-08-16): a `--kind`-narrowed lookup is asking which record you mean, not what the archive says, so it returns `null` and does not pay for the count - two indexed scans on every debounced keystroke of a picker that never renders the caveat. Absence, never a count recomputed over the filtered rows, which would answer the same archive-wide question with a second, smaller number. The CLI keeps the note under `--kind` (`run_find_json` composes its own): that reader is usually a model doing research, and it is not typing.

The same corpus fact is a lint warning from the other direction: **W124** fires on a source carrying `accepted` claims whose files hold no words at all.

**Design decision D15 (implemented 2026-08-16):** **a hit that came from an unchecked machine reading says so, on its own line.** D14 closed "the search cannot see"; this closes the hole it opened. A transcript a model produced by reading a scan is loaded into `transcripts_fts` like any other, so it is searchable and, to a reader, indistinguishable from evidence - and it does not fail the quiet way an untranscribed source does. It returns confident **hits**, and a misread word then travels as a fact nobody re-examines. By the reasoning in AGENTS.md's "You cannot conclude absence from a search", that is a coverage claim too, and the same rule applies: say what you actually read.

- **The mark is per result, not per search.** D14's note is a caveat on the whole search, printed in a footer. This one cannot be: one search can return a transcript a human has compared against the scan and a transcript nobody has ever looked at, and the difference between those two results is whether the hit is evidence. So the label `[unchecked AI transcript]` rides on the matching result's own line.
- **Only the transcript surfaces earn it.** A match in a record body, a claim value, a note, a person profile or a photo caption is a match on what somebody wrote down, not on a machine's reading of a picture, and is never marked - including a profile carrying `<!-- AI-DRAFT … -->` biography prose, which is the same marker pair on a file that is not a transcript of anything. Both halves of the search apply the rule: the `transcripts_fts` pass and the re.search fallback over the documents root, which checks the path against the set the index loaded (`find._indexed_transcript_paths`) so the label does not depend on which pass found the file.
- **The state is read from the text the index already holds** - the companion's full body is the `transcripts_fts.content` column, so no file is opened to answer this on a search that runs constantly.
- **Four states, and only one of them is loud.** The rule is the `transcribe-source` skill's marker contract, implemented once in `_lib.transcript_review_state` over the same `<!-- AI-DRAFT … -->` / `<!-- AI-ACCEPTED … -->` regexes `strip_unaccepted_drafts` and `fha confirm draft` use: **unreviewed** (a complete AI-DRAFT marker), **verified** (a complete AI-ACCEPTED marker and no draft marker), **unmarked** (neither word - a human's typing, or an `fha source extract` dump of a PDF's own text layer), **damaged** (the literal word outside any complete marker). *unreviewed* outranks *verified*; *damaged* is treated as unreviewed, failing closed exactly as `strip_unaccepted_drafts` does. `_lib.transcript_text_is_unchecked` is that collapse, so every consumer inherits the fail-closed posture instead of remembering it.
- **`unmarked` is silent, and that is load-bearing.** A mechanical text-layer dump is the file's own words, not a reading of them, and hand-typed transcripts carry no marker either - together they are most of the transcripts in an archive. Flagging them would put the label on nearly every transcript hit and teach the reader to skip it, which is precisely how the ones that matter would get read as evidence.
- **The explanation prints once**, after the results and before D14's coverage note: the label is on every affected line, but repeating a paragraph between hits would bury the results it is warning about. It names what the label means, that the image is the evidence, and `fha find <S-id>` for getting to the file.
- **Every surface marks it, in its own idiom (extended 2026-08-16).** `fha find --json` and `fha serve`'s `/api/find` add `"unchecked": true` to the hit - additive, present only when true (see §4a's `--json` contract); the workbench dropdown renders that as a caution chip beside the `text` kind chip, carrying the same sentence as its hover title. The rule is applied once, in `find._ranked_search`, from the same `transcripts_fts.content` column the CLI reads and through the same `_lib.transcript_text_is_unchecked` collapse - so the CLI, an agent and the browser cannot disagree about whether a given hit is evidence.

There is no verb yet that flips a transcript's marker from draft to accepted (`fha confirm draft` takes a `<P-id>` and edits a person profile), so today every AI-written transcript stays *unreviewed* and keeps drawing the label - which is at least true. The gap is recorded in `.claude/skills/transcribe-source/GAP.md`.

**Design decision D9 (implemented milestone 2 audit):** A stale index is still preferable to a bare tree scan for `fha find <ID>` because it preserves structured reports (person companions, claim summaries, source inventories, citation rows). Staleness is `newest_record_mtime > index mtime`, where the watermark covers records only - the generated companion views (timeline / sources-index / draft-queue) are **excluded**, because `fha views` writes them FROM the index and counting them made every view write stale the index it had just read (the documented per-person close-out failed on its second call, D-2026-08 / #37); the human-written `research` companion still counts. Because the watermark can no longer notice a companion changed, the view writers keep those rows current themselves: every `.md` companion written or deleted by `fha views` has its `notes_fts` body and `person_files` row rewritten in place through the shared `_lib.sync_generated_view_rows` (views cannot import index - tools never import tools), so `fha find --text` never serves a regenerated view's superseded text and `views clean` never leaves rows for files it deleted. Staleness is surfaced as a warning; an absent or unreadable index falls back to grep-style scanning outright, and a stale index that has no row for the requested ID also falls back to a scan (the record may have been added after the last `fha index` run) rather than reporting a false "not found". The watermark also fails **closed** on a folder it cannot list. `rglob` reports an unreadable subdirectory as an empty one, which SUBTRACTS its records' mtimes from the answer - so an index built without those records read as current, and `fha find`, `fha doctor` and `fha views` all trusted it. `newest_record_mtime` (and its `newest_source_record_mtime` / `newest_person_record_mtime` siblings, and `photoindex_status`'s own walk of the photos root) therefore walk with `_lib.walk_files` and an `unreadable_dir_recorder`, and report `time.time()` when anything went unread: a watermark is a promise that nothing newer exists, and a walk that skipped a subtree cannot make it. Every cache then reads stale for exactly as long as the folder stays shut, which is self-clearing and needs no state anywhere - and `fha index` and `fha lint` (W123) name the folder, so the staleness is never unexplained.

**Update (#48, 2026-08): a watermark cannot see a deletion.** `newest_record_mtime > index mtime` catches a modified or newly-added record - the watermark rises above whatever mtime the cache was stamped at - but deleting a record raises nothing: no *remaining* file gets newer, so the comparison above read a cache holding a deleted source's rows as current, silently, for as long as nothing else in the tree changed (the reported bug - a duplicate source filed twice, deleted in Finder, still "found" for weeks). The fix tracks the SET of paths a cache was built from, not just their max, in a small JSON file beside the cache it describes (`.cache/index_manifest.json` for `index.sqlite`, `.cache/photos_manifest.json` for `photos.sqlite`) - `_lib.py`'s "Freshness manifests" section: `record_path_manifest`/`person_profile_path_manifest`/`source_record_path_manifest` build the same `{path: mtime}` sets the watermark functions above reduce to one number (literally the same walk - `_md_file_mtimes` backs both), `write_path_manifest`/`update_path_manifest` persist them (a full rebuild replaces the file; an incremental writer - `upsert_source`, photo reconcile/tag-person/set-summary - patches just the paths it touched), and `manifest_diff` compares a stored set against a fresh listing: a path present in the stored set but absent from disk is a deletion, invisible to the watermark and the one case this closes. The fix is purely **additive** - every reader (`open_index_db`, `find._index_is_fresh`, `doctor._index_freshness`, `photoindex._index_is_fresh`, `photoindex_status`) ORs the manifest check onto the exact watermark comparison described above, never replacing it, so the fail-closed unreadable-folder rule and the #37 generated-companion exclusion keep working unchanged. Content hashing was explicitly ruled out - path+mtime fixes the reported bug at a cost that stays cheap on a large photo library. **Bootstrapping is the one place this must fail in a specific direction:** a missing manifest (an archive upgrading from before #48, or `.cache/` freshly wiped) is treated as "everything changed", exactly like a missing `index.sqlite` already is - never "nothing to compare, assume fresh", which would silently reintroduce a worse version of the same bug on the very first run. A missing manifest therefore reads stale exactly once; rebuilding writes one, and the archive is self-consistent from then on. `fha serve`'s workbench snapshot is a third, simpler freshness scope (§ Research workbench, TOOLING_INTERFACE.md) with no cache file of its own - its manifest is kept in memory only (`ServeState._snapshot_manifest`), rebuilt every process start regardless, and compared the same additive way in `snapshot_is_stale`.

**D9 addendum (2026-08, #76): the profile's own `## Sources` region.** A person's `## Sources` section (SPEC §16, §21b) is generated content that happens to live INSIDE the profile file rather than in a companion of its own - the profile itself is never on the exclusion list above (any other edit to it, a line of Biography, correctly stales the index), so this is not a second entry on that list. Instead, `views._generate_sources_index_person` writes the region and then immediately re-syncs `notes_fts` for that ONE profile through `_lib.resync_person_profile_rows` - the profile-row twin of `sync_generated_view_rows`, differing only in WHAT it updates (an existing person's FTS body, never `person_files`, since the profile's own row already exists and neither its path nor its `person_id` changed). That second write touches `index.sqlite` itself, which advances the DATABASE FILE's own mtime past the profile's just-written one - the same mechanism that keeps a companion write from staling the index, applied here to win a race rather than to sit outside the watermark's count. A failed re-sync is therefore not silent the way a failed companion sync would be safe to ignore: the profile's mtime has genuinely moved past `index.sqlite`'s, so the watermark now correctly reads stale until `fha index` reruns - `run_sources_index` and `run_refresh` both surface this as `data['index_stale']` / exit 1, identically to a failed companion sync (D9 above), even though the underlying safety mechanism is different underneath. **#48 interaction:** this in-place edit changes the profile's own mtime - a real content change, not a companion write, so it is very much a path the #48 manifest tracks - and the mtime-bump trick above says nothing about that JSON file. Left unpatched, the manifest would keep the pre-edit mtime forever and read the profile as "modified" on every later check, silently re-staling exactly the write this function exists to make free. `resync_person_profile_rows` therefore also patches the manifest entry for each profile it successfully re-reads (`update_path_manifest`, the same incremental-patch primitive `upsert_source`/`relocate_person_in_index` use), in the same pass and with the same fail-together posture as `notes_fts`: a profile whose read failed keeps its OLD manifest entry too, so the SQL row and the manifest entry go stale (and get fixed) together rather than one silently outrunning the other.

**`fha find --json <ID|text> [--kind K,K…] [--limit N]` (implemented plan 17).** A machine-readable result list instead of a human report - the reference-resolver backend a UI or workbench autocomplete calls to turn a typed name/ID fragment into candidates (`fha serve`'s `/api/find` is a thin wrapper over the same engine, `search_json`). A pure ranked search over aliases, `persons`, `sources`, `places`/place names, and `notes_fts`, deduped by id and sorted by match tier (0 exact / 1 prefix / 2 substring) then label; each hit is `{id, type, label, detail}` (the field shapes of §9/§14), printed as one `json.dumps` document or nothing on zero matches. `--kind` narrows to `person`, `source`, `place`, `hypothesis`, `claim`, `text` (comma list; default every kind); `--limit` caps the count (default 20). `photo-source` (2026-07-17) is an extra *filter* value, not a hit type: only sources that actually own photo assets (`source_type: photo`, or any `source_files` path with a photo extension) - hits still carry `type: source`. Built for pickers that only make sense over photos (the workbench's set-profile-photo lookup); a pasted bare S-id still resolves under it, since an explicit id is an explicit pick. Valid with a bare ID/text query or `--text`. Like `--related`, an absent/incompatible index is a hard error (exit 3, no tree-scan fallback - the ranking has no meaningful equivalent outside the index), using the same `open_index_db` plain-message + exit-3 contract `--related` established. Not combinable with `--related` - there is no defined meaning yet for "the neighborhood of X, as ranked search results" - refused with a plain message naming the supported combinations (exit 2).

**The machine surface carries the same two warnings the human one does (2026-08-16).** `--json`'s reader is usually another model, which is exactly the reader whose null-result reasoning #46 records, so leaving D14/D15 on the human surface alone would have fixed the wrong half. Neither change touches what stdout is:

- **The coverage caveat goes to STDERR** - the identical sentence `_searchable_text_note` composes for the human search (D14), printed before the JSON document and only when there is something to caveat (an archive whose sources all hold readable text emits nothing on stderr at all). stdout stays the bare hit array, byte for byte, so anything parsing it today parses exactly what it parsed before. `fha serve`'s `/api/find` gets the same sentence as a `coverage` field beside `results` (null when there is nothing to say).
- **An unchecked transcript hit gains one additive key**, `"unchecked": true` (D15). **Present only when true** - never `"unchecked": false`, because a key that is there-or-not-there is cheaper to read and cannot be mistaken for "checked", which is a claim nobody has made about an unmarked transcript, a record body, a claim value, a place or a photo caption. The four documented keys are unchanged and every other hit still carries exactly those four.

## 5. `fha stubs` - stub minter

Scan claims for P-ids without person records (E005 set) → create `people/stubs/{surname}__{given}_{P-id}.md` with minimal frontmatter (`tier: stub`).
Name/surname resolution: from claim `value` text where parseable, else `unknown__unknown_{P-id}.md` flagged for hand-rename.
Also supports `--from-names "Ethel Hartley; Frances Hartley"` interactive minting (new IDs + stubs in one step).
A trailing generational suffix (Jr, Sr, II, III, IV, V) is never taken as the surname (issue #53, `_lib.strip_generational_suffix` - the same rule `fha person new` uses); "Roy Eugene Dodson Jr" files under `dodson__`, sorting beside "Roy Eugene Dodson" rather than under a `jr__` prefix of its own. `--from-names` mints a batch in one call with no per-name override, so a name needing an explicit surname (a Spanish double surname, a particle) is minted individually via `fha person new --surname` instead.
Never overwrites; never moves a stub out of `stubs/` (placement into couple folders is a human act). The one carve-out is `fha person promote` (and its batch form `fha views brackets --fix-promote`, §7): the explicitly human-invoked graduation verb is the single sanctioned tool move out of `stubs/` - still the human's act, only executed by the tool.

## 6. `fha process` - processing assistant

`fha process <file|folder> [--type TYPE --title "…" --slug …]`
`fha process refile <S-id> [--file NAME] --to photos|documents [--type TYPE] [--dest SUBPATH] [--yes] [--dry-run]`

**Which root a file goes to (`--type` decides, not the extension).** Three questions in order. **Where it already lives:** a file under either asset root stays under it - `fha process` never carries a filed original across the roots, which is refile's job alone (SPEC §12.1). **What the human said it is:** a stated `--type` other than `photo` - or a source stub's `source_type:` hint, with `--type` outranking it - names a *record* (SPEC §14's vocabulary is a vocabulary of records), and records live in the documents root that SPEC §12 fills with "scans, clippings, recordings, transcripts"; so a scanned census supplied as a `.jpg` is filed under `documents/{type}/` and scaffolded at `sources/{type}/`, extension notwithstanding. A stated `photo` never pushes a file the other way - the photo library is another program's tree and only a real photograph enters it - so `--type photo` on a `.pdf` files the asset as a document while the record still reads `source_type: photo`. **What the file looks like:** a known photo extension is a photo, everything else a document. The type is validated (SPEC §14's list) once, before any branch or file I/O, so an unknown `--type` is refused on the photo path as well as the document path. A file that already sits in the photos root and is given a non-photo `--type` keeps its place - the record is typed and filed as asked, nothing moves, and the output names `fha process refile` as the way to move the file itself.

**Folder mode:** runs the triage scorer (§15b) over the folder, prints ranked candidates with signals, and processes only the ones the human selects.

**Before any keyword write:** the `SOURCE:` keyword is the FIRST time fha touches a photo's bytes, so `originals_backup:` (§13f) takes its pristine copy there - the photo exactly as the camera or scanner left it. A copy that fails refuses the keyword write (and with it the scaffold); an absent setting warns once per run and proceeds.

**Path resolution (forgiving):** `FILE` is taken as typed first (relative to where the command runs); a relative path that misses is retried under the resolved archive root, so the cheat-sheet spelling (`inbox/scan.jpg` typed from the workshop folder beside the archive) works. A double miss names both searched locations. The same doctrine covers `--more FILE`.

**Filing out of the inbox keeps the original (#109).** When `FILE` (or `--more FILE`, or a `-back`/`_back` sibling pulled in alongside it) resolves under the inbox, `fha process` never empties the inbox of it: the bytes are COPIED (`shutil.copy2`, so timestamps/metadata survive) into the documents/photos root under the name the rest of this section describes, and the ORIGINAL is then MOVED - never deleted - to `inbox/processed/<the relative path it had inside inbox/>`, preserving whatever subfolder structure it was staged under. This mirrors `fha capture --ingest`'s own park-don't-delete precedent for `.ingested/` (TOOLING_INGESTION.md): a human processing a large batch (the filed issue's own case - "several hundred files") can spot-check the originals before clearing `processed/` by hand, rather than deletion being a side effect of processing. A same-named file already parked there (e.g. a second run over a file already processed once) refuses cleanly, the same way a destination-already-exists collision at the documents/photos root does. `--dry-run` names both destinations without writing to disk. A refusal anywhere downstream of the relocation (`process_document`'s own `documents/dna/` requirement for a `dna`-typed file, a `dna` restriction rewrite that cannot be safely applied, …) undoes BOTH the destination copy and the `processed/` park, leaving the original back at its exact starting path in `inbox/`. `inbox/processed/` is excluded from the workbench's Inbox page and its item count (it holds already-filed originals, not new material) but still counts toward `fha doctor`'s "items older than 14 days" nudge, same as everything else left sitting in the inbox.

**Input** is a bare file, a **source-stub sidecar** (one asset + `*.notes.md`), a **source-stub bundle folder** (multiple files + a `notes.md` - e.g. recording + transcript; each file becomes a role-tagged version sharing the minted S-id, the folder dissolves, SPEC §12.1), a **variation group** (see below), or a folder to triage. **File mode**, transactional (any failure → roll back):

**Variation detection - implicit grouping from a mixed folder.** A real photo library has variation-siblings scattered among unrelated photos: three scans of the same portrait at different resolutions, a front-and-back pair, a color original and a restored version. They don't need a bundle folder - `fha process` (and `photoindex`) detects them automatically using two tiers:

*Tier 1 - deterministic (free, always on):* files sharing the same basename root with only a suffix variation (`portrait_1880.jpg`, `portrait_1880_back.jpg`, `portrait_1880b.jpg`, `portrait_1880b_back.jpg`) are flagged as a candidate group. Known role suffixes: `-b` or `-c` etc. (multiple scans of the same original photo, each may have separate context though), `b` or `c` etc. (photo variation letters don't always start with a dash), `-negative` (the film negative of the photo), `-front` (occasionally fronts are tagged with backs), `-page-N` (if a multi-page photo book it could have multiple pages), `-back` (reverse side), `-bw` (greyscale version), `-crop` (cropped). Any unrecognized suffix is kept as a freeform role. The primary is the file with the shortest/root name; others list as variants.

*Note on `-page-N` variations:* photo books are usually scanned twice over - the whole page plus each individual photo on it - so page-level variants share less context than other variation kinds, though the whole-page scan still matters as original source documentation.

*Tier 2 - model-assisted (optional, gated behind `--with-vision`):* a vision pass over candidate pairs to confirm perceptual similarity - catches variations with unrelated names (e.g. `scan001.jpg` and `scan002.jpg` that are actually front/back of one photo). Expensive; used only on ambiguous cases Tier 1 can't resolve. Backlog until the core tools exist.

**Filename parsing algorithm.** Suffixes are stripped in this fixed priority order (implemented in `parse_media_filename`):
1. Strip `-crop` suffix first → `is_crop = True`. Crop stacks on any other suffix combination.
2. Strip part-kind suffix: `-negative` checked before `-back` / `-front` / `-pageN`.
3. Detect trailing single-letter variant ID - hyphen-letter (`-b`) or letter immediately after a digit (`034b`).
4. Remaining stem → `base_id`.

Result: `ParsedName(base_id, variant_id, part_kind, page_num, is_crop)` where `part_kind` ∈ `"front" | "back" | "page" | "negative" | "none"`. **Semantics:** `-negative` is mutually exclusive with `-front`, `-back`, and `-pageN` - it marks a scan of the physical film or glass-plate negative; in the grouper it is always stored at the stem level regardless of any variant letter (a negative is source material for the root image, not a print variant). `-crop` marks a derivative detail image (zoomed text, face close-up); crops are stored in dedicated `_crop` slots alongside their parent scan and supplied as supplementary AI context, never treated as independent primary images. A missing `-page1` is never inferred by the parser - if a group contains explicit `-pageN` siblings, the grouper may promote an untagged file to page 1, but the parser itself never does this.

**Multi-image batch types.** When a folder contains multiple images for one source, classify the set before processing:

| Type | Description | Treatment |
|---|---|---|
| **A - Variant scans** | Same physical side/object, different crop/exposure/rotation/quality | Merge into one source |
| **B - Front/back** | One or more front scans and one or more back scans of the same physical photo, postcard, or document | Merge into one source |
| **C - Multi-page document** | Different pages of a booklet, album, scrapbook, or document set (filenames `-page1`, `-page2`, …) | One ordered document set; preserve page order exactly; transcribe text across all pages labeling each section `[Page 1]`, `[Page 2]`, … in captions |
| **D - Helper crops** | Small crops from a larger page to aid legibility of text or a detail | Supplementary views of their parent page only - not independent pages or sources |

**Processing a variation group:** when a group is detected, `fha process` surfaces it with a confirmation prompt:

```
Found 3 files that appear to be variations of the same photo:
  portrait_1880.jpg        [primary]
  portrait_1880_back.jpg   [role: back]
  portrait_1880_bw.jpg     [role: bw]
Process as ONE source (shared S-id) or separately?  [one / separate / skip]
```

On one: a single S-id is minted. The photos stay exactly where they are - names and locations unchanged. The root photo is flagged as `is_primary=true`. The source record's `files:` inventory lists each file at its existing path with a role annotation:

```yaml
files:
  - file: photos/1880/portrait_1880.jpg
    role: primary
    is_primary: true
  - file: photos/1880/portrait_1880_back.jpg
    role: back
  - file: photos/1880/portrait_1880_bw.jpg
    role: bw
```

The `SOURCE: S-xxxxxxxxxx` keyword is written into each file's embedded metadata via exiftool so identity travels with the file if it moves. That is the only write to the files themselves - content and filename are untouched.

On separate: each is processed as its own source. If one is clearly a derivative of another, a provenance note is suggested. On skip: deferred to the next session.

The role annotations in `files:` are the only thing binding the variants - role lives in the record and the embedded `SOURCE:` keyword, not the filename. This is the opposite of documents-root files, which do carry the S-id in the filename precisely because they can be renamed; photos cannot be, so the record carries the meaning instead. The `photo_groups` index table caches the grouping for fast "show me all variants of this photo" queries.

(1) mint S-id; (2) mark identity - **documents root:** rename to `{slug}_{S-id}.{ext}` in place (record `original_filename`) - except a file sitting at the documents root TOP level (the flat inbox relocation, or a hand-drop at the root), which renames into `documents/{type}/` instead, the same destination bundles always used (owner decision 2026-07-22: routine intake must not pile everything into one flat folder; a file the human pre-filed into any subfolder keeps its place - SPEC §12.1, folders are the human's projection); **photos root: NEVER rename** (Lightroom catalog integrity) - keyword only; (3) `exiftool -keywords+="SOURCE: {S-id}" -overwrite_original_in_place` where the format supports keywords; (4) scaffold `sources/{type}/{slug}_{S-id}.md` from the §14 template, inventory pre-filled, empty `## Claims`; (5) print the path. `--more FILE role[:copy]` attaches versions.
Refuses files already carrying an S-id (filename or keyword).

**Refile - the cross-root correction (SPEC §12.1 carve-out).** Moves one of a source's files to the other asset root when the original filing decision was wrong. The record is located by S-id tree scan (never the index); the file to move is the inventory's single non-derived entry, or `--file NAME` when the record lists several (`derived: true` companions move only when named explicitly, never by default); already-under-the-target-root refuses toward `fha reconcile`. Going **into photos**, `--dest SUBPATH` is required (containment-validated inside the photos root, created if absent - the tool never invents photo-library organization) and the file takes its last-chance rename (recorded `original_filename` restored, else the `_{S-id}`/role/copy suffixes stripped), then the `SOURCE:` keyword is embedded - a missing exiftool or a non-photo format warns and proceeds, since the inventory still carries identity. Going **into documents**, the move breaks the external photo catalog's knowledge of the file, so it warns and confirms ([y/N], or `--yes`; non-interactive without `--yes` refuses); the file is renamed into the §13 grammar and lands in `--dest` or `documents/{type}/` (the M11.2 convention); the embedded keyword is deliberately not stripped. **`--type TYPE` carries the source's type across with its file:** `source_type:` is rewritten value-exactly and the record file itself moves to `sources/{type}/`, planned before any byte moves (a collision at either destination refuses with the archive untouched) and undone by the same reverse-order rollback. It is **required** going into documents when the record is still typed `photo`, because the type is then wrong by construction - a scan that leaves the photo library is not a family photo - and the default destination would otherwise be a `documents/photos/` folder invented for the purpose; the refusal names the flag and an example, and `--dry-run` prints the identical refusal. `--type photo` on that same move is honoured as a deliberate choice (the record keeps its type and its place). Both directions rewrite the one inventory `file:` line value-exactly (the reconcile matcher discipline), append a dated provenance paragraph to `## Notes` (naming the re-type when there was one), preserve the record's line endings, and are transactional with reverse-order undo; `--dry-run` previews every step. Follow-ups printed: `fha index` and `fha photoindex`. Exit codes: 0 ok/dry-run · 1 not-found/working-copy · 3 refusals. Out of scope by design: same-root moves (reconcile's domain).

The deterministic command is Stage A of the **process pipeline**; Stages B (AI draft: read the file incl. vision, resolve names/places against the index, draft `suggested` claims with anchors, pull `## Stories`) and C (review) are the `process-source` and `review-claims` skills (§16).
Lint E012 for photos checks keyword↔inventory agreement (no filename carrier).

## 6a. `fha media` - dedupe and container probe for incoming recordings

`fha media dedupe FILE [FILE...] [--root PATH] [--json PATH] [--quiet]`
`fha media probe FILE [--root PATH] [--json]`

Two read-only verbs (issues #43, #44) that answer a question *before* `fha process` files something - which is why they sit beside it rather than under their own top-level section. Neither renames, moves, deletes, or embeds anything; `fha process` is still the only thing that writes. Both retire an `import-recordings` skill owner exception (`_STANDARD.md` §6) - see that skill's `GAP.md` for the closed-gap record and `.claude/skills/import-recordings/scripts/find_duplicate_media.py`, the hardened interim script whose coverage-walking and dedup logic this module ports rather than re-derives.

**`fha media dedupe`** content-hashes each incoming file against everything already filed under the archive's `documents`/`photos` roots (`_lib.get_roots`/`resolve_path`, not a hand-rolled reader - an external root is found the same as everywhere else in the suite). Size-compare first (read straight off the directory entry, nothing opened), SHA-256 only on a size collision. `new` is a **coverage statement**, not a search result, and it takes all five of the following holding at once - anything short of any one is `indeterminate`, never `new`:

1. **Roots** - every media root `fha.yaml` names was resolved and is readable right now. A root the config *names* and the disk lacks is a coverage gap (drive unplugged, folder renamed), distinct from a default alias the config never mentions (an ordinary young archive).
2. **Enumeration** - every file under every root was listed: hidden folders and folders behind a directory symlink included, each folder visited once (a followlinks walk with a `(device, inode)` loop guard).
3. **Domain** - the same audio/video extension rule applies to both sides; a path named on the command line that falls outside it is reported as not checked, never given a verdict. "Archived" means **filed** - the inbox is staging even when SPEC §12.4 lets it sit inside a media root, so a file waiting there is never "already filed."
4. **Candidates** - every same-size archived file was opened and hashed; one that could not be read leaves the question open.
5. **Batch** - the incoming files are compared against each other too, so one sitting exported twice under two names yields exactly one `new` and the rest `duplicate … in the same batch`.

Two consequences follow: a file handed to the verb that already lives in a media root is the archive's own copy, reported `duplicate … already filed`, never cleared; and the verb must never answer a *smaller* question in the same words - there is no folder-narrowing override, unlike the interim script's `--media-root` (dropped: the real verb always resolves the archive's configured roots).

**Exit codes are a bespoke four-code ladder** (GAP.md's contract, not the suite's usual 0/1/2/3 = clean/warnings/errors/failure meaning): 0 = every incoming file was checked against every candidate and none matched; 1 = usage or configuration error (bad path, unparseable `fha.yaml`, a configured root that is not there); 2 = at least one incoming file is byte-identical to a filed recording or to another file in the same batch (a clean "found, nothing to do" answer, not a failure); 3 = the check could not be completed for at least one file, so nothing in the run is cleared for import.

`--json PATH` also writes the findings as a report file - alias-form paths only (`documents/…`, or `incoming/…` for the bundle being checked), never an absolute machine path. That path is canonicalised and the run refused **before the first byte is hashed** if it would resolve onto an incoming recording, an archived one, `fha.yaml`, or anywhere inside a media root - a read-only tool's one way to break its own promise is a report written last, over a file it has already cleared as safe to import.

**`fha media probe`** reads a recording's true duration and container `creation_time` (`ffprobe` primary backend - optional dependency, reported by `fha doctor` the way exiftool is; PyAV fallback when `ffprobe` is absent, the same library `transcribe-audio`'s `transcribe_audio.py` already uses) and derives the local start time, following the same rule the interim `ffprobe` + manual-arithmetic enactment used (SKILL.md step 4): QuickTime/MP4 writes `creation_time` in **UTC at the moment recording stopped**; an app-written filename clock names **local time at the moment it started**. So `local_start = (creation_time + offset) - duration`, and the offset is never guessed - it is reported alongside where it came from:

1. **`com.apple.quicktime.creationdate`**, when the container carries one - local time *with* its own offset, naming the same instant as `creation_time`. Settles the question outright.
2. **The filename clock, solved for the offset** - `offset = filename_time + duration − creation_time`, rounded to the nearest quarter hour; a fit missing by more than a couple of minutes is rejected as unsolved, not forced.
3. **Neither** - the verb reports `offset_source: none` and says so plainly. It never falls back to the machine's own timezone or to the file's filesystem mtime (a fact about the file, not the recording); asking the human is left to the skill layer, since the verb cannot ask a question.

Flags `crosses_midnight` when the derived local start's calendar date differs from the UTC date. Ordinary 0/1/2/3 exit ladder: 0 = offset settled, local start reported with confidence; 1 = duration and `creation_time` read but the offset could not be established; 2 = the container carries no usable creation timestamp at all; 3 = tool failure (unreadable file, or neither `ffprobe` nor PyAV available).

Registered in `fha.py`'s `COMMANDS` as the `media` subcommand group, the same pattern `fha confirm`/`fha gedcom` use for their own sub-subcommands. Implementation status: `tools/README.md`.

## 7. View generators - `fha views`

Timeline and draft-queue write GENERATED-headed `.md` companions into the tree; all views derive purely from the index. The per-person forms of timeline and draft-queue skip a stub person with a plain note (exit 1) - companion views are curated-person files (SPEC §16), and the guard lives in the tool so no caller has to remember it. **`sources-index` is the one exception to both of those (#76):** its per-person form no longer writes a companion file at all - it rewrites the profile's own `## Sources` GENERATED-BEGIN/END region in place (SPEC §16, §21b) - and it does NOT skip a stub or misplaced-curated person, because the issue this shipped for is exactly "a stub should not need its sources list rebuilt again the moment it is promoted." Only its couple-folder form (`--couple-folders`) still writes a separate `sources-index.md` companion, unaffected by any of this. The three content views (timeline, sources-index, draft-queue) and `refresh` also take **`--format md|html`** (default `md`; `refresh` additionally accepts `both`): `html` renders the same content as a standalone single-file page under `generated/views/` - see design decision D11 below for the conventions. `sources-index`'s per-person form refuses `--format html` outright (there is no companion file to render standalone into; see below), so `html`/`both` cover only timeline, draft-queue, and the couple-folder sources-index.

- **`fha views timeline [P-id|--all-curated] [--format md|html]`** → `…_timeline_{P-id}.md`: accepted + needs-review claims for the person, sorted by `date_min`, grouped by decade, each line `EDTF - type: value [[S-id]]`, suggested claims listed in a trailing "unreviewed" section. A not-yet-settled line carries a plain-word tag at its end: `[unconfirmed - parked {date}]` on a needs-review claim (bare `[unconfirmed]` when it carries no `reviewed:` date yet - the parked verdict, SPEC §8.1), `[low confidence]` on an accepted claim with low confidence (SPEC §8.5) - the private research artifact keeps the unsettled material visible, tagged, where the published site (§12) is accepted-only.
- **`fha views draft-queue [P-id|--all-curated] [--format md|html]`** → `…_draft-queue_{P-id}.md`: accepted claims whose source is not cited in the profile body - the writing backlog. Consumed by the `write-biography` skill. See §14b for the full design.
- **`fha views tree <P-id> --mode ancestors|descendants|fan [--generations N] [--format json|dot]`** → traverses the `relationships` edges from the person. `ancestors`: parent-edges recursively (pedigree). `descendants`: child-edges recursively (the v1 hero - "all descendants of T.E."); spouse edges are added as one-hop leaf nodes per visited descendant (in-law branches appear as connected nodes without recursing into their own lineages). `fan`: the person plus kin plus social edges, two hops by default; `--generations N` overrides the hop depth. All modes use BFS with a visited-set cycle guard. Every node carries its `[[P-id]]` (→ links to the person page) and every edge its source `claim_id`. Output is **the neutral tree JSON** - the stable data contract (nodes: `{p_id, name, vitals, sex}`; edges: `{type, from, to, claim_id, subtype, genetic, dates}`) - or GraphViz DOT. Nodes and edges are deduplicated (by P-id for nodes, by `(from, to, type)` for edges). This JSON is what the spec pins down; the *rendering* of it (the site's vendored tree library, styling) is deliberately left to the build. A renderer adapter maps this neutral shape to whatever library is in use. **Node vitals field:** `{"birth": edtf_or_null, "death": edtf_or_null}` where each value is the `date_edtf` from the first accepted claim of the matching vital type for that person, or null if none. (D3) **Edge dates field:** `dates.start` / `dates.end` are populated only for spouse edges (marriage and divorce/death dates from the `relationships` table); all other edge types carry `null` for both. **Edge nature field:** `genetic` is `false` for a non-genetic parent/child bond (adoptive, step, foster, guardian, social) and `true` otherwise; an unset or legacy `subtype` defaults to genetic (SPEC §12.2), so a legacy tree is unchanged. `subtype` carries the raw nature string, or null. The site renderer draws a non-genetic edge distinctly (a dashed line); the relationship and bloodline answers stay genetic-only for numbering. **`--format html` for the tree remains a refusal:** the HTML tree ships with the site's full-tree feature, as a thin single-file wrap of that renderer (building it against the current per-person renderer would mean shipping it twice); until then passing it emits a plain error directing the user to `fha site`. The content views' `--format html` (D11) is unaffected. (D6)
- **`fha views sources-index [P-id|--all-curated|--couple-folders] [--format md]`** → every source with ≥1 claim naming the person(s), grouped by source_type. **Per person (2026-08, #76):** rewrites the profile's own `## Sources` section IN PLACE as a GENERATED-BEGIN/END region (`_lib.write_generated_region`) - a visible notice plus the grouped list, bounded by `<!-- GENERATED-BEGIN sources-index by sources-index on {date} -->` / `<!-- GENERATED-END sources-index -->` markers right where the human-authored `## Sources` heading already sits; nothing outside that span is touched. Works on a stub or a curated person parked anywhere, INCLUDING `people/stubs/` and a misplaced folder (deliberately NOT the usual per-person skip-a-stub guard other views apply, since the point is a stub's sources list is already current the moment it graduates - it never needs rebuilding on promotion). `--all-curated` still means curated-tier only, by its own name; it is the BATCH form, not a relaxation of the single-person one. Refuses `--format html` outright for a single `P-id`, and for `--all-curated` unless `--couple-folders` is also given (there is no per-person companion file to render standalone any more - the content lives inside the profile, whose own page is `fha site`'s job, not a private research artifact's; `--all-curated --couple-folders --format html` is still fine, since it runs only the couple-folder pass, which does have an HTML twin). **Per couple folder (`--couple-folders`, unaffected by any of the above):** still a separate companion file, `sources-index.md` at the folder root (no P-id - the folder is its context), with paths; its HTML twin prefixes the folder name (`generated/views/{folder}_sources-index.html`) because every couple folder shares that `.md` stem. The couple-folder pass runs whenever either `--all-curated` or `--couple-folders` is given (`--couple-folders` narrows a batch call to ONLY that pass, skipping the per-person one; it adds nothing when combined with `--all-curated`, since that pass already includes it). Freshness: the per-person write stales-then-immediately-resyncs the index rather than sitting outside the watermark (D9 addendum above); the couple-folder write is an ordinary companion, watermark-excluded like timeline/draft-queue.
- **`fha views brackets`** → folder maintenance for the `people/` tree, covering four concerns in one pass (all previewed; `--fix` applies 1-3, `--fix-promote` applies 4, `--realign` applies all four together - see below):
  1. **Bracket lists and the couple name** - refresh stale `[child, …]` annotations in couple-folder names from accepted `relationship` claims, marking a child who joined other than by birth (`(adopted)`, `(step)`, `(foster)`, …) so a shown-but-not-numbered child reads clearly, and adding cross-link entries for any occupant who homes to a lower-numbered folder (`Thomas Hartley (also #128 - see 040)`). The same pass proposes adding the missing **`+ second spouse`** half of the folder's base name (SPEC §12.2's illustrated convention; a promote-created folder starts with one partner's name) - strictly **add-only**: it fires only when the folder's derived couple has exactly two members, the base carries no `+` yet, and the text after the prefix exactly matches one partner's recorded name; an existing `+ …` half (even a hand-written nickname) is never rewritten, and a hand-crafted base matching neither/both partners is never guessed at (`_lib.spouse_extended_base`, shared by lint and views). (W103)
  2. **Ahnentafel numbers** *(requires `root_person` in `fha.yaml`)* - derive each direct-line couple's correct number by walking accepted, non-negated **genetic** parent edges (`subtype: biological` [default], `surrogate-genetic`, `donor-sperm`, `donor-egg`) outward from `root_person`, seeded at the position `root_generation` names (`self`, the default - `root_person` IS #1, today's behavior unchanged; `children` - `root_person` is #2, and #1 is left to `root_person`'s own children, collectively, SPEC §12.2 - issue #72; an unrecognised value is rejected, W129, rather than silently read as `self`) - the edges a `relationship` claim's `roles:` map records, and since #71 a `birth` claim's too, since "born to X and Y" is the same fact written the way a register writes it; social and legal parent edges are skipped for numbering but listed in the bracket annotations. The parent with `sex: M` takes position 2n, `sex: F` takes 2n+1; for same-sex or `sex: U` pairs the first-encountered parent (by P-id, deterministic) takes the lower slot. Where two genetic contributors share a role (a `surrogate-genetic` and a `donor-egg` mother), the genetic contributor anchors the number and the other is shown beside it. Report folders whose numeric prefix disagrees with the derived number; with `--fix`, rename. (W110) One case gets its own report-only note: when a couple has exactly ONE resolved parent and that parent's `sex:` is unrecorded, the even slot is a **default, not a derivation** - a completely normal early-research state that nevertheless produces a confident-looking folder number W110 can never dispute (the folders match their own flawed derivation). That placement is surfaced as **W120**, naming the person, the defaulted slot, and the one-line fix (record `sex: M`/`sex: F`, re-run the check). Two resolved parents with unset or matching sex stay silent - that is the genuine same-sex/unknown case the deterministic tie-break exists for. W120 fires in both `fha lint` and `fha views brackets`; no fix flag touches it, because the missing fact is the human's to record. A second report-only note rides the same pass: **W127**, the one thing this walk cannot check by comparing folders to numbers, because it is about where the walk STARTS. A `root_person` with a genetic child on record while `root_generation` is `self` is anchored a generation too high (SPEC §12.2 puts #1 at the youngest generation), so every number derived here - and every folder `--fix` or `--realign` renames from them - is one generation off while W103, W110 and W119 all report clean, since the folders match this same walk. Silent the moment `root_generation: children` is set (#72): that field says a child on record is deliberate, so there is nothing accidental left for W127 to catch - it exists for the case where the shift was NOT intended. Like W120 it fires in both `fha lint` and `fha views brackets`, takes no fix flag, and names the human's repair: add `root_generation: children` to `fha.yaml` (keeps `root_person` naming the same person) - or re-anchor `root_person` to a child directly - then `fha index` and `fha views brackets --realign` (the reindex first, because editing `fha.yaml` stales the index and `--realign` refuses on a stale one).
  3. **Person file placement** *(requires `root_person`)* - report direct-line person files (all companion kinds: profile, research, timeline, draft-queue - sources-index is no longer one of these since #76, see §16/§21b: the per-person list now lives INSIDE the profile, so it moves with it automatically and is never separately placed or misplaced) living in the wrong couple folder; with `--fix`, move them to the correct folder, creating it when absent. Non-direct-line occupants (siblings, half-siblings, connections) are never moved. A person derived at several positions is placed in the **lowest-numbered** couple folder; the higher positions are emitted as bracket cross-links in their folders, not as moved or duplicated files. With `--fix`, placement follows the lowest-number home rule deterministically. (W110)
  
  4. **Direct-line stub promotion** *(requires `root_person`)* - report any person with a derived Ahnentafel position ≥ 2 whose record is `tier: stub` or lives under `people/stubs/` - a direct-line ancestor still filed as a stub, worded as a lead, never a defect. `--generations N` narrows to positions within N generations (1 = parents). Report-only by default; with `--fix-promote`, batch-apply the shared promote engine (`_lib.promote_person_record` - tier flip, §16 body-section backfill, couple-folder move, optional research-companion move; the same engine behind `fha person promote`, §3c, never a research-file scaffold since #76) under the existing preview + `Apply? [y/N]` gate, each person transactional on its own, then drop the index cache and advise `fha index` + `fha views refresh` for the new curated people's companions. When a brand-new couple folder must be invented and BOTH partners are in the batch, it is named for the couple from the start (`004 Robert + Jeanne`, even slot first); a folder created for one partner alone keeps the single name and check 1's spouse rule adds the other once both are curated there. A partner with no recorded name (`name: unknown`, the `fha stubs` mint) is left out of the folder name on EITHER side: when only the odd-slot partner is named, that name becomes the temporary base (`004 Jeanne`), because `004 unknown + Jeanne` already carries a `+` and check 1's add-only rule would never repair it once the unnamed person is named. Only when neither partner is named does the placeholder stand, exactly as promoting one unnamed stub does today. `--fix` and `--fix-promote` are refused together (a folder rename would invalidate the promotion destinations computed in the same pass); run them as two passes, or use `--realign` below. (W119)

  5. **`--realign`** - the whole-tree recovery verb: everything checks 1-4 found, applied in ONE previewed pass. One combined preview (the renames/moves and the promotions together), one `Apply? [y/N]` gate, then the fix half runs first and the promote half second, each person still transactional with rollback, one cache drop, one `fha index` + `fha views refresh` reminder at the end. The promotion destinations are **recomputed against the post-rename tree** (`views._realign_promotion_dests`): a folder about to gain a different prefix stops attracting the promotions computed against its old prefix (it was misnamed - that is why it is being renamed), while a folder renamed with its prefix intact carries its promotions with it; if two folders would share one couple prefix after the renames, the run refuses rather than guess. Refused in combination with `--fix`/`--fix-promote` (it subsumes both). This is the standing answer whenever the derived tree may have drifted from the promoted folders - a re-anchored `root_person` (edit `fha.yaml`, then `--realign --dry-run` to see the whole shift), a corrected `sex:`, a newly accepted parent claim, a merge. A folder freshly created by the promote half still gets its bracket list on the NEXT pass (a promotion names folders, never brackets them), so full convergence can take one follow-up run - the output says so.

  Every rename/move path preflights the WHOLE plan before its first mutation: folder-rename destinations and file-move destinations together (`views._bracket_fix_conflicts`, which reads each move's destination back through the pending renames, since the folder it lands in may not exist yet). A destination that is already occupied refuses the entire pass - before the `Apply? [y/N]` gate, and identically under `--dry-run` (exit 3, nothing written) - because applying the folder renames and then skipping the blocked move (and, in `--realign`, every promotion after it) leaves a command sold as one whole-tree pass half applied. The same preflight refuses a plan whose renames would leave TWO couple folders carrying one number (a couple filed in two places, each claiming the number from its own occupant): that tree is the ambiguous-prefix one the next run refuses to read at all, so it is named as a merge-by-hand before anything moves.

  If any rename or move in the fix half fails non-fatally (a folder open in another program on Windows), `--realign` skips the promotion half and says so: those destinations assumed the renames had landed, and promoting into them would create the never-renamed folder beside the old one - a couple split across two same-prefix folders. Resolve the failure and re-run.

  All three fix flags share one `Apply? [y/N]` gate; **`--yes`** skips it for scripted or non-interactive runs (a harness with stdin closed used to read EOF and abort - safe, but unusable). The full preview still prints, so the audit trail is the same; without `--yes`, EOF still declines.

  When `root_person` is absent from `fha.yaml`, checks 2, 3 and 4 are skipped with an informational note. Renaming folders and moving person files are both safe: folder names and paths carry no machine meaning - the `P-id` in each filename is the identity.

- **`fha views clean [--root PATH] [--dry-run]`** - delete all GENERATED-headed view files, in two sweeps under one rule: companion `.md` files from the `people/` tree (timeline and draft-queue for every person, sources-index for every couple folder), and single-file `.html` views (plus any stray `.md`) under `generated/views/`. Uses the `<!-- GENERATED … -->` header as the sole deletion signal, **file by file** (marker-per-file, never folder ownership - a hand-written file parked in `generated/views/` survives); never touches profile, research, or manually authored files. **A profile's own `## Sources` region is never touched either (#76)** - it is not a whole file `views clean` can see as a deletion candidate at all, only a region inside one (SPEC §21b); there is nothing to sweep, and nothing regenerates it but `fha views sources-index`/`refresh` running again. A pre-#76 archive's leftover PER-PERSON sources-index companions (`…_view_sources-index_P-xxxx.md`) are still swept here like any other GENERATED-headed file - `views clean` recognizes them by header regardless of what current tooling still writes. `--dry-run` lists both sweeps without writing. A people/-tree companion's index rows (its `person_files` entry and its body in `notes_fts`) are deleted in the same pass, so the sweep exits 0 clean; `generated/views/` files are never indexed and need no cleanup. Exit 1 only when something is left for the human: a file that would not delete, or would not READ (ownership is decided by its first line, so an unreadable file is unknown rather than not-ours - locked or read-only, named, skipped, the rest of the sweep still runs; `data['failures']` / `data['unreadable']`), or a row cleanup that failed (the reindex note, `data['index_stale']`). Primary uses: compacting the archive for sharing (generated files are reproducible bulk) and resetting before a full `fha views refresh`.

- **`fha views refresh [--format md|html|both] [--root PATH]`** - regenerate all content views for every curated person and every couple folder in one shot: runs `timeline --all-curated`, `draft-queue --all-curated`, and (for `md`) refreshes every curated person's own inline `## Sources` region **plus** the couple-folder `sources-index.md` files - the same two passes `sources-index --all-curated --couple-folders` runs, just called directly rather than through that CLI surface, since the inline per-person write has no `--format html` twin to also drive. `--format html` regenerates the standalone `generated/views/` set instead (timeline, draft-queue, and the couple-folder sources-index only - nothing per-person, since that view has no HTML form any more); `both` writes the `md` set (inline regions included) and the `html` set in one pass (default `md`). Requires a fresh `.cache/index.sqlite`. One person's failure (a hand-written file in the way, a folder the index no longer finds) warns and skips that file rather than aborting the pass - and the run then exits 1 with `data['skipped']`, because a partly-regenerated set must not report success. Every `.md` companion written keeps its own index rows current (see D9), and every refreshed profile's `## Sources` region keeps ITS row current the same way (D9 addendum); if either update fails the run exits 1 with `data['index_stale']`, because #37 keeps the watermark silent and nothing else would ever notice.

**Design decision D11 (implemented 2026-07, usability wave): single-file HTML views.** Timeline, draft-queue, the couple-folder sources-index, and `refresh` render HTML from the **same queries and the same line rendering** as their `.md` twins - the HTML serializer re-renders the finished `.md` lines, so the two formats cannot drift in what they say. (Per-person sources-index is the one exception since #76 - it has no `.md` companion to twin any more, only an inline profile region, so it has no HTML form either; see above.) HTML views are private research artifacts, not site pages (`fha report --format html` is deferred by owner decision - it is agent-facing, not print-facing). These conventions bind **every fha single-file HTML artifact** (the photo gallery inherits them verbatim):

1. **Marker placement** - `<!-- GENERATED by fha <tool> <subcommand> on <date> - do not edit; regenerate instead -->` is **line 1 of the file, before `<!DOCTYPE html>`** (a comment before the doctype is valid HTML and does not trigger quirks mode). Ownership is judged by `_lib.is_generated_text` (first non-blank line) - the same guard for `.md` and `.html` alike; the view writer refuses to overwrite any file without it.
2. **CSS** - one inlined `<style>` block: `design/view.css`, a curated ~5 KB subset of `design/styles.css` (§2 tokens, §3 base, §6 ledger table) with a **system font stack** - never woff2 data URIs, never a `<link>`. No external requests of any kind (no CDN, no fetch, no external `<script src>`); the page opens from `file://`, mails, and prints as one document.
3. **Banner** - private artifacts carry a visible one-line banner: *"Private research companion - generated from the archive; not redacted for publication. Share through `fha site` instead."* Views stay private-by-default and **unredacted** (SPEC §21 scope: views are not a public-output path; §8: public sharing goes through `fha site`) - mis-sharing is a deliberate act, not an accident.
4. **Naming / landing** - one self-contained `.html` per artifact under a visible `generated/<area>/` folder (views: `generated/views/{md-stem}.html`; the couple-folder sources-index prefixes its folder name). Any embedded data goes in a non-executable `<script type="application/json">` read from the DOM (the `_tree.html` pattern - `file://` has no network).
5. **Exit codes** - writes under `generated/` touch nothing the indexer scans, so HTML runs never stale the index and exit 0 clean with no reindex advice. A `.md` companion write exits 0 too (#37: generated companions are outside the freshness watermark - a real generated file, in the place the generators write it: under `people/`, carrying the GENERATED header, either P-id-named or the bare `sources-index.md` at a couple folder's root; a human file that borrows one of those names, or a `notes/sources-index.md`, is a record and keeps its vote) and updates its own index rows as it goes. A refreshed profile's inline `## Sources` region reaches the same exit-0-clean outcome by a different route (D9 addendum above): the profile was never on the watermark-exclusion list, so the write re-syncs `index.sqlite` itself rather than sitting outside its count. Two different outcomes, deliberately: no index to update is not this run's fault - it prints the ordinary "run `fha index` when convenient" reminder and stays exit 0; an update that FAILED leaves rows disagreeing with the files while the watermark keeps calling index.sqlite fresh, so it exits 1 with `data['index_stale']`, the same on a single-person run as on a batch.
6. **`[[ID]]` tokens** render as plain styled text (`<span class="cite">`), never links - a standalone file has nothing durable to link to, and views never read or link into `generated/site/` (owner decision: the standalone-file property wins over cross-linking).

- **`fha relate <P-A> <P-B> [--json] [--root PATH]`** - walks the typed relationship graph (nodes = persons, edges = accepted `relationship` claims, each tagged genetic-vs-social by `subtype` and directional by `roles:`). Returns two answers: the **blood relationship** - restrict to genetic edges (`biological`, `surrogate-genetic`, `donor-sperm`, `donor-egg`), find the lowest common ancestor(s), and name the tie by the generation/removal formula (Nth cousin M-removed, great-…-grandparent) - and the **shortest social path** - BFS over all edges, rendered as a chain of role-named hops ("your brother's friend's sister's father"). The two are reported separately, since they answer different questions. Output is the structured `Result` (`{a, b, blood: {relationship, common_ancestors, gens_a, gens_b}, any: {path, rendered}}`) per the headless core; the text formatter renders the sentences, `--json` serves a UI. A pure read query over the index (an absent index is a hard error, never a silent wrong answer); no schema change, no writes. Half/step/in-law rendering uses a small extensible label table in the renderer. *(`--include-hypotheses` to walk speculative edges is ⚑ deferred: the index derives only accepted edges today.)*

## 8. `fha packet` - person data dump

`fha packet P-de957bcda1 [-o out/] [--include-research] [--include-restricted] [--include-dna] [--no-photos] [--dry-run] [--overwrite]`

Gathers, as **copies**, into `packet_{surname}_{P-id}_{date}/` then zips:

```
README.txt        ← generated manifest + "derived export, not research data" disclaimer + date
profile/          ← person .md (+ research file only with --include-research)
timeline.md       ← freshly generated (needs-review entries tagged "[unconfirmed - parked {date}]",
                    accepted-low entries "[low confidence]" - a packet is family research
                    material, not publication, so unsettled claims stay in, marked)
sources/          ← every source record citing the person
files/            ← those sources' files (copied, original names kept)
photos/           ← ALL photos of the person (see below)
```

**Photo gathering** (the "all photos of grandma" requirement): union of (a) photos carrying the bare `{P-id}` keyword; (b) photos whose face-region/people tags match the person's `face_tags:` exactly; (c) `name`/`name_variants` matches - listed in the README as *name-matched, unverified*, counted at the variation-group level rather than per scan (the copied variants of a name-matched photo carry the caution even when the matched scan itself is off disk; a group tied to the person anywhere by P-id keyword or exact face tag is verified and never counted); (d) files of sources citing the person.
A photo `reconcile` has flagged `MISSING:` (§9) is the one member of a group that does not travel: a packet is a bundle of real files, so it is skipped, named in the README's missing-files list under the path it had (the prefix is internal bookkeeping and never appears in an export), and warned about with `reconcile` as the next step - while its still-present siblings ship and its own person tags still count toward the living-person caution.
Requires a fresh main index because privacy/source filters come from SQLite. Requires the photo index (§9); refuses with a clear message if it is missing/stale unless `--no-photos`.

**Audience: `fha packet` is a family/private research export, not a public publication format** - included materials may mention other living people.
Public sharing goes through `fha site --standalone` (or another exporter), which redacts living and unknown-living persons by default.
The packet README cautions name both `living: true` and `living: unknown` persons.

**Privacy enforcement:** `living: unknown` is treated as living.
Packet subjects with `living: true` or `living: unknown` are refused before any output is written; packets have no `--include-living` override.
Anything `restricted` is excluded by default (excluded sources listed in the README by ID and reason, never with their titles) unless `--include-restricted`, which opens plain restrictions on a source, claim, person, or name; the no-override types are honored regardless - `restricted: dna` stays excluded until `--include-dna` is also passed, and `restricted: by-request` is never included by any flag. A `restricted: by-request` person vanishes from packet content but keeps their folder number so the pedigree chain stays intact. A restricted name redacts to the person's unrestricted display name. Any *other* person in the packet's materials with `living: true` is named in a README caution.
DNA never included by default.
**A record the packet could not read is treated as restricted.** The `restricted` marker lives in the record file - the index carries it for sources only as a bare 0/1, and for persons not at all - so the decision is made by reading a file, and a failed read hands back exactly what an unrestricted record hands back. An unreadable **subject** profile is refused (`restricted-subject`, exit 3, nothing written); an unreadable **source** is excluded along with its asset files and named in the README by ID with the reason `could not be read`, never miscalled `restricted`. Both under every flag, because `restricted: by-request` is precisely what an unreadable record cannot rule out and it is the one type no flag opens. "Could not be read" covers four shapes, and only the first raises anything: a file that will not open or decode, frontmatter that is not valid YAML, frontmatter that does not parse to a block of fields, and - the shape that raises nothing and reports nothing at all - **a record with no frontmatter block**, whose empty `meta` reads exactly like a record carrying no marker. A frontmatter block that parses, even to no fields, is the record stating it carries no restriction, and is honored as such. Distinct from the claims-block guard, which is the narrower one: a source whose *claims* YAML will not parse has its record and its claims withheld while its asset files still ship, because its own frontmatter marker was read and passed.
Missing source asset files are listed in stderr and README.txt rather than silently dropped.
Existing same-name packet output refuses unless `--overwrite`; `--dry-run` previews checks and paths without writing.

## 9. `fha photoindex` - photo metadata catalog

**Purpose.** The photo library currently lives in photo organizing software (Lightroom); finding anything must not require opening the other software.
This tool scrapes embedded metadata for the entire `photos/` tree into `\.cache/photos.sqlite` - a disposable catalog making the library searchable in milliseconds.
**`photos_ignore:`** in `fha.yaml` (a list of fnmatch patterns matched against each path relative to the photos root, e.g. `- 'Flickr Export'`, `- '*.tif'`) keeps a subtree or file class out of the catalog entirely: a matching folder is pruned unwalked, a matching file is skipped, rows an earlier scan catalogued for them are swept out on the next scan, and the same patterns prune the freshness check (`photoindex_status`) - a change under an ignored subtree is not a reason to call the catalog stale, and the check must not walk the subtree the setting exists to skip. The setting itself IS a freshness dependency: the scan stores the settings it built from (the pattern set and the configured `roots: photos` value) in the catalog's `meta` row, and `photoindex_status` reports `stale` when either has changed since. Editing them moves no photo's mtime, so the watermark alone cannot see it, and neither direction self-heals - an added pattern leaves the newly excluded rows searchable, and a removed one leaves files whose mtimes predate the catalog uncatalogued forever while the status reads `fresh`. The commands name the setting that changed, so the rescan they ask for has a stated reason. A catalog scanned by a build older than the stamp has nothing to compare and is never reported stale on this ground; the next scan stamps it. This is the sanctioned way to keep a bulk photo-service export inside the root from drowning the scanned ancestor photos in triage - narrowing `roots: photos` is not (it orphans already-filed `files:` entries; §1 roots). `find`, `gallery` and `triage` also take **`--under PATH` / `--not-under PATH`** (relative to the photos root, or in `photos/…` alias form) to scope a query to, or away from, a subtree at query time, matched at the group level like every other filter.

**Update (#48, 2026-08): deletion detection.** The watermark mechanism above (D9's update, §4a) catches a modified or added photo/person/sources-photos record but not a deletion - nothing else's mtime rises when a file disappears. `photoindex_status` ORs a path-manifest check onto its existing watermark comparison: the photos-root half is built as a byproduct of the walk the status check already runs (no second pass over a root that can hold tens of thousands of files, #35/#41), the person-profile and sources/photos half is `_lib.photoindex_record_manifest`, and both are compared against `.cache/photos_manifest.json`. Every writer that touches `photos.sqlite` keeps that manifest current at the same cost discipline the cache rows already follow: `run_scan` (a full walk already happened) and `run_reconcile` (ditto, via `_on_disk_aliases`) replace/patch the photos-root half from what they actually saw on disk, never from the `photos.mtime` column - `tag-person` and `set-summary` do not update that column (only `photo_keywords`/`user_comment` are), so deriving the manifest from it would read a just-rewritten photo as "modified" on the very next check, a false staleness those two commands would have caused themselves. They instead stat the exact files they just wrote and patch only those entries.
The other `fha.yaml` setting this tool reads is **`originals_backup:`** (§13f): the two commands here that write into an original photo - `tag-person` and `set-summary` - keep one pristine copy of each file before writing to it, refuse the write when that copy fails, and warn once per run when the setting is absent.
(It reads *files*, never the external catalog: embedded metadata is the durable layer.
If a good open-source media browser is later adopted, it slots in at the interface layer; this catalog stays the scriptable surface.
Candidates evaluated in the owner's private tool log.)

**Scrape - the field set that matters** (batched `exiftool -j … -r photos/`, one process, JSON out, ~50-100 files/sec; incremental by `(path, mtime, size)`; `--full` rebuilds). A file exiftool cannot read (locked, empty, truncated) is reported and skipped, never fatal, and any prior catalog row for it is kept - stale metadata beats none. When such a file is *new or changed*, its current metadata never reached the catalog, so the cache's mtime is pulled back behind it and `photoindex_status` keeps reporting `stale` until a later scan reads it; the scan says so and names the fix. An unreadable file whose cached row still matches its `(mtime, size)` - the `--full` case - is as indexed as it can be and holds nothing stale, so one permanently damaged photo cannot pin the catalog out of date forever. A **folder** the walk cannot list is the same fault one level up and fails closed harder, because the incremental scan's other half deletes: "gone from disk" may only ever mean the walk reached the folder and the file was not in it. The walk therefore collects its own traversal errors (`os.walk(onerror=…)`), every cached row under an unlistable folder is held rather than swept - its keywords, face regions and person matches with it - the cache is pulled back behind the folder so the catalog keeps reading `stale`, and the run names the folders in plain words and exits 1. Deleting there would take photos still sitting on disk out of `find`, galleries and packets with nothing to say they were dropped; aborting the whole scan would let one changed permission bit stop the rest of the library being catalogued. The one thing still swept under such a folder is a row `photos_ignore:` excludes, since that answer never depended on seeing the files. `reconcile` follows the same rule from the other side: rows under an unlistable folder are held, never flagged `MISSING:`, because it decides "missing" by subtracting the on-disk listing from the catalog and an unlistable folder contributes nothing to that listing. The rule reaches one level past the photos root as well: `photo_people` is deleted and recomputed on every scan, and its `source-people` tier is read from the source records through `_lib.find_source_record` - which globbed `sources/**/*.md`, so an unreadable folder there returned "no such source", the tier read that as "this source names nobody", and the photo's people were deleted in a run that reported success. That lookup now takes an `unreadable` out-parameter; a non-empty list means incomplete, never empty, so the existing `source-people` rows are carried across the rebuild exactly as the weak tiers are under a stale index, the folders are named in `unreadable_record_dirs`, the cache is held stale behind them, and the run exits 1 saying in its own words that the photos are all there but who your sources say is in them could not be read:

| Field | Meaning in this library |
|---|---|
| `Title` | Usually null; set only when the photo's identity is unmistakable |
| `Caption` (Description) | **What is written in or on the photo** - direct transcription of contents |
| `UserComment` | **Contextual info** that may not be on the photo, incl. the pipeline's AI summary - the richest text field |
| `DateTimeOriginal` | The date's *value* (the pipeline's forced full `YYYY-MM-DD`, SPEC §20 rule 2). It resolves to `edtf` **only together with a `DATE:` precision keyword** (`Y!M!D?` + `1916:06:10` → `1916-06`); the keyword's presence is what marks a date as reviewed. A photo carrying an EXIF date but no keyword stays undated by design - unreviewed machine metadata (often the scan's own date) never enters the same field as confirmed fact. Within the keyword, SPEC §20 rule 1's grammar is read exactly: `!` confident, `~` best guess, **`?` and an omitted marker both unknown**. So `Y!M` + `1916:06:10` → `1916` (the month was never affirmed) and `YMD` → no date at all - promoting an unmarked component would make the forced EXIF value truth, which rule 2 forbids |
| `Sub-location` ("location") | Neighborhood / specific area within a city |
| `City` / `State` / `Country` | Place hierarchy as tagged |
| `GPS` lat/lon | **Authoritative when present** - logger-recorded or manually verified; never second-guessed, and a backfill source for `places.yaml` coords |
| `Keywords`/`Subject` | Incl. `SOURCE: S-…`, bare `P-…` person ids, `DATE:` patterns |
| Face regions | `XMP-mwg-rs` RegionInfo (the trickiest: structured regions object, parsed for names + areas) → face-tag strings |

**The letter form is the only `DATE:` form read** (archive-owner decision, 2026-08-16). SPEC §20 rule 1 defines the keyword grammar as per-component precision letters - `Y!M!D!`, `Y!M!`, `Y!M~`, `Y!`, `Y~` - and nothing else; the parenthesised `(1942-11-25)` in that table is a gloss on the resulting date, not a second syntax. A keyword carrying digits is therefore **not** a date the archive will read: a hand-typed `DATE: 1880`, the AI pipeline's digit-plus-marker form `DATE: 1942!-11!-25!`, and a raw EDTF string `DATE: [..1900]` all leave the photo undated. An owner may type whatever he likes into his own keywords; the system simply does not treat a non-spec form as evidence of a date. This is reported, never silent: the scan counts such photos as `nonspec_date_keywords` and prints a plain-language note saying they stay undated, what the letter grammar looks like, that the value comes from `DateTimeOriginal`, and how to fix one (rewrite the keyword in the letter form, set the capture date, rescan).

**Schema.**

```sql
CREATE TABLE meta(key TEXT PRIMARY KEY, value TEXT NOT NULL);  -- schema_version + build_config (the fha.yaml settings the catalog was scanned with)
CREATE TABLE photos(path TEXT PRIMARY KEY, mtime REAL, size INTEGER,
  title TEXT, caption TEXT, user_comment TEXT,        -- §field table above
  exif_date TEXT, date_pattern TEXT, edtf TEXT,       -- (letter pattern + exif_date)→EDTF via SPEC §20 table; NULL without a letter-form pattern
  sublocation TEXT, city TEXT, state TEXT, country TEXT,
  gps_lat REAL, gps_lon REAL,                         -- authoritative when present
  source_id TEXT,                                     -- from SOURCE: keyword
  group_id TEXT, is_primary INTEGER DEFAULT 0,        -- variation grouping (below)
  variant_copy TEXT, variant_role TEXT);              -- parsed from filename suffixes
CREATE TABLE photo_groups(group_id TEXT PRIMARY KEY, primary_path TEXT,
  edtf_resolved TEXT, date_conflict INTEGER DEFAULT 0, file_count INTEGER);
CREATE TABLE photo_keywords(path TEXT, keyword TEXT);
CREATE TABLE photo_face_regions(path TEXT, name TEXT, region_type TEXT, area_json TEXT);
CREATE TABLE photo_people(path TEXT, person_ref TEXT, via TEXT); -- via: pid-keyword | face-tag | name-match
CREATE VIRTUAL TABLE photo_fts USING fts5(path, title, caption, user_comment, keywords);
```

**Variation grouping.** Versions of one physical photo must index as **one logical photo**.
Group key, in priority order: (1) shared S-id (filename or `SOURCE:` keyword) - processed photos group by source; (2) same directory + same base stem after stripping the recognized suffix grammar `[-{copy}][-{role}]` (`b`, `c`,`-b`, `-c`, `-negative`, `-back`, `-front`, `-page-N`) - the pipeline's own naming convention; "text from alternate version" keywords corroborate a grouping but never create one (too fuzzy). (NOTE letter variations are not always started with a dash, they always appear as the last thing before any additional tags however.)
Grouping is conservative: never across directories, never on caption similarity.
The **primary** variant is, in order: a file with no variant/role/crop suffix at all (the plain scan), else the front of copy a, else the lexicographically first path - chosen among the variants still on disk, so a group whose plain scan has been flagged `MISSING:` leads with a file a human can actually open rather than with a path that is not there. A `MISSING:` row groups by the alias underneath its prefix, so a vanished variant stays attached to its own physical photo instead of being filed under a folder called `MISSING:photos`. Search results and the packet's photo gathering return *groups*, copying all variants but counting the photo once (`--files` exposes raw rows).

**Group data structure.** After grouping, each stem's entry holds the following slots (parallel to the `group_folder_images` output used by the photo pipeline, see §6 for the parsing algorithm):
- `primary` - `{front, back, front_crop, back_crop}`: the main front/back scans and their `-crop` detail images
- `variants` - ordered list of `{version, front, back, front_crop, back_crop}`: version-letter (a, b, c…) alternates and their crops
- `pages` - `{page_num → path}`: multi-page document pages keyed by integer
- `page_crops` - `{page_num → path}`: crop detail per page number
- `negative` / `negative_crop` - scan of the physical film/glass-plate negative and any crop of it

Negative grouping rule: negatives are stored at the stem level regardless of any variant letter in their filename - a negative is source material for the root image, not an A/B variant of the print. For page sets, `all_fronts` is the sorted page list and `all_backs` is all-None; `photo_groups` in the schema caches this structure for "show me all variants" queries. The `photos.variant_role` column holds the compound role value (`front`, `back`, `front-crop`, `back-crop`, `negative`, `negative-crop`, `page-1`, …).

**Group date resolution.** Each variant may carry its own `DATE:` pattern and EXIF date (different backs say different things - that is evidence, not noise).
The group's `edtf_resolved` is the **best-confidence variant's** EDTF: score by number of `!` components (D > M > Y), then `~` over `?`; deterministic tie-break by path. Only variants carrying a letter-form `DATE:` keyword carry a date (above), so an EXIF-only back scan - or one keyworded in a non-spec form - contributes nothing and can never manufacture a conflict against a reviewed front. A group all of whose variants are undated has `edtf_resolved = NULL` and `date_conflict = NULL`: it falls to the gallery's Undated tail, answers no `--edtf` query, scores no confident-date triage signal, and is not a `report` conflict. A variant flagged `MISSING:` by `reconcile` contributes no date either - a group must not keep reporting a date, or a conflict badge, that only a file no longer on disk carried - though it stays a member of its group, keeping its caption and keyword history attached to the physical photo it belongs to.
If any two dated variants' EDTF bounds (per §1 `edtf_bounds`) fail to overlap, set `date_conflict = 1` - and `fha photoindex report` lists all conflicted groups, because a date disagreement between the front and the back of the same photo is a research finding worth a question, not a value to silently average. `date_conflict` is three-state: `NULL` when fewer than two variants are dated ("nothing to compare"), so an undated library can never read as "no conflicts"; the scan summary reports the dated-group count alongside the conflict count for the same reason, and `nonspec_date_keywords` beside them so a library keyworded the wrong way reads as undated *with a reason*.
Person/keyword attributes aggregate as the union across variants.

`photo_face_regions` caches XMP region names, region types, and the provider-specific area object as compact JSON. This table is scraped metadata, not a derived query table: it lets `photo_people` be rebuilt when the person index changes without re-reading unchanged image files through exiftool. Existing otherwise-compatible caches that predate this table are not considered fresh; the next `fha photoindex` run backfills face regions. Older incompatible or corrupt `photos.sqlite` files are disposable and may be recreated from the photo files.

`photo_people` resolution is rebuilt from cached `photo_keywords` + `photo_face_regions` on every scan. Confidence order: (1) bare `P-…` ID keywords (regex `^P-[0-9a-hjkmnp-tv-z]{10}$`, case-insensitive) → `via=pid-keyword`, authoritative; (2) cached face-region/people-tag strings matched **exactly** against person records' `face_tags:` → `via=face-tag`; (3) `name`/`name_variants` matches → `via=name-match`. Caption/comment-only person hints are deliberately not inserted into `photo_people` in the scan phase; they remain triage/query signals for later photoindex commands.
A tag string matching multiple persons is **ambiguous**, never guessed - surfaced for tag-person resolution. **`fha photoindex tag-person <P-id> [--from-face-tag "X" | paths…]`** writes the bare `P-id` keyword (via exiftool, previewed list first) across a face-tag match or onto specific photos - making identifications in-file durable and settling same-name collisions.

**`fha photoindex set-summary (<path> | --group <group-id>) --text "…" [--append] [--dry-run]`** writes a photo's embedded AI summary (`UserComment`) via exiftool - the caption-improvement write SPEC §20 rule 5 already sanctions. `<path>` writes one catalog file; `--group` writes every member of the variation group, so fronts/backs/copies stay consistent. The compose rule fails toward preservation: new text is always written AI-marked (`AI: <text>`, the `^(AI|Model):` convention triage already recognizes); an existing AI-marked comment is replaced (`--append` keeps it and adds the new block below); a mixed comment - human text ending in a blank-line-delimited trailing `AI:`/`Model:` block, the shape this command itself writes - keeps the human prefix verbatim and replaces only that trailing AI block (`--append` keeps it and adds the new block below); any other unmarked comment is human text - preserved verbatim with the AI block appended below, flag or no flag; anything not clearly delimited as a trailing AI block counts as human. The human-caption fields (`Caption-Abstract` / `XMP-dc:Description`) are never touched. Preview plus `[y/N]` confirm like tag-person (`--dry-run` shows old → new per file and writes nothing); requires a **fresh** photoindex (a stale cache could address the wrong file for a mutating write - hard block, not a warning); refuses in working-copy mode (§13d). The cache (`photos.user_comment` + `photo_fts.user_comment`) is patched in the same call for the paths that wrote, so `fha find --text` sees the new summary with no rescan. Exit 0, or 3 when any per-file read/write fails (partial success reported per file).
**Reconciliation - `fha photoindex reconcile` (and the general `fha reconcile`).** Because assets are organized by moving files (and other systems rename them), the on-disk reality drifts from the index's stored paths.
Reconcile compares disk to index across all asset trees: files whose path still matches → untouched; a stored path now missing on disk → **re-match by embedded ID** (`SOURCE:` keyword for photos, filename S-id for documents) and, on a hit, update the stored path silently; files on disk that the index doesn't know → log as new (and, if they carry a `SOURCE:`/S-id, attach to the source's inventory).
Anything unmatchable is reported for human attention - kept in the catalog under a synthetic `MISSING:` + last-known-alias key, so its caption, keywords and dates stay searchable. Marking a row `MISSING:` (or re-matching one) re-derives its group's primary file and resolved date from the members that remain, by the **same functions the full rebuild uses** - the tie-break that puts the primary's date ahead of an equally confident sibling's, and the choice of primary itself. Two implementations of one rule is a divergence waiting to happen, and it happened: ordering by filename here and primary-first there meant flagging an unrelated third variant missing changed a group's `edtf_resolved`, and the next full scan changed it back, so a date filter or a gallery heading depended on which maintenance command had run last. That key is bookkeeping about a path, not a different path: everything that reasons about WHERE a photo was reads the alias underneath the prefix (its variation group, and the `--under`/`--not-under` subtree filters, which must be able to include a missing variant of the folder asked about and exclude its group), while everything that would OPEN the file - gallery tiles, `tag-person`, `set-summary` - refuses on the prefix and names `reconcile` as the next step.
This is why folder location is never truth: identity rides in the file (keyword/ID), and paths are a refreshable cache.
Runs incrementally; folded into `fha doctor` and the report's freshness step. Whenever a run leaves files on disk that the catalog does not reflect - untracked new files, rematched paths whose content was never re-scraped - the cache's own mtime is pulled back behind the oldest of them, so `photoindex_status` keeps reporting `stale` instead of calling a knowingly incomplete catalog current. The scan applies the same rule to a file exiftool could not read (see **Scrape** above). That pull-back IS the signal, so a pull-back that fails (a read-only `.cache`, a mount refusing `utime`, a photo root unplugged since the commit) is reported, never swallowed: `stale_hold_failed` in the result, exit 1, and a plain message naming `fha photoindex --full` - the one rebuild that does not consult the marker. Left silent, the catalog would read `fresh` to every later `find`/`packet`/`site` while missing the very files the run knew about. **`fha reconcile`** (built 2026-07-22, BUILD.md M11.1) applies the same disk↔record path-healing to every file type in one command: the documents side re-matches a record `files:` entry whose path no longer resolves by its `_{S-id}` filename anywhere under the documents root - a unique hit rewrites the entry line-surgically, a duplicate name is ambiguous (reported, never guessed), and on-disk S-id files no record lists are reported with the `fha process --more` attach path - then the photos side runs this section's `photoindex reconcile` machinery when a catalog exists. `--dry-run` previews every re-tie; working-copy mode is a clean no-op, and an unreachable documents root warns without mass-flagging. This is what makes SPEC §12.1's "folders are projection" true across time: rearrange the documents tree in any file browser, run `fha reconcile`, done.

**Query.** `fha photoindex find --person P-… | --keyword … | --edtf 192X | --text "…" | --under PATH [--not-under PATH]` → paths (filters AND together at the group level when combined - a filter matching any variant matches the whole logical photo, so a date on the front scan and caption text on the back still count as one hit). `--person` must be a P-id and `--edtf` must be valid EDTF; bad input is reported, not silently treated as match-all. Default output dedupes matches to one row per group (`primary_path`); `--files` returns every raw row of each matched group instead (including sibling variants that didn't themselves match a filter). Requires `.cache/photos.sqlite`: absent/unreadable (including a present-but-incompatible schema) is a clear error (exit 3); stale still queries but warns.

**Gallery.** `fha photoindex gallery --person P-… | --keyword … | --edtf 192X | --text "…" [--out FILE]` turns the same query into one throwaway, self-contained HTML page you open with a double-click - a private "fake file browser" over the real photo files. It takes the **same filters as `find`, matched by the same shared code** (AND at the group level), with the same input validation (bad P-id / invalid EDTF are refusals, at least one filter required), so gallery and find can never disagree about what matches - with one deliberate exception: `reconcile` keeps a vanished file's row queryable but prefixes its path `MISSING:` (its caption/keyword history stays searchable via `find`), and a gallery page exists to be clicked, so a group whose every variant is `MISSING:` is dropped from the gallery entirely rather than rendered as a permanently broken link/image; a group with some variants still on disk renders from those, never from the vanished one. Each logical photo is one row (the group's `primary_path`) with its variants as zero-JS `<details>` chips, sorted into decade sections newest-first with an "Undated" tail and a count strip; a slash-interval or bracket-qualified date (`1912/1915`, `[..1900]`) keeps its range/qualifier in the row's plain-language date label ("1912 to 1915", "before 1900") rather than collapsing to its first or boundary year alone; when `--person` is set, weaker `face-tag`/`name-match` groups fall into a "Verify these" section that points at `tag-person`, its printed command shell-quoting the example path so a space or shell punctuation in the catalog path never splits it into two arguments. The output is a **disposable private artifact under `generated/gallery/`** (a gitignored sibling `fha site` never reads or clears): `{slug}_{P-id}.html` for a bare person filter, with the same filter tokens appended when `--person` is combined with other filters (so `--person X --keyword farm` and `--person X --keyword school` never overwrite each other), `gallery_{filter tokens}.html` otherwise, `--out` overriding. Filter tokens keep distinct EDTF forms distinct - `1912` and `1912~` slug to `edtf-1912` and `edtf-1912-approx`, not the same stem; an interval is mapped half by half, so `[..1900]/1910` keeps its own page rather than the plain `1900/1910`'s. **No two distinct filter values may share a landing spot.** The person half is safe by construction (the P-id rides along), but `_slugify` is lossy, so every free-text value - `--keyword`, `--text`, `--under`, `--not-under` - carries a short stable digest (`-h` plus six hex characters) whenever its slug is not simply the value itself: `--under A/B` and `--under A-B` both read `a-b` and would otherwise let the second run overwrite the first's page, silently, because a generated marker makes overwriting legal. The readable stem survives ahead of the digest, since a browsable folder of galleries is the point of the default landing spot; a lossless encoding was rejected for producing names nobody can read. Case and surrounding space fold away first (every one of these filters matches case-insensitively), and `--under`/`--not-under` resolve to the catalog's alias form before naming, so the several ways of writing one subtree share one page while different subtrees never do. The exact filename is filter-dependent, so a caller relays the path the command **prints** rather than predicting it. It is unredacted like the plan-13 views and bound by the **same single-file-HTML conventions - see D11 (:437)**: marker on line 1 before the doctype (overwrite-by-default; a marker-less file at the target is refused, never clobbered), inlined `design/view.css`, the private-artifact banner, and `file://` hrefs with lazy `<img>` pointing straight at the photos (renderable `.jpg/.jpeg/.png/.webp/.gif`; other formats get a placeholder tile that still opens the file on click). Refuses in working-copy mode - the `file://` links would all be broken - exiting clean with `status=working-copy`. Cache posture mirrors `find`: absent/unreadable/old-schema is exit 3 with the rebuild message; stale still builds (warns, exit 0); zero matches writes nothing and exits 0; a build prints the file's path and its `file://` URL.

**Design decision D10 (implemented milestone 3, all phases shipped):** `fha photoindex` shipped first as scan/schema/grouping/person-resolution cache infrastructure (phase 1), then `photoindex find` (phase 2), with triage (phase 3), reconcile and tag-person (phase 4), set-summary (phase 5), and gallery (phase 6) following in later phases - all six phases are shipped as of this section. Face regions are cached in `photo_face_regions` because they are scraped metadata needed to rebuild weak person matches after `index.sqlite` changes; forcing an exiftool re-scrape merely to refresh name/tag resolution would make incremental scans slower and less equivalent to full rebuilds.

## 10. `fha places` - registry + geocoder

`fha places lint` (orphan L-ids, duplicates by normalized name, dangling/cyclic `within:` links, a place that is itself a `within:` target also carrying its own outward `within:` link) · **`fha places candidates`** - the recurrence detector: normalize unlinked claim `place_text` (case, punctuation, abbreviation expansion: St/Street, Co/County), cluster near-variants (token-set match), emit groups ≥3 occurrences with their claims and date spread; plus photo-GPS clusters (≥3 photos within ~150m) near no known place's coords. Scoped to active claims (`accepted`/`needs-review`) by default - a still-unreviewed `suggested` claim might be disputed away before it becomes fact, so the everyday view leaves it out. `--include-suggested` widens the status filter to also count `suggested` claims (Codex review, PR #150, following issue #79 point 4): its one sanctioned caller is the setup-interview skill's one-time, pre-family-interview backlog scan, which has to see the exact shape a fresh `fha gedcom import` leaves behind (every claim minted `suggested`) - without it that check silently found nothing on the scenario it exists to catch.
Elevation is a guided flow: human confirms → mint L-id (+`within:`) → per-claim `place:` backfill, each shown (same text across decades may be different buildings); `place_text` never altered.
This deterministic-cluster → human-confirmed-elevation pattern is the template for future recurring-people (FAN) detection. · `fha places geocode` - backfill `coords`/`alt_names`.
Gazetteer: **GeoNames** offline dump (`cities15000` + `allCountries` as needed), downloaded once into `\.cache/geonames/`; no live API dependency.
Match `name` + `hierarchy` tokens against GeoNames name/admin1/admin2/country; on a unique high-confidence hit, propose `coords` and alternate names; **every write requires interactive confirmation** (place identity is a research judgment, not a string match).
Writes preserve YAML comments (`ruamel.yaml` permitted here, or regenerate the file wholesale with a GENERATED note for hand-restoration of comments).

**`fha places set` / `fha places note` / `fha places edit-note` (2026-07-17)** - the human-directed registry write-backs the workbench place page drives:

```
fha places set <L-id> [--coords "LAT, LON"] [--aka NAME]... [--history "PERIOD | HIERARCHY"]... [--dry-run]
fha places note <L-id> --text TEXT [--dry-run]
fha places edit-note <L-id> --old-text TEXT --text TEXT [--dry-run]
```

`set` replaces exactly the fields given - coordinates (forgiving on shape, strict on ±90/±180 ranges, catching the classic swapped pair), the complete `alt_names:` list (one repeatable `--aka NAME` per name, each taken verbatim so "Washington, D.C." stays ONE alias; the workbench modal speaks one-name-per-line for the same reason), the complete dated `history:` list (one `PERIOD | HIERARCHY` entry per flag/line; the period takes the same forgiving-then-strict date rule as claim dates - valid EDTF kept as-is, loose wording like "circa 1858" normalized by `normalize_date`, anything unreadable a plain refusal, so a typo period can never index at the all-time `0001..9999` bounds and scramble names-over-time order) - each a FULL per-field replace; omitted fields untouched. `note` appends a DATED paragraph to the place's `notes:` (reference prose, SPEC §15 - loose citations welcome), preserving whatever is already written and re-emitting the key as a `notes: |` block scalar. `edit-note` rewrites ONE entry of that log, named by its exact current text - the same position-free per-entry edit `fha person edit-note`/`fha source edit-note` give the other running logs, with the same refusals (not found / ambiguous / empty replacement). Both are the same one-block surgical text edit geocode performs (comments and every other entry preserved). **No interactive `[y/N]` gate, deliberately:** geocode's gate exists because geocode INFERS coordinates; these verbs only ever write values the human personally supplied - typed into the command, or into the workbench form and applied through its dry-run-preview-then-confirm two-step - so the command itself is the confirmation the coordinate rule (AGENTS.md) requires. Exit codes: 0 written/dry-run · 1 unknown L-id or missing registry (with the `fha find` next step) · 3 invalid id shape, out-of-range coordinates, unreadable history period, nothing-to-change, unreadable/unwritable registry.

## 11. `fha convert-mining` - interview converter

Migrates a legacy transcript-mining pipeline output (`facts.txt` table rows, `stories.txt` blocks, `questions.txt` blocks, `sources.txt`, alias files) into conformant records.

1. **Sources first:** each legacy `S###`/transcript → copy transcript into `documents/interviews/`, process (mint S-id, rename, scaffold record with `people:` resolved via alias files → P-ids, `source_type: interview`), record the legacy extraction pass in `## Notes` (model: gpt-4-class, dates from run headers).
2. **Facts → claims:** parse the markdown table rows + `Update(T###)` continuation lines (merge updates into the claim's `notes`). Field map: Claim→`value`; Earliest/Latest→EDTF (`same date` → single value; range → interval; their `~`/`??` → EDTF `~`/`X`); Confidence High/Medium/Low→`confidence`; Section → dropped; `status: suggested` for all (AI-extracted); `type` assigned by keyword heuristics (birth/marriage/served/lived-at → vocabulary) defaulting to `event` + `subtype` from the legacy Section.
3. **Anchors:** best-effort - take the 3 rarest content words of `value`, search the transcript; a unique window → `anchor: line N`; else omit.
4. **Stories → `## Stories`**, people refs resolved to P-ids; **questions → `notes/questions.md`** (`open`, with `[[S-id]]` references mapped).
5. **Audit trail:** write `\.cache/convert_mapping.csv` (`legacy_id, new_id, notes`) and a dry-run report; `--apply` to write. Unresolvable people → minted stubs via §5.

## 12. `fha site` - static HTML explorer

**Output:** `generated/site/` (or `--out`), fully relative links, no CDN, no JS frameworks - works from `file://` and a USB stick; the packet tool can embed a single-person slice.

**Scope: the whole-family site** - the archive as a browsable website, not a single profile (the packet embeds a one-person slice of the same generator).

**Pages:** **Home** (#115 redesign) - a **marriage-aware ancestor pedigree**: the same server-rendered, self-contained SVG family-chart engine the person page uses (below), seeded on `site.home_person` (falling back to `root_person`) and scaled to a configurable depth (`site.home_pedigree_generations`, default 5, max 8) instead of the person page's fixed 2 generations. Couple pairing at every ancestor generation falls out of Ahnentafel numbering itself (slots 2N/2N+1 are always a couple); the hub's own row additionally shows spouse(s), children, AND siblings (the pedigree-chart trade-off's "lost aunts/uncles/cousins" mitigation - everyone sharing one of the hub's recorded parents). Each ancestor card is tinted by paternal/maternal line (Ahnentafel parity - halve the slot until it lands on 2 or 3) - **except** when the slot that split reduces to (2 or 3) was filled by elimination among unknown-sex parents rather than matched by a recorded `sex:` (`sex_derived: False`, #152 review fix, P2): coloring a slot nobody actually evidenced as paternal or maternal would assert a fact the record does not have, so that branch renders untinted instead. A short caption plus a small axis label orient a first-time visitor ("{name}'s family, tracing back through the generations →"). A deeper ancestor **that already has its own generated page** is one click away, carrying the same chart re-centered on them - not an unbounded canvas; a still-stub ancestor (a name in the tree with no page written up yet) shows as a plain, unlinked name instead. **Redaction-safe hub (standalone only):** `root_person`/`home_person` is typically the living archive owner, so a redacted seed hands off to the closest non-living/non-redacted ancestor on its recorded line (`_apex_ancestor`, repurposed - see below); when even that finds nobody, the page falls back to a FULLY blank hub-only render - no ancestor columns AND no family row either (spouse(s)/children/siblings withheld too, PR #153 fix: showing that real, dated, linked family bracketed onto the hub's own blank card would out a living owner's specific close relatives on the site's highest-traffic page, the same leak `_build_family_wings` guards against for every other redacted person) - plus a plain-language note, never a page anchored on a blank "Living Person" card with any real names drawn near it. The base chart is a complete, correct, static `<svg>` needing no script; `fha-tree.js`'s pan/zoom viewport (`wrapStatic`) wraps it as a pure enhancement for a deep chart or a small screen. Plus the surname A-Z index and recent-discoveries teaser. The **interactive descendant explorer** (the pre-#115 home hero: expand/collapse nodes forward from a person, all rendered from the `relationships` edges) is demoted to a per-person opt-in link on the **Person (curated)** page ("See descendants of {name} →", inside a native `<details>` disclosure) - the same vendored renderer, adapter, and neutral tree JSON, just re-seeded per person instead of once per build. **Person (curated)** - summary block; a server-rendered, self-contained SVG **family chart** (plan 17, widened from the original ancestors-only pedigree): children | subject + spouse(s) | parents | grandparents, four columns from one Ahnentafel walk - a redacted or absent spouse/child is dropped outright rather than shown as a placeholder (unlike an unresearched ancestor slot, you cannot enumerate someone's unknown children, so silence is the safe rendering). Family lines route **couples-first** (owner decision, review 2026-07-17): the subject's and a spouse's lines join at that couple's junction before one line splits to that couple's own children - the ancestor elbow, mirrored - and children are grouped by which drawn spouse is their other parent (children by different spouses hang off different junctions; a child whose co-parent is unrecorded or redacted hangs off the subject alone, the privacy-safe fallback); biography with `[[S-…]]` rendered as numbered footnotes, `[[P-…]]` as links; **timeline** (same shape as `fha views timeline`'s main chronology - sorted by date, grouped by decade, each entry showing type, value, and source link - with an audience split, owner decision 2026-07-22: the published standalone timeline is **accepted claims only**, a low-confidence accepted fact carrying a visible "low confidence" flag; linked/workbench keeps needs-review entries, each marked "unconfirmed - parked {date}"; suggested never renders); photo strip (via §9 person resolution, i.e. face_tags); Stories; Friends & Family; **sources index** (HTML rendering of the same index query as `fha views sources-index`: every source with ≥1 claim naming the person, grouped by source_type, with citation and file links - the HTML and `.md` views share the same query). **Person (stub)** - one-line entries on their couple's section. **Source** - a record-head scan **thumbnail** (plan 17: the same resolved/privacy-checked image the Files list already has, framed as a portrait plate, preferring a `role: front` image else the first resolvable one - never a second derivative or a second privacy check) linking to the full-size scan; citation, metadata, claims table with status badges (standalone: accepted claims only - the same audience split as the timeline; linked/workbench: every status with its badge, needs-review rows additionally tinted in the serve workbench; an accepted low-confidence claim carries a "low confidence" flag in every mode), and the full files list (thumbnails + links). **Place** - name, an **embedded OpenStreetMap view** with a marker when coordinates exist (owner decision 2026-07-17, reversing the earlier no-embedded-map stance: a plain iframe, no JS library, degrading to an empty ruled frame offline while the ordinary map *link* beside it always works), the registry's `notes:` reference prose, dated `history:`, claims naming it (same audience split as the timeline), contained micro-places (`within:` children). **Discoveries** - rendered from `notes/discoveries.md`. The home page's **Sources** listing is grouped by the decade of each record's own date (`date_min`), alphabetical within a decade, undated records last - a long list stays scannable.

**Assets - self-contained snapshot by default.** The generated site is a **standalone snapshot**, not a live view of the archive: the generator produces its **own web-optimized image derivatives** (resized, EXIF stripped so living-person/location metadata never leaks) and copies them into the site folder, so the site depends on *nothing* outside itself - deploy it to a USB stick, a static host, or hand it to a relative, with the archive absent.
Full-resolution originals never leave the archive; the site carries derivatives only.
A photo the catalog knows only as a `MISSING:` row (§9) is not a picture the site can show: it is dropped from a person's photo strip rather than allowed to represent - and so hide - the variants of that photo still on disk, and it is never preferred over a live file when a `profile_photo:`/hero/embed reference is resolved. When such a reference is a bare filename and has to be looked up by scanning the photos root, that scan honors `photos_ignore:` (§9) exactly as the catalog scan does - the site does not guess out of a subtree the archive has excluded from its library - while an explicitly written path is still honored.
The snapshot contains **only publication-eligible material** - `living`/`unknown` persons redacted, anything `restricted` excluded wherever it appears (a source, a claim, a person, or a name - a restricted name renders as the person's unrestricted display name), DNA excluded, `rights.publication_ok: false` sources withheld - so "generate the site" is also "produce the safe-to-share version." `--linked` is the opt-in alternative for fast *local* preview (relative links to real files, no copying, no redaction guarantees - developer mode only).
**A source image the photo catalog knows is tagged to a living person is not published** in a standalone build (the tag matches on either spelling of the path, so a photo whose file has come back before the next rescan cannot publish past it). **This is the one privacy rule in `fha site` that fails open by design** (owner decision, 2026-08-16): with no usable catalog the gate cannot answer and the image publishes, because the site is meant to build without `.cache/photos.sqlite` at all and refusing every source image until `fha photoindex` has run costs more than it saves. The obligation it trades against is a single per-build warning naming the catalog state, what was therefore not checked, and the next step - the check is not silently skipped, it is handed to the human, and the build finishes on the ordinary warnings exit. Both gate and warning are narrower than the snapshot rule above them: they cover the images a *source* page publishes from its `files:`, while a hand-written `profile_photo:`/hero/embed reference is resolved on its own path - checked against the catalog while one is open, but published on the author's word once there is none, and never warned about. So a photo tagged to a living person can still reach a *deceased* person's page unremarked. A known gap, held over as its own decision.
**A record the build could not read is treated as restricted.** The `restricted` marker at the person, claim and name-variant level lives only in the record file - the index carries it for sources, as a bare 0/1, and not at all for persons - so the exclusion set is built by reading files. That makes a failed read fail *open*: a missing marker is indistinguishable from no marker, and a `restricted: by-request` person whose file would not open used to get a page on the public snapshot with their name on it. So an unreadable or unparseable person record is withheld (no page, rendered as the redaction label everywhere it would have appeared) and an unreadable source record is withheld along with every fact it is the evidence for - the per-claim markers live in that same file, so there is no way to know which of its claims were private. Both carry a warning naming the file and the fix. This covers both failure shapes: an exception, and the `parse_errors` list `read_record` returns *instead* of raising for the ordinary cases (a file that is gone, a permission error, malformed YAML). Note what the page-set design does and does not promise: it guarantees the site never *links* to a page it did not build; it does not check whether a page *should* have been built, and there is no separate audit pass that does - so every input to that decision has to be right on its own.

**A file the build could not decode is named, not crashed on (#68).** The third failure at this seam, after the unreadable folder and the unparseable record: `UnicodeDecodeError` is a **ValueError**, not an `OSError`, so a record saved in another codepage (cp1252 is a Windows editor's default, and the names an archive is full of - Krakow, Muller, nee - are exactly the bytes that differ) went straight past every `except OSError` guard. Two shapes, both closed. Every RECORD read goes through `_lib.read_record` with an `on_decode_error` callback, so the failure arrives as a reportable condition rather than a raise: the reads that already showed the human `str(e)` now show W128's plain cause instead of byte offsets and codec names, and the enrichment reads that branch on `undecodable: True` say so explicitly instead of leaning on a catch-all that could not tell a bad decode from a bad parse. Where an undecodable file is the *only* thing wrong, the build still degrades rather than fails: the privacy pre-pass withholds the person or source exactly as the paragraph above describes (a decode failure is a missing marker like any other), the person page loses its prose, alternate names, tags and portrait rather than the page, and the source page falls back to its index title. The one read that never went through `read_record` was `notes/discoveries.md` - a plain `read_text` behind `except OSError`, so a discoveries log in another codepage raised straight out of `run_site` *after* every page had been written, breaking that function's contract to return a `Result` (the CLI's catch-all reported it as raw codec text and exit 3; `fha serve`'s workbench rebuild, which calls it directly, got the exception itself); it reads through `_lib.read_text_or_report` now, keeping a missing file the ordinary silent skip it has always been and reporting only the decode. Warnings, never rewrites: the file is the human's and it is not damaged, only saved in another encoding, so every message names the file, the cause and the re-save, and the build finishes on the ordinary warnings exit. `fha lint`'s W128 is the same finding said in full.

**Modularity:** because the site is a snapshot, it is decoupled from the archive's churn - regenerating is idempotent, and an old site folder remains a valid frozen view even as the archive moves on.
Thumbnails/derivatives via PIL.

**Data source - SQLite index, not .md views.** The site reads all structured data (claims, relationships, vitals, sources, citations, place references) directly from `.cache/index.sqlite`, making the output as fresh as the last `fha index` run. The generated companion `.md` views (timeline, sources-index, draft-queue) are *not* read - they are research aids for the agent, not the site's input. Biography prose and Stories sections are read directly from the curated person `.md` file (the only parts that live in prose, not structured claims). This means `fha site` is independent of `fha views` - a site can be generated without ever running `fha views`.

**Implementation:** Jinja2 templates in `tools/templates/`; biography/stories prose rendered to HTML via a minimal stdlib converter (headings, bold, lists, links - the profile format is deliberately simple) to avoid a markdown dependency; structured fact sections (timeline, sources table, relationships) rendered from index queries; image derivatives via `PIL`.
Token swap: each `[[ID]]` link → a relative href, preferring its `|display` text for the label and falling back to the resolved record name; a name/stem `[[ ]]` resolves through the alias map (so a `living` person named by `[[P-…]]` or `[[Name]]` is redacted name-and-all), and an unresolved non-ID `[[stem]]` renders as plain text, not a broken-cite. Unresolved well-formed ID links render highlighted (already lint errors).

**Tree rendering - borrow the engine.** The interactive trees (descendant explorer, ancestor pedigree, FAN graph) are rendered by a **vendored client-side library**, not hand-rolled D3 - current best candidate **family-chart** (donatso, MIT, D3-based, framework-agnostic, has its own JSON input format).
It is a *replaceable rendering adapter* in the borrow-the-engines spirit: `fha views tree` emits the neutral tree JSON (§14b), the site bundles the library and feeds it that JSON (mapped to the library's format), and swapping renderers later touches only the adapter.
The library is vendored into the site bundle so the snapshot stays self-contained and offline.
Verdict + alternatives (Yakubovich/descendant_tree, others) evaluated in the owner's private tool log.
**Implementation status (M8.5, re-seeded by #115):** the vendored engine that shipped is a small, dependency-free SVG collapsible-tree renderer authored in-repo (`tools/templates/vendor/fha-tree.js`), *not* family-chart - it was chosen so the milestone needs no network fetch and the bundle carries no large third-party blob. The borrow-the-engine *contract* is fully honored: `tools/templates/vendor/tree-adapter.js` is the single seam that maps the neutral tree JSON to the renderer, so dropping in family-chart (or any D3-based engine) later replaces only those two files. Each descendant-explorer page embeds its tree JSON inline (read from the DOM, not `fetch`ed - `file://` has no network) and also writes it to `site/data/tree_{P-id}_descendants.json` as the reusable artifact; redaction is applied server-side in that JSON (living/unknown → "Living Person", no vitals, no link). **Since #115, the home page no longer embeds this renderer at all** - it moved to a per-person opt-in section on curated person pages (one tree per person that has any descendant edges, seeded on THAT person rather than once on the root's apex), so `_apex_ancestor` lost its only caller as a descendants seed and was repurposed as the home pedigree's redaction-safe hub walk (Pages, above) rather than deleted. `fha-tree.js` also exports a second, independent entry point, `wrapStatic(container, options)` (#115): it wraps an already-drawn static SVG (the home pedigree) in the same pan/zoom viewport, with no layout pass of its own - a static-chart caller, not a hierarchy caller, of the same vendored file. Curated person pages carry a separate, server-rendered static chart for the immediate family - not the JS engine - described under Pages above (plan 17's widening of the original 3-generation ancestor-only pedigree; #115 generalized that same renderer's ancestor-column math to any depth for the home page, while the person page keeps its original 2-generation default).

## 13. `fha wikitree` - profile exporter

Renders a curated profile to the user's **extended WikiTree dialect** (established in existing profiles, e.g. Hartley-6084), not vanilla markup:

- **Named-ref convention:** `[[S-id]]` → `<ref name="S-id"/>` at use sites; full `<ref name="S-id">{citation}</ref>` definitions gathered into the hidden `<div name="references" style="display: none">` block at top (the dialect's reuse pattern).
- **Spacetime spans, auto-generated:** each factual statement backed by a cited claim with `place`/`date` wraps in `<span class="spacetime" data-loc="{place name}" data-date="{ISO date}">…</span>` - the dialect's machine-readable annotations, emitted from claims instead of hand-built. Accepted claims only (a span stamps fact; low confidence still qualifies - sometimes that's the best there is).
- **Research Notes from parked claims:** the subject's needs-review claims export as open questions under `== Research Notes ==` (WikiTree's home for uncertain information) - "Unconfirmed: {value} - noted in "{source}". Not yet verified - corroboration welcome." - so collaborators can pick them up; never as facts. Appends to an existing profile-authored Research Notes section rather than duplicating the heading. Privacy: restricted claims, restricted/DNA/`publication_ok:false` sources, and claims naming living persons are withheld entirely.
- `[[P-id]]` → `[[{external_ids.wikitree}|{name}]]` where recorded; plain name otherwise.
- `{{Ancestry Image|db|id}}` emitted from source `external_links` matching Ancestry image refs.
- **Template hooks:** optional claim-type→infobox mappings (e.g. military service → `{{US Civil War}}` with enlisted/mustered fields) in `tools/wikitree_templates.yaml`.
- Sections map 1:1 (the profile structure and the dialect already agree); `== Sources ==` ends with `<references/>`. Output to stdout or file; never uploads.
- **A record the export cannot read refuses it (#68).** The subject's `restricted:` marker lives in the record file, not the index, so a subject record that is malformed or **not saved as UTF-8** (`UnicodeDecodeError` is a ValueError, and cp1252 is what a Windows editor writes by default) is refused rather than read as empty frontmatter, where an absent marker reads as "not restricted". A cited source or linked person whose record will not decode fails closed in the same scan as a restricted one and keeps that scan's status - the statuses name the scan that refused, not the marker it found - while the message names the encoding, the file, the re-save, and `fha lint`'s W128 for the rest, because removing a restriction is not a fix for a file whose only defect is how it was saved. Never re-encodes or rewrites the file.
- **Privacy (mandatory, SPEC §21 - fail closed, no opt-in).** WikiTree is a public-publication path, so it enforces the redaction contract with no `--include-living`/`--include-restricted` escape hatch (unlike `fha gedcom`'s `--include-living`): a `living: true`/`living: unknown` **subject**, or a `restricted` subject (any value, including `by-request`), is refused outright; a profile that cites any `restricted` (`true` or any type), `source_type: dna`, or `rights.publication_ok: false` source - or links a `restricted` **person** - is refused (the offending records are named for cleanup, not silently dropped); any *other* living/unknown person referenced by a `[[P-id]]` link in the rendered prose is redacted to `[living person]`; and a restricted **name** renders as the person's unrestricted display name. Restricted/DNA sources are also filtered at the SQL layer as defense in depth.

## 13a. `fha gedcom` - relationship exchange export

Derives a standard GEDCOM 5.5.1 file at export time - never stored, never re-imported as truth (GEDCOM is a one-way export bridge; the plain-file archive remains the corpus). `fha gedcom <P-id> [--mode descendants|ancestors|connected] [--generations N]` or `--all`.
From the `relationships` edges and vital claims: INDI records (name, sex, birth/death/marriage from accepted vital claims with dates), FAM records (from spouse + child edges). A marriage claim's date and place are written onto the FAM of the couple that claim marries - scoped by `roles:` through the same `_lib.spouse_parties` rule the index uses (§197), never by position on the certificate, so a son's wedding cannot land on his parents' family record. A marriage event the export cannot place on any family record - a `roles: spouse:` naming three or more, which no two-person FAM key can match - is named in the run's messages beside the redaction counts, because refusing to guess which two of the three to hang it on is right but dropping a wedding date out of a complete-looking file in silence is not. `living`/`unknown` persons are redacted by default (living individuals → name withheld, à la standard privacy); `--include-living` overrides.
GEDCOM is a public-export path, so it honors `restricted` wherever it appears: a `restricted` source (any value, including DNA) is not an eligible fact source, a `restricted` claim is withheld, a `restricted` person's name becomes `/Restricted/` (their structural links kept so the tree shape survives), and a restricted name renders as the person's unrestricted display name. `restricted: by-request` is honored with no override - `--include-living` lifts only the living redaction, never `restricted`.
Sources: each fact's `[[S-id]]` becomes a SOUR note referencing the source citation.
Output is a `.ged` file; round-tripping back in is explicitly unsupported - GEDCOM is a one-way bridge to other apps. (A *foreign* GEDCOM arriving here is a different matter - that on-ramp is §13a2 below.)

## 13a2. `fha gedcom import` - the Ancestry on-ramp (GEDCOM importer)

`fha gedcom import <file.ged> [--apply] [--plan-out FILE] [--root PATH]` - the import side of the
one-way-bridge contract, extended: the archive's own **export** is never re-imported as truth (the
importer's self-import guard refuses a file stamped `HEAD SOUR fha`), but a **foreign** GEDCOM -
fifteen years of Ancestry clicking - is a legitimate on-ramp. It is filed the way this system files
everything: the `.ged` file is **copied** (original untouched) into `documents/gedcom/` and becomes
**one source record** (`sources/other/`, `source_type: other` + `subtype: gedcom`,
`source_class: derivative` - a compiled tree, not a record); every individual becomes a **person
stub** in `people/stubs/` (with provisional `birth:`/`death:` estimates so the tree is immediately
legible, and extra NAME lines as `name_variants:`); and every assertion becomes a
**`status: suggested` claim** on that source, `confidence: low` (`medium` when the event carried a
GEDCOM citation), with `anchor: "line N"` into the filed copy. GEDCOM `SOUR` titles ride along as
research leads (claim `notes:` + the record's `## Notes`), never as minted S-records - we do not
hold that evidence. `PLAC` values land in `place_text:` only; no place is ever minted. Nothing
imported is ever `accepted`; the imported tree joins timelines, exports, and the family tree
gradually as claims are accepted (the relationships table derives from accepted claims only).

Contract highlights: **plan-then-apply, one-shot** (dry-run default prints the plan and writes
nothing; `--plan-out FILE` writes the full uncapped plan, refused inside the archive except
`out/`, and is written *before* an apply so a bad destination refuses while nothing has been
written); UTF-8 only in v1 (ANSEL/UTF-16 refused with a re-export fix); a file that defines the
same xref twice is **refused as malformed, never guessed**; **sentinel + rollback** -
the audit CSV `.cache/gedcom_import/{sha12-of-file-hash}.csv` maps every GEDCOM xref to its minted
id AND is the re-run guard (same file twice = refusal naming the date and S-id; a *different*
export imports cleanly and the dedupe report flags overlaps); every write registers an undo first
and any failure rolls everything back (the audit CSV is the final write, so a failed run leaves no
sentinel); an unreachable documents root (an unplugged external drive) refuses the apply before
any write, naming the drive and the `roots:` fix. On a `WORKING_COPY` machine (§13d) the dry-run
plan still runs; `--apply` is in the asset-mutating refusal class and points at the main archive. Possible duplicates against people already in the archive are **reported, never
auto-merged** - merging is a human decision (merge-identities). The **`living:` heuristic** is the
one privacy-relevant default the import writes: DEAT present (even dateless) or latest-plausible
birth year more than 110 years back → `living: false`; everyone else stays `unknown` (treated as
living by every export) - a single isolated predicate (`living_flag_for_import`), owner-reviewable
in one place. Implemented in `tools/gedcom_import.py`; routed by a dispatcher intercept in
`fha.py` (the `fha id check` mechanism, §4a) so the exporter's positional `P-id` surface is
untouched.

## 13b. `fha capture` - web record capture (the intake on-ramp)

> **Full design: [`TOOLING_INGESTION.md`](https://github.com/asielen/plaintext-family-history/blob/master/TOOLING_INGESTION.md).** The intake on-ramp - the engine, every delivery form (paste, browser extension, native host, Claude-in-Chrome), the browser→inbox transport, the staged-bundle contract, and the `fha capture --ingest` sweep - is specified there in full. This section is the summary that the rest of TOOLING/SPEC cross-references.

The primary way starter sources enter the archive.
Most existing research lives behind logins (Ancestry especially), so capture is designed to run **on the page the human already has open** - it never logs in, never scrapes credentialed endpoints on its own, and sees only what the browser is already showing.
The companion's output is a **source stub** in the inbox (SPEC §12.1), never a finished record: a `{slug}.notes.md` whose light, optional frontmatter holds the citation fields a recipe recovered (`source_type`, `citation`, `repository`, `external_links`, `source_date`, and `people:` *names* the page listed) and whose body is the page's visible text or the human's notes. Processing later mints the S-id and drafts `suggested` claims; capture only stages.

**Backend `fha capture`** (built - [`tools/capture.py`](https://github.com/asielen/plaintext-family-history/blob/master/tools/capture.py)): chooses a **site recipe** (Ancestry, FamilySearch, Newspapers.com, FindAGrave - each knowing where that site keeps title/date/collection/repository/image-URL/persons) or falls to the **generic recipe** (title, URL, accessed-date, visible text); extracts citation fields (explicit `--title`/`--type`/`--date` override the scrape); writes the stub + asset; and logs the search (SPEC §16). The recipe set is data (`tools/capture_recipes/`), extensible without touching the engine.

**Asset handling, three cases (cited elsewhere as (a)/(b)/(c)):** **(a)** a downloadable image/document → it becomes the source's asset (with an interactive *capture-what's-shown* `provisional-image` fallback for an on-screen-but-not-downloadable viewer image); **(b)** the record *is* the page → store a cleaned **HTML snapshot** (`documents/web/…`, an acceptable second-tier format per SPEC §2); **(c)** the page only points elsewhere → no asset, citation + `external_links` only, written with `asset_elsewhere: true` so `fha process` knows the missing companion is deliberate.

**Boundaries:** capture reads the open DOM/HTML only - it does not paginate, query APIs, or fetch behind auth; bulk or automated retrieval against a site's terms is out of scope by design. Everything it produces enters at `suggested`/needs-review like any intake. The governing principle - **fast, forgiving capture now; structured review later** - and the four-phase companion workflow (invoke → confirm → capture the evidence → stage, don't process) are detailed in [`TOOLING_INGESTION.md`](https://github.com/asielen/plaintext-family-history/blob/master/TOOLING_INGESTION.md) §5.

**`fha capture --ingest [DIR] [--dry-run]`** (built) - the local sweep that turns browser-staged bundles into inbox stubs. A delivery form (the extension, the native host, Claude-in-Chrome) drops a `<slug>-<timestamp>-<token>/` bundle (`page.html` + optional `asset.*` + `capture.json`) into a staging folder; `--ingest` feeds each bundle through the same `run_capture` engine - so the stub is byte-identical to the paste path's - and parks the swept bundle in `.ingested/` (never hard-deleted). `DIR` defaults to the `fha.yaml` `capture_staging:` key, else `~/Downloads/fha-inbox`. The sweep is idempotent (a name already parked is skipped) and resilient (a malformed bundle is reported and left in place, never aborting its siblings). It writes only to `inbox/`, so it stays available on a `WORKING_COPY` machine. Full contract: [`TOOLING_INGESTION.md`](https://github.com/asielen/plaintext-family-history/blob/master/TOOLING_INGESTION.md) §6.

## 13c. `fha install` / `fha update-tools` - scaffolding & updating a private archive

Vendoring the operating layer into an archive - and keeping it current as the public repo evolves - is a fixed ritual that should be a command, not a remembered checklist.
This pair handles both, and both are **generic glue** (they move operating-layer files between a public-repo clone and a private archive, and touch no family data), so they live in the public tool suite.

**The manifest (the package's own packing list).** The public repo ships a `manifest.json` (or equivalent) that *is* the definition of the operating layer: every path that belongs in an archive, plus a content checksum and the spec/tool version for each.
This is the single source of truth for "what gets copied" - when the package grows (a second tools folder, a fifth doc), it's added to the manifest, and `update-tools` automatically knows to copy it.
The list lives in versioned data, never hardcoded in prose or memory.

The manifest covers the **operating layer** - everything a genealogist needs to operate an archive: `tools/` (and any future tool folders), the `design/` package, the rulebooks (`SPEC.md`, `TOOLING.md`, `AGENTS.md`, `CLAUDE.md`), the two owner entry docs at the root (`GETTING_STARTED.md`, `CHEATSHEET.md`), the whole `docs/` folder, the root launchers (`fha`, `fha.cmd`, `serve.cmd`), and the agent workflow procedures under `.claude/skills/` - plus the **skeleton** (`fha.yaml`, the empty record dirs, a seeded `places.yaml`, `design/custom.css`).
The **tool-building** docs (`BUILD.md`, `BUILD_INGESTION.md`, `BUILD_INTERFACE.md`, `TOOLING_INGESTION.md`, `TOOLING_INTERFACE.md`, `AGENTS_TOOLING.md`) are deliberately **not** shipped: no tool reads them at run time and operating an archive never needs them. They describe how to *build* the tools, which is a workshop-clone activity.
It explicitly **excludes** spec-repo furniture that never enters an archive: `example-archive/`, `archive-template/` (its contents seed the skeleton; the folder itself is not copied), `tests/`, `.github/`, `.claude/settings.json` (agent permission grants are personal - never committed to the public repo and never shipped; each user approves their own), `PRIVACY.md` (the public-repo "no real data" policy - actively contradictory inside a real archive), and `RELEASE_CHECKLIST.md`.

**`fha install <archive-path>`** - the first-time bootstrap, **run from a clone of the public repo** (the only place the code exists before anything is copied).
Creates `<archive-path>` if absent (skeleton + full operating layer), or populates an existing folder that has no tools yet.
Stamps `.plaintext-version` recording the manifest version and per-file checksums received.
After this the archive is self-contained - tools and rulebook both vendored - and `update-tools` can run from within it.
*(Bootstrap note: `install` necessarily runs from the clone, e.g. `fha install ~/my-family-archive`, because the archive has no `fha` yet. This is the one command that can't be run from the archive - by definition.)*

**Archive layout: `.fha/`.** An installed archive keeps its *machinery* in a hidden `.fha/` folder - `.fha/tools/`, `.fha/design/`, and `.fha/browser-companion/` (the capture extension, ready for chrome://extensions "Load unpacked"; a front-end tool like the serve workbench, shipped so no workshop clone is ever needed to use it - its dev tests/fixtures stay in the repo) - so the archive root reads as the genealogy: the record folders, `fha.yaml`, the rulebooks, `GETTING_STARTED.md` and `CHEATSHEET.md`, `docs/`, `.claude/skills/`, and the launchers. The project `README.md` is **not** installed - it is repo-facing (badges, roadmap, contributing, links to `example-archive/` and the other repo-only folders), so an installed archive has no root `README.md` and `GETTING_STARTED.md` is its entry point.
There is no migration path and none is planned: a fresh `fha install` produces this layout directly, and an archive predating it is not something the tools undertake to convert.
The workshop repo itself stays **flat** (`tools/`, `design/` at its root); the remap is install-time only, recorded by the manifest's existing `src` (repo-relative) vs `path` (archive-relative) seam, so the install/update engine needs no layout knowledge.
Owner-facing `docs/` deliberately stays at the archive root with the rulebooks it links to and from: remapping either side would break every relative link in the pair (`docs/FAQ.md` from the root; `../SPEC.md` from a doc), and an archive has to stay navigable in a plain file browser - most of all when something is wrong, which is when the manual gets opened. The exception is PROJECT documentation: `docs/DESIGN.md` (the visual language, for whoever builds the templates) and `docs/SITE_PLAN.md` (a roadmap of work not yet done) install to `.fha/docs/`, since neither is guidance for an archive owner. The handful of cross-links that cannot be relative-correct in both the repo and an archive are absolute URLs.

**Docs are split by audience, expressed through location** (owner decision 2026-08-16). The two an archive owner needs on day one - `GETTING_STARTED.md` (what to do) and `CHEATSHEET.md` (the one printable page) - sit at the archive **root**, unmissable; the rest of the owner's manual stays in `docs/` and is linked from those two; tool-facing docs live under `.fha/` (`.fha/tools/README.md`, `.fha/docs/`). Because there is no install-time link rewriting anywhere in the engine, those two also live at the **repo** root: repo path == install path is the invariant that lets one set of relative links be correct in both contexts. A doc whose repo depth differs from its archive depth can only resolve in one of them.
Root detection is unaffected - it still finds `fha.yaml` at the archive root either way.

**`fha update-tools`** - run from the archive (or the clone, pointed at it) any time the public repo improves.
Reads the public manifest, compares against the archive's `.plaintext-version` stamp, and reconciles **without ever destroying anything**:

| Situation | What update-tools does |
|---|---|
| Manifest has a **new** file/folder | Copy it in. |
| File is **unchanged from stock** (checksum matches the recorded version) | Overwrite silently - no work to lose. |
| File was **customized** (checksum differs - you edited it) | Move your version to `.plaintext-backup/{date}/`, install the new stock version, and **report it** so you can reconcile your changes. |
| File **removed from the manifest** upstream (a tool retired/renamed) | Move it to `.plaintext-backup/{date}/` - **never deleted** - and report it. |

Then it refreshes the stamp and prints a summary (added / updated / backed-up / quarantined, with the backup path).
`--dry-run` reports the plan without writing.

**The governing principle: the updater never deletes and never silently overwrites your work.**
It only adds, replaces-pristine-with-stock, or moves-aside-and-reports.
Customizations and retired files accumulate in `.plaintext-backup/` for the human to prune when confident - the same project-wide bias as everywhere else: *never lose the human's work; make the human the one who throws things away.*
You may edit any operating-layer file freely (a tool, `AGENTS.md`, the spec); the checksum compare detects your change and protects it on the next update.
(`.plaintext-backup/` and `.plaintext-version` are the updater's only footprints; both are safe to inspect or delete by hand.)

**Operating layer vs. skeleton seeds.** The reconciliation above governs the **operating layer** (`tools/`, `design/`, `browser-companion/`, the rulebooks, the docs, the launchers). The **skeleton seeds** - `fha.yaml`, the seeded `places/places.yaml`, `inbox/_TEMPLATE.notes.md`, `design/custom.css` (the per-archive style hook), and the `.gitkeep` placeholders - are written **once by `install`** and never overwritten by `update-tools`. One narrow delivery path exists alongside that: a seed the manifest has gained since this archive was created, absent from BOTH the disk and the stamp, is installed - it has demonstrably never been delivered here, so writing it cannot overwrite an edit, and cannot resurrect a seed the owner deleted (a deletion IS recorded in the stamp). `.gitattributes` is the case in hand: without it a Windows checkout rewrites the launchers' line endings and every later update reports stock files as customized. Absent from disk AND absent from the stamp - both, or the seed is left alone. Those two files in particular fill immediately with the human's own configuration (`fha.yaml`'s asset roots) and data (`places.yaml`'s registry), so "refreshing" them upstream would clobber exactly the work the updater exists to protect. The manifest tags each file `operating` or `skeleton`; `update-tools` reconciles only the former and carries the latter's stamp entries over unchanged. (A genuinely improved template reaches an existing archive only when the human opts to copy it; a fresh `install` always gets the latest.)

## 13d. Working-copy mode (the `WORKING_COPY` marker) - asset-less plain-text copies

**Status: shipped (`BUILD.md` M10).** Recorded here as the tool-level design.

**The scenario.** The main archive lives on one machine with its photo/document libraries (often external roots). The plain-text core is synced to a second machine via git - `sources/`, `people/`, `places.yaml`, `notes/` travel; the binary assets do not. The genealogist wants to do real work there that needs no originals (write narratives from existing accepted claims, build inference against existing records, drop new material into `inbox/` to carry back). The hazard is that asset-aware tools, run where the files are absent, *misbehave*: `fha photoindex`'s incremental scan **prunes cache rows for files it cannot find** (it would empty the photo cache), `fha lint` floods E011 for every asset, and `fha index` records every `source_files.exists_on_disk = 0`.

**The flag is a git-ignored marker file, not an `fha.yaml` key.** Working-copy status is a property of *this copy on this machine*, so it must never sync. A key in `fha.yaml` would be committed and pulled back to the main archive, silently flipping *it* into working-copy mode - the exact failure the mode exists to prevent. Instead, the presence of a **visible, git-ignored** file `WORKING_COPY` at the archive root is the flag (SPEC §12.4): visible because it is a human-managed control (the whole archive is meant to be legible in a file browser), git-ignored because it must stay machine-local. Only existence matters; the file's content is a plain note for whoever finds it. This also means a working copy never edits `fha.yaml`, so `fha.yaml` may keep syncing without conflict.

**The governing rule.** The marker declares assets **assumed-present-elsewhere, never missing or deletable.** The plain-text surface is unaffected - `fha index` rebuilds the claim/person/source/relationship query surface from the `.md` files (which *are* present), which is exactly what narrative-writing and inference read - so the mode is *not* "block rebuilds"; it neutralises only the **asset** side.

**`fha working-copy on | off | status`** is the friendly front door for the marker, so a
non-technical genealogist never has to know the filename or its contents (`fha never makes the
human learn the implementation`). `on` writes `WORKING_COPY` (with its explanatory text) and
confirms the archive's `.gitignore` lists it - adding the entry, or warning if the copy is not a
git repo so the never-sync-back guarantee can't be assured; bare/`status` reports the current
mode. `on` only ever *withholds* asset behaviour, so it needs no confirmation. `off` is the
asymmetric, **riskier** direction: it re-enables asset-aware behaviour, so on a machine where the
originals are actually absent, a later `fha photoindex` would prune the catalogue and lint would
treat every asset as missing. `off` therefore **prompts for confirmation** (`y/N`, default No)
with a plain warning of that consequence, and sharpens the warning when it can see the risk -
if the mapped asset roots are unreachable or empty, it says so ("the photos root `C:/Photos`
looks empty or unreachable - turning the mode off here is probably a mistake") rather than
silently switching. `--yes` bypasses the prompt for scripted use (the confirm callable is
injectable for tests, matching `fha places geocode`/`photoindex tag-person`). Each verb is
idempotent (`on` on an already-flagged copy just confirms it; `off` on a full archive is a no-op
note) and prints, in plain words, exactly what changed. The command lives in
`tools/working_copy.py`; the shared predicate below lives in `_lib` so every other tool reads the
mode without importing it.

| Tool | Behaviour when `WORKING_COPY` is present |
|---|---|
| shared (`_lib`) | `is_working_copy(archive_root)` = `(archive_root / 'WORKING_COPY').exists()` - a one-line existence check, no `fha.yaml` parse needed. The shared CLI entry prints a one-line banner (`working copy - photo/document files assumed on the main archive`) so the mode is never silent. |
| `fha working-copy` | `on` creates the marker (+ ensures the `.gitignore` entry), `off` removes it, `status` reports - the only command that *writes* the marker. `fha install`/`update-tools` never do. |
| `fha lint` | Suppress E011/E012 (asset-on-disk checks); emit one note (`working copy: N asset files assumed present in the main archive`), not a per-file warning flood. All non-asset codes run normally. |
| `fha index` | Record `source_files.exists_on_disk = NULL` (unknown), never `0`; skip the on-disk asset-reconciliation glob. The record-derived surface is built unchanged. |
| `fha photoindex` | A scan **refuses and prunes nothing** (`this is a working copy - run photo indexing on your main archive`). Read-only photo queries return whatever the existing cache holds. |
| asset-mutating commands | `fha process <file>`, `fha photoindex tag-person`, `fha photoindex set-summary`, `fha packet`, `fha site`, and `fha gedcom import --apply` refuse with a plain pointer to the main archive (exit clean, not a crash). The refusal is a warning-level `Result` - `ok=True`, exit 0, `data.status='working-copy'` - not a failure; `data.status` is the machine discriminator that nothing was filed. (`fha gedcom import`'s dry-run plan still runs, printed under the working-copy banner.) `fha capture` → `inbox/`, plain-text editing, `find`, `views`, `report` stay available. |
| `fha doctor` | Headline the mode; stop flagging missing asset roots as errors. |
| `fha backup` | A records-only backup **runs** (it reads the tree and writes outside it - not in the asset-mutating refusal class) with one honest note that the main archive is the copy needing the real backup; the `.cache/last_backup.json` stamp is still written (a per-copy fact). `--include-assets` is refused warning-level (`ok=True`, exit 0, `data.status='working-copy'`) - an asset backup with no assets in it must not exist. §13e. |

The archive's own `.gitignore` must list `WORKING_COPY` (and `.cache/`) so the marker cannot be committed. The M10 build therefore also seeds a starter `.gitignore` into the skeleton (archives created from `archive-template/` currently have none) - or, minimally, documents the one-line entry - so a git-syncing genealogist gets the guarantee without having to know to add it.

**Why behaviour stays obvious** (the locked project bias): one visible marker file the human owns; every command announces the mode; the mode only ever *withholds* destructive/asset actions (never fabricates a claim, never silently rebuilds over absence); the file-browser + text-editor experience is unchanged. Round-trips are safe by construction - `.cache/` and `WORKING_COPY` are git-ignored, so a working copy's caches and mode flag never reach the main archive, and the return path is the existing `inbox/` workflow. The marker is written only by `fha working-copy on` (or a hand-created file) and removed only by `fha working-copy off` (or by hand); the scaffolding tools (`fha install`/`update-tools`) never create or remove it - it is the human's declaration about *this* copy.

## 13e. `fha backup` - a dated zip snapshot (restore = unzip)

**Status: shipped (plan 04, 2026-07 usability review).**

```
fha backup [--to PATH] [--include-assets] [--dry-run] [--allow-incomplete] [--root PATH]
```

One command that copies the whole archive into a single dated zip **outside** the archive, so a dead disk costs nothing. **Restoring needs no tool at all: a backup is just your files, zipped - unzip it anywhere and the archive is back.** No restore verb is built, by design; the command's success output and the docs say so in one line. Plain files zip trivially - this is the payoff of the whole design - so the command adds exactly three things over "zip the folder yourself": it knows what *not* to include, it knows where the assets really live, and it leaves a stamp so `fha doctor` can tell the truth.

**Destination - outside the tree, always.** Default: a sibling folder next to the archive root, `{root-folder-name}-backups/` (visible in the same file-browser window as the archive itself). Configurable via the optional `fha.yaml` key `backup: {path: <folder>}` (absolute used as-is, relative joined to the archive root - the `roots:` tolerance, SPEC §12.4); `--to PATH` overrides both. A destination that resolves (symlinks resolved first) *inside* the archive root or any mapped asset root is **refused** (exit 3, message names the conflicting setting and the fix) - a zip inside the tree would be swept into the next backup or into an asset scan. Zip name: `{root-folder-name}-backup_{YYYY-MM-DD}.zip`; a same-day re-run appends `_2`, `_3`, … - an existing backup is never overwritten.

**Records-only by default; walk-and-subtract.** Everything under the archive root goes in *except* a stated exclusion list - the walk subtracts rather than enumerating includes, so a folder the human added by hand is never silently skipped (backup errs toward inclusion). Excluded, with the reason printed: `.cache/` (rebuildable databases), `generated/` and `out/` (rebuildable deliverables), `.git/` (its own history), the `WORKING_COPY` marker (machine-local by design, §13d), and the resolved photos/documents roots **wherever they live** - even alias roots sitting inside the archive root (one predictable rule). An `inbox/` that resolves inside the root is always included (staged material is irreplaceable); an inbox mapped outside is treated like the other asset roots. Every records-only run states, in plain words with real estimated sizes, that the photos and documents are NOT in this backup and how to cover them.

**`--include-assets`.** Zips each *external* mapped root under its alias name (`photos/…`, `documents/…`), and a root mapped *inside* the archive at a different path (`roots: photos: media/photos`) under its real relative path (`media/photos/…`), so an unzip restores exactly the layout the zipped `fha.yaml` describes; the output notes the one wrinkle for external roots (move them back and keep `fha.yaml`, or leave them inside and delete the `roots:` mapping). If an archive folder and a mapped root would land on the same name inside the zip, the run **refuses** (exit 3, nothing written) naming the folder, the `roots:` line, and the fix - a zip with duplicate member names silently loses a copy on extraction.

**Completeness - a walk that did not see everything must not certify everything.** `os.walk` cannot tell a folder it may not list from an empty one, so a backup that could not read part of the archive used to write a zip missing it and report success; the human finds out at restore time, the one moment recovery is impossible. Every walk that feeds the zip therefore carries the `_lib.unreadable_dir_recorder` error seam, and a run that did not read everything is **REFUSED before anything is written** (exit 3, `data.status='unreadable-folders'`, `data.complete=False`) - a refused backup costs one re-run, an incomplete one that looks complete costs the archive. **Three things count as "did not read it"**, because all three end with files missing from the zip and nothing else able to tell: (a) a folder that raises on listing (permissions, a disconnected share); (b) a subfolder that is a **symbolic link** - `os.walk` defaults to `followlinks=False` and drops the subtree without calling `onerror`, so links are recorded as unread rather than followed (following would pack content from outside the root under a name inside it, and unzipping would hand back a real folder where the link was - a restore shaped differently from the archive); (c) with `--include-assets`, a **mapped asset root that is not a directory** - an unplugged external drive - when the alias appears in `fha.yaml`'s `roots:`. An alias that exists only as the spec default (`photos`/`documents` in an archive that never made the folder) is *not* something the human asked to pack and is still just skipped. The refusal names each folder and gives the fix that matches its cause. `--allow-incomplete` is the escape for a folder that is gone for good: the run exits 0 but **marks the artifact, not the terminal** - the zip is named `…-INCOMPLETE.zip`, carries a `BACKUP_INCOMPLETE.txt` member listing what is missing, and stamps `complete: false` for `fha doctor` to report months later. One honest gap remains and is stated rather than papered over: a mount point that still exists as an empty folder while its drive is away is indistinguishable from an empty folder, so an included asset root that contributed no files gets a plain **warning** naming that possibility (exit 0, still `complete`) - refusing every archive that has yet to file its first photo would teach the human to reach for `--allow-incomplete` by reflex.

**Integrity.** After writing, every member's CRC is verified (`zipfile.testzip`) and the run reports `backup verified: N files, SIZE`. On any write or verify failure the partial zip is **deleted** and the run exits 3 - a backup that might be corrupt and says nothing is worse than no backup. Exit codes: 0 written+verified / dry-run / WC `--include-assets` refusal / `--allow-incomplete` run; 2 argparse only; 3 unresolvable root, refused destination, duplicate-member-name refusal, a folder that was not read (without `--allow-incomplete`), malformed `fha.yaml` (strict load), write/verify failure. There is deliberately no exit-1 arm: a partial or suspect backup is never a warning.

**The doctor stamp.** A successful backup writes `.cache/last_backup.json` (`date`, `zip`, `files`, `bytes`, `assets_included`, `complete`, `unreadable_dirs`). It lives in `.cache/` - not the tree, not `fha.yaml` - because it is a statement about *this copy on this machine* (the §13d rationale); losing it degrades in the safe direction (doctor over-reminds), and it is excluded from the zip itself so a *restored* archive honestly reports "no backup recorded" and prompts a fresh one. `fha doctor`'s section 12 leads with the stamp's real state (date, age, zip, records-only vs assets) or an honest "none recorded - run `fha backup`"; the check is **info-level with a CLEAN exit contribution** even when absent or old (the detectors' alarm-blindness rule, §14a), followed by the always-printed list of paths a full backup must cover.

**Working-copy mode (§13d).** A records-only backup *runs* in WC mode (backup reads the tree and writes outside it - not in the asset-mutating refusal class), with one honest note that the main archive is the copy needing the real backup; the stamp is still written (a per-copy fact). `--include-assets` is **refused** warning-level (`ok=True`, exit 0, `data.status='working-copy'`): an asset backup that silently contains no assets is the worst possible output for a backup tool.

`--dry-run` prints the full plan - destination, per-top-folder file counts and sizes computed at plan time, the exclusion list with reasons, the assets note - and is byte-for-byte side-effect-free (the destination folder is not even created); it previews the completeness refusal too, since a preview that promises a backup the real run would refuse is not a preview of that run. `run_backup` returns a `Result` (`data.status`, `zip_path`, `files`, `bytes`, `assets_included`, `skipped_roots`, `folders`, `excluded`, `unreadable_dirs`, `complete` - the same keys on every arm; `changed` = zip + stamp on a live run); `_cmd_backup` renders it.

## 13f. `originals_backup:` - one pristine copy before a photo is written into

**Status: shipped.**

```yaml
# fha.yaml
originals_backup: D:/PhotoOriginals     # absolute, or relative to the archive root
```

**The problem this answers.** Four call sites write embedded metadata into an original photo: `fha process`'s `SOURCE:` keyword and its rollback (§6), `fha photoindex tag-person`'s P-id keyword and `fha photoindex set-summary`'s `UserComment` (§9). All four invoke `exiftool -overwrite_original_in_place`, and that flag stays: it edits the file rather than replacing it, which is what keeps an external photo library (Lightroom, or any DAM tracking these files by identity) from losing the photo. The cost of that choice is that an interrupted write, a bad exiftool build or a bug rewrites the only copy of an irreplaceable photograph. The answer is not to stop writing in place; it is to take our own copy first.

**One copy, once, per file.** Before the first write to a file, its bytes are copied to the destination, filed under the file's alias path (`photos/1912/margaret.jpg` -> `<dest>/photos/1912/margaret.jpg` - the same identity the source record's `files:` entry carries, and the one a human can read in a file browser). If a copy already exists there it is **never overwritten**: the valuable artifact is the file as it was before fha ever touched it, so the second keyword write must not replace the pristine copy with an already-modified version. That rule is also what bounds the disk cost at one copy of each photo the tools have written to - not a second copy of the library. The copy lands via a `.part` temporary and `os.replace`, so an interrupted run leaves a complete copy or none; a half-written one would read as pristine on the next run, which is the one wrong answer here.

**What happens when a photo later moves** (SPEC §12.1: a photo's filename is not its identity - the embedded `SOURCE:` keyword is, with the recorded path as a hint). The copy stays where it was made, under the old path. Nothing is lost - it is still on disk with its original bytes - but a later write to the photo at its new path takes a fresh copy there, and *that* one is of a file fha has already written to. Keying the copies by the durable identity instead would not close the gap, and this is the reason it is worth stating rather than filing as a limitation: the first write of all is `fha process` **minting** the `SOURCE:` keyword, so at the exact moment the pristine copy matters most there is no keyword to key it by. A path-mirrored tree is therefore the right shape, and a human who reorganises the library and wants the copies to follow moves the folders the same way (nothing in the tools reads the copies back).

**The destination must be outside the archive and outside every asset root**, checked in both directions (a destination inside a root, and a destination that *contains* one) and against the folded spelling as well as the exact one - on a Mac or a Windows PC `PhotoOriginals` and `photooriginals` are one folder, and the harmful direction is answering "outside" about a folder that is really inside. A copy inside the photos root would be scanned, keyworded and counted as a second photo of the same picture, defeating what it is for. **Inside the archive but outside the roots is refused too**, for `fha backup`'s reason (§13e): a copy that shares the archive's disk, its sync folder and its accidents is not much of a copy. Same tolerance as `roots:` and `backup: path:` - absolute used as-is, relative joined to the archive root.

Because the folder is outside the archive and outside every asset root, `fha backup` (§13e) does not sweep it into its zips - correctly: these copies are already a backup, and packing a backup into a backup doubles the size for no restore value. They are the human's to keep on whatever disk he chooses, and nothing in the tools ever reads them back.

**Fail closed.** If the setting is configured and the copy does not happen - the folder is unwritable, the disk is full, the value is malformed - **the write is refused**, per file, through the same per-file error channel an exiftool failure already uses (so partial success across a batch is still reported per photo, and `fha process`'s existing rollback runs unchanged). A backup that silently did not happen is worse than none, because it is relied on. The refusal names the file in alias form, the cause, and the next step, including "remove `originals_backup:` from fha.yaml to write without safety copies" - the human decides, not the tool. A malformed value is an error, never read as "not configured": degrading to "off" would drop protection the human asked for.

**Not configured: warn once per run, then proceed.** Safety copies are opt-in, so an archive that has never set the key keeps working. The warning names the setting, says what it protects and is emitted **once for the whole run** - once per photo would be unreadable on the 88,000-file library that motivated `photos_ignore:` (§9). The interactive writers (`tag-person`, `set-summary`) announce it **before** their confirm prompt, where it can still be acted on.

**`--dry-run` previews the guard, and only announces it.** Every preview that would lead to a keyword write says where the copies would go, or that none are configured; it copies nothing and writes nothing. A preview that hides the guard the live run applies is not a preview of that run.

**Report.** Every run that made copies says how many originals were copied, how many already had one, and the bytes written - a human deciding whether to keep the setting on needs the size. `run_*` engines carry these as `Result` messages (code `originals-backup`) so a headless caller sees the same text; `fha process` prints them.

**Implementation.** One class, `_lib.OriginalBackup`, built once per run and handed to every writer in that run - a data-safety guard duplicated four ways is a guard that drifts. `ensure(path)` is the whole contract: it returns quietly, warns once, or raises `_lib.BackupRefused` carrying the finished sentence. `fha doctor` does not check the setting today (the failure is reported at the moment of the write, which is the only moment it matters); adding a "safety copies: on/off, N GB kept" line there is the obvious next step.

## 14a. `fha xref` - cross-reference pass

Triggered at the end of every review session (by the `review-claims` skill) and inside `fha report` - never scheduled. **Deterministic candidates** from the index: (a) corroboration - pairs of accepted/needs-review claims, same person + same type + overlapping EDTF bounds + different sources, not already linked; (b) contradiction - same person + same type + non-overlapping bounds, or same type with incompatible `value`s (vital types only for value comparison; substantive types compare dates only).
Output (read-only): candidate pairs with both claims' context. `fha xref` never writes - it only proposes.

**Marriage/divorce grouping reads `roles:`, not `persons:` (#63).** `persons:` on a marriage/divorce claim is who the claim is ABOUT, not a couple list (SPEC §8.3) - a certificate routinely names both sets of parents alongside the couple. Every marriage/divorce claim is bucketed by who `_lib.spouse_parties` says it names as the couple (the same rule `fha index`'s spouse edges and `fha gedcom`'s FAM grouping already use), not by every other person listed: a resolved couple buckets narrowly by that couple; a `negated: true` claim (SPEC §8.6, a real "researched, did not happen") is read off its own field - never inferred from an empty party set - and compared against every marriage/divorce claim on file for that person, narrowed further when a specific ex-partner was named; a claim naming fewer than two people at all takes that same broad path. A non-negated claim naming 2+ people that `spouse_parties` cannot resolve to a couple (a roles-less certificate, or a `roles:` map naming fewer than two spouses) is AMBIGUOUS - comparing it against everything would fabricate contradictions against unrelated marriages, so it is excluded from every comparison bucket and reported instead in the Result's `unscoped` list (the CLI prints it as a separate section, naming who was on the claim and that a `roles: spouse:` map would enable comparison). A person named on a claim but not among its resolved parties (a witness, an informant, a parent on a certificate) is never bucketed under that claim at all.

**Birth/death/baptism/burial bucketing reads `roles:` the same way (#136's second deferred fix).** The other vital types (`_VITAL_TYPES` minus the couple types above) had the identical "everyone named shares a bucket" bug: a mother's own birth claim and her son's birth claim - which names her under `roles: {parent: [...]}` - landed in the same bucket for her, and non-overlapping dates on a vital type read as a fabricated contradiction between two different people's births. Fixed the same way, through `_lib.vital_subjects`: a claim is only bucketed under a named person when that person is among the claim's resolved subjects (`VITAL_SUBJECT_ROLES`'s subject role when the claim names one, otherwise whoever `roles:` left unroled); a legacy claim naming at most one person with no `roles:` map at all keeps the old broad behavior (nobody else to be ambiguous about). A legacy claim naming two or more people with no `roles:` map at all has not said which of them it is about, and enters neither person's bucket (#126, reopened) - reported instead in the Result's `unscoped` list, the same treatment the roles-less marriage/divorce certificate above already gets (#172; unlike `fha lint`'s W132, this also covers `needs-review` claims, matching every other comparison `fha xref` makes). This scoping applies ONLY to the four genuine vital types - a substantive claim like `census` or `residence`, where `roles:` legitimately roles every person on the record (`head`/`household_member`, ...), keeps its original unscoped same-type bucketing untouched.

The three detectors (`fha xref`, `fha cooccur`, `fha places candidates`) **exit 0 by design whether they find zero candidates or fifty** - a candidate is a lead, not a defect, and leads are the steady state of an active archive, so exit-on-findings would train alarm-blindness. Gate a "there is unreviewed work" check on `fha report` (which surfaces all three) or `fha lint` (which grades real archive problems), never on a detector's exit code.

**Judgment + gate.** The skill layer assesses each candidate; the human picks. The write-back itself is mechanical, so it is its own deterministic command, **`fha confirm xref <C-a> <C-b> --as corroborates|contradicts`** (§14a3): it writes the `corroborates:`/`contradicts:` link reciprocally into both claims' source records (incremental reindex follows) and, for a `contradicts` confirm, spawns a structured question (`origin: tool`, both C-ids referenced) in `notes/questions.md` so lint E009 ("`contradicts:` with no open question") stays satisfied - the same machinery `fha lint --spawn-questions` uses. The detector reads and the confirmer writes are kept apart so `fha xref` can advertise a clean read-only contract: a detector that also wrote would be two owners for one surface.

## 14a2. `fha cooccur` - connection candidate detection

The recurrence detector pointed at people and named entities - sibling to `fha places candidates`, same deterministic-cluster → human-confirm discipline, consumed through the report.

**People co-occurrence → candidate social edges.** From the index: person-pairs named together in **≥2 distinct sources** with no existing `relationship` edge between them (kin or social).
Rank by co-occurrence count and source variety (different `source_type`s weigh more - a census + a newspaper + a photo back beats three pages of one census).
Output (read-only): candidate pairs with the shared sources and T.E.'s-side context. `fha cooccur` only proposes - the writes live in `fha confirm` (§14a3): **`fha confirm cooccur <P-a> <P-b> --source S --subtype friend|associate|neighbor`** mints the `relationship` claim (the confirming source cited), and **`fha confirm dismiss <P-a> <P-b>`** records the tombstone so the pair isn't re-proposed.
Noise control is the threshold + the human gate: every witness co-occurs with everyone on a document, so low-variety pairs rank low and most are dismissed - threshold tuning is pilot-data work.

**Shared-place co-occurrence → candidate social edges.** Accepted/needs-review claims of different, unlinked people sharing a place (`place_id` if both have one, else normalized `place_text`) with overlapping EDTF date bounds - e.g. two people each placed in the same town the same year by different sources - with no existing `relationship` edge between them. Same exclusion rules as person co-occurrence (existing edge, dismissed tombstone).

**Organization/entity recurrence → connection hubs.** Named entities living as claim *values* (employers in `occupation`, units in `military`, clubs in membership `event`/`note` claims) that recur across **≥N people or sources** are surfaced as candidate hubs: "Plains Junction Railroad - 4 people, 6 sources."
Organizations stay as claim values for now - no dedicated `O-` record type; the detector simply makes the shared affiliation visible and queryable, and flags it should the recurrence ever justify promoting to a real record later.
No schema change.

All three feed the report; all three render in the FAN view as provisional (dashed) edges distinct from confirmed claims.

## 14a3. `fha confirm` - the detection write-back layer

The deterministic *detection* tools (`fha xref`, `fha cooccur`, `fha places candidates`) only ever read - they print candidate pairs/clusters for a human to judge. `fha confirm` is the matching write floor: once the human has picked a candidate - or, for `merge`, made the identity call the merge-identities skill laid out - the write-back is mechanical, so it lives in one tool any front door (chat now, a click later) can drive. Keeping the writes here preserves each detector's read-only contract. Every verb is surgical (sibling claims, key order, and hand comments survive), locates records by scanning `sources/`/`people/` directly (works when the index is stale or absent), ships `--dry-run`, and returns a `Result` whose `changed[]` lists every file written.

One narrow, deliberate exception to "detectors only read" (#48): `fha cooccur` will migrate a legacy `.cache/cooccur_dismissed.json` to its durable home the first time it reads the dismissed-pairs tombstone, exactly as `confirm dismiss` does on write (below). That carries forward bytes a human already decided; it does not add a second owner for WHICH pairs get dismissed, so it does not reopen the "two owners for one surface" problem the read-only contract exists to avoid. It is never a *silent* write, either: `Result.data['migrated_legacy_dismissed']` reports it, the CLI prints it, and `fha report` §8 narrates it - so a "read-only" run still never touches the archive without the human seeing that it happened.

| Verb | Write-back |
|---|---|
| `confirm xref <C-a> <C-b> --as corroborates\|contradicts` | Confirm an `fha xref` pair: reciprocal `corroborates:`/`contradicts:` link into both source records; a contradiction also spawns the `origin: tool` open question (E009-satisfying). |
| `confirm cooccur <P-a> <P-b> --source S --subtype friend\|associate\|neighbor [--accept]` | Confirm an `fha cooccur` person-pair: mint a `relationship` claim (source cited). **Minted `suggested` by default** - the confirm proposes the edge; accepting it into a load-bearing graph edge still goes through claim review (§3b), since `_derive_relationships` is accepted-only. `--accept` is the escape hatch for a human treating the confirm *as* the review (stamps `reviewed:` like `fha claim`). Idempotent: a live relationship claim already covering the pair + subtype (any status except `rejected`/`superseded`) is never duplicated - without `--accept` (or when the existing claim is already `accepted`) the run is a no-op `already` naming the existing claim; **with `--accept` on a still-`suggested`/`needs-review` claim it promotes that existing claim to `accepted` (stamping `reviewed:`) instead of dropping the request** - a rejected edge never blocks a fresh confirm. |
| `confirm dismiss <P-a> <P-b>` | Record a co-occurrence pair in `notes/cooccur_dismissed.json`, the tombstone `fha cooccur` reads (durable, not `.cache/` - #48: these are a human's decisions, not derived data). Nothing else writes a NEW dismissal to this file. Also carries a legacy `.cache/cooccur_dismissed.json` forward the first time it runs on an archive that has not yet migrated; `--dry-run` never migrates, only previews the merged count. |
| `confirm place <C-id> [<C-id> …] (--name NAME [--hierarchy H] \| --into <L-id>)` | Confirm an `fha places candidates` cluster: mint a new `L-id` place in `places/places.yaml` (or merge via `--into`) **and** relink the named claims' `place:`, so the cluster stops surfacing as unlinked. |
| `confirm discovery "<text>" [--refs S-…,P-…]` | Append a dated entry (with `[[S-…]]`/`[[P-…]]` refs) to `notes/discoveries.md`, the research-wins log `fha report` §0 leads with. |
| `confirm draft <P-id>` | Flip a profile's `<!-- AI-DRAFT … -->` markers to `<!-- AI-ACCEPTED … (accepted DATE) -->` (§20: draft prose carries the marker until the human accepts it). The original date/model stay in the marker - provenance preserved, not erased. |
| `confirm merge <P-merged> --into <P-survivor> --reason "<why>"` | Enact a human-confirmed identity merge - the full SPEC §9 write in one verb, planned entirely in memory then applied with an undo journal (any failure rolls the whole archive back). Folds the merged record's `name`/`name_variants` (restricted `{value:, restricted: true}` mappings preserved), `external_ids:` (**a same-key different-value conflict is never silently resolved**: the survivor's value is kept, the warning names both values, exit 1, and the tombstone keeps the losing value), and `relationships:` entries (deduped by to+type+subtype; survivor-self edges skipped with an evidence warning) into the survivor; writes the four tombstone fields (`status: merged`, `merged_into:`, `merge_reason:` from the required `--reason`, `merged_date:`), strips what folded from the tombstone's frontmatter (W115 protection) and reduces its `aliases:` to the bare P-id; renames the file to `MERGED-INTO-P-survivor__<original>` **last**, after content writes succeed (the file persists forever, never deleted); relinks every claim's `persons:`/`roles:` across **all** statuses (E016 has no status filter; bare, `[[P-id]]`, `[[P-id\|Name]]`, and resolving-name forms; survivor-already-listed deduped; a file the per-file re-parse guard cannot rewrite safely is a refusal naming it, with zero writes anywhere), other profiles' `relationships:` targets, and source frontmatter `people:` lists. Prose `[[P-merged]]` mentions are deliberately left for lint W107's gradual-cleanup list (counted and reported). The merged person's generated companion views are deleted (GENERATED-header-verified; hand-written lookalikes kept and warned) and the tombstone's `tier:` is stripped, so `views refresh` regenerates nothing for it; alias resolution registers a tombstone by its bare P-id only - the folded name resolves at the survivor. Idempotent `already` on a re-run of the same merge; refusals (exit 3) for self-merge, unknown ids, a tombstone `--into` target (the message names the chain's final survivor), a different-survivor re-merge, and a rename collision. **Exit-code note:** an unknown/not-found P-id here is exit **3**, deliberately NOT the exit-1 posture the other `confirm` verbs use for a missing target - `merge` reserves exit 1 for "the merge *landed* but carries warnings", so a not-found returning 1 would be indistinguishable from a successful merge-with-homework; keeping refusals at 3 keeps the two outcomes unconfusable for a script. Evidence judgment stays the skill's and the human's: the verb may WARN (e.g. an existing relationship edge between the two), never refuses on evidence grounds. The split (`confirm separate`) stays hand-guided per §9 - deliberately not built. |

`confirm cooccur`/`dismiss` are the write owners for the `fha cooccur` candidates; `confirm xref` for the `fha xref` candidates; `confirm place` for the `fha places candidates` clusters; `confirm discovery` and `confirm draft` are the report's "act on a discovery" and the `write-biography` skill's "accept this draft" gestures made into deterministic, replayable CLI actions; `confirm merge` is the write owner for the `merge-identities` skill's human-confirmed merge decision (SPEC §9 - the skill judges, the human decides, this verb enacts).

## 15a. `fha report` - the session report (research feed)

**Purpose.** The "login screen": one command that refreshes state and tells the researcher where to focus.
Surfaced in the workbench as the `/today` skill (the skill runs the report, then narrates and offers to start the top item, e.g. a `review-claims` session).

**Steps.** (1) `fha photoindex` incremental refresh; (2) `fha index` rebuild; (3) lint in report mode; (4) diff current IDs/statuses against the snapshot in `.cache/last_report.json`; (5) assemble sections; (6) write the new snapshot.

**Sections.** *(Discoveries lead - the report is a research narrative first, a chore list second.)*
0. **Discoveries since last session** - questions answered, contradictions resolved, first corroborations (a claim gaining its first independent second source), profiles newly vital-complete, confirmed connections. With confirmation, each is appended to `notes/discoveries.md` (dated, with `[[S-…]]`/`[[P-…]]` refs) - the durable log of research wins.
1. **Review queue** - suggested claims grouped by source, oldest first (lint W102).
1b. **Worth a second look** - parked needs-review claims (looked at, unsettled - SPEC §8.1; oldest `reviewed:` first) and accepted low-confidence claims (built on, ripe for superseding - SPEC §8.5): counts plus the oldest few each, never the full backlog. Leads, not defects; ranking them into concrete searches is `research-next`'s job.
2. **New since last session** - sources, claims, people added/changed (the snapshot diff).
3. **Vitals gaps** - curated people first, then people touched since last report (lint W101).
4. **Contradictions** - `contradicts:` pairs lacking an open question (lint E009 set).
5. **Search-log awareness** - leads in any section are annotated "already searched (date)" from the search_log; nils older than a configurable horizon (default 18 months) are flagged as worth re-running (collections grow).
5b. **Answerable questions** - open questions whose referenced gap (person+type) now has an accepted claim, or whose referenced C-ids changed status: each *proposed* for `answered [[S-…]]` or review. **Closing requires human confirmation** - the report proposes, never executes.
6. **Photo processing triage** - top N candidates (§15b). This section also carries the refresh scan's own note, printed ahead of the triage list (and ahead of an absent/unreadable-catalog verdict, which the scan often explains): files exiftool could not read, and - when any of them are new or changed, the case where the scan deliberately holds the catalog's date back (§9) - a plain sentence saying the catalog stays marked out of date until they can be read, naming `fha photoindex`. Without it the resulting "photo index is stale" notices elsewhere read as a separate, permanent fault. A candidate group named by a `MISSING:` row is listed under the path it had, pointing at `reconcile` rather than at an `fha process` command whose argument does not exist.
6b. **Place candidates** - recurring unlinked `place_text` clusters and GPS clusters (`fha places candidates`), with elevate-or-dismiss prompts.
7. **Hypotheses & draft queues** - open hypotheses awaiting verification; per-person draft-queue counts (§14b).
7b. **Promotion candidates** - stubs that have earned a real page, stateless: (a) direct-line ancestors still filed as stubs (the W119 set, derived via the shared Ahnentafel walk from `root_person`), closest generations first, each offering `fha person promote`; (b) any stub whose accepted-claim count reaches `promotion: claims_threshold:` in fha.yaml (default 5) - a non-direct claim-heavy stub is now offered the verb too (#80), `fha person promote <P-id> --into connections/` (SPEC §12.3), rather than a dead-end note. Counts plus the top few; leads, never defects; the report proposes, the human promotes.
8. **Possible connections** (`fha cooccur`) - deterministic leads, never facts, with confirm/dismiss prompts: (a) person-pairs co-occurring in ≥2 sources with no relationship edge; (b) accepted claims of different unlinked people sharing a place with overlapping EDTF bounds; (c) recurring organizations/clubs/employers as shared-affiliation hubs. The `/today` skill may narrate judgment on top.

**Place-text oversight escalation (issue #79 point 2).** When one of §6b's own place-text clusters reaches **20 or more claims** sharing one unlinked `place_text`, it is no longer just another §6b candidate to weigh - it is treated as a standing oversight and promoted into a banner printed **above every section**, the same lead position `archive_notes` uses (right under the title, before §0), because a pile that size proved unreliable to reach sitting only at position 10 of 13 (the issue's own motivating case: a 13-month-old archive with 47% of its claims unlinked). Each escalated cluster's line is the identical line §6b itself prints for that cluster (never a second, divergent rendering) and carries a ready-to-run `fha confirm place` command: `--into <existing L-id>` when the cluster's text already matches - exactly, or near enough ignoring word order/abbreviations, the same normalization the claim-write-time resolver (issue #79 point 3, SPEC §15) uses - a place already in `places/places.yaml`, so the human links the cluster instead of minting a duplicate; `--name=...` (mint a new place) only when no registered place matches at all. The banner prints on `--section`-filtered runs too, matching `archive_notes`' own rule - and when the active filter is anything other than `place-candidates` (so §6b itself is not in this run's output), it names the exact follow-up command, `fha report --section place-candidates`, rather than pointing at a section the filtered output omits. The escalated clusters are also exposed on the structured `Result` a headless consumer reads (`data['place_escalations']` as raw cluster dicts, and `data['sections']['place-escalations']` alongside every other section's rendered lines) - not only in the rendered markdown.

Output: markdown to stdout and `.cache/report_{date}.md`.
Flags: `--full` (ignore snapshot), `--section <name>`.

## 15b. `fha photoindex triage` - processing candidates

Answers "which of these thousands of photos deserve source records?" - consumed almost entirely through the report's triage section, rarely called directly.
Ranks unprocessed photo groups (no `source_id`) by evidence signals: +3 caption contains transcribed text; +2 any bare `P-id` person keyword; +1 date pattern at `Y!` or better; +1 group has a `-back` variant (writing likely); −2 AI caption only (no human/verbatim text).
Emit top N with path, signals, and suggested next step (`fha process …`). `--under PATH` / `--not-under PATH` scope the ranking to (or away from) a subtree of the photos root, so a mixed library can be triaged one branch at a time; `photos_ignore:` (§9) is the durable answer for material that should never be catalogued at all.
Feeds report §15a.6. *(Flagged as a future-intelligence focus: a model-assisted scoring pass over caption/UserComment text, learning from past process/skip decisions, is the designed upgrade path - backlog.)*
