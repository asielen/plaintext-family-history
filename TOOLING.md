# TOOLING.md: Plaintext Family History Tooling Design

**Who this is for:** developers building or extending the `fha` tools. To use the archive, start with `GETTING_STARTED.md` in the archive's `docs/` folder.

**Version 2.31, 2026-11-24 · companion to SPEC.md v2.31 (versions track the SPEC)**

SPEC.md states *what* each tool must do; this doc states *how* (schemas, algorithms, commands, edge cases), enough to rebuild any tool in any language. The archive works by hand without the tools, and everything they generate is a disposable cache. A tooling change that affects the spec is made in SPEC.md too.

Sibling docs (linked absolutely because they are not vendored into an installed archive, §13c); the build order for all three is §15:
- this doc: core `fha` tools
- [`TOOLING_INGESTION.md`](https://github.com/asielen/plaintext-family-history/blob/master/TOOLING_INGESTION.md): capture, the inbox and web intake
- [`TOOLING_INTERFACE.md`](https://github.com/asielen/plaintext-family-history/blob/master/TOOLING_INTERFACE.md): workbench + skills

**Operating principles.**
- No daemons, watchers or schedulers: freshness is refresh-on-use (cheap incremental refreshes at the start of tools that need them, e.g. `fha report`).
- Deterministic work belongs in `fha` tools, AI judgment in skills; human review is the only gate to `accepted`. AI passes are always invoked and recorded.
- **Single writer, no lock.** No tool locks files or coordinates processes. One writer at a time: a human or one agent, never both, never two agents; concurrent writers lose changes silently (last writer wins), a real risk in syncing folders (Dropbox, iCloud, OneDrive). `docs/FAQ.md` and `docs/TROUBLESHOOTING.md` say this in plain words.

## 1. Shared foundations

All tools are subcommands of one CLI, **`fha`**: one Python file per tool under `tools/`, each also runnable standalone (`python tools/lint.py`).

**Imports.** Shared code lives in `tools/_lib.py`, which every tool imports. Leaf tools import only `_lib`. The dispatcher, the workbench or a composing tool may import another tool's module to call its engine: `fha.py` (dispatcher) imports every tool; `serve.py` (workbench) the tools it drives; `report.py`, `doctor.py`, `reorganize.py`, `reconcile.py` the tools they compose (some lazily). `site.py` loads by path via `_lib.load_site_module()` (name clash with stdlib `site`). Never an import cycle.

**Environment.** Python ≥ 3.10; `PyYAML`, `Jinja2` (site only); binary `exiftool`; else stdlib. No network except the geocoder's optional gazetteer download.

**Archive root.**
- The directory holding `fha.yaml`, found by walking up from the CWD; `--root PATH` overrides. Record directories are not needed for detection.
- `--spec-root PATH` locates `SPEC.md`/`TOOLING.md` when not at the root. `fha install` writes them at the root and vendors machinery under `.fha/` (`tools/`, `design/`, `browser-companion/`). The spec repo's fixture runs as `fha lint --root example-archive --spec-root .`.
- Every subcommand defines its own `--root`: `fha --root X lint` and `fha lint --root X` both work; the subcommand's wins. Only `lint` has a subcommand-level `--spec-root`; the dispatcher threads the global one through and strips it before forwarding to a subcommand whose parser lacks it (e.g. `doctor`).

**Paths.** Stored paths are alias-form with forward slashes. `resolve_path(p)` maps the first segment (`photos/…`) through `fha.yaml` `roots:` (absolute as-is; relative joined to the root; missing alias → internal directory of that name). Every tool touching assets (lint E011/E012, photoindex, packet, process, site) resolves through it.

**Generated content.** Non-`.md` artifacts (index, photo catalog, logs) live in gitignored `.cache/`. Three conventions:
1. **Whole-file header** (machine-owned, disposable): `<!-- GENERATED by fha <tool> on <date> - do not edit; regenerate instead -->`, first line of generated `.md` views (and of `.html` views under `generated/views/`, before the doctype, §7 D11; a place note, which must open with frontmatter for Obsidian, carries it on the first line after its frontmatter, §7). Lint warns on hand-edits; `fha views clean` deletes by it alone.
2. **Region** (SPEC §21b), one section of a human-owned file rewritten in place: `<!-- GENERATED-BEGIN {region} by {cmd} on {date} -->` … `<!-- GENERATED-END {region} -->`. Used for a profile's `## Sources` and its summary lines under the title (§7, §16); never stripped by `views clean`; `fha packet` drops both from what it ships, `fha wikitree` the summary.
3. **Purpose block** (SPEC §16a): a visible blockquote opening every tool-written document, saying what it is, who writes it and where to work instead. Wording in `_lib`; `fha packet` strips it, `fha site` never renders it.

In the header and region markers the date is when the content last changed, not when it was last regenerated. A writer compares its new text with what is on disk with the marker dates masked (`_lib.generated_text_differs`) and leaves the file alone when only the date would change, so a refresh with nothing new writes no files.

**Parsing (`_lib.py`).**

```python
ID_RE    = re.compile(r'\b([PSCLH])-([0-9a-hjkmnp-tv-z]{10})\b', re.I)  # Crockford Base32
TOKEN_RE = re.compile(r'\[\[?([PSCLH]-[0-9a-hjkmnp-tv-z]{10})(?:#[^|\]]*)?(?:\|[^\]]*)?\]\]?', re.I)
FRONT_RE = re.compile(r'\A---\r?\n(.*?)\r?\n---\r?\n', re.S)
CLAIMS_RE = re.compile(r'^## Claims.*?```yaml\r?\n(.*?)```', re.S | re.M)
```

- `TOKEN_RE` is the one ID chokepoint (`[[ID]]`, `[[ID|text]]`, `[[ID#frag]]`, and a file-stem target `[[{stem}_{ID}…]]`; group 1 = ID). `WIKILINK_RE` matches `[[name/stem]]` for the citation indexer and `fha normalize-links`; `LEGACY_TOKEN_RE` finds single-bracket `[ID]` for `normalize-links` to upgrade.
- `link_parts(target, display)` is the one link resolver every reader goes through (`extract_tokens`, `extract_wikilinks`, `strip_link_wrapper` and the site, views and WikiTree renderers call it). A file-stem target reads as the ID it ends in, whatever its leading part says, so a stem left stale by a rename still resolves. A source target whose display is exactly a claim ID (`[[source_stem#Claims|c-…]]`) reads as that claim with no display, and a display that is exactly the link's own ID is no display (`[[source_stem|s-…]]` reads as `[[s-…]]`, one footnote on the site; WikiTree shows such a person link by the person's name, or `[living person]`, like `[[p-…]]`). The `#fragment` never changes resolution. A reader asking which sources a text cites uses `cited_source_ids`, which counts a claim link as the source holding the claim (falling back to the source a `[[source_stem|c-…]]` link names when the claim is unknown): the WikiTree restricted-source gate, its citations and dates, the draft queue, the report backlog and the lint summary check. Its `for_gate=True` mode, used by the WikiTree gate, also counts the source a link names when that differs from the claim's own source, so a restriction on either one refuses. `ID_RE` treats an underscore as an edge, so the ID at the end of a stem is found by every bare-ID scan.
- Other links resolve through the alias map (`build_alias_map`/`resolve_ref`); a non-ID `[[stem]]` that no record claims as an alias is an inert note-link. Alias keys are the `aliases:` text as written (`alias_key_text`), never read down to an ID.
- `LinkWriter` is the one link formatter every writer goes through (SPEC §18 link mode); `link_writer(archive_root, fha_config)` builds it from `fha.yaml`'s `links:` (`link_mode`; an unknown value reads as `id`). A writer builds the ID form it always has and passes it through the writer: `link`, `convert`, the `links=` argument of `link_entry`/`yaml_link_item`/`link_list_lines` (a source's `people:`), or `convert_written_links(before, after, links)`, which converts only the lines a verb wrote and leaves every other line byte for byte. In `id` mode all of these return their input unchanged and read nothing on disk, so the archive files a verb writes are the same bytes in an archive that never sets `links:`. In `obsidian` mode a person or source link targets the record's file stem (people/ and sources/ file names, read once per run; a person's stem is its profile), a claim link targets its source's stem with `#Claims` and the claim ID as display (the claim's source found by scanning sources/), a place link targets its place note's stem (`places/{slug}_{l-id}.md`, written by `fha views places`, §7; a place with no note keeps the ID form), and a missing display becomes the person's or place's `name` or the source's ID. A link to a merged person points at the survivor its tombstone names, and one to a merged source at the keeper whose `aliases:` hold its ID. Place links with no note, unknown IDs, a claim link with its own display, an `![[…]]` embed, and anything on a `_link_line_kinds` 'skip' line (`id:`, `aliases:`, code, GENERATED-BEGIN/END regions) or in inline code keep their form. Code is `code_line_mask`, the one code tracker the link scanners share (normalize-links too): a fence closes only on the same character with a run at least as long, and a four-space-indented block after a blank line is code unless it continues a list. A frontmatter link outside double quotes gets no added display, since an unquoted `[[…]]` is a YAML list. In a table (`table_line_mask`: the rows around a `--- | ---` separator, edge pipes or not) the display is written `[[stem\|Name]]`, Obsidian's own table form, and every reader (`link_parts`, `TOKEN_RE`, `extract_wikilinks`) reads `\|` as the separator in either mode. `rewrite_record_links_to_stems` applies the same rule to a whole record for `fha normalize-links --obsidian` and lint W161, so the warning and the fix cannot disagree. The writers: `fha process` and the mining import (`people:`), `fha claim` and `fha lint --fix-applied`/`--fix-reciprocal` (`relationships:` entries), `fha person relate`/`edit`/`note`/`edit-note`, `fha source note`/`edit-note`/`merge`, `fha confirm merge`/`discovery`, `fha views` (companion files, place notes and the summary and `## Sources` regions), `fha relate`'s output, and `normalize-links`. `rewrite_stale_stem_links(text, stems)` re-points only links already written with a file name that is no longer current (`fha views places` after a place rename), leaving ID-form links and displays alone; it is the rename rewrite below in its `follow_only` form, so the two cannot disagree. A claim's `persons:` stays in the ID form in both modes.
- Renames in `obsidian` mode (SPEC §18): every verb that renames or removes a record file points the links to it at its current file in the same run, with the same rewrite (`rewrite_record_links_to_stems`). `rename_link_writer(archive_root, fha_config, ids, stems=, names=, survivors=, claim_sources=, old_stems=)` returns a `LinkWriter` set up for the archive as it will be after the rename (`LinkWriter.expect_renamed`), touching only links to those records: by ID, by any file stem ending in the ID, a claim link whose claim or source is one of them, and, with `old_stems`, a plain `[[old name]]` that Obsidian followed by a file name the rename retires; in `id` mode it returns None. `plan_rename_links(archive_root, links, pending=, gone=)` computes the edits over `link_record_files` (people/, sources/, notes/; no templates, no GENERATED files) before anything is written, reading `pending` text for a file the verb is writing anyway, so `--dry-run` prints the count the write makes; `rename_links_message` is that line ("Pointed 4 links in 3 files at …"), printed only when there is at least one. The verb writes the edits inside its own undo, on a failure or a Ctrl+C alike. `write_rename_links` restores every file it wrote before raising and lists any it could not put back on the exception (`rename_links_stuck`), and the verb names those files and what they hold (`rename_links_stuck_text`) instead of claiming a clean undo. An undo step is registered only once its write has landed, so a file the run could not write (read-only, held open) is never "restored" and reported as damage. The verbs: `fha person rename` (the new stem and name), `fha confirm merge` (links to the merged person go to the survivor, folded into the merge's plan, and the W107 count is taken after them), `fha source merge` (links to the retiree and claim links to its claims go to the keeper) and `fha lint --fix-ids` (a `[[old name]]` link becomes `[[new_stem|old name]]`). `fha person promote`, the W110 folder moves and `fha process refile` move a record file to another folder under the same name, which Obsidian still finds, so they change no link.
- `read_record(path)` → `{meta, claims, stories, body}` + `parse_errors`; never raises. YAML booleans/dates become canonical strings (`living`: `'true'|'false'|'unknown'`; ISO dates).
- Person companions (`_research`, `_view_timeline`, `_view_draft-queue`) link via `person_files`. The kind word counts only immediately before `_{p-id}` (`parse_filename`, SPEC §13).
- An unparseable claims block is a lint error, never a crash. All IO is UTF-8.

**Writing a record.** `write_text_exact_atomic`: sibling temp file, `fsync`, `os.replace`; a failed write leaves the old bytes. Line endings byte-faithful (`newline=''`). Keeps an existing file's mode, group and owner; new files get the umask default. A file the caller cannot write is refused with `PermissionError` before any temp file (read-only pins a record). A link target is replaced, not written through; xattrs/ACLs are not kept; a read-only parent folder refuses.

**EDTF.** Tools need validation and sortable bounds. `edtf_bounds(s) -> (min_iso, max_iso)`:

| EDTF | min | max |
|---|---|---|
| `1850` | 1850-01-01 | 1850-12-31 |
| `1850~` / `1850?` | 1849-01-01 | 1851-12-31 |
| `185X` | 1850-01-01 | 1859-12-31 |
| `1850-05` | 1850-05-01 | 1850-05-31 |
| `1850-~05` / `1850-05~` | 1850-04-01 | 1850-06-30 |
| `[..1920]` | 0001-01-01 | 1920-12-31 |
| `[1920..]` | 1920-01-01 | 9999-12-31 |
| `A/B` | min(A) | max(B) |

- Anything outside this subset is lint `E014`, including `1920/..` (one spelling per meaning, SPEC §11).
- An interval must run forwards: `min(A) <= max(B)` (`1950/1940`, `[1920..]/1910` refused; `1941~/1940` passes). Checked in `is_valid_edtf`, so it binds lint, `normalize_date` and every `--date` flag (`claim`, `claim new`, `person estimate`, `process`, `find`). Impossible dates (`[1900-02-31..]`) are refused.
- `normalize_date`: `before`/`bef` → `[..X]`; `after`/`aft`/`on or after`/`later than` → `[X..]`; trailing dots after such a word are noise. Hedges are kept on both ends: `about 1891-1893` → `1891~/1893~`, `maybe 1880-1885` → `1880?/1885?`. Refused with a plain `format_edtf_error` message: a backwards range (never swapped), a hedged decade, a hedged backwards range, before/after on a decade or range (offers `[1880..]` or `after 1889`), a bare `1850..`.
- Backwards message shape: *"date '1950/1940' runs backwards: it starts at 1950 but ends earlier, at 1940 … if you meant 1940 to 1950, write 1940/1950; if one of the two dates is a typo, correct that one."*
- `[X..]` sorts at its start, ranks in `vital_pick_key`'s wide tier below dated claims, reads "after X" (`humanize_edtf`), and is quoted on write (`'[1920..]'`). GEDCOM: `AFT X` both ways; `1910/[1920..]` → `AFT 1910`; `[..1900]/1910` → `BEF 1910`; open both ends → no date. Date spreads omit open sentinels (`format_date_spread`).

**Exit codes (all tools):** `0` clean · `1` warnings only · `2` errors · `3` tool failure. `--json` for machines; human lines are `SEVERITY CODE path: message`.

**Result contract.** `run_*` computes and returns `_lib.Result`; it prints no report text and never calls `sys.exit` (file writes and prompts may happen inside). `_cmd_*` alone renders it and returns the exit code. Fields: `ok`, `exit_code`, `data` (JSON-serializable), `messages` (`Message{level, text, next_step, code, path}`; a lint finding maps onto it), `changed` (paths written; empty under `--dry-run`). `lint` is the reference (§3). Every caller (terminal, agent, report orchestrator §15a, workbench) calls the same `run_*`; write-backs (§3b, §14a, §14a2, §15a) run only at a human's direction.

**Restriction (all exports).**
- `restricted` on a source, claim, person or name is excluded from public output. `fha packet` excludes it by default; `--include-restricted` opens plain restrictions; `dna` also needs `--include-dna`; `by-request` has no override. Restricted names resolve internally and redact on export.
- A source with `rights.publication_ok: false` (SPEC A.6) is left out exactly like a plain `restricted` source, by the index's `publication_ok = 0`: `site`, `gedcom` and `wikitree` withhold it; `packet` withholds it unless `--include-restricted` and names it in the README as "not cleared for sharing".
- Enforced by ID in `site`, `wikitree`, `packet`, `gedcom`: the person's record, page, tree position, facts and `[[p-id]]` links (shown as the redaction label). Names in free text are not matched.
- **Privacy carries through a merge** (`_lib.carry_to_survivors`). A tombstone's `restricted:` or explicit `living: true` (`living_carried_to_survivors`) keeps its survivor out of `site`, `packet`, `gedcom` and `wikitree` too: the claims `fha index` hands the survivor are about the same human. A tombstone's `unknown` or missing `living:` carries nothing; the survivor's own `living: false` wins. A refusal names the tombstone file whose `living: true` holds the survivor back (`living_tombstones_of`), since `fha person set-living` on a merged record acts on the survivor.
- An unreadable `restricted:` marker means restricted (`read_restriction_marker`): non-UTF-8, no or invalid frontmatter, or frontmatter that is not a mapping. `fha index` still keeps such a person's row from the filename's p-id (name `unknown`, `living: unknown`).
- **A shared privacy reader for GEDCOM and new exporters** (`_lib.export_privacy`): `gedcom`, and any new exporter that is not the site, reads what the record files withhold through it, once per run, and so does the site's search file as a second gate beside the site's own rules (`packet` and `wikitree` still keep their own readers): restricted people, sources and claims, the files that would not read, and the survivors a restricted tombstone speaks through. Beside it, `public_source_sql` is the index's own source filter, `person_withheld` is the site's redaction rule (living, unknown or restricted, merges followed; a caller asking about everyone passes `living_carried_to_survivors` in once as `carried`), and `export_tie_ok` is the family-walk rule: a relationship line or tree number may pass through a living or unknown relative, never named, but not through a restricted one or on withheld evidence. `fha views family-sheet` and the printed reports that follow read through all of them.
- **One rule for a claim that names a living person** (`_lib.claim_people_verdict`, SPEC §21), read by `site`, `gedcom` and `wikitree`, each with its own living and restricted tests: withheld when it names a restricted person (by-request included); when it is an event of a living or unknown person's own (`claim_subjects`: the `child`, `deceased` or a `spouse`, plus anyone it leaves unroled or gives a misspelling of that role); when it is a `relationship` claim naming one; or, on any other claim, when everyone it is about (`subject`/`head`/`household_member`, else everyone it names) is living or unknown. Otherwise, when it names a living or unknown person, kept without its wording and without that person (a godparent on a baptism, a living child in a census household); otherwise shown. A copy may be stricter, never looser. `packet` is a private export (§8) and does not use it.

## 2. `fha index`: the index builder

Rebuilds `.cache/index.sqlite` from the tree: the query surface for every tool and for ad-hoc `sqlite3`. Never appended to, never authoritative.

**Build.**
1. Glob `sources/**/*.md`, `people/**/*.md`, `places/places.yaml`, `notes/**/*.md`; parse each (§1).
2. Insert in one transaction, building `aliases` from every `aliases:` plus person/place names and variants.
3. Scan prose for `TOKEN_RE` → `citations`, storing the resolved canonical ID.
4. Resolve frontmatter links (`people:`, `places:`, note `persons:`/`sources:`) → `source_people`, `source_places`. A source gets a `c-…` alias only when a `[[c-…]]` citation exists.
5. Glob asset trees for s-id filenames → reconcile `source_files`.
6. Load question entries with working answers (SPEC §17a-b) → `hypotheses`; `notes/research-log.md` (§17c, including `fha capture` entries) → `search_log`.
7. Build FTS tables.

Target: ~5k sources / ~30k claims in under a minute; correctness first.

The tool reads captures from `notes/research-log.md`.

**Incremental.** `fha index --source s-xxxx` upserts one source (run after review sessions). Delete children first: claim IDs → `claim_persons`, `claim_links`, then `claims`; `sources.path` → `citations`, `notes_fts` (no FTS cascade); then `sources`, `source_files`, `source_people`. Any incremental/full difference is an incremental bug.

**Unreadable input** (full and `--source` alike):
- A record whose YAML fails: one warning per record, code **E010** (same as lint), naming the archive-relative path, what is lost (claims, or the whole record), the parser's line/column with a valid example, and the fix. Listed in `data['unreadable_records']`. Never guessed at.
- A non-UTF-8 file in `notes/**` or the research log (catch `UnicodeDecodeError`, a `ValueError`): one warning naming the files, saying their words are missing from `fha find --text` and their searches from the log, that the file is untouched, and to re-save as UTF-8. Never rewritten.

**Exit codes.** `0` clean. `1` warnings (unopenable folder, unparseable record, hand-edited `places.yaml` coords, `roots:` change orphaning assets). `3` no `fha.yaml`, malformed `fha.yaml`, or a bad / unknown `--source` or no full index to update. No `2`: an incomplete cache is still usable; `fha lint` names the repair.

**Schema.** Table `meta` (and `PRAGMA user_version`) holds the schema version; readers refuse a mismatched index until rebuilt.

```sql
CREATE TABLE persons(id TEXT PRIMARY KEY, name TEXT NOT NULL, surname TEXT, sex TEXT,
  living TEXT NOT NULL,  -- 'true'|'false'|'unknown' (unknown = living for exports)
  tier TEXT NOT NULL, status TEXT DEFAULT 'active', merged_into TEXT,
  no_known_marriages INTEGER DEFAULT 0, no_known_children INTEGER DEFAULT 0,
  birth TEXT, death TEXT,  -- provisional unsourced estimates (§9)
  path TEXT NOT NULL);
CREATE TABLE person_variants(person_id TEXT, variant TEXT);
CREATE TABLE person_face_tags(person_id TEXT, tag TEXT);
CREATE TABLE person_files(person_id TEXT, kind TEXT, path TEXT, generated INTEGER DEFAULT 0,
  PRIMARY KEY(person_id, kind));  -- profile | research | timeline | draft-queue
CREATE TABLE person_external(person_id TEXT, system TEXT, ext_id TEXT);
CREATE TABLE sources(id TEXT PRIMARY KEY, title TEXT NOT NULL, source_type TEXT,
  date_edtf TEXT, date_min TEXT, date_max TEXT, repository TEXT, restricted INTEGER DEFAULT 0,
  source_class TEXT, publication_ok INTEGER,  -- from rights.publication_ok
  status TEXT DEFAULT 'active', superseded_by TEXT, path TEXT NOT NULL);
CREATE TABLE source_files(source_id TEXT, path TEXT, role TEXT, copy TEXT,
  derived INTEGER DEFAULT 0, original_filename TEXT, date_edtf TEXT,
  exists_on_disk INTEGER, in_inventory INTEGER,
  is_primary INTEGER DEFAULT 0);  -- 1 on the source's main file (SPEC §14)
CREATE TABLE claims(id TEXT PRIMARY KEY, source_id TEXT NOT NULL, type TEXT NOT NULL,
  subtype TEXT, date_edtf TEXT, date_min TEXT, date_max TEXT, place_id TEXT, place_text TEXT,
  value TEXT NOT NULL, status TEXT NOT NULL, reviewed TEXT, confidence TEXT, information TEXT,
  evidence TEXT, anchor TEXT, hypothesis TEXT, negated INTEGER DEFAULT 0, notes TEXT);
CREATE TABLE claim_persons(claim_id TEXT, person_id TEXT, position INTEGER, role TEXT);
CREATE TABLE claim_links(claim_id TEXT, rel TEXT, target_id TEXT);  -- corroborates|contradicts
CREATE TABLE source_people(source_id TEXT, person_id TEXT);
CREATE TABLE source_places(source_id TEXT, place_id TEXT);
CREATE TABLE relationships(person_id TEXT,
  rel TEXT,  -- parent|child|spouse|friend|associate|neighbor
  other_id TEXT, claim_id TEXT, date_start TEXT, date_end TEXT,
  UNIQUE(person_id, rel, other_id, claim_id));
CREATE TABLE places(id TEXT PRIMARY KEY, name TEXT, hierarchy TEXT, within TEXT,
  lat REAL, lon REAL, notes TEXT);
CREATE TABLE place_names(place_id TEXT, alt_name TEXT);
CREATE TABLE place_history(place_id TEXT, period_edtf TEXT, date_min TEXT, date_max TEXT, hierarchy TEXT);
CREATE TABLE search_log(date TEXT, person_id TEXT, question TEXT, repository TEXT,
  collection TEXT, years TEXT, terms TEXT, result TEXT, source_id TEXT, path TEXT);
CREATE TABLE hypotheses(id TEXT PRIMARY KEY, person_id TEXT, question TEXT, guess TEXT,
  basis TEXT, verify TEXT, origin TEXT, status TEXT, path TEXT);
CREATE TABLE hypothesis_persons(hypothesis_id TEXT, person_id TEXT);  -- the people in refs:
CREATE TABLE citations(token TEXT, kind TEXT, path TEXT, line INTEGER);
CREATE TABLE aliases(alias TEXT, canonical_id TEXT, kind TEXT);  -- id|stem|name|variant|claim
CREATE VIRTUAL TABLE notes_fts USING fts5(path, content);
CREATE VIRTUAL TABLE transcripts_fts USING fts5(source_id, path, content);
```

- Lookup indexes `idx_{table}_{col}` on `claims(source_id)`, `claim_persons(claim_id)`, `claim_persons(person_id)`, `source_files(source_id)`, `source_people(source_id)`, `source_people(person_id)`.

- `claim_persons.role`: every role that person carries, in `roles:` order, joined by U+001F, control characters dropped (`clean_role_word`); NULL if none. Read only via `_lib.claim_role_pairs`.
- `aliases.alias` is lowercased: each record's ID, stems, on-demand c-ids, names and variants, the resolution surface of `find`, `lint`, `normalize-links`.
- `transcripts_fts`: every `files:` entry with role `transcript`, `transcription` or `extracted-text` that is a `.md`/`.txt` on disk.
- Lookup indexes are created `IF NOT EXISTS` on every write open, so old caches gain them without a version bump; readers never create them (it would hide staleness). Queries whose order reaches output say `ORDER BY` (often `rowid`).
- `person_files.kind` must be one of profile, research, timeline, draft-queue (`sources-index` writes no companion, §7); current code still lists `sources-index` in `_lib.COMPANION_KINDS`.

**Relationship derivation** (accepted claims only; edges are pure cache, traversal crosses in-law branches):
- `relationship` whose `roles:` name a `child` and a `parent` → `child` edge (subject → parents) + reciprocal `parent` edges, whatever its `subtype:` nature. `birth` → the same pair, by roles only.
- `marriage`, and `relationship` whose `roles:` name `spouse`s → reciprocal `spouse` edges dated from the claim; `date_end` from a `divorce` between the pair or a `death` of either.
- Social subtypes → `friend` / `associate` / `neighbor`.
- A `relationship` claim yields every tie its roles support (`_lib.relationship_claim_parties`, SPEC §8.3): a child, a parent and a couple on one claim give both the parent edges and the spouse edges, and power-tie roles add their edges beside them. The index, lint W159 and the `relationships:` writer (`claim_owed_relationship_entries`, used by `fha claim` and `--fix-applied`) read the same rule.
- Every role a person carries counts (`roles_by_person`, SPEC §8.3); `roles:` order never decides. A person named twice (`[p-a, "[[Alice Smith]]"]`) counts once.
- Kin synonyms read as the role they name (`_lib.role_meaning`, SPEC §8.3): `mother`/`father` → `parent`, `son`/`daughter` → `child`, `husband`/`wife` → `spouse`. Every role comparison goes through it.
- Only `persons:` entries are candidates (`resolve_claim_persons_with_roles`): a `roles:` target that is not in `persons:` is dropped before `vital_subjects`, `spouse_parties` and `parentage_parties` see it. Lint W133 reports it, because dropping it can leave one unroled person read as the subject.

*Couples (`_lib.spouse_parties`)* (index edges and divorce `date_end`, `fha gedcom` FAM placement, lint W115/W125). Scoped by `roles:`, never by all of `persons:`:
1. `spouse:` names ≥2 distinct persons → those (≥3 = serial marriages, all pairings).
2. Else exactly two distinct persons, neither holding only non-spouse roles → those two. A `spouse:` list resolving to <2 falls through here.
3. Else no edge (`{spouse: [p-a], parent: [p-b]}` never pairs them). A false spouse edge reads as fact downstream; a missing one is only missing. W125 reports couple claims with ≥2 distinct persons and no couple.

*Parentage (`_lib.parentage_parties`)* (index `birth` and `relationship`; lint W126). Directed, so no two-person fallback:
- `birth` with `roles:` naming a `child` and a `parent` mints the same pair as a `relationship` claim does. Unroled → nothing.
- Child and parent on one claim → child only; both sides of a directional tie (`employer`/`employee`, `enslaver`/`enslaved`) → no self-edge.
- A map naming the child and a role for everyone else, with no parent, is complete and silent.
- W126: ≥2 distinct people, no parent edge, and no `child` or someone unroled; or a person who is both child and parent.
- `baptism`, `burial` are not derived; adding a type needs W126 coverage.

**Significance** is computed at query time from the SPEC §8.2 table (`_lib.SIGNIFICANCE`). No per-claim override.

## 3. `fha lint`: the linter

**Purpose.** Verify the archive against SPEC. Report-only by default. Lint runs file-by-file checks, then cross-file passes over a fresh in-memory index it builds itself; it never requires `fha index` to have run.

**Exit code.** 0 when clean; non-zero when any error or warning is reported. Informational lists never move the exit code.

**Messages.** Every finding names the file, the plain problem and the next step (a command that exists, or the exact hand edit). Warnings that describe a normal research state are worded as leads, not defects.

**Needs-sourcing backlog** (informational, never moves the exit code): a provisional `birth:`/`death:` (§9) or a `(TODO: import source)` line with no backing accepted claim. **Formatter** (`--format-check` / `--format-write`): `--format-check` reports (W109) and writes nothing; `--format-write` applies the same changes (`--dry-run` previews).
- Every `.md` file gets LF line endings and one final newline.
- Source records and person profiles also get: frontmatter keys in the SPEC §14 / §9 order (keys it does not know keep their own order after the known ones), each `files:` entry's keys in the §14 order, IDs lowercase in ID fields only (frontmatter `id`, `aliases`, `people`, `places`, `merged_into`, a `relationships:` entry's `to`/`claims`/`source`/`hypothesis`; a claim's `id`, `persons`, `roles`, `place`, `corroborates`, `contradicts`, `hypothesis`), `value` first in each claim, runs of blank lines outside fenced blocks collapsed to one, and `##` sections in the §14 / §16 order.
- It works on lines, not a YAML round-trip, so frontmatter comments survive and a leading BOM is kept. Left whole and reported: a file whose header is not opened and closed by bare `---` lines, or does not read as YAML, and a claims block that does not open with a claim. Kept as content: blank lines inside fenced blocks (a fence closes only on an equal-or-longer fence), HTML comments, GENERATED regions and indented code. Each rewritten frontmatter or claims block must parse back to the same data or the file is left alone.
- Sections move whole, and only when nothing is in doubt: every heading is a usual one or an owner's own heading that already sits after them all, no heading repeats, no comment or `<!-- private -->` fence spans two sections, and no text says "above" or "below". Otherwise the order is reported for a human to fix.
- It never rewrites or reflows prose, and never touches a filename. Link normalization is `fha normalize-links` (§17), not the formatter.

**Fix modes** (each behind its flag; `--dry-run` previews):
- `--mint-stubs` (E005): create stubs in `people/stubs/`.
- `--spawn-questions` (E009): append a question entry to `notes/questions.md`.
- `--fix-claims-fence` (W114): wrap unfenced `## Claims` content in a yaml fence.
- `--fix-ids`: mint and rename an id-less hand-authored record to the §13 grammar, keeping the slug and old stem as aliases (after a person's name and public other names). An old name that another `.md` file in the archive also carries (any case, dot-folders skipped as Obsidian skips them) is left as written and reported for a hand fix, since the link may mean that file. A template placeholder id (all underscores) counts as missing. GENERATED files and READMEs are never minted. A guess for the same tie is never folded or deleted: the sourced entry is added beside it, and W155 names the guess for the owner to remove. The same header check and refusals as `--fix-reciprocal`; `--dry-run` prints them.
- `--fix-surnames` (W138): write the implied `surname:` line after `name:`.
- `--fix-aliases` (W111): bring `aliases:` into step with the shared mirror rule (`_lib.sync_person_aliases`, the same one every name-writing verb uses): the own ID first, then a person's `name:` and the public values of `name_variants:`, `name_at_birth:`, `married_name:` and `also_known_as:`; a restricted value from any of those fields is taken out (written plain, as `"[[Name]]"`, or as an unquoted `[[Name]]`, all read as one handle by `_lib.alias_entry_key`), the only removal, and counted rather than named in the output. Entries a human added (and old names) stay, and existing entries keep their text. E011 has no lint fix mode; `fha reconcile` is the fixer.

**Checking only what changed** (`--changed [REF]`, REF defaults to `HEAD`): every check still runs over the whole archive, because the cross-record checks are only right with every record read, but the report keeps only the findings on files that differ from the git commit REF (staged or not, deleted ones included), on new files git does not ignore, and on the records those files name by ID or that name a record they hold. A deleted file's ID comes from its name, so the records still linking to it are reported. An ID an edit removed (in the file's text at REF but not now) is followed both ways as well, so deleting a question block brings in the claims it named. Links written only as a name are not followed. A finding on a folder of records is kept when the folder holds a file in scope; findings about the archive as a whole (fha.yaml, places.yaml, AGENTS.md) and W123/W128 are always kept. The asset folders an archive keeps out of git (documents, photos, or roots outside the repository) never count as changed, so every finding that reads files on disk is always kept too: E011, E012, W131 and W137 (a deleted or moved scan still shows). The needs-sourcing backlog is left out. Exit codes count the kept findings. When fha.yaml or places/places.yaml has changed (files no record lives in but every record can depend on), it says so in one line and reports the whole archive; it does the same outside a git repository and for a REF git does not know. A fix flag or `--format-write` is refused beside it, because those work on the whole archive. It is the quick check before a commit; a full `fha lint` stays the check before a release and after `fha update-tools`.

**Timings** (`--timings`): after the report, the seconds each group of checks took, once, on stderr (so `--json` output stays one document).

**Speed.** A check that asks a question per person or per claim reads the archive once into an index and looks the answer up (the accepted claims naming each person, the kin claims naming each person, the question blocks, the resolved asset roots and folders). It never walks every claim again for each person.

**Dates that cannot all be true (W163-W170).** These read accepted, non-negated claims only, and merge every accepted claim of one type for one person into one range (the earliest start to the latest end), so two readings of one birth widen the range instead of firing; that disagreement is `fha xref`'s. A check fires only when the conflict holds for every date the claims allow: a year-only date spans its year, a date marked `~`, `?` or `%` (on the day or month as much as on the year) widens at least a year each way, an interval written backwards is not read, and an open side (the start of `[..1890]`, the end of `[1890..]`) is unknown and never fires one. The family checks (W167-W169) read birth ties only, since an adoptive or step parent can be younger than the child or dead before the birth, and a mother's rule applies only to a parent recorded `sex: F`; any other parent gets the father's, more generous, rule. The rules live in `_lib` (`one_person_problems`, `family_problems`), so every tool that asks them gets the same answer. W173 reads the same accepted claims the other way: it asks whether someone still marked `living: unknown` was born more than 110 years ago, and only asks.

**Leads to check.** After the findings, lint can print a short list headed "Leads to check (informational, not errors)". It never moves the exit code, `--changed` leaves it out, and it is not in `--json`. A lead is something a correct record can carry, so it is not a warning he could clear. The first lead is a person with no `sex:` whose first name is shared by at least five people in the same archive who do have one, at least 95% of them one sex. It says how many, tells him to find a record that states the sex, and names `fha person set-sex` for him to run. Only the archive's own people are counted; a name never sets `sex:` (SPEC §9).

**Vocabularies.** Claim `status` and `confidence` are closed sets (E019). `source_type` is open: an unrecognized value is W109. A tool derives a default `confidence` from `source_type` when it mints a claim. The `restricted:` marker is open like `subtype`: `true` or any free-text type is valid on a source, claim, person or name entry; export paths enforce it (§1, §8, §12, §13).

**Summary-block parsing (E013).** The block is the run of `**Label:** …` entries after the H1 and before the first `##`, leaving out the generated `summary` region (that one is the tools' own reading of the claims, rewritten by `fha views summary`). Labels: `Born`, `Died`, `Married`, `Parents`, `Children`. Entries may be one per line or several on one line, so scan for label positions and split between them, never by line. From each segment take the `[[s-…]]` and `[[p-…]]` IDs (display and fragment ignored). Each source ID must back an accepted claim of the matching type for this person from that source (`birth` also counts on `Parents`/`Children`). Each person ID on `Parents`/`Children` must match a derived parent edge, from a `relationship` claim, or a `birth` claim whose `roles:` names a child and a parent; a negated claim backs nothing.

## 3a. `fha doctor`: archive health

One read-only command answering "what is wrong with this archive?". Run it first after a machine move; other tools' error messages point here. `Result.data` carries `lines` (report text), `checks` (`{id, status, detail, next_step}`, status ok/info/warn/error) and `counts`. Exit codes as §1 (0 clean, 1 warnings, 2 errors); info never changes the exit code.

**Every `next:` is runnable:** spelled with the launcher (`./fha …`, `.\fha …` on Windows) and `--root "<archive>"`, since `fha` is a file at the archive root, not a program on PATH. One top line explains the prefix. `checks[].next_step` uses the same spelling.

**Absent caches (decision D5).** A missing index or photoindex reports "not yet built" at exit 1, not 2, so doctor is safe on a fresh archive or after wiping `.cache/`.

### Git checks

Both ask git, never hand-parse the files, and are silent when git cannot answer.
- **`.gitattributes`** (needs `.git` at the archive root): for each mapped root inside the archive, `git check-attr text` over probes (`.txt .csv .md .ged .jpg`, none). Anything but `unset` warns; suggested fix `<root>/** -text`, quoted if it holds a space.
- **`.gitignore`** (any enclosing repo, even with no `.git` at the archive root): `git -c core.quotePath=false check-ignore -v` over every root alias name and every `sources/` subfolder, output decoded as UTF-8, because an unanchored `photos/` also matches `sources/photos/`. Top-level `.gitignore`: anchor it (`/photos/`); nested `.gitignore`: remove the line or add `!photos/` after it; `.git/info/exclude` or global `core.excludesFile`: outside the archive, so add a negation to the root `.gitignore`. `!`-negated `-v` lines are not findings.

### Back scans

For each photo listed in a source's `files:`, look beside it for an unlisted `{base_id}-back`/`_back` image or PDF (filename comparison only; photos are never renamed). Grouping uses `fha process`'s variation grammar, keyed by `(folder, base_id)`. Files listed under any role are dropped first; groups that already list a back are still scanned. Copy-lettered listed files are skipped (a copy is a separate print). A listed main file missing from disk is reported instead, routing to `fha reconcile` or a hand fix.
- **One candidate** (`orphaned_back_photos`): one runnable, shell-quoted `fha process <main> --more <back> back`.
- **Several for one main file** (`ambiguous_back_photos`): no guess; one complete command per candidate; never advise renaming or deleting a photos-root file.
- **Candidate where a back is already listed** (`duplicate_back_photos`): investigate by hand; no attach command.

Photos root only; documents-root backs are pulled in at import (§6).

### `wrong_main_image`

By filename only: group a record's photos-root `files:` by folder and grouping stem; in a group of 2+ holding the `is_primary: true` entry, compare it with the variation-primary pick (plain scan, then front, then other). Report only when the marked file ranks worse (two plain scans or two fronts are a human's even choice). `next:` is `fha source set-primary <s-id> --file <front> --root ...` (§3d), bare filename when unique on the record, else full alias.

Doctor does not detect bit rot; that belongs to the backup strategy. A `--fixity` checksum option is an idea (see BACKLOG.md).

## 3b. `fha claim`: claim-review write-back and minting

Move an existing claim's `status:` (stamping the review), correct its fields, or mint a new claim onto a source.

```
fha claim <c-id> [<c-id> …]
                 [--status accepted|disputed|rejected|superseded|suggested]
                 [--value "…"] [--date EDTF] [--type TYPE] [--place l-id] [--place-text TEXT]
                 [--persons p-id[,p-id…]] [--confidence high|medium|low]
                 [--information primary|secondary|undetermined]
                 [--evidence direct|indirect|negative] [--anchor TEXT] [--notes TEXT]
                 [--clear FIELD ...] [--reviewed DATE] [--reviewed-by NAME] [--keep-living]
                 [--root PATH] [--dry-run]

fha claim new --source s-id --type TYPE --value "…" [--date DATE]
              [--place l-id] [--place-text TEXT] [--persons p-id[,p-id…]] [--subtype WORD]
              [--status suggested|accepted] [--negated] [--confidence high|medium|low]
              [--information primary|secondary|undetermined]
              [--evidence direct|indirect|negative] [--anchor TEXT] [--notes TEXT]
              [--reviewed-by NAME] [--keep-living] [--root PATH] [--dry-run]
```

### Review contract (SPEC §8.2, §8.4, §8.5)

- Only the human accepts, by directing this tool; it never accepts on its own.
- `--status accepted` always writes `reviewed:` (`--reviewed DATE`, else today; lint E006).
- Every status move writes `reviewed_by: human` on the next line, or `--reviewed-by NAME`. `claim new` writes the pair on an `accepted` mint, neither on `suggested`. `fha confirm cooccur --accept` and `fha serve`'s review route share the engine. Nothing back-fills; a rerun at the same status and date writes nothing.
- `disputed` (actively contested, e.g. a `contradicts:` standoff), `rejected` (ruled out) and `superseded` change status, never delete.

**Field edits.** `--status` is optional; at least one status, field flag or `--clear` is required.
- Field flags REPLACE (no append); `--persons` replaces the whole list. Validation is shared with `claim new`; `--information`/`--evidence` use §8.5's vocabularies.
- `--value` is refused on a block-scalar `value:`. `--notes` may replace a block-scalar `notes:` (whole span replaced).
- `--persons` that drops someone the existing `roles:` still names by bare p-id is refused (W133). `roles:` has no flag; edit by hand.
- A live write echoes each free-text value written (`--value`, `--place-text`, `--anchor`, `--notes`) on its own line, so a shell-mangled argument is visible; other fields echo in the summary line.

**`--place` / `--place-text`** are independent keys (SPEC §15). Both given: both written; explicit `--place` wins. `--place-text` alone (and, on review, no existing `place:`) is looked up in `places/places.yaml`: an exact normalized match attaches `place:` in the same write ("attached" / under `--dry-run` "would attach place: automatically"); a near match is noted, never attached; a missing registry is a quiet no-op; an unparseable one warns with a `fha lint` pointer.

**`--clear FIELD`** (repeatable) removes an optional field: `place`, `place_text`, `date`, `information`, `evidence`, `anchor`, `notes`. Required fields (`value`, `type`, `persons`, `status`, `confidence`) are refused, naming the correcting flag.
- The whole value goes as YAML reads it (block scalar, multi-line quoted string, block list); every other line, comment and line ending stays. A first key on the `- ` line hands the dash on.
- Refused: a key the edit cannot find (quoted key, space before colon, also when setting); a key listed twice; `--clear evidence` on a negated claim (§8.6); `--X` with `--clear X`.
- Clearing an absent field says so (alone: `already-done`, exit 0).
- Empty `--value` refused; empty `--date`/`--place`/`--place-text`/`--anchor`/`--notes` refused pointing at `--clear`; `--persons ""` refused.

**Surgical write.** Only the named claim's entry in its source's `## Claims` block changes; siblings, key order and comments survive. Found by scanning `sources/`, so a stale index never blocks it; run `fha index` after. Before writing, the block is re-parsed and compared: it must parse, the change must have landed, a cleared key be gone, nothing else in this claim or any other claim changed. Otherwise refuse, nothing written, naming cause and file. `fha confirm`'s claim edits share this guard. `changed[]` names the file (empty under `--dry-run`).

**Accepting says whose event it is, and refuses the wrong person** (SPEC §8.3). Moving a `birth`, `baptism`, `death`, `burial`, `marriage` or `divorce` claim to `accepted` (one claim, a batch, or `claim new --status accepted`):
- refuses, nothing written, a claim naming two or more people that leaves someone without a role or names no one in the subject role (`_lib.event_role_gaps`, lint E021/W147): add `roles:`, then accept;
- refuses a `death`/`burial` whose deceased is marked `living: true`, unless `--confirm-deceased` says the human checked the record really is theirs: then it is accepted and only the deceased is marked `living: false` (a living spouse on the same record keeps her flag); otherwise the record is someone else's;
- on success, says it in plain words: "c-… records the DEATH of Thomas Edward Hartley (p-…)."

**Batches.** `fha claim c-a c-b --status accepted`:
- status only: several distinct ids with a field flag or `--clear` are refused;
- every id checked before any write; one bad id refuses all, naming it;
- duplicates applied once, in order, and reported;
- each claim goes through the single-claim write; `fha index` reminders fold into one line; a mid-batch failure stops, naming what was and was not applied and the command that finishes the rest.

### Accepting a death marks the person not living

`living: unknown` counts as living (SPEC §19). Accepting a `death` or `burial` claim is the human deciding the person died, so each person the claim says died has `living: unknown` (or none) set to `false` through `fha person set-living`'s writer (§3c), one plain line each ("Ada Hartley is now marked as no longer living (death claim c-…); shared exports and the site may now include her.").

**Who died:** the person under `roles: deceased:`, or the one person on a claim with no `roles:` (as lint W136). Nobody is marked, and a warning names the fix, when the person is `living: true` (never overwritten); the claim names several people with no roles (W132); it names nobody `deceased:` and the deceased could only be read by elimination; it names someone it cannot place on its own `persons:` (W133) or any name link (no index used), this warning names nobody to mark; or the person is a merged tombstone (warning gives the survivor's command, W107).

- Negated claims and other statuses mark nobody; `living: false` already is silent.
- Only a move INTO `accepted` marks; a re-accept never undoes `--keep-living`.
- Per person across the command: one claim naming them `deceased:` suffices.
- Judged from the claim as written: single accepts parse the saved text; batches re-read each record after all writes (warn, naming W136 and `set-living`, if unreadable) and mark each person once; `claim new` parses what it appended.
- Compare-and-set: the flag changes only if still unknown/missing at write time.
- Same helper for single, batch, `claim new` and `fha serve` (which then rebuilds the index in full).
- `--dry-run` previews ("Would mark …"). `--keep-living` skips this; a stopped batch's recovery command carries it. Exit code unaffected.

Moving an accepted death/burial claim out of `accepted`, or editing it so it stops naming someone as deceased, never reverts the flag; it warns for each such person still `living: false`, with `fha person set-living <p-id> unknown`. A newly named person is not marked (W136 reports them).

### Accepting a kin claim writes the relationships: entries

A `relationship`, `marriage` or `birth` claim (with child and parent roles) that the command moves into `accepted` (one claim, a batch, or `claim new --status accepted`) is applied to the person records it connects (SPEC §9), one plain line per record changed ("Thomas Hartley's record now lists Margaret Cole as a parent (claim c-…).").

- Which entries, and on whom, is the rule lint W115 reads (`_lib.claim_owed_relationship_entries`): the couple a marriage's `spouse:` role names; the child and parents a birth or relationship claim names, a `parent` entry on the child and a `child` entry on each parent. Negated claims, social ties and other claim types owe nothing. Each owed entry is judged on its own (`_lib.relationship_entry_applies`): it is already applied when an entry for that person and role cites the claim, or cites the claim's source with `source:` and no `claims:`. An entry whose `to:` name no record answers to counts when it reaches the claim either way, as lint reads it by the owner's side alone. W115 reads the same test, so a birth claim cited on the father's entry still asks for the mother's.
- Only a record that already has a `relationships:` list is written (a `relationships: []` counts, and opens into block form). The list is opt-in, and once there lint asks it to hold every tie, so a record without one is left alone; when its other side was written, one line says so (lint then reports the missing mirror as W116, `--fix-reciprocal` adds it).
- The one entry for that person and role gains the claim in its `claims:` list: any entry naming them in that type whose nature lint would not call a mismatch (a parent or child entry with no subtype is biological, so it never joins an adoptive claim, nor an adoptive entry a biological one; a spouse entry or claim with no subtype matches any), with the claim's subtype written onto it when it had none (a `civil` marriage onto a plain spouse entry). Otherwise a new entry citing the claim is added. A guess (`status: hypothesis`) is never rewritten, and a bare `source:` entry for another source is not joined: the new entry goes beside it (W155 names the guess). After a write, entries for the same tie fold into the first (`_lib.collapse_relationship_entries`), but a later entry is folded only when nothing it says is lost: it holds no key beyond `to:`, `type:`, `subtype:`, `claims:`, `source:`, `status:` and `hypothesis:` and no comment, or the first entry already says all of it. An entry with a note, another key or a comment stays where it is, and W160 names it for the owner to remove by hand. Every writer that folds (`fha claim`, `--fix-applied`, `--fix-reciprocal`, `fha confirm merge`) goes through this one rule.
- Moving a claim to `disputed`, `rejected` or `superseded`, or from `accepted` back to `suggested`, takes it out of every `claims:` list on a person record, dropping the `claims:` key once its list is empty, unless the owner typed a comment on it or inside it: then it stays as `claims: []` with the comment (own-line comments above it), which every reader takes as no claims. No entry is ever removed, since a plain `to:`/`type:` entry carries nothing that says whether the owner typed it; an entry left with no claims, no `source:` and no `status: hypothesis` gets one line ("Margaret Cole's record still lists John Hartley as a spouse, with no evidence now; remove that entry by hand if it is wrong."). A hand-written `relationships: []` is still a kept list: lint asks for the person's ties, and `fha claim`, `--fix-applied` and `fha person relate` write into it.
- Every person edit is worked out and checked in memory before any person record is written (the header must still read, nothing but `relationships:` may change), each record is written once, atomically, and `--dry-run` prints the same lines. A record that cannot be edited safely (a `relationships: [...]` flow list, say) is a warning naming the entry to add by hand; the claim's own change stands and the exit code is unaffected. `fha lint --fix-applied` writes any entries still missing.
- `fha serve` rebuilds the index in full after such a change.

### `fha claim new`

Mints a claim onto a source's `## Claims`: the workbench "add a claim" button and the by-hand alternative to AI drafting. `fha.py` intercepts `claim new` before the review parser.
- Default `--status accepted` (typing it is the review); an AI caller must pass `--status suggested` (AGENTS.md).
- `--confidence` defaults from `source_type` (`vital-record` high, `interview` low, else medium), named in a message.
- `--persons` optional; omitting it warns with the follow-up.
- `--negated` mints a SPEC §8.6 confirmed absence: `negated: true` + `evidence: negative`; any other `--evidence` is refused.
- Writes through the claim-append helper `fha confirm cooccur` uses, with the same corruption guard.

**Relationship scope (both verbs).** Neither creates or changes a claim to type `relationship` (it needs `roles:`, SPEC §8.3). Use `fha person relate` (§3c), `fha confirm cooccur` (§14a3), or a hand edit.

The `review-claims` skill (§16) and `fha report` drive `fha claim`; the accept is always the human's. Detection write-backs (§14a/§14a2/§15a) live in `fha confirm`.

## 3c. `fha person`: person-field write-backs

Safe one-line commands for the person-record fields and prose that exports and the workbench depend on. Twelve verbs.

```
fha person set-living <p-id> true|false|unknown [--dry-run] [--root PATH]
fha person set-profile-photo <p-id> PHOTO [--dry-run] [--root PATH]
fha person set-sex <p-id> M|F|intersex|unknown [--dry-run] [--root PATH]
fha person set-external-id <p-id> SITE ID [--replace] [--dry-run] [--root PATH]
fha person new "Name" [--sex M|F|intersex|unknown] [--gender TEXT] [--birth DATE] [--death DATE] [--birth-place TEXT] [--death-place TEXT] [--surname TEXT] [--force] [--dry-run]
fha person new --from-file PEOPLE.tsv [--force] [--dry-run]
fha person rename <p-id> "New Name" [--keep-variant] [--surname TEXT] [--dry-run] [--root PATH]
fha person relate <p-id> (--parent|--child|--sibling|--spouse) <p-id2> [--subtype WORD] [--reciprocal] [--working-answer H-ID] [--dry-run]
fha person estimate <p-id> [--birth DATE|-] [--death DATE|-] [--birth-place PLACE|-] [--death-place PLACE|-] [--dry-run]
fha person edit <p-id> --section biography|stories|research (--text TEXT|--file PATH) [--append] [--dry-run]
fha person note <p-id> --section stories|research --text TEXT [--dry-run]
fha person edit-note <p-id> --section stories|research --old-text TEXT --text TEXT [--dry-run]
fha person promote <p-id> [--into FOLDER] [--dry-run] [--root PATH]
```

### Single-field verbs (`set-living`, `set-sex`, `set-profile-photo`)

- Locate by scanning `people/` for `_{p-id}.md`, never the index.
- Change only the one top-level key line (hand comment and CRLF kept). A missing key is inserted in template order (`living:` after `name:`; `sex:` after `name`/`name_variants`/`face_tags`, before `living`).
- Guard: the new frontmatter must parse, the key equal the target, `id` and every other field unchanged; else refuse, nothing written.
- A merged tombstone is refused, naming the survivor (SPEC §9). Same value: `already`. `--dry-run`: unified diff. A live write reminds to run `fha index` (advice, not a warning exit).

**`set-living`.** `living:` drives redaction in every export (SPEC §9, §19). Output states the privacy consequence (`false` opens exports; `true`/`unknown` redact). The death-accept step (§3b) uses this writer with a compare-and-set guard; `set-living` itself has none. Exit codes: 0 written/`already`/dry-run · 1 not found (with `fha find`) · 2 argparse · 3 bad root or id, tombstone, guard refusal, file error. `data.status` ∈ ok/already/dry-run/not-found/merged/refused.

**`set-sex`.** M | F | intersex | unknown, case-folded. `sex:` drives Ahnentafel placement (§7: `F` mother/odd slot, else father/even; W120). A live change says: run `fha index`, then `fha views brackets`, `--realign` to apply; index first, since placement reads the indexed `sex:`. Workbench verb `person.set-sex`.

**`set-profile-photo`.** Sets `profile_photo:` (SPEC §9). `PHOTO` (filename, path or s-id) is written as given, safely quoted, and resolved leniently at site build; unresolvable just shows no portrait.

**`set-external-id`.** Writes or replaces one key of `external_ids:` (SPEC A.7), so the next capture and the WikiTree export match the right person. The site name is lower-case letters, numbers and `_`. Known sites' ids are shape-checked so a pasted web address is refused (`wikitree` Name-123, `findagrave` and `ancestry` all numbers, `familysearch` XXXX-XXX, written in capitals); other sites are taken as typed. A different id already there needs `--replace` (status `needs-replace`); a site name typed with capitals by hand is refused with a by-hand fix rather than doubled. An id another person holds (any key case, anywhere under `people/`, by file scan) is refused naming that person; a person file the scan cannot read also refuses, since it might be the holder. Guard: every other `external_ids:` entry and every other field must read back unchanged; a one-line `external_ids: {...}` is refused with a by-hand fix. Exit codes and statuses as `set-living`, plus `needs-replace`.

### `new`

Mints a p-id and writes a stub under `people/stubs/` (the "+ add person" button), rendered by the same code as `fha stubs` (which mints for names already referenced in claims).
- `aliases:` lists the p-id, then the name (SPEC §9); an `unknown` stub lists only the p-id.
- `--sex`/`--gender`/vitals validate as §9; `--birth`/`--death` are provisional, strict EDTF or loose wording (normalized with a gloss).
- All input is validated before minting, so a bad flag burns no id. `--dry-run` draws a real id but writes nothing.
- `--from-file PEOPLE.tsv` mints a batch; column 3 is a per-name `--surname`. An unclosed or multi-line quote refuses before minting.

### Filenames and surnames (SPEC §13)

- **Suffixes.** A trailing Jr, Sr, Esq, II-V (any case, period/comma-tolerant) is never the surname: "Roy Eugene Dodson Jr" → `dodson__roy_eugene_jr_p-….md`. Regnal VI-XXX counts only when in capitals in a name not all capitals ("Henry VII" → `unknown__henry_vii_p-….md`, GEDCOM `1 NAME Henry VII` with no slashes, since an empty slash field says "no surname"). One word left ("Cher", "Roy Jr") files under `unknown` (surname not known); the empty slot (`__cher`) needs `--surname ""` or a `surname: ""` line, and a GEDCOM NAME marking the surname empty (`Cher //`) imports as `__cher` with `surname: ""`. `fha gedcom` writes the empty slash field only for a recorded `surname: ""`, and a one-word name with nothing recorded as `1 NAME Cher`, so the round trip keeps "not known" and "none" apart. `fha person new`, `rename`, `stubs --from-names`, `gedcom import` and `lint --fix-ids` share this rule. "Jinping XI" needs `--surname XI`, which beats the suffix rule. One shared rule for slugger, lint and index.
- **Accent fold.** Before slots keep only `[a-z0-9_]`: NFKD minus combining marks, plus a table for ł ø æ ß đ ð þ ı œ ħ ŧ ŋ (and capitals). "Guðrún Þórðardóttir" → `thordardottir__gudrun_p-….md`. Shared by `person new`/`rename`, `fha stubs`, `lint --fix-ids`, `gedcom import`, xref's town key. `name:` keeps full spelling; source slugs are not folded.
- **`--surname TEXT`** overrides the split (double surnames, particles, surname-first). `name:` is written as typed; a `surname:` line records the choice. `--surname ""` writes `surname: ""`: empty sort slot (`__henry_tudor_p-….md`), GEDCOM `Jon Thorsson //`. `fha stubs --from-names` has no `--surname`.
- **Reading a surname.** Always from the record: the `surname:` line (empty = none), else the last word of `name:` minus a suffix. `fha index` stores `persons.surname` ('' none, None no usable name); GEDCOM, site A-Z, `fha find`, report and packet read it. A file name is only a sort handle.
- `rename` keeps an existing `surname:` and files by it unless `--surname` replaces it; no flag removes it (delete by hand). `fha gedcom import` writes `surname:` only when `/…/` differs from the automatic split. `fha lint --fix-ids` files id-less records by a hand-written `surname:`.

### `rename`

1. Replace `name:`; `--keep-variant` appends the old name to `name_variants:`. `aliases:` follows (SPEC §9): the new name is added and the old one stays, so a link written under it keeps resolving. A rename never removes an alias; only a restricted name's value is taken out, the same privacy rule as `--fix-aliases`. Because a kept old name could later clash with a real person of that name, the preview and the result say the old name stays in `aliases:` and to remove it there by hand if it belongs to someone else.
2. Rename the profile to the filename the new name derives (§13, honouring `--surname`).
3. Rename a research companion alongside, if any.
4. Delete generated companions (timeline/sources-index/draft-queue, identified by generated header, never by name) at the old filename and regenerate via `fha views … <p-id>`. A non-generated look-alike is left and named.
5. If the record is in a couple folder whose name contains the old name as exactly one partner segment, rename the folder; 0 or 2+ matches are left alone.
6. With `links: obsidian`, point every person link to the record at the new file name across the archive (§1 `rename_link_writer`): planned before step 1, the profile's own links folded into its write, the other files written after step 3. The preview and the result give the count.

Steps 1-3 and 6 roll back on failure and on Ctrl+C (which then goes on up, after the verb says what it put back); a file that could not be put back is named; step 4 is not rolled back. Step 5 alone may fail (`data.status = 'ok-folder-unrenamed'`, exit 1). A shell whose working directory is inside the folder is detected and named before trying. A live write ends with the `fha index` reminder (`site`/`packet`/`gedcom` refuse a stale index).

### `relate`, `estimate`

**`relate`** appends a `relationships:` entry (parent/child/sibling/spouse), always `status: hypothesis` (SPEC §9, §17); a sourced tie is a claim (§3b). `--subtype` per §8.2. `--reciprocal` writes the mirror too; each side's idempotency is checked separately, so a rerun fills only the missing half. `--working-answer h-…` writes the entry's `hypothesis:` line (on both sides with `--reciprocal`), naming the question entry the guess rests on; an id no question entry defines is refused before anything is written. An entry already on either side is left as written, and the output names the `hypothesis:` line to add under it by hand.

**`estimate`** writes provisional `birth:`/`death:` (see Dates), superseded by an accepted vital claim. Needs `--birth` or `--death`; `-` clears; both validate before either is written.

### Prose verbs: `edit`, `note`, `edit-note`

Bounded edits of `## Biography`, `## Stories`, `## Research Notes`; everything else stays byte-for-byte.
- **`edit`** replaces (or `--append`s) from `--text`/`--file`; warns (exit raised) when a replacement drops a balanced private fence.
- **`note`** (Stories/Research Notes) always appends a paragraph; refuses when the section's fence is unbalanced.
- **`edit-note`** rewrites ONE paragraph (what one `note` wrote): the workbench per-entry edit button. Named by its exact text `--old-text`, never position. It must be the whole paragraph: exact match, else exactly one match after collapsing whitespace. Misses refuse (exit 3) with `data['reason']`: `entry-partial` (part of one; quotes its opening words, or counts matches), `entry-spans` (several paragraphs; checked first), `entry-not-found`, `entry-ambiguous` (duplicate text; edit the file), `no-section`. Empty `--text` refused. `fha serve` re-words all but `entry-ambiguous` as "reload the page".

### The private fence (`<!-- private -->` … `<!-- /private -->`)

Fenced text and markers are dropped from every shared copy. An unclosed opener drops everything after it; fences nest by depth; a stray closer hides nothing; no flag opens a fence. Resolved over the whole body. Where AI drafts are also withheld, draft and fence ranges are computed on the original text and their union cut once, so every surface shows the same text; a damaged draft marker refuses even inside a fence. Never-written sections are cut first (the Research Notes placeholder holds an example fence).

- Applied by `fha site --standalone`, `fha wikitree` (whole body, before privacy scans), `fha packet` (profile, `--include-research` file, copied source records; the README counts notes withheld, ignoring the example fence, and names living people only from what ships).
- Kept (markers stripped) by the `--linked` preview and the workbench; kept whole by `fha backup` and `fha views`. `fha gedcom` has no prose; original files copy byte-for-byte.

### `promote` (stub graduation)

SPEC §4 stub → curated, the one sanctioned tool move out of `people/stubs/` (§5). Never a side effect of accepting a claim. One transactional engine shared with `fha views brackets --fix-promote`:
1. flip `tier:` to curated (set-living's edit and guard);
2. add missing SPEC §16 body sections (additive, same write);
3. move the record to its destination (folder created if needed);
4. move a research companion along if one exists; never create one.

**Destination.** Direct line: the Ahnentafel couple folder `{NNN} {name}` from `root_person` over accepted genetic relationship claims, seeded by `root_generation` (`self` #1 default, `children` #2; SPEC §12.2/§12.4); needs a fresh index; invalid `root_generation` refuses. Not direct line: `--into connections/` → `people/connections/` (§12.3); without `--into`, refused naming that command; a direct-line person sent there is refused. `--into FOLDER` (one folder under `people/`, not `stubs/`) overrides for a direct-line person. A record already outside `stubs/` is promoted in place (mismatches are W110's job). Curated and filed: `already`.

After a move the index is updated in place (rows moved, tier applied), so batches need no rebuild; if that fails, exit non-zero naming `fha index`. Output suggests `fha views refresh`. Exit codes: 0 ok/already/dry-run · 1 not found · 3 any refusal, nothing half-written.

## 3d. `fha source`: source-field write-backs

Write-backs to a source's own text and files. Seven verbs; all locate the record by scanning `sources/`.

```
fha source new --type proof-argument --title TEXT [--people P-IDS] [--date EDTF] [--dry-run] [--root PATH]
fha source note <s-id> --text TEXT [--dry-run] [--root PATH]
fha source extract <s-id> [--pages RANGES] [--copy LABEL] [--dry-run] [--root PATH]
fha source edit-note <s-id> --old-text TEXT --text TEXT [--dry-run] [--root PATH]
fha source clear-keyword <s-id> --keyword TEXT [--replace-with TEXT] [--file NAME] [--dry-run] [--root PATH]
fha source set-primary <s-id> --file NAME [--dry-run] [--root PATH]
fha source merge <keeper> <retiree> [--dry-run] [--root PATH]
```

**`new`.** `--type proof-argument` writes `sources/proofs/{slug}_{s-id}.md` (§14): `source_class: authored`, `repository: this archive`, a citation dated from `--date` (default today), `people:` from `--people` (known p-ids only), no `files:`, the purpose block, an empty `## Claims` fence, then empty `## The question`, `## The evidence`, `## The reasoning`, `## Conclusion` and `## Notes`. Any other `--type` is refused: other sources start from a file (`fha process`). A fresh s-id each run; `--dry-run` prints the path and text.

**`note`.** Appends a paragraph to `## Notes` (SPEC §14), adding the heading at the end if missing. Append-only, no AI marker. Refuses if the `## Claims` block was sound before and not after (Claims-less sources are fine), or on several `## Notes` headings. Superseded sources are not refused.

**`edit-note`.** `fha person edit-note`'s twin for one `## Notes` paragraph (§3c), with `note`'s guards.

**`extract`.** Dumps a PDF's text layer to `{slug}[-{copy}]-extracted-text_{s-id}.md` beside it (a `-primary` ending on the slug is dropped), `[Page N]`-labelled in the PDF's own pagination so `anchor: "page N"` lines up, header naming the copy label. Appends `role: extracted-text, derived: true` to `files:` via `fha process --more`'s writer. The original is untouched (SPEC §12.1).
- **Which PDF:** `--copy LABEL` (any capitals; unknown lists labels); else the main-file PDF, the unlabelled one if several (none or several unlabelled: refuse naming `--copy`); else the single non-derived PDF (several: refuse).
- One dump per source; rerun is `already`, naming the PDF it came from; never overwrites.
- `--pages 1-60,102` (1-based, checked against page count).
- No text layer on a page: placeholder line. All-image PDF: warning refusal toward OCR, nothing written. Encrypted: refused, naming the unlock path.
- pypdf is optional; absent, this verb alone refuses with `python -m pip install pypdf`.
- Record-write failure removes the dump and restores the record (and says so plainly if that fails).

**`extract`: lost word spaces.** OCR layers that squeeze or kern words make pypdf's default reading glue them ("ThomasHartley,sonofEdward"). Per page:
1. **Trigger:** ignoring leaders, repeated runs, punctuation pieces, addresses and space-less scripts, flag when >1/5 of characters are in pieces over 15 long or >1/10 of pieces look glued (capital after lowercase; `,;:` then a letter; two letters against a digit). Skip pages under 100 such characters.
2. **Re-read:** `pdftotext` (plain) when on PATH, once per contiguous page block, budget 60 s + 2 s/page; else or on failure pypdf layout mode. A `progress` callback hears of runs of 10+ pages (the CLI prints it). A failed pdftotext run is named in one line.
3. **Accept** if it leaves ≤ half the suspicious text, ≤1/10 of characters in pieces over 40 letters/digits, and only spacing changed: line-end hyphens removed, letters+digits equal as a multiset, other characters within 0.5% (min 2), difflib ratio ≥ 0.995. "Hart ley" is acceptable.
4. **Else plain** when the re-read keeps ≥9/10 suspicious pieces whole and changed nothing, unless most lines are one piece over 15 or >1/10 is in pieces over 40.
5. **Else** keep the default reading, list the page at the top of the dump and warn that `fha find --text` will miss phrases there, and why. Exit 1 (as for failed pages), also under `--dry-run`.

**`clear-keyword`.** The only way to remove or correct a wrong embedded keyword on a documents-root asset (SPEC §20 rule 7), typically lint W131's stray person tag.
- File: automatic if one documents-root file; `--file NAME` if several; none refuses.
- Reads the file's Keywords/Subject, including Lightroom `lr:hierarchicalSubject` (`People|Name` matches by last part); `--keyword` matches case-insensitively; removal takes the exact on-file value from every field. Not present: refuse, naming what is there.
- `--replace-with TEXT` adds the correction to every keyword field the format takes (§6), skipping fields that already name it; preview, write and post-check share one per-field plan.
- `OriginalBackup` safety copy (§13f); remove and add in one exiftool call.
- Documents root only; photos-root correction is undesigned.

**`set-primary`.** Moves the main-file mark (the fix §3a's `wrong_main_image` names). Text surgery on frontmatter `files:` only: the `--file` entry (alias or bare name, exact then case-insensitive) gets `is_primary: true`; the old main entry gets `is_primary: false`, the role its filename spells (`back`, `negative`, `page-2`; else `variant`) and `copy:` if its name has an unrecorded copy letter. Nothing else changes; no photo is touched.

Refuses, nothing written: `--file` matches none, several, or a non-photos-root entry; one-line list or entry form; 2+ other files already marked main; current main file not a photo; result without exactly one `is_primary: true`. The new text must parse to the planned list with all else unchanged before the atomic write (CRLF kept); then it is re-read and restored if wrong. `--dry-run` previews in words plus a diff; rerun is `already`.

**`merge`.** Makes two records of one piece of evidence into one (SPEC §9 "Merged sources"): the retiree folds into the keeper and its record file is removed.
- **Files.** Documents-root files are renamed beside where they are into the keeper's grammar, `{slug}[-{copy}][-{role}]_{keeper}.{ext}`, by `--more`'s naming rule (`_lib.attachment_base`); `original_filename:` keeps the entry's own, else the name the file had. Photos-root files are never renamed. A file whose role and copy label the keeper already has takes the next free copy letter (`b`, `c`, ...); the retiree's main file is no longer main. Every file that holds keywords gets `SOURCE: {keeper}` in place of the retiree's, through the one keyword writer (§6 Keywords). Files are compared as the file on disk they name (resolved path, letter case folded where the filesystem folds it), not as typed, and a new name carries the keeper's id once, at its end.
- **Record.** Claims move into the keeper's `## Claims`, ids unchanged, re-indented to its items. `aliases:` gains the retiree's id and its aliases; `people:`, `places:`, `external_links:` (by URL) and `ai_passes:` gain what is new; `files:` gains the moved entries; `merged_from:` gains one entry (SPEC §14). Notes gains a dated paragraph naming the merge, listing each other field the retiree held that the keeper does not share (`title`, `citation`, `source_date`, `repository`, ...), and every comment written in the retiree's frontmatter (whole-line or after a value). The retiree's `## Notes`, `## Stories` and any other section are appended to the keeper's section of that name; prose above its first section goes to Notes, less the purpose block (matched by its signature; any other `>` quote is kept). A `<!-- private -->` fence that crosses a `##` heading, or is never closed, is moved whole, opener to closer, into Notes (an unclosed one gets its closer, and its `##` headings become `###`, so it starts no section and later Notes land after its closer), so a section split never lets fenced text out.
- **Refusals, before any write and the same under `--dry-run`:** an invalid or repeated id; an id that is not a source (persons merge with `fha confirm merge`); either record missing (exit 1) or unreadable; a working copy; both records holding accepted claims whose named people (`persons:` and `roles:`, a merged person counted as its survivor, read from the person files) do not overlap at all, naming them; the two records protected differently from shared output (the `restricted:` value, where `true`, `dna` and `by-request` all differ; `source_type: dna`; `rights: publication_ok: false`), naming both sets of markers and asking the owner to choose one protection and write it on both records; a retiree with no marker merges into a marked keeper, and identical markers merge; a claim id on both, or a claim with no id; a file listed on both, or twice on the retiree, outside both asset roots, or missing from disk (`fha reconcile`); a file carrying a third source's `SOURCE:` keyword; a photo whose keywords cannot be read (exiftool missing). A document whose keywords cannot be read is renamed with a warning, its old keyword still resolving through `aliases:`.
- **Links (`links: obsidian`).** Links to the retiree and claim links to the claims that move are pointed at the keeper's file across the archive (§1 `rename_link_writer`), planned before any write and listed in the preview with their count; the keeper's own links join its one write, and each other file's write has an undo step.
- **Transaction.** The keeper's new text is built and re-parsed first: its frontmatter must read back as exactly the planned values and its claims as the keeper's followed by the retiree's. Then renames, keyword writes, the keeper's atomic write and the retiree's removal, each with an undo step (a document's bytes are put back from a private copy; a photo gets the inverse keyword write); any failure undoes them in reverse and says plainly what could not be put back. Ctrl+C part-way runs the same undo (printing what could not be put back, as a failure does), then stops: a merge left between files would have some named for one source and some for the other. The plan is printed in the future tense before the writes (`The merge will: ...`), and `Merged ...` only after every write has succeeded.
- Next steps printed: `fha index`, then `fha photoindex` when photos were re-keyworded; lint W107 lists links still naming the retiree.
- Exit codes: 0 merged or previewed · 1 a record not found · 2 refused · 3 a read or write failed (rolled back).

**Exit codes (the other five):** 0 written/already/dry-run · 1 s-id or asset not found (with `fha reconcile`/`fha find`) · 3 bad id; blank `--text`/`--old-text`/`--keyword`; file error; multi-heading record; ambiguous or absent documents-root file; keyword absent; entry-match refusals; Claims regression. `changed[]` names the record (for `clear-keyword`, the asset).

## 4. `fha id`: minting

`fha id mint P [-n 5]` prints fresh IDs. `fha id check <ID>` is an alias for `fha find <ID>` (§4a).

1. Draw 10 characters with `secrets.choice` from lowercase Crockford Base32 `0123456789abcdefghjkmnpqrstvwxyz` (no `i l o u`).
2. Check candidates against one tree scan per mint call: every `.md`/`.yaml`/`.yml`/`.txt` under the archive root, skipping only the root-level `.git`, `.cache`, `.fha`, `.claude`, `.obsidian` and `generated/`. Deeper dot-folders (`people/.old/`) are scanned, since `fha index` reads them. Never the index: its freshness cannot vouch for every ID, and a collision guard must be right, not usually right.
3. Retry on collision.

`fha id --help` documents hand-minting (10 characters from the alphabet, then a search). Input IDs are lowercased before matching.

## 4a. `fha find`: the universal locator

`fha find <ID>` says where any ID lives. Photos are never renamed, so disk search cannot find a photo by s-id.

| ID | Output |
|---|---|
| s-id | record; every asset file (via `fha.yaml`; documents by filename, photos by inventory + keyword); citation sites, the source's own links and every link to one of its claims (`[[c-…]]`, `[[s-…#Claims|c-…]]`, the file-name form), each claim site marked with the claim's ID, read by the rule the exports use (`_lib.cited_source_ids`); claim count by status. An s-id merged into another (in that record's `aliases:`, SPEC §9) says so and shows the kept record, here, under `--related`, and in `--json` (and so in the workbench pickers) |
| p-id | person file, couple folder, claims naming them, photo count (§9), citation sites |
| c-id | source record and line, status, links in and out |
| l-id / h-id | record and every reference |

`fha find <text>` is a text search (`--text`).

**Index use (bare and `--text`).** A stale index warns and is still queried (it keeps the structured reports). An absent or unreadable index falls back to a tree scan with the warning. A stale index with no row for the ID also falls back to a tree scan rather than "not found".

### `--related <ID>`

Ranked, read-only index query, built on `xref` and `cooccur` data. Absent or unreadable index: exit 3 (no fallback). Stale: warns, queries.

- **p-id:** relationship edges (type, backing-source count); co-occurring people without an edge (shared-source count, the `cooccur` grouping); recurring places (claim `place_id`/`place_text`); shared entities (occupation/military/membership values, with who shares them); source count; photos via `photo_people` (note when no photoindex). Backs the FAN view and Friends & Family suggestions.
- **l-id:** claims naming it; their people by frequency; source count; photos geotagged within about 0.002°; micro-places `within:` it.
- **s-id:** claims by status; people; places; sources corroborating or contradicting its claims (`claim_links`, both ways); sibling sources sharing a person or `repository`; the citation sites the plain `fha find <s-id>` lists. `--json` (and so `/api/find` and the workbench) gives a source hit for an s-id the same sites as a `citations` list of `{path, line, claim}`, `claim` null for a link to the source itself.
- **c-id:** source, persons, place; claims it corroborates/contradicts (both ways); sibling claims (same person, same type).
- **h-id:** the people its question is about (`refs:`, from the `hypotheses` index), and claims referencing it (`claims.hypothesis`, SPEC A.4). With no index row, the people come from those claims.

**`--date <EDTF>`**: accepted and reviewed-but-open claims (`suggested` with `reviewed:`, SPEC §8.1) (and their people, sources, places) whose `date_min`/`date_max` (§1) overlap the range. Standalone it joins no photos. With a p-, l- or s-id it narrows that neighborhood; C and H ignore it.

### `--text "…"`

One query over:
- record bodies and notes (FTS plus a regex pass);
- every plain-text file under the documents root (regex pass): `.md`, `.txt`, a tree export (`.ged`), a captured page's saved copy (`.html`/`.htm`/`.xhtml`, read by its visible text including CDATA, never its tags or script), site data (`.json`, read by its values, never its field names), `.csv` and `.xml`. A page's visible text is kept in `.cache/page-text.sqlite`, keyed by full path, modification time and size, so a page is parsed once until it changes. `fha index` reads new or changed pages into it and drops pages that are gone, printing one line first when there are more than 20; a search about to read more than 20 unread pages says so on stderr. The cache is disposable, and a missing or read-only one only costs speed. A file with a UTF-16 byte-order mark is read as UTF-16; otherwise the file is read as UTF-8, and only the bytes that are not valid UTF-8 are read as Windows ANSI (cp1252). A damaged cache file is deleted and started afresh;
- photo/document captions, comments, keywords (§9), only when `.cache/photos.sqlite` is fresh (present, schema OK, newer than the photos root); else skipped with a note;
- `transcripts_fts`, filled by `fha index` from `.md`/`.txt` companions with `role: transcript` (or `transcription`) or `extracted-text`. A role on a media file is skipped, and a tree export is never loaded (it would swamp ranked search).

`fha search` and a bare text `fha find` behave the same. A photo whose file is gone keeps its caption searchable (§9 `MISSING:` row); hits print its last path marked `(not on disk)`, never the internal key. A photo group is shown by a member still on disk; a group with none shows its last path, marked, with `fha photoindex reconcile` as the next step.

**Coverage note (D14).** Every text search, hit or miss, ends with the count of sources holding no searchable text (at least one file, none a `.md`/`.txt`/`.ged` or text-role companion, and not a source of saved page copies only; the predicate `_lib.files_carry_searchable_text` that lint W124 and `fha metrics` share). A saved page or site data beside a record image is searched but buys no coverage: it is the site's copy, not the record's words. A surface that searches only the index (`--json`, `/api/find`) counts a tree export as unread too, since the index never loads one, and names `fha find --text` as the search that reads it. A miss over unreadable scans otherwise looks like a miss over evidence that was read, and hits feel like confirmation.
- Wording: "not the whole picture" on a hit, "could not look everywhere" on a miss.
- Names only real verbs: `fha source extract <s-id>` for a PDF with a text layer, else reading the file.
- Computed from the index (`source_files`, `transcripts_fts` keys), plus a page-only source's site-data file, read to see whether capture failed to save the record's image. A file the index marked absent buys no coverage; a source with no files counts in neither half.
- No usable index: says coverage was not checked and names `fha index`.
- One composer for all surfaces: `--json` prints it on stderr; `/api/find` returns `coverage` (null when nothing to say, and null for a `--kind`-filtered picker lookup); the workbench shows it under results. The CLI keeps it under `--kind`.
- Lint W124 is the reverse view: `accepted` claims on a source whose files hold no words.

**Unchecked transcripts (D15).** A hit whose words came from a transcript no human checked against the image is labelled `[unchecked AI transcript]` on its own line.
- Only transcript hits; never bodies, claims, notes, profiles (even AI-DRAFT biography prose) or captions. Both the FTS pass and the regex fallback apply it (the fallback matches paths to the indexed set).
- State comes from `transcripts_fts.content` (no file opened), by the `transcribe-source` marker contract and the `fha confirm draft` regexes: **unreviewed** (complete AI-DRAFT marker), **verified** (complete AI-ACCEPTED, no draft), **unmarked** (neither word: hand-typed or an extract dump), **damaged** (the word outside a complete marker). Unreviewed beats verified; damaged counts as unreviewed. Only those two are labelled.
- Unmarked is silent: it is most transcripts, and labelling it would teach readers to ignore the label.
- One explanation prints after the results, before the coverage note: what the label means, that the image is the evidence, and `fha find <s-id>`.
- `--json` and `/api/find` add `"unchecked": true`; the workbench shows a caution chip. One rule for all surfaces.

No verb flips a transcript from draft to accepted (`fha confirm draft` edits profiles and a source record's body, not a transcript companion), so AI transcripts stay unreviewed (idea, see BACKLOG.md).

### `--json <ID|text> [--kind K,K…] [--limit N]`

Ranked search for pickers and autocomplete; `/api/find` wraps the same engine.
- Over aliases, persons, sources, places and place names, `notes_fts`. Deduped by id; sorted by tier (0 exact, 1 prefix, 2 substring), then label.
- Hit: `{id, type, label, detail}`, plus `"unchecked": true` only when true. stdout is one JSON array, or nothing on zero matches.
- `--kind`: `person`, `source`, `place`, `hypothesis`, `claim`, `text` (default all); `photo-source` filters to sources owning photo assets (`source_type: photo` or a photo-extension file), hits still `type: source`, a bare s-id still resolves.
- `--limit` default 20. Works with a bare query or `--text`.
- Absent/incompatible index: exit 3, plain message. With `--related`: refused, naming supported combinations (exit 2).

### `--sounds-like NAME [--limit N] [--json]`

The people whose names sound like NAME in any spelling the archive holds (Hartley, Hartly; Kowalski, Kowalska, Kovalsky), grouped by the spelling that matched. Every word of NAME must sound like some word of one of the person's public names (`name`, the public values of `name_variants`, `name_at_birth`, `married_name` and `also_known_as`, and other names typed into `aliases:`), in any order; a word that is a known given name also matches its forms in other languages (Jan, John, Johann, Иван). Merged tombstones are left out. A name marked restricted in any field is never shown, even where an older copy sits in `aliases:` or a public field repeats it: the index narrows the search, then each match is checked against the record's public names; a record that cannot be read is left out, named by its ID on stderr.

- **Sound codes.** Two words sound alike when their Daitch-Mokotoff codes share one (`_lib.dm_soundex`, written from Gary Mokotoff's published coding chart; a name can have several codes). A Cyrillic word is coded through its passport, German and Polish spellings (`_lib.name_sound_codes`); a Serbian, Macedonian or Belarusian letter is written as that language's Latin alphabet writes it. The header prints each word's D-M codes, which search every spelling at once on JewishGen and Stephen Morse's pages, and its census Soundex code (`_lib.american_soundex`, the National Archives' rules), which the 1880-1930 census Soundex cards are filed under. A prefix (Van, De, La) gets the census Soundex code as written; the Archives file such names under both forms.
- **Words.** Apostrophes are dropped (O'Brien is OBrien) and anything else that is not a letter splits words. A one-letter word is an initial and is not compared on its own. A surname prefix and the word after it also count as one word, so Van Deusen and Vandeusen (O Brien and OBrien) find each other; a prefix is a word of up to three letters or one of a few longer ones (Fitz, Vander, Della), and a prefix followed by a particle such as der, la or von joins too (Van der Meer, Vandermeer). A copy of a private name that differs only in accent encoding or spacing is treated as that name.
- **Ranking.** People with more words in the query's exact spelling (accents and case aside) first, then by name; a group sits where its best person does. `--limit` (default 50) cuts the people listed and says how many more there are.
- **Output.** Each person with their years (own accepted birth or baptism and death or burial, else the record's provisional `birth:`/`death:`) and p-id, a name other than their main one shown as "as …", and the closing line "Sounding alike is only a hint: these can be different families." `--json`: one array `[{id, type: "person", label, detail, matched}]` on stdout (`[]` on no match), `matched` being the spelling that matched; messages on stderr.
- **Exit codes.** 0 found; 1 no one sounds like it; 2 a name that cannot be compared (no Latin or Cyrillic letters, initials only, empty), or `--date`/`--kind` given with it; 3 no usable index (no fallback scan).

### `--spelling-groups [--limit N] [--json]`

One advisory list of the surnames in the archive that sound alike ("Hartley (6), Hartly (2), Hartlie (1): 9 people"), so a researcher sees that three spellings are probably one family. It changes nothing.

- **Grouping.** Each active person's surname (the last word, by the SPEC §13 rule, of `name` and of each public other name, as for `--sounds-like`) is coded with Daitch-Mokotoff, and spellings are grouped by the first code only, not by any shared code, so one odd spelling cannot chain two families together. A group needs two or more distinct spellings (accents and case aside). Names in another script have no code and are left out. The engine is `_lib.surname_spelling_groups`; it takes the surnames already checked as public and reads no file.
- **Privacy.** As for `--sounds-like`: the index only lists the people, and every name grouped comes from the person's own record, so a private spelling never appears.
- **Output.** Groups largest first, each spelling with how many people write it, and the closing lines "Names are left exactly as each record wrote them; nothing has been changed." and a pointer to `--sounds-like`. `--json`: the array `[{code, spellings: [{spelling, count}], people}]`. `--limit` (default 50) cuts the groups.
- **Exit codes.** 0 whether or not groups exist ("No surnames in your records sound alike."); 2 with `--date`, `--kind` or a name; 3 no usable index.

### Index freshness (D9)

Shared by `find`, `doctor`, `views`, `photoindex`.

**Watermark:** stale when the newest record mtime exceeds the cache mtime.
- Generated companions (timeline, sources-index, draft-queue) are excluded; the human `research` companion counts. `fha views` rewrites the `notes_fts` and `person_files` rows of every companion it writes or deletes, so search never serves a superseded view.
- A profile's generated `## Sources` and summary regions (SPEC §16, §21b) live in the profile, which counts. After writing one, `views` re-syncs that profile's `notes_fts` row and manifest entry, moving `index.sqlite`'s mtime past the profile. If the re-sync fails, the index reads stale; `run_sources_index`/`run_summary`/`run_refresh` report `index_stale` and exit 1.
- Fails closed: an unlistable folder makes the watermark "now", so caches read stale while it stays shut. `fha index` and lint W123 name the folder.

**Manifest:** a watermark cannot see deletions, so each cache has a `{path: mtime}` manifest from the same walk: `.cache/index_manifest.json`, `.cache/photos_manifest.json`.
- Full rebuild replaces it; incremental writers (`upsert_source`, photo reconcile/tag-person/set-summary, the profile re-sync) patch their paths.
- A listed path missing from disk means stale. Readers OR this with the watermark.
- A missing manifest means stale (once), never fresh. No content hashing.
- `fha serve` keeps its snapshot manifest in memory (TOOLING_INTERFACE.md).

## 4b. `fha date`: dates in other calendars

```
fha date convert DATE --from julian|gregorian|hebrew [--json]
fha date feast NAME YEAR [--church western|orthodox] [--json]
```

A record may give its date in the old (Julian) calendar, as a church feast, or in the Hebrew calendar. `fha date` works out the day in today's (Gregorian) calendar so no one drafting a claim does the arithmetic in their head. It prints the day, its weekday, and the claim's lines: `value` keeps the record's words, `date:` is the day in today's calendar, `notes:` says which calendar the record used. Pure computation: no archive is read or written, so it runs anywhere; `--root` is accepted and ignored. Not to be confused with `fha calendar` (§7b), the family's anniversaries.

- **`convert`.** Julian or Gregorian input takes the plain forms `normalize_date` reads (`1732-02-11`, `11 Feb 1732`, `February 11, 1732`, `Feb 1732`, `1732`), plus a double year (`11 Feb 1731/32`, `1731/2`, `1699/1700`), read as the later year; the part after the slash must be the next year's last digits, or the date is refused. A double year is written only for 1 January to 24 March, so one on a later day (`3 Sep 1731/32`) is refused rather than read a year late. A hedged or ranged date ("about 1732") is refused: the hedge belongs in the claim, around the converted date. `--from julian` gives today's day and how many days the old calendar ran behind; `--from gregorian` gives the old-calendar day. Both also print the Hebrew date. Hebrew input is a full day: `15 Nisan 5650`, with `Adar I`/`Adar 1`, `Adar II`/`Adar 2`/`Adar Sheni`; Russian month names are read too.
- **Precision.** A day converts to a day. A month alone prints the span of days it covers in the other calendar, for information, and its `date:` stays the month as written, since converting it would only move its edges. A year alone needs no conversion.
- **Adar.** Plain "Adar" in a Hebrew leap year could be Adar I or Adar II: both readings are printed, labelled, with no `date:` (exit `0`). Day 30 can only be Adar I (Adar II has 29 days), so it gets that one reading. Adar I or Adar II in a common year is refused, naming the plain form.
- **The 1752 caution.** An old-calendar date in January to March (to 24 March) before 1752 with a single year gets one line: in England and its colonies the year began on 25 March, so the date may belong to the next year; type both years if the record shows them. Nothing is guessed. A Gregorian date before 15 October 1582 gets a line saying no record of the time used that calendar.
- **`feast`.** The day a feast or fast fell on in YEAR. `--church western` (the default; Catholic and Protestant) computes in today's calendar, from a fixed day or from Western Easter (the anonymous Gregorian algorithm), once that calendar had begun (15 October 1582). Before then every Western church kept the old calendar and the old Easter rule, so the feast is worked out in those. From 1582 until Britain changed (14 September 1752) a feast had two days, one in Catholic lands on today's calendar and one in England and its colonies on the old one: both are printed, labelled, each with its own `date:` and `notes:`, and no single `date:` (the record's place decides). When the two calendars' Easters fall on the same day the feast gets one reading; `--church orthodox` computes in the old calendar, as the church keeps it, from Orthodox Easter (Meeus's Julian algorithm), and converts. The churches differ: Orthodox Trinity is Pentecost, Western Trinity Sunday is a week later; Orthodox St Michael is 8 November (old calendar), Western Michaelmas 29 September. A fast prints both ends and its `date:` is the EDTF interval between them. Whitsunday gets a line noting the Scottish legal term day (15 May).
- **Names.** Looked up exactly, after folding accents and case, "Saint"/"St." to "st", dropping "'s" and a closing "Day", and one leading word such as "on", "na", "w" or "на" ("on St. Stephen's Day" is `st stephen`). No fuzzy match: an unknown name exits `2` with the church's list; a name only the other church's list holds names the `--church` to use.
- **`--json`.** One object on stdout: `input`, `from`, `julian`, `gregorian`, `hebrew`, `weekday`, `difference_days`, `precision`, `date`, `notes`, `cautions`; plain Adar adds `readings`; feasts carry `input`, `year`, `church`, `feast`, `calendar` (`old` or `new`, the one the day was worked out in), and `from`/`to` for a fast; a Western feast with two days carries `readings` (each with `calendar`, `where`, `julian`, `gregorian`, `weekday`, `date`, `notes`) in place of the top-level `calendar`, `julian`, `gregorian`, `weekday`, `date` and `notes`, which are absent or null. A refusal prints `{error, example}` with the input.
- **Exit codes.** `0` converted (including plain Adar's two readings). `2` input refused (not a date, an unknown feast, a day that does not exist such as 30 February, a Hebrew month the year lacks, a year outside 1 to 9999, or outside 1 to 9998 for a feast), always with an example that works; argparse's own usage error is also `2`.

## 5. `fha stubs`: stub minter

`fha stubs [--dry-run]` finds p-ids in source claims with no person record (the E005 set; `[[p-…]]` and `[[p-…|Name]]` count) and writes `people/stubs/unknown__unknown_{p-id}.md` (frontmatter `tier: stub` plus the person body scaffold) for hand-renaming. Naming stubs from claim values is not built (idea, see BACKLOG.md).

`--from-names "Ethel Hartley; Frances Hartley"` mints IDs and `people/stubs/{surname}__{given}_{p-id}.md` in one step.
- Each name is first checked against `name:`, alternate-name fields and `aliases:` (not filename-stem or ID entries) of every person file on disk (never the index) case-, accent- and punctuation-insensitive. Files are identified as `fha index` does (`id:`, else filename p-id); a profile with a `name:` and no id counts.
- A match, or a name repeated in the list, refuses the whole batch (exit 3, nothing written; `--dry-run` shows the same), naming each record (`p-… (people/…)`) and the alias matched.
- `--force` mints anyway (two people sharing a name: the human's call, as the refusal says). `--force` without `--from-names`: exit 2.
- Unreadable person files are named in one stderr warning.
- A generational suffix (Jr, Sr, II-V) is never the surname (`… Dodson Jr` → `dodson__`). Names needing an explicit surname go through `fha person new --surname`.

Non-UTF-8 files are skipped with one warning naming them and how to re-save. Never overwrites. Never moves a stub out of `stubs/`, except through the human-invoked `fha person promote` (or `fha views brackets --fix-promote`, §7).

## 6. `fha process`: processing assistant

```
fha process <file|folder> [--type TYPE --title "…" --slug …] [--variants one|separate]
            [--dest SUBPATH] [--more FILE ROLE[:copy]] [--people P-ID,…]
            [--physical-location HOLDER] [--dry-run]
fha process refile <S-id> [--file NAME] --to photos|documents [--type TYPE] [--dest SUBPATH] [--yes] [--dry-run]
```

Stage A of the process pipeline. Stage B (draft `suggested` claims) and C (review) are the `process-source` and `review-claims` skills (§16).

### Algorithm for one item

Transactional: a failure undoes every step in reverse order. `--dry-run` prints each step and writes nothing.

1. **Resolve** `FILE` as typed, else relative to the archive root; a double miss names both. (Same for `--more`.)
2. **Refuse** a file already carrying an s-id (name or keyword); anything under `inbox/processed/`; a file outside every root and the inbox ("isn't in your inbox (...) or in the archive's folders - move it into the inbox first"); a non-image in the photo library (move it to the inbox).
3. **Read the shape:** bare file; stub sidecar (asset + `*.notes.md`); bundle folder (files + `notes.md`); variation group; or a folder to triage.
4. **Type and root** (below); `--type` is validated against SPEC §14 before any I/O.
5. **Group variations** and ask one / separate / skip (or `--variants`).
6. **Mint** the s-id.
7. **Copy out of the inbox:** copy (`shutil.copy2`) to the destination, then move the original (never delete) to `inbox/processed/<path inside inbox>`. Applies to the `-back` sibling and `--more` too.
8. **Name.** Documents root: rename to `{slug}_{s-id}.{ext}`, recording `original_filename`; a file at the documents-root top level goes into `documents/{type}/`; one in a subfolder keeps its place (SPEC §12.1). Photos: never renamed. A bundle's documents are `{slug}[-{copy}][-{role}]_{s-id}.{ext}`: a file with a capture's generic name (`clipping`, `page`, `record`, `page-snapshot`, `record-data`, … or a name that is just its role) takes the source's slug from its title, any other keeps its own; the slug never ends with the role word about to be appended (`hartley-wedding-clipping_…`, not `…-clipping-clipping_…`). New files only; filed files are never renamed for this.
9. **Who keeps the original.** Filing an image or PDF into the documents root that is not a web capture (its stub names no `external_links`), the tool asks once "Who keeps the original of X?" and writes the answer as `physical_location: {holder, as_of: <this month>}` (SPEC A.6); Enter skips. `--physical-location HOLDER` answers without asking; with no one at the keyboard (no TTY, the workbench) nothing is asked or written. The flag is refused with `--more`, a folder, or a file being filed as a photo.
10. **Keyword:** take the `originals_backup:` copy (§13f), then embed `SOURCE: {s-id}` in photos and documents-root TIFF/JPEG/PNG/PDF.
11. **Scaffold** `sources/{type}/{slug}_{s-id}.md`.
12. **Consume the stub:** hints become §14 fields, prose goes to `## Notes`, the stub is deleted, a bundle folder dissolves (SPEC §12.1).
13. **Print** record path, filed paths, kept-original line, follow-ups.

### Scaffold

SPEC §14 order: `id`; `aliases: [s-id, stem]` (stem keeps old `[[stem]]` links working); `title`; `source_type`; `source_date` (if hinted); `source_class` (`authored` for `proof-argument`, else a valid hint, else `original`); `repository` (or `unknown`); `citation` (or title); `people` (`--people`, else `[]`); `restricted: true` (hinted; always `dna`); `provenance`; `external_links`; `physical_location` (step 9); `files:`; `created`. Body: the §16a purpose block, an empty `## Claims` YAML fence, `## Notes`.

- `files:` entry keys in order: `file`, `role`, `copy`, `is_primary`, `original_filename`. Pointer-only sources (§13b) omit `files:`.
- The main file carries `is_primary: true` and the role its name spells, if any (`front`); a single document has no role. AI passes are added later as `ai_passes:` frontmatter (SPEC §14).

### Type and root

1. **Where it lives.** A file under an asset root stays there; only `refile` crosses roots. A file in an inbox that sits inside a root (SPEC §12.4) is not "under" it.
2. **What the human said.** A non-`photo` `--type`, stub `source_type:` hint (`--type` wins) or `intake_defaults` rule names a record, filed in the documents root: a census `.jpg` goes to `documents/{type}/`. `--type photo` never sends a non-image to the photo library (a `.pdf` files as a document typed `photo`).
3. **What it looks like.** Photo extension → photo; else document.

A file already in the photos root with a non-photo `--type` stays put; the output names `refile`.

**`intake_defaults:`** (`fha.yaml`): list of `{match: <pattern under the inbox>, source_type: <type>}`.
- Used only with no `--type` and no stub hint; the first match acts as `--type` and is always announced ("x.tif: type letter from intake_defaults 'Postcards/**'").
- Matching follows `photos_ignore:` (fnmatch, case-insensitive, `*` crosses folders), against each ancestor folder and the whole path, after dropping a leading triage folder. `Postcards`, `Postcards/*`, `Postcards/**` all match `Postcards/1908/card.tif`; `**/Postcards/**` matches only a nested one.
- Covers single files and `-back`, inbox `--more` files, bundles (by `notes.md` path), the workbench `process.file` verb, the `--dest` checks and the inbox-folder refusal.
- A `dna` rule only matters for `--more` (a DNA primary must already be in `documents/dna/`, SPEC §8.5.5).
- Bad entries are skipped with a `WARNING:` and a `fha doctor` line: non-list, not a `match:`/`source_type:` pair, unknown type, an unmatchable pattern (inbox's own name, absolute, drive letter, `..`), any `source_type: photo` rule.

### Inbox rules

- A same-named file already in `processed/` refuses. A refusal after the copy undoes copy and park. The line "The original X is kept at ...; the copy filed above is ..." prints only on success.
- `inbox/processed/`, hidden files and `_TEMPLATE*` are left out of the workbench Inbox page and `fha doctor`'s 14-day nudge (which looks inside triage folders).
- **`inbox_triage_dirs: [review, already-existing]`**: a leading listed folder is dropped from the park path (`inbox/review/A/x.png` → `inbox/processed/A/x.png`), case-insensitive, sidecars too, everywhere the park path is used. A collision there refuses with nothing moved (compare, then rename or remove the earlier copy). Bad values (non-list, a path, `..`, `processed`) are skipped with a warning.
- A `--dest` resolving inside an inbox that lives in a root is refused.

### `--dest` for photos

An inbox photo lands at the top of the library unless `--dest SUBPATH` names a library folder (`inbox/A/B/x.jpg --dest C` → `photos/C/x.jpg`; bundles too). Inbox folders are never mirrored.
- Validated before anything moves: relative, no `..`, inside the library, not in a `photos_ignore:` folder (names the pattern). A created folder is removed on refusal. Refile uses the same check.
- Without it, output says "top of the library" and names `--dest` (the workbench suppresses that advice).
- Refused on a document, a file not in the inbox (name `fha reconcile`), a pointer-only stub, a bundle with no photos, with `--more`, on a triage folder.

### Keywords

One writer for every keyword fha adds or removes (`SOURCE:`, p-ids from `--people`/`tag-person`, `fha source clear-keyword`, rollbacks):
- One exiftool call writes IPTC `Keywords`, XMP `dc:subject` (spelled `XMP-dc:Subject`), `lr:hierarchicalSubject`; reads union all three. Add is `-TAG-=V -TAG+=V` (one copy per field); remove clears all three. No IPTC on PNG, GIF, HEIC, PDF.
- exiftool's report is read; an add that updated no file fails.
- Values pass via a UTF-8 argument file (`-@`). IPTC writes set `CodedCharacterSet` UTF-8, unless the block already holds untagged Latin-1, which stays Latin-1; a value Latin-1 cannot spell goes to XMP only, with a message. Non-ASCII writes are read back and checked.
- Limit: a RAW file's separate `.xmp` sidecar is not updated.

**Photos:** a failed keyword write aborts the filing. A failed `originals_backup:` copy refuses it; an unset setting warns once per run.

**Documents:** same writer, backup guard and rollback (primary, `-back`, bundle documents, `--more`).
- A failed write still files, with a warning (name and record carry identity).
- Rollback restores the original bytes from a private copy. A file already keyworded for this source keeps it.
- Recordings and text files get no keyword.
- The keyword is read before any rename: a scan that lost its `_{s-id}` name but keeps a `SOURCE:` keyword is refused, pointing at `fha find <s-id>` (or `refile --to documents` if that source is a library photo).

Lint E012 checks photo keyword/inventory agreement.

### Back scans

A `-back`/`_back` sibling of a document scan attaches automatically if it is an image or `.pdf` (the §3a orphaned-back rule). `x-back.md`, `.xmp`, `.json` notes stay in the inbox.

### Variation groups

**Filename parsing** (case-insensitive, in order):
1. Strip `-crop` → `is_crop` (stacks with anything).
2. With a trailing `-back` or `-front` set aside, strip a final `cover | folder | mount | envelope | sleeve | note[-N]` (closed list, SPEC §13; only `note` takes a number; any other word stays in `base_id`) → `part_kind = "attached"`, `attached = "envelope"` / `"envelope-back"` / `"envelope-front"` / `"note-2"`.
3. Else strip one of `-pageN`/`-page-N`, `-negative`, `-back`, `-front`, `-bw`.
4. Strip a copy letter: `-b`, or a letter after a digit (`034b`).
5. The rest is `base_id`.

Result `ParsedName(base_id, variant_id, part_kind, page_num, freeform_role, is_crop, attached)`; `part_kind` ∈ `front | back | page | negative | bw | attached | none`.
- Other words belong to the name (`smith-farm-01400-back.tif` is the back of `smith-farm-01400.tif`; `smith-family.jpg` and `smith-house.jpg` are two photos). In a capture bundle the last word does name the role (`letter-envelope.jpg`).
- An attached object's role is its `attached` value (plus `-crop`), never `back`, so an envelope's back is not counted as the photo's. In choosing the primary and ordering members, attached objects come after the photo's own scans (back included) and are never the main image.
- A negative excludes front/back/page and drops its copy letter (stored at stem level).
- A crop sits in a `_crop` slot beside its parent, as AI context, never primary.
- The parser never infers `-page1`; the grouper may promote an untagged file when `-pageN` siblings exist.
- Primary: the plain scan, else the front. Others take their part kind; a bare copy letter gives role `variant` with `copy:`.

**Batch type** is shown as context only (precedence C, D, B, A):

| Type | What | Treatment |
|---|---|---|
| A: Variant scans | same side, different crop/exposure/quality | one source |
| B: Front/back | both sides of one item | one source |
| C: Multi-page | `-page1`, `-page2` … | one ordered set; transcribe labelled `[Page 1]`, `[Page 2]` |
| D: Helper crops | detail crops of a page | views of the parent only |

```
Found 3 files that appear to be variations of the same photo:
  portrait_1880.jpg        [primary]
  portrait_1880_back.jpg   [role: back]
  portrait_1880_bw.jpg     [role: bw]
Process as ONE source (shared S-id) or separately?  [one / separate / skip]
```

- **one:** one s-id; files keep names and places; each gets `SOURCE:` (the only write to them). Photo filenames carry no s-id; `files:` roles plus the keyword bind the group, and `photo_groups` caches it.

```yaml
files:
  - file: photos/1880/portrait_1880.jpg
    role: front
    is_primary: true
  - file: photos/1880/portrait_1880_back.jpg
    role: back
  - file: photos/1880/portrait_1880_bw.jpg
    role: bw
```

- **separate:** one source each; a provenance note is suggested for an obvious derivative.
- **skip:** nothing filed; a photo moved out of the inbox is put back, and the output says so.

**`--variants one|separate`** answers in advance; the set is still listed. With no flag and no stdin, the run stops naming the flag, writing nothing (folder triage too). Refused with `--more` and on documents; on a lone photo it notes nothing to decide.

Matching variations with unrelated names by a vision pass is not built (idea, see BACKLOG.md).

### Folder mode

Runs the triage scorer (§15b), lists ranked candidates with signals, processes those selected. It keywords photos in place, so an inbox folder of photos without `notes.md` is refused up front with `fha process "inbox/<folder>/<photo>" --type photo --dest <folder>` (triage-folder prefix dropped; the plain command when an `intake_defaults` rule makes them records). `--dest` on a triage folder is refused.

### `--more FILE ROLE[:copy]`

- **Primary in documents:** a file not yet in a root goes beside it in documents, any extension. A file in the photo library stays. `--type photo` files a real photograph into the library.
- **Primary a library photo:** a `--more` photo goes into its folder; a taken name is refused with `--more "<path as typed>" ROLE:b` or a rename.
- **Name:** `{slug}[-{copy}]-{role}_{s-id}.{ext}` (SPEC §13); slug from the primary document's stem, or the record's when the primary is a photo; arrival name kept as `original_filename:`.
- **Kept names:** a file already carrying this s-id; a name starting `{slug}-`; on a recording source with slug `{session}-audio`/`-video`/`-recording`, a name `{session}` or `{session}-…`. A suffix already present is not doubled (`{slug}-c-back.tif` as `back:c` → `{slug}-c-back_…`).
- **Merged sources:** an s-id in the target's `aliases:` with no record of its own is the target; a documents file named or keyworded with it is renamed and re-keyworded. One already listed under its old name is refused as attached. A photo keyworded with it is refused.
- A repeated role is refused with a copy-letter suggestion.

### `refile` (SPEC §12.1 carve-out)

Moves one of a source's files to the other root.
1. Locate the record by s-id tree scan (not the index).
2. File: the single non-derived entry, or `--file NAME` (`derived: true` files only when named). Already under the target root: refused toward `fha reconcile`.
3. **Into photos:** `--dest` required (validated as above, created if absent). The file regains `original_filename`, else loses its `_{s-id}`/role/copy suffixes; then `SOURCE:` is embedded (no exiftool or non-photo format: warn, proceed).
4. **Into documents:** confirm `[y/N]` (breaks the catalog link) or `--yes`; non-interactive without `--yes` refuses. Renamed into §13 grammar, into `--dest` or `documents/{type}/`. Keyword kept.
5. **`--type TYPE`:** rewrites `source_type:` value-exactly and moves the record to `sources/{type}/`, planned first (collision at either end refuses, nothing changed). Required into documents while typed `photo` (refusal, also in `--dry-run`, names the flag with an example); `--type photo` there is honoured.
6. Rewrite the `file:` line value-exactly, append a dated provenance paragraph to `## Notes`, keep line endings. Transactional; `--dry-run` previews.
7. Follow-ups: `fha index`, `fha photoindex`.

Exit: 0 ok/dry-run; 1 not found/working copy; 3 refusals. Same-root moves belong to reconcile.

## 6a. `fha media`: dedupe and container probe for incoming recordings

```
fha media dedupe FILE [FILE...] [--root PATH] [--json PATH] [--quiet]
fha media probe FILE [--root PATH] [--json]
```

Read-only checks run before `fha process` files a recording (used by `import-recordings`). Nothing is renamed, moved, deleted or embedded.

### `dedupe`

Hashes each incoming file against everything filed under the configured `documents`/`photos` roots: size first (directory entry), SHA-256 on a size match. `new` is a coverage statement and needs all five, else `indeterminate`:
1. **Roots:** every root `fha.yaml` names exists and is readable (a configured root missing is a gap; an unconfigured default is not).
2. **Enumeration:** every file listed, hidden folders and directory symlinks included, each folder once (`(device, inode)` guard).
3. **Domain:** one audio/video extension rule for both sides; arguments outside it are "not checked". Inbox files (even in a root) are never "already filed".
4. **Candidates:** every same-size filed file was hashed.
5. **Batch:** incoming files are compared with each other (`duplicate … in the same batch`).

An argument already in a media root is `duplicate … already filed`. No folder-narrowing option.

Exit: 0 all checked, none matched; 1 usage/config error (bad path, unparseable `fha.yaml`, configured root missing); 2 a duplicate found; 3 a check could not complete, so nothing is cleared.

`--json PATH` writes a report with alias-form paths only (`documents/…`, `incoming/…`). Refused before hashing if the canonical path is an incoming or filed recording, `fha.yaml`, or inside a media root.

### `probe`

Reads duration and container `creation_time` (`ffprobe`, optional, reported by `fha doctor`; PyAV fallback). `creation_time` is UTC at recording stop; an app filename clock is local at start: `local_start = (creation_time + offset) - duration`. The offset is reported with its source, never guessed:
1. `com.apple.quicktime.creationdate` (local with offset) settles it.
2. Else from the filename clock: `offset = filename_time + duration - creation_time`, rounded to a quarter hour; a fit off by more than a couple of minutes is rejected.
3. Else `offset_source: none`. Never the machine timezone or file mtime.

Flags `crosses_midnight` when local and UTC dates differ. Exit: 0 offset settled; 1 offset unknown; 2 no usable creation timestamp; 3 tool failure (unreadable, or no `ffprobe`/PyAV).

## 7. View generators: `fha views`

All views derive purely from the index. `fha views places` writes the place notes of Obsidian link mode into `places/` (below). Timeline and draft-queue write GENERATED-headed `.md` companions into the `people/` tree; their per-person forms skip a stub with a plain note (exit 1), since companion views are curated-person files (SPEC §16). `sources-index` and `summary` write no companion: each rewrites a region of the profile itself and does not skip stubs. Printed reports (`fha views family-sheet`) are described below. Content views and `refresh` take `--format md|html` (default `md`; `refresh` also `both`); `html` writes a standalone page under `generated/views/` (D11).

### Content views

- **`fha views timeline [p-id|--all-curated] [--format md|html]`** → `…_timeline_{p-id}.md`. Accepted and reviewed-but-open claims (`suggested` with `reviewed:`, SPEC §8.1) sorted by date (an open-ended date by its known bound: `[..1895]` by 1895, `[1883..]` by 1883), undated last, grouped by decade, each line `EDTF - type: value [[s-id]]`; an accepted low-confidence claim (SPEC §8.5) ends `[low confidence]`, a reviewed-but-open one `[unconfirmed - parked {date}]`. Never-reviewed suggested claims follow in a trailing "unreviewed" section. The private view keeps unsettled material visible; the site (§12) is accepted-only.
- **`fha views draft-queue [p-id|--all-curated] [--format md|html]`** → `…_draft-queue_{p-id}.md`: accepted claims whose source the profile body does not cite, the writing backlog for `write-biography` (§14b).
- **`fha views sources-index [p-id|--all-curated]`**: every source with ≥1 claim naming the person or listing them on its `people:`, grouped by `source_type`, written inside the profile's `## Sources` section between `<!-- GENERATED-BEGIN sources-index by sources-index on {date} -->` and `<!-- GENERATED-END sources-index -->` (`{date}` is when the list last changed, §1), with a visible notice; nothing outside the span changes. Works on any person, including `people/stubs/` and misplaced folders; `--all-curated` is the curated-only batch form. Refuses `--format html`. The write re-syncs that profile's index row (D9, §4a). There is no couple-folder `sources-index.md`; one left by an older version carries the GENERATED header, so `fha views clean` removes it.
- **`fha views summary [p-id|--all-curated]`**: the profile's summary lines (SPEC §16) between `<!-- GENERATED-BEGIN summary by fha views summary on {date} -->` and `<!-- GENERATED-END summary -->` (`{date}` is when the lines last changed), with a visible notice naming how to take the lines over by hand.
  - Placement: after the H1 and its purpose blockquote. An existing region is rewritten where it stands and left byte-identical (date included) when nothing changed.
  - Content, from accepted, non-negated claims only: `Born`/`Died` the person's own vital picked as the site and tree pick it (`claim_is_own_vital`, `vital_pick_key`), falling back to a baptism (`baptized …`) or burial (`buried …`), shown `date - place` with its source; `Married` each spouse from the derived spouse edges (`[[p-…|Name]] - date, place [[s-…]]`, the marriage claim when there is one), by date; `Parents` (father first) and `Children` (by birth date) from the derived parent edges, each person once with one source. A line with nothing behind it is left out.
  - Profiles whose opening already holds hand-written summary lines with no markers are left alone (reported); a BEGIN marker with no END is reported and skipped.
  - Works on stubs; `--all-curated` is the curated batch. Like `sources-index`, the write re-syncs the profile's index row. The draft queue does not count a citation inside the region as written up.
  - **The Records line (opt-in).** With `views: completeness_line: true` in `fha.yaml` (default off; anything but `true` or `false` warns and counts as off), the region ends with one more line, `**Records:** 3 of 5 - no marriage record; censuses 2 of 6 years`: the person's completeness from the shared engine (§7a, `person_completeness` in accepted mode, worded by `completeness_summary_line`), so it says what `fha metrics <p-id>` says. The line never starts a region by itself: a person with no accepted facts gets none. It is rewritten with the rest of the region, so a refresh after no change writes nothing, and turning the setting off removes it on the next `fha views summary` or `fha views refresh`. **Privacy:** the line is written for every person, living and unknown included, because no export carries the summary region: `fha site` never reads it (SPEC §21b), and `fha packet` and `fha wikitree` cut the whole region out of the profile they ship (both also refuse a living or unknown subject outright). Any new export that copies profile text must strip the region the same way.

### `fha views places [--dry-run] [--root PATH]`: place notes for Obsidian

With `links: obsidian` in `fha.yaml` (SPEC §18), writes one note per registered place, `places/{slug}_{l-id}.md` (SPEC §15). `{slug}` is the place's `name` folded by `fold_accents` (as person file names are: `Suwałki` → `suwalki`, `Großdorf` → `grossdorf`), lowercased, and every other run of characters made one hyphen (`_lib.place_note_slug`; `place` when nothing is left). With `links: id` it writes nothing and says so, and names `fha views clean` when notes from an earlier Obsidian spell are still there. Needs a fresh index; it reads `places`, `place_names` and `place_history`.

- **The note.** Frontmatter first, because Obsidian reads `aliases:` only at the top of a file: `aliases:` holds the l-id, `name` and each `alt_names` entry. A place with coordinates also gets `location: [lat, lon]`, written with the same numbers as the body's `Coordinates` line, which Obsidian's map views (the Maps view of Bases, the Map View plugin) read. Then the whole-file GENERATED header (§1), so the note's ownership is judged on the first line after its frontmatter (`is_generated_text(..., after_frontmatter=True)`); then `# {name}`, the purpose block, and a list of `Place` (hierarchy), `Inside` (the `within:` place, as a place link), `Coordinates` and `Also called`; then `## History` (each `history:` entry as `{period in words}: {hierarchy}`, in places.yaml order) and `## Notes` (the `notes:` text). A field the registry leaves out is left out. No people or sources are listed. Links in the note are written in the stem form like any view's.
- **Rewrites nothing that has not changed.** A note whose only difference is the header date is left alone (`generated_text_differs`, §1).
- **Renames and removals.** A generated note whose name no longer matches its place (renamed in places.yaml), or whose place is gone, is removed. Then every link in `people/`, `sources/` and `notes/` written with a place note's file name that is no longer current is re-pointed at the current one (`_lib.rewrite_stale_stem_links`: display, `#heading` and table `\|` kept; frontmatter `id:`/`aliases:`, code and GENERATED regions skipped; ID-form links left for `fha normalize-links --obsidian`). It looks for every stale name, not only this run's renames, so a run cut short finishes on the next one. Rewritten records stale the index: the run exits 1 with `data['index_stale']` and a line saying to run `fha index`, since only a rebuild re-reads everything a record feeds.
- **The Obsidian tables.** With `links: obsidian`, the run (and `fha views refresh`'s `md` pass) also copies three ready-made Obsidian Bases files from `tools/templates/obsidian/` to `notes/obsidian/`: `People.base` (everyone, curated, stubs by `tier`, people still marked living or unknown), `Sources.base` (all, by type, by repository) and `Places.base` (all, with coordinates, no coordinates yet; it reads a place note's `location:`). They are core Obsidian Bases tables, so they need no plugin. They are written only when `notes/obsidian/` does not exist, so Obsidian's saved column and sort changes, a file the owner deleted, and any file the owner added there are never rewritten or removed; `fha views clean` leaves them. They sit outside `people/`, `sources/` and `places/` and are never indexed, exported or read by any tool. `--dry-run` prints `would write`. A write failure warns and does not change the exit code. With `links: id` or no setting, nothing is written.
- **Never the human's file.** A place's note is the file named `place_note_stem(l-id, name)` that carries the places header (`_lib.is_owned_place_note`); the link writer, lint W161 and `normalize-links` take a place's stem from that file only (`scan_place_note_stems`), and with no such file a place link keeps the ID form. Any other file in `places/` with the place's ID in its name (`fairview-research_l-….md`) is never a link target, never overwritten and never removed: the run names it as carrying the place's ID but not being its note, and carries on. A hand-written file at the note's own name blocks the note: it is named with the fix, and the run exits 1.
- **Index.** Place notes are not indexed: the citation scan skips them (they mirror places.yaml, which is data), and they are outside the freshness watermark.
- `--dry-run` prints the same lines (`would write`, `would remove`, `would re-point`) and writes nothing. Exit codes: 0 done or nothing to do; 1 something skipped (`data['skipped']`) or links re-pointed (`data['index_stale']`); 3 no usable index.

### `fha views canvas [p-id] [--dry-run] [--root PATH]`: family canvases for Obsidian

With `links: obsidian`, writes one JSON Canvas 1.0 file per direct-line couple folder into `notes/obsidian/canvas/`, beside the Obsidian tables and outside `people/`, `sources/` and `places/`. The file is named for the folder without its bracket list (`040 Thomas Edward Hartley.canvas`); given a p-id it makes one canvas for that person and their spouses, named for their profile. A canvas has three rows of cards, each card the person's own profile (a person with no profile gets a text card with the name): the folder's couple and any other spouse in the middle, their parents above (father first when `sex:` says so), their children below by birth date, undated last. Parent-to-child lines run down; a tie that is not by birth is coloured and labelled with its nature; spouse lines run across, labelled `married {year}` when the tie has a date. Cards name files by path, so the canvas reads the same in either link mode. Layout is fixed (320 by 240 cards, rows 360 apart, each row centred), so a second run is byte-identical.

- **A view, never a record.** A canvas holds nothing that is not in the records (SPEC §3). It is rebuilt each run, so a card the owner moved is put back; deleting one loses nothing. Private like the other views: nothing is redacted, and `fha site`, `fha packet` and every export ignore the folder.
- **Ownership.** A canvas is the tool's when it parses as JSON and its first card has id `fha-generated` and a text starting `**Generated by fha views canvas`. It is rewritten only when its content differs ignoring the date in that card, removed when its couple folder is gone, and any other file in the folder is never touched: it is named with the fix and the run exits 1. `fha views clean` removes owned canvases; `fha views refresh` (md pass, `links: obsidian`) rebuilds them after the place notes.
- **The tables are not blocked.** `notes/obsidian/canvas/` alone does not count as "the folder exists" for the Obsidian tables above.
- With `links: id` or no setting nothing is written. `--dry-run` prints `would write` / `would remove`. Needs a fresh index. Exit codes: 0 done or nothing to do; 1 something skipped; 3 no usable index or a malformed p-id.

### `fha views tree <p-id> --mode ancestors|descendants|fan [--generations N] [--format json|dot]`

- `ancestors`: parent edges recursively. `descendants`: child edges recursively, plus spouses as one-hop leaves (in-law lineages not recursed). `fan`: kin plus social edges, 2 hops (`--generations N` sets hops).
- BFS with a visited-set cycle guard; nodes dedupe by p-id, edges by `(from, to, type)`. An edge two claims back keeps the first claim's `claim_id` and `subtype` and the stronger `confidence`.
- Output: the **neutral tree JSON** (the stable contract) or GraphViz DOT. JSON `{version, seed, mode, nodes, edges}`; `version` is 2 (absent means 1), and version 2 only adds keys, so a version 1 reader keeps working. Nodes `{p_id, name, vitals, sex, line_confidence}`, `vitals` = `{"birth", "death"}` each the `date_edtf` of the accepted, non-negated claim of that type picked by `_lib.vital_pick_key` among the person's own vitals (`claim_is_own_vital`; §12 "Which claim gives a life date"), or null. Edges `{type, from, to, claim_id, subtype, genetic, kind, confidence, dates}`; `dates.start/end` only on spouse edges; `genetic` is false for adoptive, step, foster, guardian, social, true otherwise (unset `subtype` = genetic, SPEC §12.2); `kind` is `genetic`, `legal` (not genetic) or `other` (friend, associate, neighbor).
- `confidence` is the edge's best claim confidence (`low | medium | high`, SPEC §8.5), or null when unrated. `line_confidence` is the weakest rated parent or child tie on the person's strongest route to the seed (`_lib.line_confidence`), or null when that route has no rated tie; spouse ties are not rated and social ties are not counted.
- Rendering belongs to the build (an adapter maps the JSON to the site's tree library; non-genetic edges dashed). `--format html` is refused with a pointer to `fha site`.

### `fha views brackets`: folder maintenance

Four checks, all previewed. `--fix` applies 1-3, `--fix-promote` applies 4, `--realign` applies all.

**1. Bracket lists and couple name (W103).**
- Refresh `[child, …]` annotations from accepted `relationship` claims; mark non-birth children (`(adopted)`, `(step)`, `(foster)`, …); add cross-links for occupants homed in a lower folder (`Thomas Hartley (also #128 - see 040)`).
- Claims decide who is listed; the human decides the token. A hand-written token is kept when every word belongs to that child's `name:` or public `name_variants:`. Tokens are assigned over the whole list at once, so the most survive and `[John + John Henry]` stays distinct. Lint and views share this logic.
- Default token: first given name, skipping a leading title (a title before one word stays: `Mrs. Lowe`); `Mrs. <husband> <surname>` → `Mrs. <surname>`; `Jr.`-style suffix dropped, `van der`-style particle kept; a bare title only if it is the child's own default.
- Propose the missing `+ second spouse` in the base name (SPEC §12.2), add-only: the couple has exactly two members, the base has no `+`, and the text exactly matches one partner's name. Never rewrite an existing `+ …`; never guess.

**2. Ahnentafel numbers (W110; needs `root_person`).**
- Walk accepted, non-negated genetic parent edges (`biological`, `surrogate-genetic`, `donor-sperm`, `donor-egg`), from `relationship` and `birth` claim `roles:`. Social/legal edges are listed in brackets, not numbered.
- `root_generation: self` (default) makes `root_person` #1; `children` makes them #2 with #1 their children collectively. Other values are rejected (W129).
- `sex: M` → 2n, `sex: F` → 2n+1; same-sex or unrecorded pairs: lower p-id takes the lower slot. Two contributors in one role: the genetic one anchors, the other is shown beside.
- Report wrong prefixes; `--fix` renames.
- **W120**: one resolved parent with no `sex:`; the slot is a default; names the person and the fix. **W127**: `root_person` has a genetic child while `root_generation: self`, so all numbers are a generation off; fix: set `root_generation: children` (or re-anchor), `fha index`, `fha views brackets --realign`. Both report-only, in lint and views.

**3. Placement (W110; needs `root_person`).** Direct-line person files (profile, research, timeline, draft-queue) in the wrong couple folder are reported; `--fix` moves them, creating the folder. Non-direct-line occupants never move. A person at several positions lives in the lowest-numbered folder; higher ones get cross-links.

**4. Stub promotion (W119; needs `root_person`).**
- Reports anyone at position ≥ 2 who is `tier: stub` or in `people/stubs/`, as a lead. `--generations N` narrows (1 = parents).
- `--fix-promote` runs the shared promote engine (§3c) per person, transactionally, behind the gate; then drops the cache and advises `fha index` + `fha views refresh`.
- A new folder for two batched partners is named for the couple (`004 Robert + Jeanne`, even slot first). An unnamed partner (`name: unknown`) is left out; if only the odd slot is named, it is the base (`004 Jeanne`).
- `--fix` with `--fix-promote` is refused.

**`--realign`**: one preview, one gate; fix half first, promote half second, one cache drop, one reminder. Promotion destinations are recomputed against the post-rename tree; if two folders would share a prefix, refuse. Refused with `--fix`/`--fix-promote`. Use after re-anchoring `root_person`, a `sex:` fix, a new parent claim, or a merge. A newly created folder gets its brackets on the next pass (the output says so).

**Safety.**
- The whole plan is preflighted before the first mutation (move destinations read through pending renames). An occupied destination, or two folders left with one number, refuses the pass before the gate and under `--dry-run` (exit 3, nothing written).
- If a rename/move fails non-fatally (a folder open on Windows), `--realign` skips the promote half and says so.
- One `Apply? [y/N]` gate; `--yes` skips it; EOF declines.
- Without `root_person`, checks 2-4 are skipped with a note. Paths carry no machine meaning; the p-id in each filename is the identity.

### `fha views clean [--root PATH] [--dry-run]`

Deletes GENERATED-headed files: companion `.md` files under `people/`, `.html` (or stray `.md`) under `generated/views/`, the place notes in `places/` (judged on the first line after their frontmatter; `places.yaml` is never touched), and the Obsidian canvases in `notes/obsidian/canvas/` (judged on their first card). The first-line marker is the only signal, file by file; profiles, research files, authored files and the inline `## Sources` region are never touched. A hand-written file in `generated/views/` survives. `--dry-run` lists both sweeps. A `people/` companion's index rows (`person_files`, `notes_fts`) are deleted in the same pass, so a clean sweep exits 0. Exit 1 when something is left for the human: a file that would not delete or read (named, skipped; `data['failures']`, `data['unreadable']`) or a failed row cleanup (`data['index_stale']`). An unreadable file is unknown, never "not ours". Uses: compacting for sharing; resetting before a full refresh.

### Printed reports (`fha views family-sheet`, `ahnentafel` and `descendants`; the register report follows on the same shell)

A page to hand to a relative who has no computer. One report is one file under `generated/views/`, named `report_{kind}_{p-id}.md` or `.html` (`kind` is `family-sheet`, `ahnentafel`, `register` or `descendants`), with the GENERATED marker, so `fha views clean` sweeps it. They are not part of `refresh`: a report is asked for by name.

**`fha views family-sheet <p-id> [--spouse <p-id>] [--format md|html] [--root PATH]`**: the person, one spouse, each spouse's parents (birth parents first, then an adoptive, step or other parent labelled so: `Father (adoptive): …`), the marriage and every child, one sheet per couple. With several spouses and no `--spouse` the sheets come in marriage-date order (undated last, then id) in one file, a page break between sheets in HTML. The other birth parent of the person's birth children with no marriage on record (a birth record names both) gets a sheet after the spouses, headed `Father`/`Mother` rather than `Husband`/`Wife`, and `--spouse` accepts them too; a restricted one gets none, and an adopted or step child's other parents never get one. A person with no spouse gets one sheet that says so, listing all their children. Each sheet numbers its notes from 1; a fact line is `Born: 14 June 1840, Fairview, Breton County, Ohio [1]` and the note is the source's title plus its `citation:`. Parent lines, child names and the names in a child's Married column cite the record of the tie as well. A parent's years keep the record's hedges (`about 1815`, `1818 to 1820`); only plain years print as `(1810-1881)`. A child with no other parent recorded at all is listed on the subject's first sheet; a child whose other recorded parent is not this sheet's spouse goes on that parent's sheet, never under this couple. A row with no shown claim is left out (no "Born: unknown").

**`fha views ahnentafel <p-id> [--generations N] [--format md|html] [--root PATH]`**: a numbered list of the person's ancestors, the way genealogy books print them: 1 is the person, 2 the father, 3 the mother, 4 the father's father. The numbering always starts at 1 for the person asked about, whatever `root_generation` says (a report about one person starts with that person), then follows `build_ahnentafel_map`'s rules (genetic edges only; father 2n, mother 2n+1; same-sex or unknown pairs by id) over the ties a report may walk, so a parent known only from a withheld record is not numbered and the ancestors above that edge drop out with it. `--generations` counts the person's own generation as the first (default 6, at most 12; a larger number is cut to 12 with a one-line note). Each generation has a heading (`Generation 3: grandparents`, then `2nd great-grandparents` and so on); empty slots are not printed. A line is the number (in bold, `**4.**`, so a markdown preview cannot renumber it) and the name, with a note for the record of the tie to the child; under it, as a short list, go Born, Baptised, Died and Buried, each with a note. A couple's marriage prints once, on the husband's line (the even number), naming the wife; the person's own marriages print under number 1. A man met again at a second number beside a second wife gets that marriage there. Someone who sits at two numbers (cousins marrying) is expanded only at the lower one and the other reads `(also no. 5)`. A living or unknown ancestor is `A living relative (not named)` with no facts, and the ancestors above them still print. A living subject is allowed: number 1 is that label, the title reads `Ancestors of a living relative`, and the deceased ancestors follow. A person's own marriages print in the order they happened (undated last). A restricted subject is refused; if nobody on the list would be named, the report is refused (exit 2): `Everyone this report would list is living or private, so there is nothing to print.` (or, when no birth parent can be shown, `This report has no birth parent it can show for this person, so nobody is numbered above no. 1.`, adding that adoptive, step and other parents are not numbered when there are some; the printed page itself never says either), after naming any file that would not read (it may be what cut the line off). `--generations` below 1 is refused (exit 2).

Privacy (SPEC §21, "Printed reports"): everything goes through `_lib.export_privacy`, `person_withheld` and `export_tie_ok`, behind one class, `_ReportPrivacy`, so every report kind agrees with the GEDCOM file.
- A living or unknown person is never named: a living parent or spouse is the label `Living Person` with none of their facts; a living child is counted (`and 2 living children (not named)`). The summary line says how many living relatives the sheet counts. A restricted person (any `restricted:` value) is left out and not counted.
- A tie to a living relative may be walked; a tie to a restricted person, or one with no accepted claim behind it (a hand-written `relationships:` entry has nothing to cite), may not.
- A fact is shown only from an accepted, non-negated claim that is not marked restricted, is on a source an export may use, and names no living or restricted person. A source withheld only because it names a living person is cited by one shared note, `A record that is not included in this report (it names a living relative or is private).`
- The subject must be deceased (the Ahnentafel report is the exception, above): a living or unknown subject is refused (exit 2) with the `fha person set-living` command to run if they have died; a restricted subject is refused without printing the name.
- A person or source file that would not read is withheld as restricted (fail closed), and the run names each such file it left something out for, with the fix (`fha lint`, then `fha index`), and exits 1 (the sheet is still written). A subject whose own file would not read is refused with the file named, never called private.

Exit codes: 0 written; 1 person not in the index, or written with a file left out because it would not read; 2 refused (living or restricted subject, or `--spouse` not a recorded spouse; for the Ahnentafel report, a restricted subject, nobody to name, or `--generations` below 1); 3 no usable index. Reports carry their own banner (`Prepared for family. Living relatives are counted but not named, and private records are left out. A number after a fact points to the record it comes from, listed at the end.`), passed to the shared HTML shell as `banner`; every other view keeps the private-companion banner.

**`fha views descendants <p-id> [--generations N] [--format md|html] [--root PATH]`**: everyone descended from a deceased person, numbered the d'Aboville way so a reader can find any branch: the subject is `1`, their children `1.1`, `1.2`, their grandchildren `1.1.1`, and so on. `--generations` counts the subject as the first (default 5, most 12; anything else exits 2). Children are the people with a parent tie to the person, birth children first, then adopted, step or other children marked `(adopted)`, `(step)`, each numbered and continued; within each group oldest first by birth date, undated last, then by name, then id. Each line is the name, the years in parentheses (worded as on the family sheet) and a note number; a `Married ...` line follows for each spouse. A person descended from two people in the report (cousins who married) is listed in full once, where their shortest line of descent puts them (so a longer line reaching them first never cuts off their children), and every other place says `(see 1.2.1)` with a note for the tie on that line. The summary counts only the people on the page and says how many generations the page really shows. A person at the last generation shown who has children gets `More descendants are not shown in this report.` Markdown nests with two spaces per generation inside a list so it reads in Obsidian; HTML nests `<ul class="report-tree">` with each number in `<span class="report-num">`.
- A living or unknown child is counted under their own parent (`and 2 living children (not named)`), never named, dated or placed. **Nothing below a living child is listed or counted**: counting grandchildren under an unnamed parent says more than the report may. That holds through a cousin marriage too: a child of a living descendant and a listed cousin is left off under the cousin as well. A restricted child is left out and not counted, and gets no number.
- A living spouse is the label `Living Person`, undated; a restricted spouse is left out.

### `fha views refresh [--format md|html|both] [--root PATH]`

Regenerates timeline and draft-queue for every curated person (`md`: plus every person's `## Sources` and summary regions, stubs included, a stub reads like any profile; `html`: the `generated/views/` set). With `links: obsidian`, the `md` pass first does what `fha views places` does, so the views written after it link places by their notes' current names; when that pass re-points links, the run exits 1 with `data['index_stale']` and says to run `fha index`. Needs a fresh index. One person's failure warns and skips; the run then exits 1 with `data['skipped']`. A failed index-row update exits 1 with `data['index_stale']`.

### D11: single-file HTML views

HTML views re-render the finished `.md` lines, so formats cannot drift. They are private research artifacts. These rules bind **every fha single-file HTML artifact** (gallery included):

1. **Marker** `<!-- GENERATED by fha <tool> <subcommand> on <date> - do not edit; regenerate instead -->` is line 1, before `<!DOCTYPE html>`. The first non-blank line decides ownership for `.md` and `.html`; the writer never overwrites a file without it. The date there, and in the visible "Generated by" line, is when the content last changed (§1).
2. **CSS**: inlined `design/view.css` (~5 KB subset of `design/styles.css`), system fonts. No `<link>`, no external requests; works from `file://`, mail, and prints cleanly (`@media print` in `view.css`).
3. **Banner**: *"Private research companion - generated from the archive; not redacted for publication. Share through `fha site` instead."* Views are unredacted (SPEC §21 scope). Printed reports carry their own banner (above): they are redacted for relatives.
4. **Naming**: `generated/<area>/{stem}.html`. Embedded data in `<script type="application/json">`.
5. **Exit codes**: `generated/` writes never stale the index; exit 0. A `.md` companion (under `people/`, GENERATED-headed, p-id-named) is outside the freshness watermark and updates its own index rows; a human file borrowing such a name counts toward freshness. No index: print "run `fha index` when convenient", exit 0. A failed row update: exit 1, `data['index_stale']`.
6. **`[[ID]]`** renders as `<span class="cite">`, never a link.

### `fha relate <p-a> <p-b> [--cm CM] [--json] [--root PATH]`, `fha relate --cm CM`

Either person may be a full name instead of an ID, resolved as `fha metrics` resolves one (§7a): exactly one person carrying it, or a refusal (exit `3`, as for a bad ID) listing everyone who shares it, or pointing to `fha find` when nobody does.

Walks accepted `relationship` edges (genetic/social by `subtype`, directed by `roles:`). Reports separately:
- **Blood**: genetic edges only. Common ancestors that are not themselves ancestors of another common ancestor, plus any that are but also reach both people by lines that leave them through different children and never meet again below them (a cousin marriage further up), grouped into routes (one ancestor, or a couple who share a child on both lines), nearest first. Named by generation and removal in everyday words (great-aunt, great-great-nephew, first cousin once removed, great-…-grandparent); a sex other than `M` or `F` takes both words ("aunt or uncle"). A route through one ancestor is *half* when the two connecting children's other parents are both recorded and differ, or an accepted `subtype: half` sibling claim names them; with an other parent unrecorded the answer keeps the full word and a second line says it may be half. When the two nearest routes are full and at the same cousin degree, and no third route shares it, they read as *double* ("double first cousin", both couples named, `; and ` between them); every further route gets its own `and also … through another line` line with its own ancestors (with "or half …" when that line may be half), at most two such lines printed and the rest counted ("and 2 more routes; run with --json to see them all").
- **By marriage**, only when there is no blood answer (blood wins: a cousin who married into the family stays a cousin, and the marriage shows on the path line): a spouse; a recorded non-genetic parent tie by its kind (stepmother, adoptive father, adopted daughter, foster son, guardian, ward); children of one parent where one is adopted, fostered or a stepchild (adoptive sister, stepbrother); a step-parent or stepchild worked out from a parent's marriage; a step-sibling (the child of a parent's spouse, sharing no parent); an in-law (brother-in-law three ways: a sibling's spouse, a spouse's sibling, a spouse's sibling's spouse; father-in-law, grandson-in-law); otherwise the blood word plus "by marriage" (an aunt's husband is an uncle by marriage). A grandparent's spouse and a spouse's grandchild read as the chain ("grandfather's wife"). The step date rule compares the marriage's dates (the marriage claim's own date; its end from the divorce or death that closed it) with the child's own accepted birth and death claims (a baptism or burial does not count), each as the earliest and latest day it allows, so "190X" or "before 1910" settles only what every day inside it would: the marriage surely ended before the birth reads "father's earlier wife"; it surely began after the child died reads "father's later wife"; it surely ran past the birth and began before any recorded death reads "stepmother"; anything else reads "stepmother" with a second line saying the dates that would settle it are not all recorded. A child with no recorded death counts as living on. A recorded parent tie beats a worked-out one. Shortest tie wins (a recorded tie or a spouse 1, siblings through one parent 2, a spouse's or a relative's tie its generations plus 1, co-in-laws and step-siblings 3), then the nearer generations, then P-id, so every run agrees.
- **Social path**: BFS over all edges, rendered as role hops ("your brother's friend's sister's father"); a parent or child hop over a non-genetic tie names its kind ("your adoptive father", "your stepson").

The text labels line up in one column (`Blood:`, `By marriage:`, `DNA:`, `Path:`), and a hedge line indents to it. Result `{a, b, a_name, b_name, names, blood: {relationship, common_ancestors, gens_a, gens_b, half, half_relationship, note, double, routes}, by_marriage: {relationship, kind, certain, hedge, explain, via, path}, any: {path, rendered}, dna}` (`half` is `true`, `false` or `null` for may be half; `note` is the may-be-half sentence or `null`; the top-level blood keys describe the nearest route, `routes` lists every route nearest first as `{relationship, common_ancestors, gens_a, gens_b, half, half_relationship}`, each with its own line's word, and `double` is `true` only when `relationship` is the double word; `by_marriage` is `null` when there is a blood answer or no tie; its `kind` is `spouse`, `step`, `adoptive`, `foster`, `guardian`, `surrogate-gestational`, `social`, `in-law` or `by-marriage`; `certain` is `false` only for a step tie the dates cannot settle, with `hedge` the sentence that says so; `explain` the chain from B's side with names, or `null` for a direct tie or a word that is already the chain; `via` the people between, in chain order; `path` the chain with no names). `names` covers everyone the text names. The text formatter renders sentences, `--json` serves a UI. Read-only; a missing index is a hard error, never a silent wrong answer. Only accepted edges are walked. Limit: a tie by marriage is not shown beside a blood tie. The engine is `_lib`'s kinship section (`kin_graph`, `kinship_answer`, `blood_answer`, `marriage_answer`, `kinship_path`, `kin_relationship`, `person_life_dates`), shared with `fha site`, so a page and the command name a relationship with the same word; `kin_relationship` gives a page one label with its kind (`blood`, `marriage`, `step`, `social`) and the note `marriage dates not recorded` for a hedged step tie.

**Shared DNA.** With a blood answer, a `DNA:` line says how much DNA such relatives usually share ("first cousins share about 866 cM on average; nearly all share between 396 and 1,397 cM"): both the full and the half row when the tie may be half, and a sentence that they may share more when more than one route joins them. `--cm N` (the number a match page shows; "1,234 cM" is read) adds whether N fits the recorded tie and which other relationships it fits, and says documents decide. `fha relate --cm N` with no people is the lookup alone, every relationship N fits with the typical amount nearest first, and needs no index. It is always several answers, never a percentage, and it reads no DNA source and stores nothing (SPEC §21: DNA evidence is restricted); the amount typed lives only in that command's output. `--cm` with one person is refused (exit `2`), and so is a value that is not a number. `data.dna` is `{expected: [{key, label, average_cm, low_cm, high_cm}], more_than_one_route, note, credit}` plus `cm`, `fits_recorded`, `fits` with `--cm` (`fits_recorded` is `null`, not `false`, when the chart gives no figure for the tie, or for one reading of a tie that may be half, and the amount fits no reading it has; also when more than one route joins them and the amount is above the nearest route's range but within what the routes' usual highs add up to, since the chart has no figure for a tie joined twice (`note` then says so); far more than that, or less than the nearest route's range, is still `false`: a gap in the chart is not evidence against the tree), and `null` with no blood answer; the lookup alone is `{cm, fits, note, credit}`. The figures are `tools/shared_cm.json`, The Shared cM Project 4.0 (Blaine T. Bettinger, March 2020; CC BY 4.0, https://creativecommons.org/licenses/by/4.0/, as stated on DNA Painter's Shared cM Project 4.0 tool page; transcribed into rows, names reworded, no figure changed), credited on every answer that prints a figure; a missing file says to run `fha update-tools`. Rows are only the ones read from the chart (a great-great-grandparent has none, because the chart gives none); a relationship with no row says the chart gives no figure for it, and with `--cm` still lists what the amount fits. The text lists five other fits and says how many more the lookup alone shows.

## 7a. `fha metrics`: person completeness

```
fha metrics [<p-id> | "<full name>" | --all] [--include-suggested] [--json] [--root PATH]
```

How well documented each person is, and what is still missing. With no argument: archive totals, the direct line by generation, then one line per direct-line person, closest first ("3 of 5: no marriage record; censuses 2 of 6 years"). Curated people stand in when `root_person` is unset, and the output says why. `<p-id>` shows one person's five checks in detail; `--all` lists everyone, stubs included. The two do not combine (exit `2`). A full name works in place of the ID when exactly one person carries it (`name:`, `aliases:` or a name variant, any case, read from the index's alias table by `_lib.persons_named`, the same surface `[[Name]]` links resolve through). A name two or more people share is refused with each one's ID and dates, and a name nobody carries points to `fha find "<name>"`; both exit `2`, and nothing is guessed.

**Five checks.** Each comes out `met`, `partial`, `missing`, or `na` (does not apply, and left out of the score).

| Check | Met when |
|---|---|
| Birth | A `birth` or `baptism` claim of the person's own (SPEC §8.3, whoever else it names) on a record of the event: a `vital-record` source whose `information` is not `secondary` and which does not record the death of anyone the event belongs to (the child of a birth, either spouse of a marriage), unless the claim says `information: primary`. One exception needs no mark: a baptism dated within 2 years of that person's own death or burial on the same register is an infant's baptism entry, so it counts; both must be dated, the baptism to within 2 years, and an adult's baptism decades before the burial stays a later reading. Judged per claim, so both spouses get the same answer. Partial when the birth is known only from later evidence. |
| Censuses | Every census year the person lived through in a country with a census table is on file: a `census` claim, or a `residence` claim on a `census` source, dated in that year and naming them as a party; someone named only as `informant`, `witness`, `midwife` or `physician` (SPEC §8.3) was not enumerated. Any other claim mined from a `census` source (an `occupation`, an `event`) counts too when the source's own `source_date` puts it in that census year (claim and source both within 2 years) and the claim's place, or else the one country the source's `places:` name, gives its country; without both it does not count. Birth, baptism, marriage, divorce, death and burial claims never count as census years. With no death year on file, never met: years after their latest record are not asked, and while the table has later years the check is `partial` and says so. |
| Parents | Two birth (genetic, SPEC §12.2) parents named by sourced claims (`relationship`, or `birth` with `child:`/`parent:` roles), read with the index's own parentage rule. Partial with one, and partial with three or more (conflicting claims to review). Adoptive, step and other parents are named in the detail but fill neither place. The detail says whether a birth record names them: a `birth` claim on a record of the event, as for Birth. An unsourced `relationships:` belief does not count. |
| Marriage | Each partner backed by a `marriage` claim on a record of the event, as for Birth. Partners are spouses named by marriage or relationship claims, and the other genetic parent of each of the person's own genetic children (an adoptive or step-parent is nobody's partner by this route). `no_known_marriages`, or a negated marriage claim naming them (one person is its ordinary shape), counts as met while no partner is on file (a later claim supersedes the flag, SPEC A.2; the detail then says to remove it). Someone who died before 14 is not asked (`na`). |
| Death or burial | An own `death` or `burial` claim. Asked of everyone marked `living: false`, whatever their age (SPEC §8.2, as lint W101). With `living: unknown`, asked only of someone born more than 130 years ago, counting from the latest year their birth records allow (`189X` could be 1899; birth claims up to 10 years apart are readings of one birth, so 1890 and 1900 read as 1900, since a person who may be 126 may still be living, while 1850 and 1900 read as 1850), or, with no birth claim, their earliest baptism, or else their first record; for anyone younger it is `na`. With `living: true` it is `na`, unless they were born over 130 years ago: then `missing`, saying the record needs checking. |

**Census years.**
- Tables: United States 1850-1950 by name, with 1790-1840 (heads of household only) and 1890 (lost) as extras; Canada 1851-1931, with the 1906/1916/1926 prairie censuses as extras; England and Wales 1841-1921 (1931 was destroyed in 1942 and 1941 was not taken); Scotland 1841-1921 (1931 is still closed under the 100-year rule); Ireland 1901 and 1911 by name, with 1821-1851 fragments and the Irish Free State's 1926 census as extras (1861-1891 were destroyed). An extra year counts when found and is never reported missing. A country with no table is `na`. Poland has no table: the 1897, 1921 and 1931 censuses survive only in fragments or as statistics, so a missing year would be noise.
- England, Wales, Scotland and Ireland are written as those four names; "England" and "Wales" both count as England and Wales, and "Northern Ireland", "Republic of Ireland", "Irish Free State", "Eire" and "Éire" count as Ireland. "United Kingdom", "UK", "Great Britain" and "Britain" name several tables, so they are left out and the place is reported as `na`, with that reason beside it: write the country it is in.
- Country: from the place registry, the last part of a registered place's `hierarchy:`, following `within:` when the place has none. A hierarchy that stops at a U.S. state or a Canadian province ("Elm Creek, Kansas"), written out in full, counts as that country, except the names that are also somewhere else a census was taken: Georgia (a country), Florida (a department of Uruguay), Maine (a historic French province), Maryland (a county of Liberia), Montana (a province of Bulgaria), Hawaii (its own kingdom and republic until 1898) and Newfoundland (not part of Canada until 1949). A place ending in one of those needs its country written. A person with no record at a registered place is reported ("can't tell which country", naming `fha report --section place-candidates`, which lists each place to register with its ready-to-run command), never guessed.
- Years asked: in each country the person's own records place them, from birth if they were born there (otherwise from their first dated record there, widened to any census year on file that fits that country's table) to death. On each census night the person counts for one country: the one their latest record dated (to within a couple of years) on or before that night places them in (with none before, the earliest after; a record that may fall either side of the night counts too, so neither a record dated only `1901` nor one dated after the night (`August 1901`) takes a man out of the Irish census of 31 March 1901, while one dated `1901-03-31` does; every record that could be the latest, such as an `about 1900` beside a `December 1900`, counts; a census on file that names no registered place may be any country's, so its year stays asked). So once a dated record shows them in another country, the country they left is not asked again until a dated record shows them back: a Cork-born man in Kansas from 1895 is asked the US 1900 and 1910, not Ireland's 1901 and 1911. An undated or loosely dated record (`1890/1900`) moves nobody, and a country only such records name is asked as before, so a stay abroad nothing dates still shows as a gap. A census year found in any country fills that year everywhere, since a person is in one census on a census night (an Irishman in the 1901 English census is not missing from the Irish 1901); when more than one country asks years, each missing year is named with its country. Only a birth claim says where someone was born; a baptism is a first record there. A date open at one end ("before 1880") keeps its known end.
- Death year: with none, years after the latest record are not asked, and while the table has later years, extras included (Ireland's 1926), the check stays `partial`; an uncertain death (`1920/1940`) asks years up to its earliest year and counts the rest when found. It comes from the best-dated death or burial claims, the ones with the narrowest date: an exact `1941-01-19` outranks a recollected `1940~` (1939 to 1941), so the 1940 census is still asked, and the detail names the date that decided and the one set aside.
- Records that count: only records of the person's own life place and date them. Being named on someone else's birth, baptism, marriage, divorce, death or burial record does not, nor being named only as informant or witness, nor on a claim other than a census entry whose `subject:` is someone else (everyone listed on a census entry was enumerated).

**Which claims count.** By default, `accepted` claims only: the standard view of what the archive has settled. `--include-suggested` counts `suggested` claims too, which shows what records have been found whether or not they are reviewed. Disputed, rejected, superseded and negated claims never count (a confirmed absence answers the marriage check). Undated claims carry no year; the index's open-ended date bounds are never read as one. The engine has a third mode, `review-queue`, for the workbench's review pointer (TOOLING_INTERFACE §1b): suggested claims count unless parked (SPEC §8.1). The mode decides only what counts; every mode reads accepted and suggested claims, parked or not, to tell what kind of record a source is.

**Archive totals.** People (curated, stubs, direct line), sources by type, claims by status, the median sources and accepted claims per curated person, the share of sources with files that hold searchable text (the W124 predicate), and the five thinnest direct-line people by accepted claims.

Computed fresh on every run and never written into a record (SPEC §17b); the one place it appears in a file is the opt-in `**Records:**` line in a profile's generated summary region (§7), which is rewritten from the engine on every refresh like the region's other lines. The engine lives in `_lib` (`completeness_context`, `person_completeness`, `archive_metrics`): the shared engine every other surface that shows completeness (the site's rings and the workbench's, TOOLING_INTERFACE §1b) uses, so they cannot disagree. Read-only. Exit codes: `0`; `1` a person ID not in the index; `2` another kind of ID, a name that is not exactly one person, or a person with `--all`; `3` no index (run `fha index`).

## 7b. `fha calendar`: the family calendar

```
fha calendar [WHEN] [--week] [--include-suggested] [--json] [--root PATH]
```

Births, baptisms, marriages, deaths, burials and arrivals (`immigration` claims) that fall in a month or on a day: the archive's "on this day". `WHEN` is forgiving: nothing (this month), `today`, a month (`6`, `june`, `Jun`), or a day (`june 14`, `14 june`, `06-14`, `6/14`, `june 14th`). `--week` covers a day (today by default) and the six after it; a month with `--week` exits `2`, saying a week needs a day to start from. An unreadable `WHEN` exits `2` with examples; no index exits `3`. Each line says how many years ago the event was; one from this year reads "this year", and a date later than today reads as a record to check.

**What is placed.** A date recorded to the month (`1880-06`) or the day (`1880-06-14`), with no qualifier or range. An approximate, uncertain or ranged date is left off: the record does not know the day, and the calendar does not guess one. A day view leaves out events known only to the month.

**Whose event.** A vital event belongs to its subject by the SPEC §8.3 rules (`vital_subjects`): a mother named on her son's birth record is not born that day, and a marriage names the couple, not its witnesses. An arrival belongs to the people its claim calls `subject`. With no `subject`, when anyone named carries a role, it belongs to the people with no role (a sponsor or relative named beside the emigrant did not arrive that day); when nobody carries a role, it belongs to everyone named. A claim whose people all carry roles, none of them `subject`, is no event. The same event recorded in several sources is one event, listing every claim and source behind it. A record giving only the month is left off when a dated record of the same event (same type and people) falls in that year and month and is at least as settled (an accepted month-only record stays beside a suggested-only dated one), and is its own line otherwise; nothing from it is added to the dated line.

**Which claims.** Accepted by default; `--include-suggested` adds `suggested`, and each event carries `accepted` (true when an accepted claim stands behind it) so the text marks a suggested-only line `[suggested, not yet reviewed]` rather than showing it as a family fact; a line resting on an accepted claim shows only a place an accepted claim gives. Negated claims are never events. `--week` follows this year's calendar.

**Privacy.** The command is the owner's own view and shows everything. Each event says whether each person counts as living (living or unknown, merges followed, as every export reads it) and whether any source behind it is `restricted` (`source_restricted`). That is not the whole SPEC §19 rule: the index records `restricted:` only on sources, so a claim or a person marked `restricted` is listed here unflagged. Any surface that shares this output must apply its own SPEC §19 export rules to the people, claims and sources an event lists.

Engine: `_lib.family_calendar_events`, the shared engine the site's month panel (§12) also reads; `fha report`'s `on-this-day` section (§15a) and the workbench home page (TOOLING_INTERFACE §1b) read the same week through `_lib.family_calendar_week`, so that two views of the same day cannot disagree. Read-only.

## 7c. Repositories: where the records are

**The list.** `tools/repositories.json` is a list of archives and record sites with, for each, what it holds (`records`, `countries`, `years` when known), what it costs (`access`: `free`, `free_account`, `paid`, `request` or `mixed`), how it is reached (`channel`: any of `online`, `in person`, `by letter`), a short `about` and `how`, the project it came from (`from`), the date that project last checked it (`checked`) and the country guide to read next (`guide`). The assistant names repositories from this list instead of from memory and quotes the `checked` date as "listed as of". The archive did not check any entry itself, so every use says "(check this)".

**Where it comes from.** Two MIT projects: genealogy-mcp (`sources.json`, strongest for Russia, Ukraine, Belarus and Poland) and autoresearch-genealogy (24 country guides, each `### Name` block with a Cost line becoming a row). `build_repositories.py` in the project repo rebuilds the list from files the maintainer downloads at a named commit; it never fetches, and reads upstream data as text and JSON only, never as code. The `sources` array in the file records each project, file, commit and the full licence text. A guide's row and a genealogy-mcp row for one site merge when their URLs match and they name a country in common (`*` alone is not one), one guide row per genealogy-mcp row; when the two disagree on cost the merged row says `mixed`, never `free`. No other rows merge (two genealogy-mcp rows, two guide rows from one guide or two, a row from a topic guide such as Jewish or African American), since each carries its own text: the England and the Scotland guides' Ancestry rows, and one guide's Spain and Portugal FamilySearch rows, stay two rows. A merge adds the guide's text, never countries: the row keeps genealogy-mcp's own. A row from a guide about two countries (Spain and Portugal, Australia and New Zealand, Russia and Ukraine, Poland and Belarus) serves only the country its heading, else its `##` section heading, else its Coverage line names, and both when none names one. `channel` is read from the Searchable, Cost and Coverage text, and a route the text says is not there ("generally not online") is not offered; a genealogy-mcp row whose text says its reading room shows the records also says `in person`. A guide's `Status` line (a closed site and where its records went) is kept in `note`. A worldwide row points at no country guide. `note`, when present, is an availability note or the guide's address line when it held more than a web address (an email, a town). A few upstream addresses that no longer answer are replaced in the build script (`URL_FIXES`, with the date checked). Upstream text is data: the rebuild's diff is read before it is committed.

**The guides.** `tools/research_guides/{stem}.md` are the autoresearch guides as prose (when civil registration began, which census years survive, which office holds what), each starting with a comment naming the project, file, commit and the date that project last checked it, with the "AI accessibility" lines removed. The licence text sits beside them in `LICENSE-autoresearch-genealogy.txt`. Like `record_collections.json`, both ship with the tools (§13c) and are never edited by hand.

**The command.**

```
fha repositories [--place l-id|TOWN | --country NAME|CC] [--year YYYY]
                 [--record birth|baptism|marriage|death|burial|grave|census|military|immigration|probate|land|newspaper|church]
                 [--topic jewish|african-american] [--access free|paid|any] [--limit N] [--json] [--root PATH]
```

Read-only. It answers "what holds death records for Fairview in 1911?" from the list above. The index is needed only for `--place`; `--country` works anywhere. `--place` takes an `l-` id or a name or alternate name (several matches are refused, each with its own `--place l-…` command to run).

**Then and now.** SPEC A.9 keeps a place's history as dated hierarchies, so a Kansas Territory birth and a State of Kansas death are looked up under different governments. `_lib.place_hierarchy_at(conn, place_id, date_min, date_max)` returns the hierarchy written for a period only when that period wholly covers the date range (a `1855/1865` claim is not inside `1858/1861`); the narrowest covering period wins, a place with no history of its own follows `within:`, and `place_hierarchy_in_year` is the one-year form. With `--year` the command reads the country from the hierarchy in force that year (`then`) and from the place's present `hierarchy:` (`now`), and searches the list for both. When they differ, each line says whether it holds "records made by the government of the day", "where the records are likely kept today", or both; when they agree the command says nothing extra. The country is the last part of the hierarchy that the command knows by name (a U.S. state or Canadian province counts as its country; "Kansas Territory" counts through "Kansas"; the Russian Empire is `RU`, Prussia `DE`, Austria-Hungary `AT` and `HU`). A name it does not know, or one that means two places such as a bare "Georgia", is said plainly with the fix: run it again with `--country`.

**Ranking.** Rows that name the country come before worldwide ones; then rows whose `years` hold the year, before rows with no years listed (rows whose years do not hold it are dropped); then `free`, `free_account`, `mixed`, `request`, `paid`; then by name. `--record` keeps rows that hold the matching kind (`death` also reads church, grave and newspaper rows); `--access free` keeps `free` and `free_account`, `--access paid` keeps `paid` and `mixed`; topic lists (Jewish, African American) are listed only with `--topic`. `--limit` defaults to 10.

**Output.** Every line says what it costs and how to reach it, quotes the project that listed it and the date it checked, and ends "(check this)", then one closing line that hours, fees and addresses change. Country guides for the rows shown are named by archive-relative path (`tools/research_guides/…`, `.fha/tools/research_guides/…` in an installed archive), never absolute. `--json` carries `place`, `year`, `then`, `now` (each with `hierarchy`, `period`, `countries`), `repositories` (the list row plus `serves`, `access_words`, `channel_words`) and `guides`.

**Exit codes.** 0 rows listed; 1 nothing matched (the message names a broader command: drop `--record`, drop `--year`, or use `--country`); 2 bad arguments (two places match, an unknown country or record kind, nothing to look up); 3 tool failure (the list is missing, or `--place` has no index to read: run `fha index` or `fha update-tools`).

## 7d. `fha compare`: the evidence for one fact, side by side

```
fha compare <p-id | "Full Name"> [--fact birth|death|marriage|parents|name|residence|<claim type>]
            [--accepted-only] [--include-rejected] [--json] [--root PATH]
```

When two records give a person two different birth years, the researcher needs one table with every record about that fact, so that the human and any skill look at the same thing. Read-only: a pure read over the index plus the frontmatter of the sources it shows; nothing is written or stored (SPEC §17b).

**With no `--fact`**, one line per fact whose records disagree: "Birth: 3 records, years 1838 to 1840 (they disagree)"; the years are the ones the records give (`date_edtf`), so "before 1840" shows as 1840. Only birth, death and marriage are checked, since a person moves house and changes jobs, so two residence records that differ are normal. Two records of the same claim type disagree when their date ranges (`date_min..date_max`) do not overlap, or their places rule each other out (two `place_id`s neither of which sits `within` the other, or, both unlinked, two `place_text`s where neither is the other with some parts left out: "New York" and "Easton, New York" both agree with "Easton, Washington County, New York"); a birth is never held against its baptism, nor a death against its burial, and two marriage records are compared only when they name the same couple (`_lib.spouse_parties`; a witness or parent named on one does not make it another wedding, and a person may marry twice). When nothing disagrees it says so and lists the facts that have records.

**Which claims count for a fact** uses `_lib.vital_subjects`, so a son's birth never lands on his mother: `birth` gathers birth and baptism claims whose own person is the child (or the sole person named); `death` death and burial (`deceased:`); `marriage` marriage (`spouse:`); `parents` relationship claims naming him `child:` plus birth claims that name `parent:` roles; a ceremony asked for by name (`--fact baptism`, `--fact burial`, `divorce`) goes through `vital_subjects` too; roles are read through `_lib.roles_by_person`, so `mother`/`son` count as `parent`/`child`; `name` and any other claim type, the claims that name him `subject:` or, with no `subject:` on the claim, everyone it names. A merged person is read through `merged_into` and the output says so. Stubs work.

**Which statuses.** `accepted`, `suggested` (a parked claim is marked) and `disputed` by default; `--accepted-only` narrows to accepted (when that leaves nothing but unreviewed records exist, it says the records are still suggested or disputed rather than that there are none); `--include-rejected` adds `rejected` and `superseded`.

**One row per claim**, in date order: what it says (`value`, `date_edtf`, `place_text`, `place_id`); the source and its date (`source_id`, `source_title`, `source_type`, `source_class`, `source_date`, `repository`, `path`); how long after the event it was recorded (`recorded_after_years`: `{min, max}` from the source's date bounds minus the claim's, `null` when either is undated or open-ended ("before 1840"); text "at the time" within a year, "about N years after", "undated"); who told it (`informants`, from `informant` roles; "not named" when none); the kind of information (`information`: "firsthand" for primary, "secondhand" for secondary, "not known" otherwise); whether it says the fact outright (`evidence`: direct, indirect, negative); `status`, `reviewed`, `confidence`; `same_origin_as`; `links` (`corroborates`/`contradicts` targets, with their row number when that claim is in the table); `anchor`.

**Same origin** means the rows are one piece of evidence, not several: two claims on one source; two sources that are one record saved from two sites (the rule of lint W162: one collection group in `record_collections.json`, the same subject in the saved site data, a person in common, agreeing dates); and, labelled "someone's tree", claims from sources written by `fha gedcom import` (`subtype: gedcom`) or a `source_type: website` source whose title names a tree ("family tree", "pedigree", "online tree"; a title like "Oak Tree Cemetery" does not count).

**Exit codes.** `0` shown; `1` no claims for that fact (the message names the facts that do have records); `2` bad arguments or an ambiguous name (candidates with their IDs listed); `3` no index or an unreadable one.

## 8. `fha packet`: person data dump

`fha packet p-de957bcda1 [-o out/] [--include-research] [--include-restricted] [--include-dna] [--no-photos] [--dry-run] [--overwrite]`

Copies into `packet_{surname}_{p-id}_{date}/`, then zips:

```
README.txt   ← manifest + "derived export, not research data" disclaimer + date
profile/     ← person .md (+ research file only with --include-research)
timeline.md  ← freshly generated; unsettled claims kept and tagged (§7)
sources/     ← every source record citing the person
files/       ← those sources' files (original names)
photos/      ← all photos of the person
```

**Photos**: union of (a) bare p-id keyword; (b) exact `face_tags:` match; (c) `name`/`name_variants` match, listed in the README as *name-matched, unverified*, counted per group (its copied variants carry the caution even if the matched scan is off disk), unless the group is tied to the person by p-id keyword or exact face tag; (d) files of citing sources. A `MISSING:` photo (§9) is skipped, listed in the README's missing-files list under its alias (the prefix never appears in an export), and warned about with `reconcile` as the next step; its siblings ship, and its person tags still count toward the living-person caution.

**Preconditions**: fresh main index; fresh photo index unless `--no-photos`.

**Audience**: a family research export that may mention living people. Public sharing goes through `fha site --standalone`.

**Privacy.**
- `living: unknown` counts as living. A subject with `living: true|unknown` is refused before output; there is no `--include-living`. Other `living: true|unknown` persons in the materials are named in a README caution.
- `restricted` material is excluded (sources listed by ID and reason, never title). `--include-restricted` opens plain restrictions; `restricted: dna` also needs `--include-dna`; `by-request` never ships. A `by-request` person keeps their folder number. A restricted name shows the unrestricted display name, and the profile copy drops a restricted entry in any name field (`name_variants`, `name_at_birth`, `married_name`, `also_known_as`, read through `_lib.person_other_name_entries`) with its `aliases:` mirror. No DNA by default.
- A guessed relationship (a profile `relationships:` entry with `status: hypothesis`, SPEC §9) is cut from the profile copy under every flag.
- `<!-- private -->` prose (§3c) is cut from every copied record under every flag; the README counts it per file ("2 notes you marked private were left out of …; they stay in your archive").
- A file-name link (SPEC §18 `links: obsidian`) names its record in the target, so every copied record's links are read back to the ID form first (`_lib.links_to_id_form`), dropping a display that is exactly the name of someone the packet withholds (counted as living, merges followed, or restricted in their own record beyond this build's flags; an unreadable marker counts as restricted), even where a person typed that name: the packet withholds the same things in both link modes.

**Unreadable = restricted** (the marker lives in the file). Unreadable subject: refused (`restricted-subject`, exit 3). Unreadable source: excluded with its files, named by ID with the reason `could not be read` (never `restricted`). Both under every flag, since `by-request` is what an unreadable record cannot rule out. Unreadable means: will not open/decode, invalid YAML frontmatter, frontmatter not a mapping, or no frontmatter block; a block that parses, even empty, is honored as unrestricted. A source whose claims YAML fails has record and claims withheld but files shipped (its frontmatter was read).

**Other**: missing files listed on stderr and in the README; existing output refused unless `--overwrite`; `--dry-run` writes nothing.

## 9. `fha photoindex`: photo metadata catalog

Scrapes embedded metadata for the `photos/` tree into the disposable `.cache/photos.sqlite`, so the library is searchable without the photo organizer. Embedded metadata is the durable layer.

### Settings and freshness

- **`photos_ignore:`** (`fha.yaml`): fnmatch patterns on paths relative to the photos root. Matching folders are pruned, files skipped, old rows swept; the freshness check skips them too. This, not narrowing `roots: photos` (§1), keeps a bulk export out.
- The scan stamps the patterns and `roots: photos` in `meta`; a change reads `stale`, and commands name the changed setting. An unstamped catalog is not stale on this ground.
- **`originals_backup:`** (§13f): `tag-person` and `set-summary` keep one pristine copy before writing, refuse if it fails, and warn once when unset.
- `find`, `gallery`, `triage` take `--under PATH` / `--not-under PATH` (relative or `photos/…` form), at group level.
- `photoindex_status` = mtime watermark (§4a) + path manifest `.cache/photos_manifest.json` (catches deletions). Writers patch the manifest from what they saw or wrote on disk, never from `photos.mtime`. Only files the scan catalogues count (not Thumbs.db, PDFs, `.tif_original`).
- **Stale hold**: when a run leaves files unreflected (new, re-matched unscraped, unreadable), the cache mtime is set behind the oldest. If that fails: `stale_hold_failed`, exit 1, name `fha photoindex --full`.

### Scrape

Batched `exiftool -j -r`, incremental by `(path, mtime, size)`; `--full` rescans all.
- An unreadable file is reported and skipped; its old row is kept. New/changed: the cache is held stale. Unchanged: nothing stale.
- "Gone from disk" only means the walk reached the folder and the file was absent. An unlistable folder (walk errors are collected) holds every row under it with its keywords, faces and person matches (no deletions, no `MISSING:`), holds the cache stale, names the folders, exits 1; the rest still scans. Only `photos_ignore:` rows are swept there. An unreadable `sources/` folder carries the source-people rows across unchanged (`unreadable_record_dirs`, cache held stale, exit 1, saying the photos are all there but who the sources say is in them could not be read).
- A stale catalog disables the site's living-person photo check, `tag-person`, `set-summary`, packet photos and caption search, so false staleness matters as much as false freshness.

| Field | Meaning |
|---|---|
| `Title` | Usually null; only when identity is unmistakable |
| `Caption` | What is written on the photo |
| `UserComment` | Context, incl. AI summary (richest text) |
| `DateTimeOriginal` | Date value (SPEC §20 rule 2); `edtf` only with a letter-form `DATE:` keyword |
| `Sub-location`, `City`, `State`, `Country` | Place hierarchy |
| GPS | Authoritative; backfills `places.yaml` coords |
| `Keywords`/`Subject`/`HierarchicalSubject` | Unioned (hierarchical contributes its leaf); `SOURCE: s-…`, bare `p-…`, `DATE:` |
| Face regions | `XMP-mwg-rs` RegionInfo → face-tag names + areas |

**`DATE:`**: only SPEC §20 rule 1 letter form (`Y!M!D!`, `Y!M~`, …). `!` confident, `~` guess, `?` or no marker unknown: `Y!M!D?` + `1916:06:10` → `1916-06`; `YMD` → none. No letter keyword → undated. Digit forms (`DATE: 1880`, `1942!-11!-25!`, `[..1900]`) are not read; the scan counts `nonspec_date_keywords` and prints how to fix them.

### Schema

```sql
CREATE TABLE meta(key TEXT PRIMARY KEY, value TEXT NOT NULL);  -- schema_version, build_config
CREATE TABLE photos(path TEXT PRIMARY KEY, mtime REAL, size INTEGER,
  title TEXT, caption TEXT, user_comment TEXT,
  exif_date TEXT, date_pattern TEXT, edtf TEXT,
  sublocation TEXT, city TEXT, state TEXT, country TEXT,
  gps_lat REAL, gps_lon REAL, source_id TEXT,
  group_id TEXT, is_primary INTEGER DEFAULT 0,
  variant_copy TEXT, variant_role TEXT, fingerprint TEXT);
CREATE TABLE photo_groups(group_id TEXT PRIMARY KEY, primary_path TEXT,
  edtf_resolved TEXT, date_conflict INTEGER DEFAULT 0, file_count INTEGER);
CREATE TABLE photo_keywords(path TEXT, keyword TEXT);
CREATE TABLE photo_face_regions(path TEXT, name TEXT, region_type TEXT, area_json TEXT);
CREATE TABLE photo_people(path TEXT, person_ref TEXT, via TEXT); -- pid-keyword | face-tag | name-match
CREATE VIRTUAL TABLE photo_fts USING fts5(path, title, caption, user_comment, keywords);
```

`photo_face_regions` lets `photo_people` rebuild without exiftool; a catalog lacking it is backfilled. A corrupt or incompatible catalog is rebuilt.

### Variation grouping

Versions of one physical photo are one logical photo. Key: (1) shared s-id; else (2) same directory + stem after stripping `[-{copy}][-{role}]` (`b`, `-b`, `-back`, `-front`, `-negative`, `-page-N`, `-crop`; a copy letter may lack a dash but is last before roles). Never across directories, never by caption.

- **Primary** (among present files): no suffix, else front of copy a, else first path. A `MISSING:` row groups by its alias.
- Slots: `primary {front, back, front_crop, back_crop}`, `variants [{version, …}]`, `pages`/`page_crops {n → path}`, `negative`/`negative_crop` at stem level. `variant_role` holds `front`, `back-crop`, `page-1`, ….
- Queries and packets return groups (`--files` exposes rows); attributes union across variants.
- **Date**: `edtf_resolved` = best variant (most `!`, D > M > Y, then `~` over `?`, ties by path; one function shared with reconcile). Only letter-keyword variants are dated; `MISSING:` variants contribute none. Non-overlapping dated variants set `date_conflict = 1` (listed by `fha photoindex report`); fewer than two dated → `NULL`, and all undated → `edtf_resolved` NULL (Undated tail, no `--edtf` match, no triage date signal). The scan summary prints dated groups, conflicts and `nonspec_date_keywords`.

### People and writes

`photo_people` is rebuilt each scan: (1) bare `^p-[0-9a-hjkmnp-tv-z]{10}$` keywords (case-insensitive) → `pid-keyword`; (2) exact `face_tags:` match → `face-tag`; (3) name match → `name-match`. Caption hints are not inserted. Ambiguous tags are surfaced, never guessed.

**`fha photoindex tag-person <p-id> [--from-face-tag "X" | --paths PATH…] [--dry-run]`** writes the bare p-id keyword (IPTC, XMP subject, hierarchical subject; §6) after a preview.

**`fha photoindex set-summary (<path> | --group <id>) --text "…" [--append] [--dry-run]`** writes `UserComment` as `AI: <text>` (SPEC §20 rule 5); `--group` writes every variant. It replaces an existing `^(AI|Model):` comment or trailing AI block (`--append` adds below); any other text is human, kept, AI block appended. Caption fields are never touched. Anything not clearly a trailing AI block counts as human. Preview + `[y/N]` (`--dry-run` shows old → new, writes nothing); needs a **fresh** catalog (hard block: a stale one could address the wrong file); refuses in working-copy mode (§13d); patches `photos.user_comment` and `photo_fts` so `fha find --text` sees it without a rescan. Exit 0, or 3 if any file fails (reported per file).

Both writers (and gallery tiles) refuse a `MISSING:` path and name `reconcile`.

### Reconciliation

**`fha photoindex reconcile [--with-exif] [--dry-run]`**:
- Present paths are untouched; unknown files are logged as new.
- `--with-exif` reads every `SOURCE:` keyword on untracked files, and a missing row is re-matched by the record-side rule below: exactly one file, catalogued or not, has its exact filename, it is untracked, and it carries its `SOURCE:` and no other, and no other row of that source shares the name (`_lib.photo_retie_target`). A keyword under another name (an `-Edit` copy, a back scan, an export) or several same-named candidates is a proposal (`proposals`), worded as the record side words it (`_lib.photo_retie_candidates`), and nothing moves.
- Unmatched rows stay as `MISSING:` + alias (still searchable); group primary and date are re-derived. Group, `--under` and `--not-under` read the alias under the prefix.
- A scan clears `MISSING:` only when the file returns to its alias or the alias is ignored, never by inference. The catalog's paths are a cache: a filed photo's identity is its `SOURCE:` keyword, and an unfiled one's is its content fingerprint.
- Reconcile is folded into `fha doctor` and the report's freshness step; the plan is computed before any row moves, so `--dry-run` matches the real run.

**`fha reconcile`** heals all types: documents re-match by `_{s-id}` filename (unique hit rewrites the line; duplicates reported; unlisted s-id files reported with `fha process --more`), then photos. Working-copy mode is a no-op; an unreachable root warns.

**Record-side photo healing**: a photos-alias `files:` entry missing on disk (not `missing-fixture`) is re-tied only when exactly one file under the photos root (`photos_ignore:` applied) has its exact filename, not counting one that carries only another source's `SOURCE:` (`_lib.photo_retie_same_named`, both passes), no record lists it (by device/inode), it carries this record's `SOURCE:` and no other, and no other entry shares the name. Otherwise: one report naming candidates and the `file:` line to edit, exit 1. The catalog pass's candidates for the same photo join that report, and its own proposal is dropped: one warning per photo. A photo the record side re-tied keeps the catalog's proposal if its catalog row stays missing. Keywords come from fresh catalog rows or `--with-exif`; after a config-stamp change none are trusted. Lint E011 names the working route.

### Content re-tie

`photos.fingerprint` = SHA-256 (128 bits) of picture data only: JPEG (`jpeg-picture-v3:`) all segments but APPn (APP14 kept) and COM, plus scan data to EOI; PNG (`png-picture-v3:`) IHDR, PLTE, tRNS, IDAT. Excluded: bytes after EOI, PNG text/Exif/time chunks and colour-management chunks (gAMA, cHRM, sRGB, iCCP, sBIT). Formats are recognised by signature bytes. It survives metadata writes, not a re-save or conversion (no match, never a wrong one). Other formats, unparseable files and animated PNGs (`acTL`): `none:v1`, never reopened. A file too large for memory reads as unknown. Failed read: `retry:v1`. Never-known vanished row: `gone:v1`.

- **Gate**: no content match while any live JPEG/PNG fingerprint is unknown (the run says how many remain).
- A match needs exactly one catalog holder (the vanished row) and one untracked file; any unreadable untracked file blocks matching that run. A different `SOURCE:` refuses; sourced rows need `--with-exif`. Keyword matches win. A match moves the row like a keyword re-match, then regroups; reported as *same picture, found by its content* (`rematched_by_content`). `gone:v1` rows neither hold the gate nor count as holders; a `gone:v1` row re-matched by keyword becomes unknown again.
- Scraped files are always fingerprinted; backfill is rationed to 30 s per scan; reconcile is not rationed.
- Schema 1 upgrades in place in one transaction (column, tables, stamps, `scan_due`); dry runs roll back; a failed upgrade says re-run, never rebuild. A half-upgraded file (every stamp says 1 or 2) is finished the same way; only an unreadable or foreign file is rebuilt. `scan_due` keeps the status stale until a completed scan. `face_backfill_due` (set by whichever writer creates `photo_face_regions`) forces one full rescrape; a row it could not rescrape has its mtime cleared for retry; only an unlistable folder keeps either marker set. Rows already `MISSING:` before the upgrade re-tie only by name and keyword. Read-only commands (`find`, `gallery`, `triage`, `report`, `tag-person`, `set-summary`) call schema 1 *out of date* and name `fha photoindex`.

### Query and gallery

**`fha photoindex find --person p-… | --keyword … | --edtf 192X | --text "…" | --under PATH [--not-under PATH] [--files]`**: filters AND at group level; bad p-id/EDTF refused; one row per group unless `--files`. No catalog: exit 3; stale: warns.

**`fha photoindex triage [--top N]`** ranks unprocessed groups (default 10). **`report`** lists date conflicts.

**`fha photoindex gallery <find filters> [--out FILE]`**: one self-contained HTML page via the same matching as `find`. Fully `MISSING:` groups dropped; decade sections newest-first, Undated tail, variant `<details>` chips; plain range labels ("1912 to 1915", "before 1900"); with `--person`, weak matches go under "Verify these" with a quoted `tag-person` command. Same validation as `find`; at least one filter. Follows D11; `file://` hrefs and lazy `<img>` point at the photos (`.jpg/.jpeg/.png/.webp/.gif`; other formats get a placeholder tile that still opens the file).
- Lands in `generated/gallery/` (gitignored; `fha site` never reads or clears it): `{slug}_{p-id}.html` for a bare person filter (other filters' tokens appended when combined), else `gallery_{tokens}.html`; `--out` overrides.
- No two distinct filter values share a file: EDTF forms stay distinct (`1912~` → `edtf-1912-approx`, intervals half by half); a free-text value whose slug is lossy gets `-h` + 6 hex digest after the readable stem; case and outer space fold first; `--under`/`--not-under` resolve to alias form first. Callers relay the printed path.
- Refuses in working-copy mode (`status=working-copy`, exit 0). Catalog absent/old: exit 3; stale: builds with a warning; zero matches: nothing written, exit 0. A build prints the path and its `file://` URL.

## 9a. `fha reorganize`: bulk-tidy the documents root

`fha reorganize [--root PATH] [--apply] [--yes] [--dry-run] [--batch-size N] [--group-threshold N] [--limit N]`

Files loose documents into `documents/{type}/` and updates each owning record's `files:`. `fha process` already files new documents this way; this is the catch-up for older or hand-dropped material.

**Eligibility, by path shape only.** A file is eligible only when it is flat at the documents root, or one level down in the folder its record's `source_type` maps to (the `sources/{type}/` mapping). Any other shape reads as human-curated and is never proposed: moving a curated file is judged far worse than leaving a mess. Within-root moves are allowed by SPEC §12.1.

**Rules.** Destination is `documents/{type}/`. A source with more than `--group-threshold` eligible files (default 3; 0 = every source) gets `documents/{type}/{slug}_{s-id}/`. Nothing eligible stays loose at the root.

**Survey** (dry-run; the default, `--dry-run` optional). Refused, never guessed: an alias claimed by more than one record (for every claimant); an entry whose filename carries a different or no s-id (drift, as `fha process refile` checks); a destination that already exists. A folder under `documents/` or `sources/` that will not list fails the survey closed. `--limit N` takes only the first N eligible files, whole records only.

**Apply** (`--apply` required). Without `--yes` an interactive terminal confirms the file/record count; non-interactive without `--yes` refuses.
- Per record, atomically: validate the text rewrite, move every file (roll back all if one fails), write the record once, re-read to confirm, restore files and text on mismatch. Only `files:` changes; no Notes paragraph.
- `--batch-size` (default 25) is a hard bound that never splits a record; a record larger than it is skipped and named ("raise --batch-size to include it").
- `fha reconcile --dry-run` (documents and photos) runs before the first batch and after each; a warning/error count that rose halts the run (single writer, §1) and reports the change. An unchanged count is pre-existing and ignored. Completed moves are kept.
- Any run that moved a file reminds the human to run `fha index`. A final `fha lint` reports counts for information; a crash in it is caught.

Photos are out of scope (identified by `SOURCE:` keyword, not path). Exit codes: 0 clean plan/apply or nothing to do; 1 survey problems or a mid-run halt (archive consistent); 3 a record left inconsistent by an incomplete rollback, or `fha reconcile` failing before the first batch. A working copy is a clean no-op.

## 10. `fha places`: registry + geocoder

**`fha places lint`**: orphan l-ids, duplicates by normalized name, dangling or cyclic `within:`, a `within:` target with its own outward `within:`.

**`fha places candidates`**: normalizes unlinked claim `place_text` (case, punctuation, St/Street, Co/County), clusters near-variants by token-set match, and emits groups of 3+ occurrences with claims and date spread; plus photo-GPS clusters (3+ photos within ~150 m) near no known place. Default scope: accepted and reviewed-but-open claims (`suggested` with `reviewed:`, SPEC §8.1). `--include-suggested` adds every `suggested` claim (for the setup-interview backlog scan after `fha gedcom import`).

Elevation: human confirms, mint an l-id (+`within:`), then backfill `place:` per claim, each shown. `place_text` is never altered. This pattern is the template for recurring-people (FAN) detection. One cluster at a time is `fha confirm place`; all of them at once is `--register`:

**`fha places candidates --register [--dry-run] [--threshold N] [--include-suggested]`**: registers a place for every place-text cluster at or above the threshold and links the clusters' claims, after one yes for the whole list.

- **Each cluster** becomes one of four things. When its label fits exactly one registered place by the write-time rule (SPEC §15), its claims link to that place. The rest are grouped by their labels alone, so the answer never depends on which cluster is bigger: a label whose first part matches another's and whose other parts all appear in it is the same place ("Chicago, Illinois" and "Chicago, Cook, Illinois" make one place, named with the label that names the most levels). A label contained in two longer labels that disagree ("Fairview, Kansas" in "Fairview, Breton County, Kansas" and "Fairview, Ellis County, Kansas") could be either town: it is listed for the human, the longer two are registered, and the list after the write names the `fha confirm place` command for each. Two groups GeoNames matches to the same entry are one place too. A label that fits several registered places, or is only near one (word order, an abbreviation), is left out and listed with the `fha confirm place` command per candidate. So is a label that fits no registered place but whose first part is a registered place's name or alt name ("Chicago, Cook County, Illinois" against a Chicago registered as "Chicago, Cook, Illinois"): it is listed as "may be" that place (with the place's hierarchy and l-id) and never registered here. The list gives both paths: `fha confirm place … --into <l-id>` if it is the same place, `fha confirm place … --name=<label>` if it is a different one, and names the parts of the text the place's hierarchy lacks (a part it does not hold, or a county it does not write as one), which the human can add if it is the same place.
- **What a new place gets.** From the GeoNames data already saved in `.cache/geonames/` (nothing is downloaded), matched as `geocode` matches: a single fitting entry gives coordinates, the missing county, state and country, and GeoNames' spellings as `alt_names` (never one another place answers to). A country, state or region gets no coordinates. A name with several fitting entries, or none, or no saved data, gets none; the closing line names `fha places geocode --all` for them. Population never picks.
- **Review.** One list (each new place with its claim count and what it gets, each cluster that joins a place) and one `[y/N]`: "Register N places and link M claims?". The claims each write would skip are listed before the question. Yes re-reads `places.yaml`: a planned place whose label now fits a place registered meanwhile is left out, and a cluster whose target place's block changed is not linked, each with one line. New places are appended in one rewrite of `places.yaml`, in the file's own line ending; then each source record gains its `place:` lines. Every write is atomic, and a failure partway puts every file back; a file that cannot be put back (another program holding it) is named with what it still holds, and the next step is to run `fha index` and the command again. `--dry-run` prints the same list and writes nothing. GPS clusters are not registered.
- Exit codes: 0 done, declined or nothing to do; 3 the index stale or unreadable, the registry unreadable, a write failed (nothing written), or `--dry-run` given without `--register`.

**`fha places link [--apply]`**: attaches `place:` to existing claims whose `place_text` fits exactly one registered place by the write-time rule (SPEC §15): claims written before their place was registered, or before an alt name or hierarchy was added.

- A dry run by default: each place text that fits, with its claim count and the place, then "Would link N claims in M source records". `--apply` is the human's yes and writes them; there is no further question. Claims of every status are linked, as write-time resolution links them.
- Texts that fit several places, or are only near one, are listed with the `fha confirm place <c-ids> --into <l-id>` command per candidate and never linked.
- **The write.** Each claim gains one `place:` line after its own `place_text:` (an empty `place:` line is filled in instead). Nothing else in the record changes: the text is split on line feeds only, so CRLF endings, comments, quoting and every other claim survive byte for byte, and the result must parse back to the same claims plus the new key, or that claim is skipped with a reason. A claim is also skipped when it already names a place (registered or not) or its `place_text` changed since `fha index`. Each record is read and parsed once for all its claims and checked once after, so a record holding thousands of claims (a GEDCOM import's one source) links in seconds. Each record is rewritten atomically; a failure partway puts every record back, and a record that cannot be put back is named with what it still holds.
- Exit codes: 0 done, dry run or nothing to link; 3 the index stale or unreadable, the registry unreadable, or a write failed (nothing written).

**`fha places geocode (--place l-id | --all) [--offline] [--dry-run]`**: fills in `coords` for specific places that lack them (or the one `--place`), plus missing hierarchy levels and GeoNames spellings, from the GeoNames export saved in `.cache/geonames/`. No live API.

- **Data.** `countryInfo.txt` (country names and codes), `admin1CodesASCII.txt` and `admin2Codes.txt` (state and county names for every country), and one per-country dump `{CC}.zip` for each country the registry's hierarchies point at. Each file is downloaded once, only when missing and never with `--offline`; a download goes to a `.part` file renamed into place. A dump is streamed and filtered to feature classes P (towns, villages) and A (states, counties, communes, the country), plus class S codes CH, CMTY and SYG (churches, cemeteries, synagogues), and stored in `.cache/geonames/gazetteer.sqlite`, which is rebuilt from the saved dumps when its schema version changes. A failed download, or a damaged dump or cache, is one plain line, never a traceback; the other countries carry on.
- **General places.** A country, a state or province, or a historic region (Prussia, Galicia, Bohemia and a short list like them) is specific enough as it is and gets no coordinates. A country or region name on its own is general at once and causes no download, with one exception: a country that is its own capital city (Luxembourg, Singapore, Monaco, Vatican City) gets the coordinates of its capital, when countryInfo names a capital with the same folded name and that country's data holds a capital (`PPLC`) of that name. Its data is downloaded for the check, the match goes into the one review table like any other, and population never decides it. Any other lone country name stays general: "Wales" is never a village called Wales, and "Georgia" stays the country. A state is general when its state entry fits and no town of the same name lies inside it; when one does (the city-states Berlin and Hamburg, New York City in New York), the state steps aside and the town is matched like any other, and a namesake village in another state does not count. A lone name that is a state somewhere ("Berlin") never implies that country, so with no country it goes to review like any other place. General places are never listed as not found; one line counts them ("3 general places (countries, states, regions) need no coordinates").
- **Country.** Read from the hierarchy's last part (for a place with no hierarchy, from its name's own comma parts, so "Krakow, Poland" is read as name and country): a countryInfo name, a common English or native form (USA, England, Scotland, Wales, Holland, Polska), or a state or province only one country has (Illinois). Two- and three-letter codes other than US, USA and UK are not country names. A place that names no country, in its name or its hierarchy, searches the countries already saved and downloads nothing, and even a single fit is listed for review, never proposed.
- **Match.** Names compare with case, accents and punctuation folded, and a leading or trailing division word dropped (County, Co., Parish, parafia, powiat, gmina, województwo, Voivodeship, Province, Department, State). A name with commas is looked up by its first part. A candidate is a feature with that name (or one of its GeoNames spellings) in those countries; it fits when every other hierarchy part names its commune, county, state or country (a division never counts itself). A church or cemetery fits only with a hierarchy, never on its name alone, and a part may also name a town in its county; it is never a candidate when a town or division of the same name (living or historical) also fits the hierarchy. One fitting candidate is a hit. Among several, in order: a living town beats a neighbourhood, abandoned or historical entry; an entry whose own name is the place's name beats one that only lists it as another spelling; a town beats a same-named division or one whose name says County (unless the place's name says so); the candidate whose divisions the hierarchy names most completely wins. Whatever is still ambiguous goes to the human; population never picks a candidate (a big city and its same-named villages are all listed).
- **What a hit adds.** Coordinates. The county, state and country GeoNames gives, slotted into the hierarchy where they are missing; existing parts are kept word for word, a city-state (a city with no county, named like its state) does not gain its own name again, while a city with a county between it and a same-named state (New York) keeps the state, a part that could be two levels counts as both, and a hierarchy out of order, written over several lines or carrying a `#` comment is left alone. The country is written the way most of the registry writes it, else GeoNames' name. GeoNames' name and ASCII name as `alt_names`, only for a place with none (an empty `alt_names: []` counts as none), and never a spelling another place already answers to (PL002). Nothing else (no notes, no history).
- **Review.** Every hit is shown in one table (place, name, coordinates, what else it adds; a church, cemetery or synagogue says the pin is that building) and one `[y/N]` asks "Write coordinates for these N places?". Every place's block is noted when the run begins, before any download. Yes re-reads `places.yaml` and writes them all in one atomic rewrite (all or nothing), editing only the matched blocks so comments survive; a place whose block changed since the run began is left as it is, with one line naming it. That yes is the human confirmation coordinates require. `--dry-run` prints the same table and leaves `places.yaml` untouched (missing GeoNames data is still downloaded into the cache). Places with several fitting candidates, or whose hierarchy no candidate fits, list their candidates (name, county, state, country, coordinates), ordered by population, each with the exact `fha places set <l-id> --coords "LAT, LON"` that settles it. An `--all` run lists the first ten and says how many more there are, with the `--place` command that lists them all; `--place` lists every one. Places with no candidate say which countries were searched, and a place that names no country says to add one.
- Exit codes: 0 done, declined or nothing to do; 1 no GeoNames data to match against, or the `--place` id is not registered; 3 neither `--place` nor `--all`, a malformed id, or the index or registry unreadable or unwritable.

`fha confirm place` mints a place without coordinates and names the next step: `fha index`, then `fha places geocode --place <new l-id>`.

**Human-directed writes** (the workbench place page):

```
fha places set <l-id> [--coords "LAT, LON"] [--aka NAME]... [--history "PERIOD | HIERARCHY"]... [--dry-run]
fha places note <l-id> --text TEXT [--dry-run]
fha places edit-note <l-id> --old-text TEXT --text TEXT [--dry-run]
```

- `set` fully replaces each given field. `--coords`: decimal degrees in any forgiving shape ("39.5631, -95.1216"), or degrees, minutes and seconds as a gravestone or survey gives them ("39°33'47\"N, 95°07'18\"W", "N39.5631 W95.1216", minutes or seconds optional, a comma or the direction letter between the two); lettered parts are read by their letter, so a longitude-first pair is swapped and the preview says so; unlettered parts are latitude first. DMS is stored rounded to six decimal places. Strict ±90/±180, minutes and seconds under 60; a packed or hyphenated form is refused with the comma form to copy. `--aka`: the whole `alt_names:` list, one verbatim name per flag ("Washington, D.C." is one alias). `--history`: the whole `history:` list; the period follows the claim-date rule (EDTF kept, loose wording normalized, unreadable refused).
- `note` appends a dated paragraph to `notes:` (SPEC §15), written as a `notes: |` block.
- `edit-note` rewrites one entry named by its exact text, with `fha person edit-note`'s rules and reason codes (part of a note / several notes / not found / ambiguous / empty replacement) and workbench wording (§3c).
- Surgical edits preserving comments. No `[y/N]` gate: the human supplied the values.

Exit codes: 0 written/dry-run; 1 unknown l-id or missing registry (with `fha find` next step); 3 bad id shape, out-of-range coords, unreadable period, nothing to change, unreadable/unwritable registry.

## 11. `fha convert-mining`: interview converter

`fha convert-mining [--root PATH] [--apply]` (dry-run default) converts legacy transcript-mining output (`facts.txt`, `stories.txt`, `questions.txt`, `sources.txt`, alias files).

5. **Audit:** `.cache/convert_mapping.csv` (`legacy_id, new_id, notes`). Unresolvable people become stubs (§5).

## 12. `fha site`: static HTML explorer

Builds the archive as a website in `generated/site/` (or `--out`): relative links, no CDN, works from `file://`. The packet embeds a one-person slice.

**Data:** structured data from `.cache/index.sqlite` (never the `fha views` files); biography and Stories prose from the person file. Jinja2 templates in `tools/templates/`; a minimal stdlib Markdown converter; PIL for images. `[[ID]]` (or its file-stem form) becomes a relative link labelled by `|display` or the record name; a name/stem resolves through the alias map (so a living person is redacted however named); an unresolved stem is plain text; an unresolved ID renders highlighted.

### Pages
- **Home**: ancestor pedigree (below) seeded on `site.home_person` else `root_person`, depth `site.home_pedigree_generations` (default 5, max 8); surname A-Z index; recent discoveries; **Sources** grouped by decade of `date_min`, alphabetical within, undated last.
- **Person (curated)**: summary; family chart; an ancestor fan (five generations; inner rings curved, outer rings radial; names on two lines when long, with years); biography (`[[s-…]]` numbered footnotes, `[[p-…]]` links); timeline (as `fha views timeline`: by date, grouped by decade, type/value/source link); photo strip (§9 face tags); Stories; Friends & Family; sources index (same query as `fha views sources-index`). A person with descendants also gets "See descendants of {name} →" in a `<details>` disclosure, opening the descendant explorer seeded on them.
- **Person (stub)**: one-line entries on their couple's section.
- **Source**: scan thumbnail (the Files list's privacy-checked image, `role: front` preferred) linking to the full scan; citation, metadata, claims table with status badges, files list.
- **Place**: embedded OpenStreetMap iframe with marker when coords exist (offline an empty frame; the map link always works); `notes:`; "Names over time" (`history:`); `within:` children; and "Through the years", one dated list that merges the place's dated names with every claim at the place and at the places `within:` it (a cemetery shows on its town's page, marked "at {place}"). A claim whose date falls wholly inside a `history:` period shows what the place was called then; a range that crosses a period boundary, an undated claim, or a period running to the present (today's name) shows none. A confirmed absence (`negated`) is not an event. Audience rules are the existing ones.
- **Person (curated), burial line**: when the person's picked accepted burial (the one the summary box shows) names a registered place with a map position, its own or that of a place it is `within:`, the page says "Buried at {place}, {where}" with an OpenStreetMap map link (zoom 16) and a directions link that leaves the visitor's own starting point blank. The links need an internet connection; there is no embedded map.
- **Graves to visit** (`graves.html`, linked under Places on the home page, built only when someone has such a burial): every person with a page who is not living, unknown, restricted, by-request or merged away, grouped by the picked burial's place with its map and directions links (or "no map position recorded yet"), the burial and death dates and the source; burials at places nobody registered come last as "Other burial places", as written. Same claim filters as the summary box, so a parked or restricted burial never shows.
- **Discoveries**: from `notes/discoveries.md`.
- **Search** (`search.html`, on unless `site: search: false`): one box at the top of every page sends the words to `search.html`, which finds people (by every public name, and by a married partner's surname from a tie the page shows), places (with their other names) and records (by title) in `data/search-data.js`, a script setting `window.FHA_SEARCH` so it loads from `file://`. Names and query fold by one rule (`_search_fold`: accents as filenames fold them, then tsch/sch/sz/cz/ph/w/y to ch/sh/sh/ch/f/v/i, doubled letters once; a name with an apostrophe also gives its joined word, so OBrien finds O'Brien), whose table the file carries for the browser; every query word must start a word of the entry (a word typed partway through a folded spelling, like "Step" for Stephen, also tries finishing it), two letters as typed are enough, own names ranking above a married surname, up to 25 per group before "Show all". The file lists only pages the build publishes, holds only names, years and titles, and on a shared build also passes `_lib.export_privacy` and `person_withheld`, so no living, unknown, restricted or by-request person, private name, private record, or count of who was left out reaches it; the linked preview lists every page. A value other than true or false leaves search off with a warning naming the setting.

Every page carries print styles: navigation and controls are left off paper, collapsed charts open, pan/zoom charts print whole; the interactive descendant explorer is screen-only.

### Optional panels (`site:` switches, default off)
Both read `true`/`false` (or `yes`/`no`, `on`/`off`); any other value leaves the panel off with a warning naming the setting. The switches are for the shared site. The workbench (TOOLING_INTERFACE §1b) always shows the ring, and puts "This week in the family" on its home page in place of the month panel.
- **`completeness_rings`**: each curated person page gets a five-segment ring and a list: the five checks of `_lib.person_completeness` (§7a), accepted claims only. Drawn by `_lib.completeness_ring_svg(result, size)`, a pure function returning inline SVG (no script, no ids, `currentColor` following the `--accent` token): `met` a filled segment, `partial` half filled, `missing` an empty outline, `na` a faint dotted outline, each with a `<title>` giving the check and its state, so the ring is never colour-only. What is still missing is said in a few plain words in a shared build (`_lib.completeness_public_phrase`: "no marriage record", "censuses 2 of 6 years"), never naming a command; the linked preview shows the result's full detail, as `fha metrics` does. Person pages only; the family chart's cards carry no ring. **Privacy:** a living or unknown person (merges followed) gets no ring and no computation in any build, the linked preview included; a restricted person has no page in a shared build. A shared build sets aside, before the checks read them, the claims no public page shows: a restricted claim, one on a restricted, DNA, by-request or not-for-publication source, and one the timeline withholds for who it names (`claim_people_verdict`), so a ring never reveals evidence no page shows. A record her page shows without its wording, because it also names a living informant, counts. Unreviewed claims that are not private stay in, because the checks read them to tell what kind of record a source is; only accepted ones score. A confirmed absence reads as such: "never married (confirmed)".
- **`calendar`**: the home page gets "This month in the family": the births, baptisms, marriages, deaths, burials and arrivals of `_lib.family_calendar_events` (§7b), accepted claims only. Every month is rendered in its own block; a small inline script shows the visitor's current month, and without it the page shows the build month above an "All months" list. Each person links to their page when the site has one (a stub is plain text). **Privacy:** the engine's flags are not the whole rule, so the site applies its own. An event is dropped when anyone it belongs to is living or unknown (in every build) or restricted (in a shared build), when any claim behind it is withheld for who it names (`claim_people_verdict`), or when any claim behind it is not publishable (a restricted claim, a hard-restricted source, or, in a shared build, an unaccepted claim). One private copy of an event keeps the whole event off.

### Family chart (server-rendered SVG)
One renderer: person page at 2 ancestor generations, Home at the configured depth. Static `<svg>`, no script needed.
- Columns: children | subject + spouse(s) | ancestors, from one Ahnentafel walk. Home's hub row also shows siblings.
- Ahnentafel slots 2N/2N+1 are a couple: both known gets one shared bracket (`ped-link-couple`); one known gets a plain elbow.
- Family wings route couples-first: subject and spouse join, then one line to that couple's children. A child with an unrecorded or redacted co-parent hangs off the subject. A redacted or absent spouse/child is dropped.
- Ancestor cards are tinted paternal/maternal by Ahnentafel parity, except a slot filled by elimination among unknown-sex parents.
- **Private cards (shared site, family chart and fan):** a living or unknown ancestor who is an adult (`_lib.is_known_adult`: a recorded birth 18 or more years before the build, or no birth recorded and a recorded child) fills their slot as a card reading "Private", with no name, dates, link, tooltip or line tint, and the walk continues to the ancestors behind them. A living person not known to be an adult, and a restricted or by-request person, is left out with no slot, and the walk stops there.
- Caption: "{name}'s family, tracing back through the generations →". An ancestor with a page links to it; a stub is plain text.
- **Home hub and private cards (shared build, SPEC §21):** the hub is the home person. Every card on Home's chart and family row goes through one rule, `_tree_card_kind`: dead and publishable is shown in full; living or unknown and an adult is a card reading "Private" (no name, dates, link, tooltip, id or branch tint), and the ancestors behind it still draw; living or unknown and not known to be an adult is left out, with no card, slot or gap; restricted or by-request (alive or dead) is left out and the walk does not pass through them. Adult (`_lib.is_known_adult`) means at least one recorded child the site may show (a child linked only by a restricted record, or who is by-request, does not count), whatever a recorded birth says; or a recorded birth date (a birth claim of any status, or the provisional `birth:` on the record or on any record merged into it) whose latest possible day is 18 or more years before the build date, the youngest deciding; or, with no birth date, a baptism that long ago. A typed date that cannot be read never makes an adult. A private hub's caption is "The family, tracing back through the generations →". Only a hub that is left out hands off to the closest shown ancestor on its line; failing that, a blank hub only (no ancestors, no family row) with a plain note. Person pages and `--linked` are unchanged.

### Interactive trees
`site.py` builds a neutral tree JSON per seed (§7), redacted server-side. In a shared build each person past the seed goes through `_tree_card_kind`, as on the family chart: a living or unknown adult is a node named "Private" under a placeholder id (`private-1`, `private-2`), with no vitals, sex, photo or link, and the walk carries on through them; anyone left out is dropped with everyone reached only through them. An edge's `confidence` counts only claims the build may show, so a sealed certificate never lifts a shared family story; a tie two claims back is one edge. Vendored `templates/vendor/tree-adapter.js` converts it to the renderer's hierarchy; vendored `templates/vendor/fha-tree.js` draws an SVG collapsible tree with pan/zoom in a viewport. Third-party code in `templates/vendor/` is pinned and loaded with plain `<script>` tags (no CDN, no build step), so every chart works from `file://`: `d3.min.js` is D3 7.9.0 (ISC), unmodified, and each library's licence sits in `vendor/licenses/`. The static charts (family chart, home pedigree, fan) are drawn server-side and load no library.

The JSON is inline in the page (read from the DOM, so `file://` works) and also written to `site/data/tree_{p-id}_descendants.json`. The adapter is the single seam: a new engine means rewriting only those two files. `fha-tree.js` also exports `wrapStatic(container, options)`, adding the same pan/zoom to a static SVG (the home pedigree).

### Which claim gives a life date
Where accepted claims for one vital disagree, every single-date surface (summary, chart labels, `fha views tree`, GEDCOM `BIRT`/`DEAT`) picks by `_lib.vital_pick_key`: (1) dated before undated (backwards range = undated); (2) precision tier: day, month, year, about-a-year or 2-3-year span, decade, wider; (3) confidence; (4) narrower range; (5) claim id. Tiers, not raw days, so a leap year never outranks confidence. Picked after the own-vital and publishability filters. `fha xref` flags non-overlapping accepted vitals; differing exactness is not a contradiction. No conflict marker on the headline.

### Audience split
Standalone shows accepted claims only (timeline, source claims, place claims). Linked/workbench also shows reviewed-but-open claims (`suggested` with `reviewed:`), marked "unconfirmed - parked {date}" and tinted in the workbench. Never-reviewed `suggested` never renders. Low-confidence accepted claims carry a "low confidence" flag everywhere.

### Privacy (standalone)
The standalone site is the safe-to-share version (SPEC §21): `living`/`unknown` redacted; `restricted` excluded wherever it appears (a restricted name shows the unrestricted display name); DNA excluded; `publication_ok: false` sources withheld. A redacted name reads "Living Person" and a withheld source "Restricted - not included in this publication", never an empty slot or a broken link.

- **A record that also names a living person.** A claim `_lib.claim_people_verdict` keeps (a baptism with a living godparent, a census of a household with a living child) stays on the timeline, the summary box, the place page, the source page and the calendar. Its wording is replaced by the deceased people it is about, linked ("marriage: Calvin Hartley and Ethel Moore"), and the living person is left out of every people list, not labelled. A living person's own event, a `relationship` claim naming one, a fact about living people only, or a claim naming a restricted person stays out, chart-node life dates included. So does a `negated` claim (a confirmed absence) naming a living person, since only its wording says it did not happen. The kept claim's source gets its page and its citation (unless it names a restricted person): the page shows the record's own citation and files, which may print the living person's name, but its claims table never lists, links or labels them, and the search file leaves it out, since its title may name them. A photograph or artifact (`source_type: photo` / `artifact`) naming a living person pictures them, so it keeps no page however its claims fare, since the photo catalog's living-tag check fails open without a catalog; nor does a source whose type is outside the archive's list (`_lib.SOURCE_TYPES`, e.g. a mistyped `photograph`). A source naming a living person with no kept accepted claim gets no page and its citation reads as withheld. No family tie comes from the kept claim: ties are the relationships the index derives, judged by `export_tie_ok`. `--linked` is a local preview: links to real files, no copying, no redaction guarantee.

- **Unreadable records fail closed.** An unreadable or unparseable person record (exception or `parse_errors`) is withheld everywhere; an unreadable source is withheld with every fact it evidences. Each warns with the file and fix. The build never links to an unbuilt page, but nothing audits whether a page should exist.
- **Undecodable files** (not UTF-8) get W128's plain cause, never a crash. The privacy pre-pass withholds them; a person page loses prose, variants, tags and portrait; a source page uses its index title. `notes/discoveries.md` reads the same way (missing = skip). Never rewritten; ordinary warnings exit.
- **Living-tagged photos.** An image the catalog tags to a living person (either path spelling) is not published. This covers source `files:`, `profile_photo:`, the hero, and every `![[…]]` embed (an s-id embed skips withheld images).
  - No usable catalog: fails open (the site must build without `.cache/photos.sqlite`), with one warning naming the catalog state, what was unchecked, and the next step.
  - Out-of-date catalog: still asked; known tags withheld; the warning narrows to tags added since the last `fha photoindex`. A photo with no row, or any after a mid-build catalog failure, gets the full not-checked warning.
  - Fresh catalog: an unknown hand-written filename is refused; a photo with any living-tagged variant is withheld.
  - Each wording appears once per build and names the home page, person pages, trees and source pages. Strips and hero/profile/embed lookups use only a fresh catalog.
- In every catalog state: a file the index lists under a withheld source is never published as any picture, matched as the file on disk (junction, `./`, `../` count); an uncheckable entry holds back pictures of the same name with one warning (picture, missing path, fix). A tag on a merged-away person follows `merged_into`; redact if anyone on the chain is redacted.
- A catalog `MISSING:` row (§9) is dropped from strips and never preferred over a live file. A bare filename scan honors `photos_ignore:`; an explicit path is honored.

### Web pictures
The site makes its own derivatives (at most 1200px, EXIF stripped) into `media/`; originals never leave. Pillow is optional: without it pictures are left out of the standalone site, never copied as originals. Regenerating is idempotent; an old site stays a valid frozen view.

**Cache** `.cache/site-derivatives/` (§1 machine cache). A rebuild clears `media/` and reuses a saved derivative when place, size, nanosecond mtime, size limit, format, Pillow version and `_DERIVATIVE_RECIPE_VERSION` match (never a content hash).
- Place = `roots:` alias + path inside it (most specific root wins; else archive-relative, else full path; on Windows as the disk spells it), so a changed drive letter still hits once `fha.yaml` is updated.
- Originals modified in the last few seconds are not saved.
- A saved picture reaches `media/` only when a page asks for it after every privacy gate.
- Remade: malformed note (unparseable; missing, extra, null or wrong-typed key), missing picture, length/SHA-256 mismatch. Unwritable cache turns saving off; unreadable makes every lookup miss. Each is one plain note after "Site built" (`notes`; info line for headless callers), not a warning; exit code unchanged.
- Pruned at the end of a standalone build: original gone or changed, other recipe/Pillow, or re-keyed by a `roots:` change. Kept when the original's whole folder is missing (likely an unplugged drive).
- Output is byte-identical with or without the cache.

**Workers.** Misses are decoded by worker processes while pages are written; privacy is decided in the main process first, and workers only return bytes. If any fails, the build is redone one at a time, so output and warning order always match a serial build. In-process: the first few pictures, types Pillow cannot open, and any with a `<key>.failed` note (pruned like a saved picture). Worker warnings show once each. `site.picture_workers` (`1` = serial; unset/`auto` = processors minus one, max 8, ~1 GB free memory each, two if unknown; a bad value warns and uses auto). Workers that fail to start or die fall back silently; Ctrl+C reaps them. `--linked` makes no pictures.

## 13. `fha wikitree`: profile exporter

Renders a curated profile to the user's extended WikiTree dialect (e.g. Hartley-6084), to stdout or a file; never uploads.

- `[[s-id]]` → `<ref name="s-id"/>`; full `<ref name="s-id">{citation}</ref>` definitions go in a hidden `<div name="references" style="display: none">` at the top.
- A statement backed by an accepted claim with `place`/`date` is wrapped in `<span class="spacetime" data-loc="{place name}" data-date="{ISO date}">…</span>` (low confidence qualifies).
- Reviewed-but-open claims (`suggested` with `reviewed:`) export under `== Research Notes ==` as "Unconfirmed: {value} - noted in "{source}". Not yet verified - corroboration welcome.", appended to an existing section. Only a claim naming nobody living, unknown or restricted goes, since the line is its wording.
- `[[p-id]]` → `[[{external_ids.wikitree}|{name}]]`, else the plain name.
- From `external_links`: an Ancestry record (`/discoveryui-content/view/{id}:{db}`, `/search/collections/{db}/records/{id}`, `dbid=…&h=…`) → `{{Ancestry Record|db|id}}`; an image-viewer scan (`/imageviewer/collections/{db}/images/{id}`) → `{{Ancestry Image|db|id}}`; other addresses none.
- Optional claim-type → infobox mappings (e.g. `{{US Civil War}}`) in `tools/wikitree_templates.yaml`. A claim `claim_people_verdict` withholds fills none; one it keeps while naming a living person (a godparent, a living child in a census) fills every field but `value`.
- Sections map 1:1; `== Sources ==` ends with `<references/>`.

**Privacy (SPEC §21, fail closed, no override flags):** refuses a `living: true|unknown` or any-`restricted` subject; refuses a profile citing a `restricted`, `dna` or `publication_ok: false` source or linking a `restricted` person, naming them; other living/unknown linked persons render `[living person]`; a restricted name shows the unrestricted display name; restricted/DNA sources are also filtered in SQL.

`<!-- private -->` ... `<!-- /private -->` text (§3c) is dropped before drafting and scans; an unclosed opener drops the rest. A malformed or non-UTF-8 subject is refused; a cited source or linked person that will not decode fails closed in the same scan, keeping its status, with a message naming the encoding, file, re-save and W128. Files are never rewritten.

## 13a. `fha gedcom`: relationship exchange export

`fha gedcom <p-id> [--mode descendants|ancestors|connected] [--generations N] [--include-living] [--basic]` or `--all` writes a GEDCOM 5.5.1 `.ged`; never stored or re-imported (foreign files: §13a2).

- INDI: name, sex, birth/death from accepted dated vitals (§12 life-date pick). FAM: from spouse and child edges.
- A marriage claim's date/place go on the FAM of the couple it marries, scoped by `roles:` via `_lib.spouse_parties`, never by position. One it cannot place (`roles: spouse:` naming 3+) is named in the messages beside redaction counts.
- Each fact's `[[s-id]]` becomes a SOUR note. `1891~/1893~` exports as `BET 1891 AND 1893`.
- `--basic` is the export for a DNA site, which only compares matches: the same people, families and redaction, but no SOUR records, no SOUR citations under events and no REFN archive ids, so a source title naming a living relative cannot leave with it. These are never written rather than filtered out afterwards, so no pointer dangles. A birth or death with neither date nor place is left out; a marriage is kept as a bare `1 MARR`, since that alone tells a match the two married. The header keeps its `1 SOUR fha` and do-not-re-import NOTE.
- Privacy: living/unknown names withheld unless `--include-living`. `restricted` sources are not fact sources, `restricted` claims are withheld, a `restricted` person becomes `/Restricted/` (links kept), a restricted name shows the unrestricted display name. A birth, death or marriage whose claim names a restricted person, or is a living person's own event, is not exported (`claim_people_verdict`); one that only names a living informant or witness is. `by-request` has no override.
- **Fails closed:** a present file whose `restricted:` marker cannot be read (not UTF-8, no frontmatter, bad YAML, not a mapping) is withheld under every flag (`_lib.read_restriction_marker`, shared with wikitree, site, packet). Each such file touching the export is named with its reason and the fix (`fha lint`, then `fha index`); exit 1. A source whose claims block alone fails keeps its record and loses its claims. An absent file reads as unmarked.

## 13a2. `fha gedcom import`: GEDCOM importer (trees from Ancestry and other programs)

`fha gedcom import <file.ged> [--apply] [--plan-out FILE] [--as-new-tree] [--root PATH]` imports a foreign GEDCOM; a file stamped `HEAD SOUR fha` is refused. Routed by a dispatcher intercept in `fha.py` (§4a).

**Writes:** the `.ged` copied into `documents/gedcom/` as one source (`sources/other/`, `source_type: other`, `subtype: gedcom`, `source_class: derivative`); each individual a stub in `people/stubs/` (provisional `birth:`/`death:`, extra NAMEs as `name_variants:`, the name and variants mirrored into `aliases:`); each assertion a `suggested` claim, `confidence: low` (`medium` with a GEDCOM citation), `anchor: "line N"`. `OBJE`/`FILE` image links are matched against the photo catalog (same path, else same file name, a variant group counting once) and listed in the plan and the source's `## Notes`; `tag-person` is offered per photo after apply. Web links are counted by host. Nothing is written to photos.

`SOUR` titles go to claim `notes:` and the record's `## Notes`, never minted. `PLAC` → `place_text:` only. Nothing is `accepted`.

**Contract:**
- Dry-run default. `--plan-out FILE` writes the uncapped plan (refused inside the archive except `out/`), before any apply write.
- UTF-8 only; ANSEL/UTF-16 refused with a re-export fix.
- `DATE`: GEDCOM 5.5.1 grammar, else `normalize_date` (as `fha claim --date`), except `YYYY-NN` is a range only when NN is a later year in the same century (else omitted), and `D/M/YYYY`/`M/D/YYYY` only when one part exceeds 12. Hedges survive on both range ends (`about 1891-1893` → `1891~/1893~`, `maybe 1880-1885` → `1880?/1885?`, `about 1908-10` → `1908~/1910~`); a hedged decade is omitted. `HEAD DATE` (→ `source_date`) uses the strict grammar only.
- An unreadable date omits `date:`, keeping the wording in the value; the plan counts read vs unread free-form dates (three of each on screen, all in `--plan-out`).
- Several `BIRT` (or `DEAT`) facts for one person: each is a claim. The stub's provisional date is the most exact readable one (an exact day beats an `about` one; the first wins a tie), so an undated or vaguer fact never blanks or overrides it. When the dated births agree, the living guess reads that date; when two cannot both be right, it reads the one that could make the person youngest, and a birth date that cannot be read but holds a year within the last 110 keeps `living: unknown`. Disagreeing dates, and an unreadable one that keeps a person hidden, are listed in the plan, on screen too.
- Dedupe compares birth windows (`edtf_bounds` ± 2 years; an open window matches its whole side), shown in plain words (`b.after 1700 ~ ... b.about 1849`). Reported, never merged.
- A duplicate xref definition is refused as malformed.
- Lines with no level number (MyHeritage) join the line above with a space. A line that starts with a digit, or with a sign or odd space then a number and a tag (`-1 NAME`; a known GEDCOM tag or one starting with `_`), is reported as unreadable instead; note prose like `-5 below zero` or `-1942 WWII took both brothers` still joins. Double-encoded HTML entities and `<br>` are decoded only in a file that has double-encoded entities or says `HEAD SOUR MYHERITAGE`. Anchors and the filed copy are unchanged; the plan counts both.
- Audit CSV `.cache/gedcom_import/{sha12-of-file-hash}.csv` maps xrefs to ids and is the re-run guard (same file refused with date and s-id). With the cache gone the same file is still refused: its hash is compared with each earlier import's filed copy. Every write registers an undo; any failure rolls back; the CSV is written last.
- An unreachable documents root refuses `--apply` before writing, naming the drive and `roots:` fix. On a `WORKING_COPY` (§13d) `--apply` is refused.
- `living:` (one predicate): DEAT present, or latest-plausible birth (`edtf_bounds` upper; `1915~` = 1916) over 110 years back → `false`; else `unknown`.

**A newer download of a tree already imported** is planned as only what changed. The plan is read-only: `--apply` refuses it (exit 2) before any write, and it mints no ids and prints no date, so the same archive and file give the same text.
- Earlier imports are the `subtype: gedcom` source records, read from the records, never from `.cache` alone. Which person a record number (xref) became comes from each earlier claim's trailing `(GEDCOM @x@)` and `persons:` (a merged record reads as its survivor, SPEC §9) and from the claim's line in the filed copy. The audit CSV only places people who had no statement of their own. A record that two numbers' claims now name because he moved a statement (not because he merged two records) belongs only to the number whose earlier name it carries. An earlier record that cannot be read, or has lost its `id:`, is a warning, and `--apply` is refused until it is fixed or `--as-new-tree` is given. A filed copy whose whole folder is missing (a documents drive not plugged in) stops the plan, except on a working copy (§13d), since without it deleted statements look new; a copy that is gone on its own is said in the plan, with that warning.
- Same tree: at least half of an earlier import's people are in the file, matched or recognisable by name and birth date. `--as-new-tree` skips the check and plans every person as new. Earlier imports that share people are read together; a separate copy of the same tree is named and set aside (the newest by `created:`, then the one holding more of the file's people).
- A person is matched only by the same record number with the same name (unless the birth years are more than 2 apart and another earlier person of that name fits better, or one side is undated and another earlier person of that name, whose number someone else now holds or (when this person has not shown they are the one at this number) is gone from the file, could be them: within 2 years when this person is dated, any when undated), the same record number with part of the name the same (first given name or last word) and the same birth date, or the same `_UID`. A different sex never matches, and neither does a record number whose person has a different `_UID` here. Names and births are the earlier file's and the record's current ones, so a name corrected by hand keeps its match.
- Everyone else is listed with the reason, and nothing is planned for them or for a statement that names them: a number that now carries another name, an earlier number whose claims name two people, a person no record places, more than one fit. One fit by name and birth date among the unmatched earlier people is named as the likely person. A person who fits nobody is new. A person whose record was deleted is not planned again.
- Statements compare download against download first: one worded as the earlier file worded it (names left out) is not planned again, whatever has since been done to its claim (edited, re-pointed to someone else, rejected, superseded, deleted). A statement the tree changed is compared with the claims as they read now. Birth, death and burial (one per person), marriage and divorce (one per couple): equal or less exact → nothing; a missing date or place added, or a date inside the earlier one → a new claim; dates that cannot both hold, different places (spellings of the United States as the last part count as one), or two dates neither of which could be read that the tree worded differently → a new claim that will `contradicts:` each live earlier claim, with one `origin: tool` question (SPEC §17b) naming both claims and the person. A child's parents: a parent the newer file no longer names contradicts that edge, even when another parent stays; a parent added does not, and when every parent of a tie he rejected or deleted comes back beside a new one, the tie is planned with the new parents only. Every other statement compares by type, subtype and wording (the tree's earlier wording or the claim's wording now).
- Listed, never written: statements and people gone from the newer file, a name the newer file changed or adds, and a death recorded for someone whose `living:` is not `false`.

## 13b. `fha capture`: web record capture

> **Full design: [`TOOLING_INGESTION.md`](https://github.com/asielen/plaintext-family-history/blob/master/TOOLING_INGESTION.md)** (engine, delivery forms, transport, bundle contract, `--ingest`). This is the summary.

Capture works from the page the human has open, in the human's own browser session: it never logs in or handles a password, and fetches only what that session can already open, on the human's action (TOOLING_INGESTION.md §2.4). Output is an inbox source stub (SPEC §12.1): `{slug}.notes.md` with optional frontmatter (`source_type`, `citation`, `repository`, `external_links`, `source_date` (none for a derivative index entry or memorial), `people:` names, and `external_ids` when the page is one person's own page) and the page text or notes as body. `fha process` later mints the s-id and drafts claims.

**Engine** (`tools/capture.py`): a site recipe (Ancestry, FamilySearch, Newspapers.com, FindAGrave) or the generic recipe (title, URL, accessed date, visible text); recipes are data in `tools/capture_recipes/`. `--title`/`--type`/`--date` override. Writes the stub and asset, and appends one entry per capture to `notes/research-log.md` in the SPEC §17c shape, with `result: staged <inbox path>` naming where the stub waits.

**Assets:** (a) a downloadable image/document becomes the asset (an on-screen-only viewer image gets an interactive `provisional-image` fallback); (b) the record is the page → a self-contained single-file copy of the page, images and stylesheets inlined (TOOLING_INGESTION.md §2.3); (c) the page points elsewhere → citation + `external_links`, `asset_elsewhere: true`.

**`fha capture --ingest [DIR] [--dry-run]`** sweeps staged `<slug>-<timestamp>-<token>/` bundles (`page.html`, optional `asset.*`, `capture.json`) through the same engine (stub byte-identical to paste) and parks each in `.ingested/`, never deleted. `DIR` defaults to `fha.yaml` `capture_staging:`, else `~/Downloads/fha-inbox`. Already-parked names are skipped; a malformed bundle is reported and left. Writes only to `inbox/`, so it works on a `WORKING_COPY` (TOOLING_INGESTION.md §6).

## 13c. `fha install` / `fha update-tools`: scaffolding & updating a private archive

Two commands copy the operating layer from a public-repo clone into a private archive and keep it current. Both are generic glue: they touch no family data.

**The manifest.** The repo ships `manifest.json`, the single definition of the operating layer: every path that belongs in an archive, its checksum, its version, and a tag `operating` or `skeleton`. A new shipped file is added to the manifest, never hardcoded. Each entry carries its archive-relative `path`, `sha256`, `spec_version` and `category`, plus a repo-relative `src` when the two differ (a skeleton seed, a vendored tool, a renamed rulebook), so the engine needs no layout knowledge. `python tools/scaffold.py write-manifest [--repo PATH]` regenerates it (maintainers only).

- **Operating layer:** tools, the `design/` package, the browser companion, the rulebooks (`AGENTS.md`, `CLAUDE.md` at the root; `SPEC.md`, `TOOLING.md` installed as `docs/SPEC.md`, `docs/TOOLING.md`), `docs/` (including `GETTING_STARTED.md` and `CHEATSHEET.md`), the launchers (`fha`, `fha.cmd`, `serve.cmd`), and the skills twice from one source: `.claude/skills/` (Claude Code) and `.agents/skills/` (Codex).
- **Skeleton:** `fha.yaml`, `START_HERE.md`, empty record dirs with `.gitkeep`, seeded `places/places.yaml`, `inbox/_TEMPLATE.notes.md`, `design/custom.css`, `.gitignore`, `.gitattributes`.
- **Never shipped:** the tool-building docs (`TOOLING_INGESTION.md`, `TOOLING_INTERFACE.md`, `AGENTS_TOOLING.md`), `example-archive/`, `archive-template/` itself (its contents seed the skeleton), `tests/`, `.github/`, `.claude/settings.json` (permission grants are personal), `PRIVACY.md`, `RELEASE_CHECKLIST.md`, and the project `README.md`. An archive's entry point is `START_HERE.md` for a reader and `docs/GETTING_STARTED.md` for the owner.

**Archive layout.** Machinery lives in hidden `.fha/`: `tools/`, `design/`, `browser-companion/` (for chrome://extensions "Load unpacked"), and `docs/` (`DESIGN.md`). The root holds the record folders, `START_HERE.md`, `fha.yaml`, `AGENTS.md`, `CLAUDE.md`, `docs/`, `.claude/skills/`, launchers. Every other doc lives in `docs/`: the owner docs (`GETTING_STARTED.md`, `CHEATSHEET.md`) sit there in the repo too, while `SPEC.md` and `TOOLING.md` stay at the repo root and install as `docs/SPEC.md`, `docs/TOOLING.md`. The repo otherwise stays flat; the remap is install-time only. Install never rewrites links, so a shipped doc's relative links must resolve where it lands; a reference that cannot be right in both repo and archive (anything to or from `SPEC.md` and `TOOLING.md`) is a plain file name or an absolute URL, never a relative link. `START_HERE.md` is a skeleton seed: written once, delivered by `fha update-tools` to an archive that never had one, never overwritten.

**`fha install <archive-path> [--repo PATH] [--dry-run]`** runs from a clone (the archive has no `fha` yet). Before writing anything it checks for Python 3.10 or later (a hard stop with a download pointer) and `exiftool` (an advisory: the install goes ahead and the photo features wait until it is installed). It creates the folder if absent, or fills an existing folder that has no tools, writes skeleton plus operating layer, and stamps `.plaintext-version` (manifest version and per-file checksums). The archive is then self-contained.

**`fha update-tools [--repo PATH] [--dry-run] [--verbose] [--root PATH]`** runs from the archive. It compares the manifest against the stamp and reconciles the operating layer:

| Situation | Action |
|---|---|
| New file in the manifest | Copy it in. |
| File unchanged from stock (checksum matches stamp) | Overwrite silently. |
| File customized (checksum differs) | Move it to `.plaintext-backup/{date}/`, install stock, report it. |
| File removed from the manifest | Move it to `.plaintext-backup/{date}/` (never deleted), report it. |

Then it refreshes the stamp and prints a summary (added / updated / backed-up / quarantined, with the backup path). The summary is plain English ("Your edited .fha/tools/fha.py has been backed up to .plaintext-backup/2026-06-22/"); diffs and checksums appear only under `--verbose`, which also lists up-to-date files. **The updater never deletes and never silently overwrites the human's work.** `.plaintext-backup/` and `.plaintext-version` are its only footprints; both are safe to inspect or delete.

**Skeleton seeds** are written once by `install` and never overwritten; `update-tools` carries their stamp entries over unchanged. One exception: a seed absent from both disk and stamp has never been delivered, so `update-tools` installs it (a deleted seed is in the stamp, so it is not resurrected). `.gitattributes` relies on this: without it Windows rewrites the launchers' line endings and every update reports stock files as customized.

`install` writes only the `.fha/` layout, and nothing moves a `tools/` folder that sits at an archive's root into `.fha/`: such a move would need rollback, half-moved detection and launcher repair.

Both commands run before PyYAML is installed (they are dispatched ahead of the bulk import). Without PyYAML, `install` reports the `roots:` check as an advisory and `update-tools` as a warning-level gap; the rest of each run still succeeds.

### External asset roots get no placeholder

- `roots:` (§12.4) mapping `documents`/`photos`/`inbox` outside the archive: `install` skips that skeleton folder. Inside at another name (`documents: archive-docs`): the placeholder goes to the renamed folder. All steps remap through one `roots:`-derived map.
- `update-tools` removes an unused placeholder only if recursively empty: every file a shipped seed whose bytes match the manifest checksum, every subfolder (hidden too) empty by the same test. Otherwise it is untouched: not removed, flagged or backed up.
- Re-pointing an alias inside recreates its placeholder via the never-delivered-seed path.
- Refused before any write: a seed spot (or a folder on its path) that is already a folder or symlink. `install` checks `roots:` shape as well as syntax (a blank `documents:` refuses).
- A former rename is recognized anywhere except inside skeleton-seeded folders. The old folder is kept if the renamed seed failed to copy. No prune touches another alias's live target or its parent.
- "Same folder?" tests are case-insensitive, erring toward keeping. Candidates go deepest-first, so a nested former home and the parent it empties go in one run.
- A failed removal, or a failed stamp write after a removal (the removal is then restored), is a reported warning.

### Browser add-ons (`browser_extensions:`)

The capture add-on is part of the operating layer; when an update changes it the run says to click its reload arrow in chrome://extensions. **Seen It** (`seen-it/`) is optional and standalone: not in the manifest, copied from the `--repo` clone into the folder one `fha.yaml` line names.

```yaml
browser_extensions: extensions                         # inside the archive (the default answer)
browser_extensions: E:/Family History/Browser Add-ons  # any folder; relative = under the archive root
browser_extensions: none                               # "no thanks" - never asked again
```

**Asked once.** When the line is absent and a person is at the keyboard, `install` and `update-tools` ask whether the human wants the add-ons and where (Enter = `<archive>/extensions`).
- Yes: leading word y, yes, ok, okay, sure, yeah, yep. No: Enter, n, no, nope. An absolute folder (drive letter, share, leading `/` or `~`, quotes allowed), alone or after a yes-word, is a yes with a place. Anything else is re-asked; after three tries nothing is saved.
- The answer, "no" included, is appended to `fha.yaml` as one commented line (rest kept byte for byte, parsed before writing, temp-file write), the only write either command makes to `fha.yaml`.
- No keyboard (pipe, CI, an agent's shell; on Windows the console is checked, since `NUL` claims to be a terminal), `--dry-run`, Ctrl-C, closed input: nothing saved; one line names the setting.
- A value with `:` other than after a leading drive letter, or a Windows-forbidden character, is refused with the line to fix.
- An add-on's own folder (a `manifest.json` with `manifest_version` 2 or 3, a `name`, and one of `background`, `content_scripts`, `action`, `browser_action`, `permissions`) is read as its parent, said so, and the parent is saved.

**A run,** per add-on, from one plan shared by preview and run:
1. Find the installed copy by its manifest `key` (which fixes the Chrome ID and so the add-on's data), even in a renamed folder.
2. Absent: build `<folder>/seen-it.part` with a marker file, then rename. A leftover marked `.part` is replaced (said so); an unmarked one is refused.
3. Identical: "up to date". Installed newer than the clone: never downgraded.
4. Otherwise back up the folder to `<folder>/_backups/<name>-<old version>-<date>` (`-2`, `-3`; skipped if an identical one exists; no change if the backup fails), then write shipped files in place, all or nothing: any failure restores every file and removes added ones, and the message names the file, cause and backup.
5. A shipped file missing from the clone refuses that add-on first, with the fix (`git -C <clone> checkout -- seen-it/<file>`, or download again).
6. Report old -> new version and "In chrome://extensions click the reload arrow on Seen It (do not remove it - that would delete its data)"; if `seen-it/host/` changed, no installer needs re-running.

Shipped = files git tracks in the clone's add-on folder (without git, walked with its `.gitignore`), minus `tests/`, `package.json`, `node_modules/`, `__pycache__/`, git files. Other files and sibling folders are never touched or deleted. Two folders with Seen It's key, or an unrelated `seen-it` folder: warning saying what to move. An unopenable folder: warning, never a stop. `none` prints nothing.

**Where the folder may be:** not the archive root, a disconnected drive, a folder the tools own or read (`sources/`, `people/`, `places/`, `notes/`, `docs/`, `generated/`, `.fha/`, `.cache/`, ...), or inside an asset root. `extensions/` inside the archive is treated like `.fha/`: git-tracked, backed up, ignored by `lint`/`index`.

**Doctor** applies the same reading and read-only locate step without a clone (Seen It's Chrome ID is built in): problems are warnings with the fix; a good folder is a tick; no line or `none` shows nothing.

## 13d. Working-copy mode (the `WORKING_COPY` marker): asset-less plain-text copies

A git-synced copy of the plain-text core without the photos and documents is flagged by a visible, git-ignored file `WORKING_COPY` at the root (SPEC §12.4); only its existence matters. It is not an `fha.yaml` key because it must never sync back. The skeleton `.gitignore` lists `WORKING_COPY` and `.cache/`. **Rule:** assets are assumed present elsewhere, never missing or deletable; only asset behaviour is withheld, and the plain-text surface works normally. Without the marker, the asset-aware tools misread a copy with no pictures: `fha photoindex` prunes the catalog rows for files it cannot find, `fha lint` floods E011, and `fha index` records every file as missing. Most tools already cope, since the index is built from the `.md` files, so the mode blocks only asset behaviour and never a rebuild.

**`fha working-copy on | off | status [--yes] [--root PATH]`** (`tools/working_copy.py`):
- `on` writes the marker (with explanatory text) and ensures `.gitignore` lists it, or warns if the copy is not a git repo. No confirmation.
- `off` re-enables asset behaviour, so it prompts `y/N` (default No) with the consequence in plain words, sharpened when the mapped roots look empty or unreachable. `--yes` skips the prompt.
- Bare or `status` reports the mode. Every verb is idempotent and says what changed.
- Only this command (or a human by hand) creates or removes the marker; `install`/`update-tools` never do.

| Tool | Behaviour when `WORKING_COPY` is present |
|---|---|
| all | `_lib.is_working_copy(root)` is an existence check. The CLI prints a banner: `working copy - photo/document files assumed on the main archive`. |
| `fha lint` | Suppress E011/E012; one note: `working copy: N asset files assumed present in the main archive`. |
| `fha index` | `source_files.exists_on_disk = NULL`, never `0`; skip the asset glob. |
| `fha photoindex` | A scan refuses and prunes nothing (`this is a working copy - run photo indexing on your main archive`). Read-only queries use the existing cache. |
| asset-mutating commands | `fha process <file>`, `photoindex tag-person`, `photoindex set-summary`, `fha source extract`, `fha packet`, `fha site`, `fha gedcom import --apply` refuse with a pointer to the main archive: warning-level, `ok=True`, exit 0, `data.status='working-copy'`. The gedcom dry-run plan still runs. `capture`, editing, `find`, `views`, `report` stay available. |
| `fha doctor` | Headlines the mode; missing asset roots are not errors. |
| `fha backup` | Records-only runs (§13e). |

## 13e. `fha backup`: a dated zip snapshot (restore = unzip)

```
fha backup [--to PATH] [--include-assets] [--dry-run] [--allow-incomplete] [--root PATH]
```

Copies the archive into one dated zip outside it. **Restore needs no tool: unzip it anywhere.** No restore verb exists; the success output says so in one line.

**Destination.** Default: sibling folder `{root-folder-name}-backups/`. `fha.yaml` `backup: {path: <folder>}` (absolute, or relative to the root) overrides it; `--to` overrides both. A destination resolving (symlinks first) inside the archive or any mapped asset root is refused (exit 3, naming the setting and the fix). Name: `{root-folder-name}-backup_{YYYY-MM-DD}.zip`; same-day re-runs append `_2`, `_3`; nothing is overwritten.

**Records-only by default, walk-and-subtract.** Everything under the root is included except, with reasons printed: `.cache/`, `generated/`, `out/`, `.git/`, `WORKING_COPY`, and the resolved photos/documents roots wherever they live. An `inbox/` inside the root is always included; one mapped outside is treated as an asset root. Every records-only run states, with estimated sizes, that photos and documents are not included and how to cover them.

**`--include-assets`** zips each external root under its alias name (`photos/...`) and an internal root at a different path under its real relative path (`media/photos/...`), so an unzip matches the zipped `fha.yaml`. The output explains the external-root wrinkle (move them back and keep `fha.yaml`, or delete the `roots:` mapping). If two sources would land on one zip name, the run refuses (exit 3, nothing written) naming the folder, the `roots:` line and the fix.

**Completeness.** A run that did not read everything is refused before writing (exit 3, `data.status='unreadable-folders'`, `data.complete=False`), naming each folder with its fix. Not read: (a) a folder that raises on listing; (b) a symlinked subfolder (recorded, not followed, so a restore matches the archive's shape); (c) with `--include-assets`, a `roots:` root that is not a directory (unplugged drive; a never-created spec-default alias is just skipped). `--allow-incomplete` exits 0 but marks the artifact: `...-INCOMPLETE.zip`, a `BACKUP_INCOMPLETE.txt` member listing what is missing, `complete: false` in the stamp. An included asset root with no files gets a warning that it may be unmounted (exit 0, still complete).

**Integrity.** Every member's CRC is verified after writing (`backup verified: N files, SIZE`). On write or verify failure the partial zip is deleted, exit 3.

**Exit codes.** 0 written+verified, dry-run, working-copy `--include-assets` refusal, `--allow-incomplete` run. 2 argparse. 3 unresolvable root, refused destination, duplicate member name, unread folder, malformed `fha.yaml`, write/verify failure. No exit 1: a partial or suspect backup is never a warning.

**Stamp.** A successful backup writes `.cache/last_backup.json` (`date`, `zip`, `files`, `bytes`, `assets_included`, `complete`, `unreadable_dirs`). It is per-copy, excluded from the zip (a restored archive reports "no backup recorded"). `fha doctor` leads its backup section with the stamp's state or "none recorded - run `fha backup`"; the check is info-level and never changes the exit code, followed by the paths a full backup must cover.

**Working copy (§13d).** Records-only runs, with a note that the main archive needs the real backup; the stamp is written. `--include-assets` is refused warning-level (`ok=True`, exit 0, `data.status='working-copy'`).

**`--dry-run`** prints the plan (destination, per-top-folder counts and sizes, exclusions, assets note, completeness refusal) and creates nothing. `Result.data` keys on every arm: `status`, `zip_path`, `files`, `bytes`, `assets_included`, `skipped_roots`, `folders`, `excluded`, `unreadable_dirs`, `complete`; `changed` = zip + stamp.

## 13f. `originals_backup:` (one pristine copy before a photo is written into)

```yaml
originals_backup: D:/PhotoOriginals     # absolute, or relative to the archive root
```

**Scope:** every embedded-metadata write into an original: `fha process`'s `SOURCE:` keyword and rollback (photos and documents-root TIFF/JPEG/PNG/PDF, §6), `photoindex tag-person`/`set-summary` (§9), `fha source clear-keyword` (§3d). All keyword writes go through `_lib.write_embedded_keywords`, which applies the guard. Writes use `exiftool -overwrite_original_in_place` (keeps DAMs like Lightroom tracking the file); the guard covers a write ruining the only copy.

**One copy, once, per file.** Before the first write the file is copied to `<dest>/<alias path>` (`photos/1912/margaret.jpg` -> `<dest>/photos/1912/margaret.jpg`) via `.part` + `os.replace`. An existing copy is never overwritten, so it stays pre-fha and cost stays one copy per written file. Copies are keyed by path because the first write mints the `SOURCE:` keyword; a moved photo gets a fresh copy at its new path. Nothing reads the copies back.

**Destination** must be outside the archive and every asset root, checked both ways and case-folded; `fha backup` therefore never zips it.

**Fail closed.** If configured and the copy fails (unwritable, disk full, malformed value), that file's write is refused through the per-file error channel (batches report per photo; `process` rollback runs). The message names the file, cause and next step, including "remove `originals_backup:` from fha.yaml to write without safety copies". A malformed value is never read as "not configured".

**Not configured:** warn once per run, then proceed; `tag-person`/`set-summary` warn before their prompt. **`--dry-run`** says where copies would go, or that none are set. Runs report copies made, already present, and bytes, as `Result` messages with code `originals-backup`.

One `_lib.OriginalBackup` per run is shared by every writer; `ensure(path)` returns, warns once, or raises `_lib.BackupRefused` with the finished sentence. `fha doctor` (§3a) reports on/where, unusable, or not set, with a ready-to-paste line.

## 14a. `fha xref`: cross-reference pass

```
fha xref [--root PATH]
```

Run by the `review-claims` skill at the end of each review and inside `fha report`; never scheduled. Read-only: it prints candidate pairs with both claims' context. Writes belong to `fha confirm xref` (§14a3).

**Input.** Accepted and reviewed-but-open claims (`suggested` with `reviewed:`, SPEC §8.1) from the index, so a parked claim resurfaces when a new source corroborates or contradicts it.

**Corroboration candidates.** Same person, same type, overlapping EDTF bounds, different sources, not already linked.
- Vital types, `relationship`, `divorce`: overlap is enough.
- Other types also need: the same `place_id` or normalized `place_text`; or both dated with the identical finite range, or each at most three years wide and overlapping (undated, open-ended or decade-only never match on dates).
- Never offered when the places differ: two different `place_id`s (town vs its own county included), or `place_text` towns (first comma part) that plainly disagree. Not a difference: added or abbreviated larger areas, accents, St./Mt./Ft., close misspellings, the town inside a phrase; "Ohio" vs "Riverton, Ohio" says nothing. A fuzzy match never admits a pair by itself.

**Contradiction candidates.** Same person, same type, non-overlapping bounds; or incompatible `value`s (vital types only). A negated claim against a positive one of the same recurring type is a candidate unless they name different places by the test above.

`event`/`note` claims never produce either kind.

**Bucketing by subject.**
- Marriage/divorce: by the couple `_lib.spouse_parties` resolves from `roles:` (as `index` and `gedcom` do). A `negated: true` claim (SPEC §8.6), or one naming under two people, is compared against all that person's marriage/divorce claims, narrowed when an ex-partner is named.
- Birth/death/baptism/burial: under a person only when `_lib.vital_subjects` makes him the subject (subject role, else whoever `roles:` left unroled); a one-person claim is about him.
- Ambiguous (no bucket; listed in the Result's `unscoped` list with who is on it and that a `roles:` map would enable comparison; lint W132 uses the same scope): a non-negated marriage/divorce naming 2+ people with no resolvable couple, or a vital claim of either polarity naming 2+ people with no `roles:`.
- Witnesses, informants and other non-subjects are never bucketed. Substantive types (`census`, `residence`) keep plain same-type buckets.

**Detector exit rule.** `fha xref`, `fha cooccur` and `fha places candidates` exit 0 whether they find zero or fifty candidates: a candidate is a lead, not a defect. Gate "unreviewed work" checks on `fha report` or `fha lint`, never on a detector's exit code.

## 14a2. `fha cooccur`: connection candidate detection

```
fha cooccur [--threshold N] [--root PATH]
```

Read-only, like `fha places candidates`; consumed through the report. Writes belong to `fha confirm cooccur` / `confirm dismiss` (§14a3). Pairs with an existing `relationship` edge (kin or social) or a dismissal in `notes/cooccur_dismissed.json` are excluded. That file is `{"pairs": [["p-…", "p-…"], …], "not_same_person": [{"persons": ["p-…", "p-…"], "date": "YYYY-MM-DD"}, …]}`, read through `_lib.load_cooccur_dismissed` (pairs) and `_lib.load_not_same_person`; this tool reads only `pairs`. Writers keep every key they do not change. It lives under `notes/` and not `.cache/` because each pair is a person's decision, which a cache rebuild must not lose.

1. **People co-occurrence.** Person pairs named together in at least `--threshold` (default 2) distinct sources. Ranked by count and source variety (different `source_type`s weigh more). Output shows the shared sources.
2. **Shared place.** Accepted and reviewed-but-open claims (`suggested` with `reviewed:`, SPEC §8.1) of different, unlinked people sharing a place (`place_id` if both have one, else normalized `place_text`) with overlapping EDTF bounds.
3. **Entity hubs.** Named entities in claim values (employers in `occupation`, units in `military`, clubs in `event`/`note`) recurring across N or more people or sources: "Plains Junction Railroad - 4 people, 6 sources." Organizations stay claim values; no record type.

All three feed the report and render in the FAN view as dashed provisional edges.

## 14a3. `fha confirm`: the detection write-back layer

The detectors only read; `fha confirm` writes what the human picks, from any caller (terminal, agent, workbench). Every verb is surgical (sibling claims, key order and hand comments survive), finds records by scanning `sources/`/`people/` (works with a stale or absent index), ships `--dry-run`, and returns a `Result` whose `changed[]` lists every file written.

| Verb | Write-back |
|---|---|
| `confirm xref <c-a> <c-b> --as corroborates\|contradicts` | Reciprocal `corroborates:`/`contradicts:` link in both source records, then incremental reindex. `contradicts` also writes an `origin: tool` question in `notes/questions.md` naming both claims (SPEC §17b), satisfying lint E009, the same machinery as `fha lint --spawn-questions`. |
| `confirm cooccur <p-a> <p-b> --source S --subtype friend\|associate\|neighbor [--accept]` | Mint a `relationship` claim citing S, `suggested` by default (graph edges are accepted-only, so review still decides). `--accept` stamps `accepted` + `reviewed:` like `fha claim`. Idempotent: an existing live claim for the pair + subtype (any status but `rejected`/`superseded`) is not duplicated; the result is a no-op `already` naming it, except that `--accept` on a `suggested` one promotes it. A rejected edge never blocks a fresh confirm. |
| `confirm dismiss <p-a> <p-b> [--not-same-person]` | Add the pair to `notes/cooccur_dismissed.json`: by default as not connected (report §8 stops proposing it), with `--not-same-person` as two different people, dated (report §4b stops listing it). The only writer of new dismissals. A damaged file is refused, never overwritten. |
| `confirm undismiss <p-a> <p-b> [--not-same-person]` / `confirm undismiss --list` | Take a pair back out of the file so it can be suggested again; `--list` prints every remembered pair with its undo command. |
| `confirm place <c-id> [<c-id> ...] (--name NAME [--hierarchy H] \| --into <l-id>)` | Mint a place in `places/places.yaml` (or merge into an existing one) and relink the claims' `place:`. |
| `confirm discovery "<text>" [--refs s-...,p-...]` | Append a dated entry with refs to `notes/discoveries.md`, the wins log report §0 leads with. |
| `confirm draft <p-id\|s-id>` | In a person profile, or in a source record's body (a proof argument; never its frontmatter or `## Claims`), flip `<!-- AI-DRAFT ... -->` markers to `<!-- AI-ACCEPTED ... (accepted DATE) -->`, keeping the original date/model. On a merged person's tombstone it writes nothing and names the surviving record to accept on. |
| `confirm merge <p-merged> --into <p-survivor> --reason "<why>"` | Enact a human-confirmed SPEC §9 merge; see below. |

**`confirm merge`** is planned in memory and applied with an undo journal; any failure or Ctrl+C rolls everything back (a step joins the journal once it has landed), and a file that could not be put back is named with the hand fix.
- Folds the names by kind (restricted mappings kept as mappings; the public names join the survivor's `aliases:`, SPEC §9): `name_at_birth` and `married_name` fill the survivor's same field when it is empty and otherwise go into `name_variants` (a record holds one of each, and `also_known_as` is for nicknames and other spellings), with a preview line naming the value the survivor already holds; `also_known_as` entries follow the survivor's own; `name` and `name_variants` go into `name_variants`. A name the survivor already shows in `name` or any of those four fields is skipped (compared without case). A name the merged record marks restricted in any of its name fields arrives restricted wherever it lands, and one the survivor lists without the marker gains a restricted `name_variants` entry, so the marker is never lost. A survivor field written as one bare value where a list is needed stops the merge with nothing written and names the list line to write. It also folds `external_ids:` and `relationships:` (deduped by to+type+subtype: a tie both records list keeps one entry whose `claims:` gains the other's claims; self-edges skipped with a warning) into the survivor. An `external_ids` key conflict keeps the survivor's value, warns naming both, exits 1; the tombstone keeps the other.
- Tombstone: `status: merged`, `merged_into:`, `merge_reason:`, `merged_date:`; `name_variants`, the other folded fields and `tier:` stripped (its `name`, `name_at_birth`, `married_name` and `also_known_as` stay as written); `aliases:` reduced to the bare id; generated views deleted (GENERATED header verified, lookalikes kept with a warning); file renamed to `MERGED-INTO-p-survivor__<original>` last, never deleted.
- Privacy: on a tombstone whose `living:` is `unknown` or missing, writes `living: false` when the survivor is `living: false`, so the merged record never hides a dead ancestor (§1 Restriction). Never copies `true`; a tombstone's own `living: true` or `restricted:` stays and keeps governing the survivor.
- Relinks `persons:`/`roles:` in claims of every status (bare, `[[p-id]]`, `[[p-id|Name]]`, resolving names; deduped), profiles' `relationships:` (an entry repointed onto a person the record already lists in that role folds into that entry), and source `people:`. A file that cannot be rewritten safely refuses the merge with zero writes. Prose mentions are left for lint W107 (counted). With `links: obsidian`, every person link to the merged record, by ID or by its file name, is pointed at the survivor's file across the archive (§1 `rename_link_writer`), folded into the plan so the preview diffs it and the undo journal covers it; the W107 count is taken after. A `relationships:` entry whose `to:` still names the tombstone reads through the survivor, so it is the edge the index derives, not a W115.
- Re-run: `already`. Exit 3: self-merge, unknown id, tombstone `--into` (names the final survivor), different-survivor re-merge, rename collision. Exit 1 is reserved for "landed with warnings". Evidence concerns warn, never refuse. Splits stay hand-guided (SPEC §9).
- A pair noted as two different people (`confirm dismiss --not-same-person`) still merges, with a warning in the preview and the result naming the `confirm undismiss … --not-same-person` command.

**`fha claim <c-id> [<c-id> …]` (T C)**: the review gesture (§3b). Driven by `review-claims` and the report's prompts; `accepted` is the human gate.
- Moves claim `status:` (`accepted`/`disputed`/`rejected`/`superseded`) and stamps `reviewed:`. A claim looked at but not yet settled stays `suggested` with a `reviewed:` date (SPEC §8.1): `--status suggested` keeps it there and stamps the date.
- At least one of `--status`/`--value`/`--date`/`--type`/`--place`/`--place-text`/`--persons`/`--confidence`/`--information`/`--evidence`/`--anchor`/`--notes`/`--clear` is required, so a field-only correction needs no status move.
- `--information`/`--evidence`/`--anchor`/`--notes` correct the Mills fields and context note surgically; every free-text field write echoes what it wrote.
- `--clear FIELD` removes an optional field whole; empty values are refused, never written as `key: ''`.
- Several c-ids apply one status move to each (status-only: field edits take exactly one c-id; every id validated before any write; duplicates deduped with a note). `--dry-run`.
- Accepting a relationship, marriage or birth claim writes the matching `relationships:` entries on the people it connects whose records already keep that list; disputing, rejecting, superseding or un-accepting one takes it out of those lists (§3b). No hand-editing of `relationships:` after a review.

**`fha person new "Name" […]` (T C)**: mint a brand-new person from nothing and write their stub (§3c).
- `--sex`/`--gender`/`--birth`/`--death` all optional; vitals PROVISIONAL until a sourced claim supersedes them.
- Surname split: a trailing generational suffix (Jr/Sr/II/III/IV/V/Esq, and a regnal number VI-XXX typed in capitals in a name not all in capitals) is never taken for the surname. A surname written in capitals that looks like one ("Jinping XI", "Thi VI") needs `--surname XI`; `--surname ""` means no surname; `--surname TEXT` overrides the automatic split outright.
- Accented letters fold to base letters in the file name (`_lib.fold_accents`); `name:` keeps them.
- Duplicate check (§5): a name that already has a record is refused before any id is drawn (status `duplicate-name`, exit 3, `--dry-run` identical, the records in `data['duplicates']`), also when the workbench passes an explicit p-id. `--force` mints anyway once the human has confirmed it is a different person. The workbench preview shows the matched records and a "Create a separate record anyway" button that re-previews with `force`.
- `--from-file PEOPLE.tsv` mints a list in one call: one person per line, tab-separated name, sex (optional), surname override (optional, `-` = no surname), an optional `name sex surname` header. Every row is validated first and one bad row refuses the whole file (exit 3) before any id is drawn; the duplicate check runs once over all rows (names repeated in the file included); all ids come from one `mint_ids(count=N)`; a write failure part-way removes the stubs already written.
- NAME and `--from-file` are exclusive, as are `--from-file` and the per-person flags (exit 2). `--dry-run`.

**`fha person rename <p-id> "New Name" [--keep-variant]` (T C)**: correct a name everywhere it is mechanically derivable (§3c).
- Rewrites frontmatter `name:`/`name_variants:`, renames the profile + research file, cleans up stale GENERATED companions (regenerate via `fha views …`), and (when the old name is unambiguously in the couple folder's own text) renames the folder too.
- The folder step alone may fail without failing the rest (`ok-folder-unrenamed`, most often a shell sitting inside the folder on Windows).
- `--surname TEXT` overrides the filename split, same as `new`. The same name is a no-op unless an explicit `--surname` changes the recorded `surname:` line or the file name it gives; an older file name (`winiewska__…`) is left alone, since no reader takes the surname from it. `--dry-run`.

**`fha source extract <s-id> [--pages A-B] [--copy LABEL]` (T C)**: dump the source PDF's embedded text layer into a derived `[Page N]`-labeled companion (`role: extracted-text, derived: true`, §3d): seconds instead of vision-reading hundreds of pages.
- Reads the source's main PDF (`is_primary: true`), or the `--copy LABEL` one. The original is never touched.
- A page without a text layer gets a placeholder saying so; an all-image PDF refuses toward vision/OCR.
- A page whose words run together is read again by pypdf's layout mode, then by `pdftotext` when installed; a page none can space is kept but named in the dump and a warning (exit 1).
- pypdf optional (refuses with the install command). `--dry-run` (same warnings, same exit).
